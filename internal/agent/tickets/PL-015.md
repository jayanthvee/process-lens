# PL-015: A bare-bones operator page

Owner: T2 · Reviewer: T1 · Depends on: PL-014, PL-014b (merged) · Phase: C

## Description
A person can now run a batch with the real extension, but the only way to see or act on a run is to call the API.
This ticket gives the operator one local web page with four jobs:
- see the runs and what each record is doing;
- pause, resume or cancel a run;
- act on parked and failed records;
- answer approval requests.

That is SYSTEM_DESIGN step F ("Results") in its plainest form.

Before any browser page talks to the API, the API gets the front door that so far only the hub has.

There is no plan step; the requirements below are the design. **There is no e2e work in this ticket.**

## Scope
- `services/api/` (a new middleware module, `runs.py`, `approvals.py`, `main.py`) and `tests/api/`
- `packages/ledger/` (the dismiss and list functions only) and their tests
- `apps/web/` (new)
- `internal/agent/reports/PL-015.md`

## Requirements

1. **The API's front door, on every HTTP route, not only the hub's.**
   - **Host:** refuse any request whose `Host` is not `127.0.0.1:<port>` or `localhost:<port>`. Reuse the hub's
     constants, don't duplicate them.
   - **Loopback:** refuse any client that is not loopback.
   - **State-changing requests** (`POST`, `PUT`, `PATCH`, `DELETE`):
     - refuse an `Origin` header unless it is the page's own origin (the API's own scheme, host and port);
     - an absent `Origin` is allowed, because a CLI or test client sends none;
     - refuse a `Content-Type` other than `application/json` whenever a body is present. This forces a browser
       preflight, and the API sends no CORS headers, so the preflight fails.
   - **Reason:** today any web page open in the browser can send a no-body `POST` to `/api/v1/runs/{id}/cancel` or
     `/resume`. That is a cross-site request forgery against a local service.
   - **Tests, one per check, each failing when its check is removed:**
     - a non-loopback client;
     - a rebound `Host`;
     - a foreign `Origin` on `POST /runs/{id}/pause`;
     - a `text/plain` body on `POST /records/{id}/requeue`;
     - an absent `Origin` from a test client is still accepted.
   - The hub routes keep their own stricter checks.

2. **The read endpoints the page needs.** All are read-only, and all follow `internal/docs/sql-patterns.md`.
   - `GET /api/v1/runs`: the most recent runs first, capped at 50. Each row carries:
     - `id`, `status`, `pause_reason`, `created_at`;
     - the recipe name and version;
     - the count of records in each state.
   - `GET /api/v1/runs/{id}/approvals`: the run's approval requests that have no decision yet, with what each one
     asks.
   - `RecordDetail` gains `commit_attempted`, if it is not already there, so the page can tell a record that may
     already have saved.

3. **Dismissing a parked record.**
   - `POST /api/v1/records/{id}/dismiss` moves a parked record to `skipped`. It uses the
     "Dismiss a parked record as skipped" pattern in `sql-patterns.md`.
   - A record that never reached a commit (`commit_attempted = false`) goes straight to `skipped`.
   - A `commit_attempted` record needs `destination_checked_by` in the request, and the same update records a fresh
     destination check. The database trigger (I26) is the authority; the endpoint maps its refusal to 409.
   - **Tests:**
     - a non-commit record is dismissed;
     - a commit-attempted record without a check gets 409 and stays `parked`;
     - with a check, it is dismissed;
     - a `verified` record gets 409.

4. **The operator identity.**
   - `decided_by` (approvals) and `destination_checked_by` (requeue, dismiss) need a person's id. There are no
     users yet (multi-user auth is out of scope).
   - The API reads one local operator id from `PROCESSLENS_OPERATOR_ID` (a UUID) and exposes it as
     `GET /api/v1/operator`. If it is unset, that endpoint returns 503, and the page says so and disables every
     action that needs it.
   - The page never invents an id.

5. **The page: `apps/web/`.**
   - **Stack:**
     - TypeScript and Vite with no UI framework, and Vitest with `happy-dom` for tests. This is the same toolchain
       and versions as `apps/extension`.
     - `npm --prefix apps/web run check` runs typecheck, test and build, like the extension.
   - **Serving:**
     - the API serves the built `apps/web/dist` at `/` with `StaticFiles`, mounted after the routers, so the page
       and the API share one origin;
     - if `dist` does not exist, `/` returns a one-line hint to build the page, not a crash.
   - **Updates:** the page polls every 2 seconds while a run is open, and stops polling once the run is finished.
     No WebSocket.
   - **Views:**
     - **Runs:** the list from requirement 2. Each row links to its run.
     - **Run:**
       - the status and pause reason, in words a person understands (`login_required` → "Log in to the site in
         the bound tab, then resume");
       - the per-state counts;
       - **Pause**, **Resume** and **Cancel** buttons, shown only when the run's status allows them;
       - a link to `results.csv`;
       - the records table: row key, state, reason and attempts. A row expands to show its transitions.
     - **Parked and failed records:**
       - **Re-queue** and **Dismiss** buttons.
       - For a `commit_attempted` record, both buttons first need a confirmation that is not pre-ticked:
         "I checked the site and this record is not there". Only then is `destination_checked_by` sent. Without the
         confirmation, the buttons stay disabled.
       - This is the only place the page can bypass the ledger's duplicate protection, so it must never be one
         click.
     - **Approvals:** each open request, with **Approve** and **Reject** buttons.
   - **Errors:** a 409 or a refused request shows the API's `detail` text next to the button. The page never retries
     on its own.
   - **Safety and privacy:**
     - render every value with `textContent`, never `innerHTML`;
     - record values come from user CSVs, so treat them as untrusted;
     - no external fonts, scripts or CDNs.
   - **Tests (Vitest):**
     - the commit-attempted confirmation gates both buttons;
     - the run buttons follow the status;
     - a 409's `detail` is shown;
     - polling stops once the run is finished;
     - a record value containing `<img onerror>` is rendered as text.

## Out of scope
- Creating runs or uploading a CSV (use the API).
- The recipe editor, the recorder flow, and the compiler UI.
- Screenshots and step timings.
- Multi-user authentication.
- Pacing.
- The cloud runner.
- Web Store readiness.
- Any e2e or Playwright test.
