# PL-122: trial — a run asks a model to find the element when the remembered one is gone

Owner: T2 (DeepSeek) · Branch `pl-122` (from `main` at 4e08cdf) · Reviewer: T1
Read first, in this order: `internal/docs/WORKING-RULES.md`, `internal/docs/AI_RUNTIME.md`, D-026 in
`internal/docs/DECISIONS.md`, `internal/docs/AI_BOUNDARIES.md`.

This is part of the trial in `AI_RUNTIME.md`. PL-123 builds on it and PL-121 runs alongside. The
trial passes only if the owner's three tasks pass. Green gates alone aren't enough.

## Why

The owner's price task (`tests/fixtures/owner/price_update_kanban.json`) parked every row in 6 s.
Its "did the search find it" check looks for a table cell, and the owner's product list showed
cards. A person sees the product either way. A fixed rule doesn't. Production sites can't be
tested in advance, so the run needs a way to find an element the recording didn't foresee.

## Change

1. **`services/ai`** (empty today). Build the pipeline from `AI_BOUNDARIES.md` for two call types,
   `find_target` and `clean_recording` (the latter is used by PL-123). That means validating the
   input, applying the data policy and redacting, calling the model with no tools, validating the
   output schema, running the code check, and writing an `ai_calls` row.
   - One provider for the trial: **DeepSeek** (owner's choice), through its OpenAI-compatible chat
     API with a JSON-only response.
   - The model is `DEEPSEEK_MODEL`, defaulting to DeepSeek's Flash model id from their API docs.
     Write the id you used in the report.
   - Retry once on `DEEPSEEK_ESCALATION_MODEL` when the output fails the schema or a gate, if
     that is set.
   - Text only: the snapshot is text, so no images are sent.
   - The key comes from `DEEPSEEK_API_KEY`, which is already in `.env.example`; add the model
     names there too. With no key, `find_target` answers "unavailable" and the row parks exactly
     as today. Nothing crashes.
   - The provider sits behind one small client interface, so another provider can be added later
     without touching callers.
   - No model SDK import outside `services/ai`.
2. **Page snapshot** (extension). A new `snapshot` command returns the bound tab's interactive and
   labelled elements, each with:
   - a short token, also written to the element as `data-pl-snap`;
   - its role, accessible name, label, placeholder, and visible text (clipped);
   - the nearest heading or section name;
   - whether it is visible and enabled.

   Typed values, password fields and hidden inputs are never included. Elements outside the
   allowed origins aren't included either. Cap the size (e.g. 400 elements, nearest the viewport
   first).
3. **Run-time finding** (runner). When a step's target resolves to no element, or more than one,
   the runner does this:
   1. Try `target_memory`.
   2. If that fails, take a `snapshot` and call `find_target` with the step's intent, action and
      recorded targets as hints.
   3. Gate the answer: the token exists and is unique, the role fits the action (fill → a text
      box or combobox, select → a combobox or listbox, click → anything clickable), and it is not
      destructive unless the step allows it.
   4. Send the step again with a first rung `{"by": "snap", "value": "<token>"}`.

   On success, the extension returns the element's own ladder (role and name, label, a stable
   CSS selector), and the runner stores it in `target_memory`. "not_here" or a failed gate parks
   the row with "ProcessLens couldn't find '<intent>' on this page."

   Cap: 6 model calls per record. A step with no `intent` uses its name.
4. **`target_memory`** (migration `0014_target_memory.sql`). Key: tenant, workflow, step id,
   origin. Value: the ladder that worked, when it was last used, and a hit count. It is read
   before `find_target` on the next run. A recipe never changes.
5. **Conditions use it too.** An `element_present` / `element_absent` condition whose targets find
   nothing may be asked as an intent ("the search result for Oak Standing Desk"). This is only for
   a branch that parks or ends a record for a person, never for a commit's `assert_after`. "not_here"
   keeps today's answer.

## Tests (write first, failing, then fix)

Use the owner's fixture. In it, the search step and branch-1 target a table cell.

- **Runner:** a page whose product shows as a card makes `branch-1` ask `find_target`, which finds
  the card. The row carries on, and the click on the product uses the found element.
- **Gates:** a model answer naming a token that isn't in the snapshot, a destructive button, or a
  text box for a click is refused, and the row parks with the sentence.
- **Memory:** a second run with the same page makes no model call.
- **Cap:** the 7th call in one record doesn't happen, and the row parks.
- **No key:** the row parks as today, and no exception is raised.
- **`services/ai`:** a schema failure is logged as `validation = 'fail'` and escalates once.
  The redaction strips typed values. Every call writes an `ai_calls` row.
- **Extension:** the snapshot never contains a password field, an input's value, or an element from
  another origin. The `snap` rung resolves only the tagged element.
- Use a stub model client in every test. No test calls a real model.

## Stay out of

`guard_record_transition()`, the ledger states, write-ahead and reconcile. Never let a model decide
`verified` or `skipped`, or a commit's `assert_after`.
