# PL-073: A saved-toast's check uses its message, not its glued-together text

Owner: T2 (DeepSeek) · Reviewer: T1 · Size: **small, 1 part** · Branch `pl-073`, built on `pl-069` · Worktree
`C:\Users\vasup\process-lens\.worktrees\deepseek2` · **Recorder only.**

## Why
PL-069's OrangeHRM timesheet golden parks at the save:

> the page never showed "SuccessSuccessfully Saved…" within 8 seconds

The recorder reads a confirmation's text with `trimmedText(node)` (`confirmationIn` in
`apps/extension/src/content/recorder.ts`), which is the element's `textContent`. A toast built from several elements
(OrangeHRM's `oxd-toast`: a title "Success" and a message "Successfully Saved") has its child texts **run
together with no space**. That string is never on the page, so the check can't pass. Many apps' toasts are built
this way (Vue, MUI, Ant, Chakra).

## The fix
When the confirmation node has more than one text-bearing descendant, record the **message**:
- the longest descendant text that matches the confirmation words the recorder already looks for (saved, created,
  updated, success…);
- otherwise the longest descendant text.

Collapse whitespace as today. A node with a single text keeps today's behaviour exactly.

Also check how the executor matches `text_visible` (`apps/extension/src/executor/assertions.ts`), and say in the
report whether it would have matched the glued text. The recorded value must be one the executor can find.

## Tests first (vitest, red before the fix)
- **OrangeHRM's toast:** the markup copied from OrangeHRM 5.7's `oxd-toast` (title "Success", message "Successfully
  Saved") records `text_visible: "Successfully Saved"`.
- **One-element toasts:** a plain "Lead created" toast is unchanged.
- **Odoo's notification:** its markup (title plus body) records the body.
- **The executor finds it:** an executor assertion test finds the recorded value on that same markup.
- **No regression:** every existing recorder observation test passes unchanged.
