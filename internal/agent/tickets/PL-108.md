# PL-108: Experiment — click and type from inside the page, so no work window is needed

Owner: T2 (DeepSeek) · Branch `pl-108` (from `main`) · Reviewer: T1 · Type: experiment, decides a
direction; nothing here ships to testers until T1 and the owner decide.

## Why

A run drives the page through `chrome.debugger`. That costs us:

- the "ProcessLens started debugging this browser" bar on every window;
- a separate work window that must stay visible: Windows marks a fully covered or minimized window
  hidden and Chrome stops drawing it (the owner's work window went black on 2026-10-26);
- the `debugger` permission, which scares people at install.

Almost all of the engine already runs inside the page through `Runtime.evaluate` (finding targets,
checks, guards). The debugger is used for the input itself (`executor/dispatch.ts`:
`Input.dispatchMouseEvent`, `Input.dispatchKeyEvent`, `Input.insertText`), page loads
(`Page.navigate`, load events), JavaScript dialogs, and the network evidence and blocking
(`Network.*`).

## Question

Can a run click, type, select and upload from inside the page (content script, `isTrusted=false`
events, React-safe value setting) well enough to be the default, falling back to the debugger only
for the steps a site refuses?

## Build (behind a flag, off by default)

1. An in-page dispatcher with the same interface as `executor/dispatch.ts`:
   - click: scroll into view, `pointerdown/mousedown/pointerup/mouseup/click` on the hit-tested
     element at its centre;
   - type/fill: the native value setter + `input`/`change` (React's value tracker), `execCommand
     ("insertText")` for contenteditable;
   - keys: `keydown/keypress/keyup`, plus the form's `requestSubmit()` for Enter in a field;
   - select, upload (`DataTransfer` on the file input).
2. Page loads via `chrome.tabs.update` / `chrome.webNavigation`; dialogs via a main-world
   `window.alert/confirm/prompt` override installed at document start.
3. Network evidence via `chrome.webRequest` (observe only).
4. A per-step fallback: if the in-page action produces no effect the step's own check can see, retry
   that one step through the debugger and record which path worked.
5. Run the page in a normal background tab of the person's own window instead of a separate
   window, and measure whether it still works there.

## Measure

Run every existing golden and fixture e2e (Odoo, Twenty, the local sites) three ways: debugger only
(today), in-page with fallback, in-page with no fallback. Then run them again with the tab in the
background and the window minimized.

Report a table: per task, pass/fail for each way, which steps needed the fallback, time per row.
Note any step where a site ignored the in-page event, and what it was (editor, dropdown, upload).

Background-tab risk to check on purpose: Chrome throttles timers and stops `requestAnimationFrame`
in hidden tabs. Menus and dropdowns that wait for an animation may stall. Say which ones did.

## Not in this ticket

- Changing the default. T1 and the owner decide from the table.
- Removing the `debugger` permission.
