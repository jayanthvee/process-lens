# PL-016: From a recording to a running recipe

Owner: T2 · Reviewer: T1 · Depends on: PL-015 (merged) · Phase: C

## Description
The owner tested the recorder by hand on 12 October 2026, on Gmail and on the lead-CRM fixture. Two things came out
of it.
- **Record and run aren't connected.** A person can record a demonstration, but cannot run it. The compiler (PL-008)
  is a Python library that only tests call, and nothing loads a recipe into the extension. The popup says "No recipe
  is loaded into this browser session."
- **The recorder drops or garbles what real pages do.** The e2e suite never caught any of this, because it runs a
  hand-written recipe (`fixtures/sites/lead-crm/recipe.json`) on a fixture built for that recipe.

This ticket connects the loop, fixes the recorder bugs the owner found, and adds a second, messier fixture site
modelled on what broke. Proving the whole chain end to end in a real browser is **PL-016b**. This ticket has **no
e2e or Playwright work**.

## Scope
- `services/api/` (a new compile route) and `tests/api/`
- `packages/compiler/`, and its tests only where a requirement needs it
- `apps/extension/src/` (content, background, popup) and `apps/extension/tests/`

## Requirements

1. **The compile route: `POST /api/v1/recipes/compile`.**
   - **Request body:**
     - the recording (the popup's event list);
     - `name`;
     - `when_to_use`;
     - `sample_row`;
     - `record_key_column`;
     - `allowed_origins`;
     - `commit_step_ids`.
   - **Response:** `compile_recording(recording, CompileOptions(...))` returns `{recipe, warnings}`, and the route
     returns it. It stores nothing.
   - **Errors:** a compiler error is a 422 that lists every problem. The commonest is a commit step with no
     `assert_after`.
   - **Security:** the route sits behind the PL-015 front door. Like the session route, it accepts the pinned
     extension origin, and only that route gains this exception.
   - **Tests:**
     - a fixture recording compiles to a recipe that passes `recipe_problems`;
     - a recording whose save has no observation gets a 422 naming the missing `assert_after`;
     - the extension origin is accepted here and still refused on `/runs/{id}/cancel`.

2. **"Make recipe" in the popup.**
   - After **Stop**, a **Make recipe** form asks for:
     - the workflow name;
     - which recorded value is the record key;
     - which step is the commit (the last click is pre-selected).
   - The form sends the recording to the compile route (requirement 1), shows the warnings, and on success stores the
     recipe under `processlens:executor-recipe` and the recorded values as the row under the existing row key. **Run**
     then works with no other step.
   - On a 422, it shows the problems in plain words and stores nothing.
   - **Tests (vitest):**
     - success stores both keys;
     - a 422 stores nothing and shows the problems;
     - the commit step defaults to the last click.

3. **Observations survive a full-page save** (bug a).
   - When a recorded click or submit is followed by a top-level navigation in the recorded tab, the content script on
     the new page reports any `role=status` / `role=alert` / toast text that appears within 3 seconds of load.
   - That report is attached as the observation for the event that caused the navigation.
   - The service worker holds the "pending observation" across the navigation.
   - **Test:** a click → navigation → status text on the new page yields one observation linked to the click, and the
     compiler turns it into that step's `assert_after`.

4. **A `<select>` is recorded once** (bug b). A change on a `<select>` emits only a `select` event, never an extra
   `fill`.
   - **Test:** one change gives exactly one event.

5. **Step ids are unique for the whole recording** (bug c).
   - The service worker assigns ids from one counter per recording session, so a page load doesn't restart the
     content script's counter.
   - **Test:** two page loads, then three clicks → `click-1`, `click-2`, `click-3`.

6. **Navigation is recorded** (bug d).
   - A top-level navigation that no recorded click or submit caused is recorded as a `navigate` event with its URL.
     That covers typed URLs, back/forward and reloads, and uses `webNavigation` transition data.
   - A navigation caused by a recorded click is not recorded a second time.
   - **Tests:** back/forward yields a `navigate`; a link click yields only the click.

7. **No invalid role names** (bug e).
   - The recorder never emits `role: "label"`, or any role outside the ARIA set the resolver supports.
   - A click on a `<label>` is recorded against the control it labels.
   - **Test:** clicking a label records its input's targets.

8. **An icon button is recorded by its own name** (bug f).
   - A click inside a button-like element with its own `aria-label` or `title` (the ✕ on a recipient chip) is
     recorded against that element and its name ("Remove …"), never against the enclosing chip, option or form.
   - Key presses stay out of scope: there is no `press` action in the schema, and adding one is a later ticket. The
     report must list which keyboard-only edits are still not recorded.
   - **Test:** clicking the ✕ inside a chip records a target named after the ✕, not after the chip.

9. **Generated ids are not used as selectors** (bug g).
   - The CSS rung drops an id that looks generated:
     - Gmail-style `:xx`;
     - ids with long hex or digit runs;
     - React `:r1:`-style ids.
   - The step keeps its other rungs. A step left with no rung at all is recorded with a warning, never silently.
   - **Tests:** `#:qq` is dropped; `#lead-email` is kept.

10. **Rich-text fields are captured** (bug h).
    - Typing into a `contenteditable` element (a message body) is recorded as a `fill` with the element's text.
    - It is never recorded if the element is inside a password-like or `autocomplete="off"` credential context;
      reuse the existing password rule.
    - **Test:** typing into a contenteditable records one `fill` with its text.

11. **The messy fixture site: `fixtures/sites/messy-crm/`.** It uses the same standard-library-server pattern as
    `lead-crm`, with its own `selftest.py`.
    - It has:
      - ids regenerated on every page load;
      - a recipient field with autocomplete and removable chips, each ✕ having `aria-label="Remove <name>"`;
      - a contenteditable notes box;
      - a full-page POST save that renders "Saved" on the next page;
      - a link to a second page and back.
    - Every value is synthetic (`@example.test`).
    - It is the target for PL-016b's e2e. Here it is only built and self-tested, and the recorder's unit tests use
      its HTML as fixtures where useful.
