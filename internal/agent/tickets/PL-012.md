# PL-012: Ledger hardening (migration 0002)

Owner: T2 · Reviewer: T1 (review and break-it tests before merge) · Depends on: PL-011 (merged) · Phase: C

## Description
Make the database enforce the ledger rules that today only code review enforces, before the runner (PL-013) starts
writing to the ledger. Every gap below was confirmed by running the current migration on PostgreSQL 16. They are not
theoretical.

## Why: what the current schema allows (confirmed on PostgreSQL 16 with `0001_init.sql`)

| # | Gap | Consequence |
| --- | --- | --- |
| G1 | `submitted_unverified -> failed -> pending -> claimed -> ... -> submitting` is accepted. So are `submitting -> failed -> pending` and `reconciling -> parked -> pending` | A record whose save may already have reached the destination can be clicked again with no reconcile: a duplicate |
| G2 | A `run_records` row can be inserted directly as `verified`, and a row in `submitting` can be deleted | The write-ahead marker can be lost, and outcomes can be forged |
| G3 | Application code can set `attempts = 0` or raise `max_attempts` | The retry cap is advisory only |
| G4 | `parked -> skipped` is rejected | A person cannot dismiss a parked record; it stays parked forever |
| G5 | `TRUNCATE` empties the append-only tables (`step_events`, `ai_calls`, `committed_keys`, `recipe_versions`); the row triggers do not fire | Audit history can be wiped |
| G6 | A state change writes no audit row; the bulk recovery updates in `sql-patterns.md` write nothing | No record of who moved a record or when |
| G7 | Two runs on the same destination can both be `running`; both verify the same key, and the second `committed_keys` insert silently does nothing | A real duplicate in the destination goes unnoticed |
| G8 | The conditional state change does not check the owner; a worker can move a record another worker claimed | A stale worker can overwrite a live one |
| G9 | `run_records` has no idempotency key; the "skip already committed" pattern compares every row against one bind parameter | That pattern cannot work for a batch |
| G10 | No table records who approved a commit | Constitution rule 11 (a person approves the first commit) cannot be audited |

### 1. Migration `0002_ledger_hardening.sql`

**a. Commit-attempted flag (G1).**
- Add `run_records.commit_attempted boolean NOT NULL DEFAULT false`.
- The guard trigger sets it to `true` whenever a row enters `submitting`. Application code never sets it.
- Add `run_records.destination_checked_by uuid REFERENCES users(id)` and `destination_checked_at timestamptz`.

**b. Replace `guard_record_transition()` (G1, G3, G4).** Use `CREATE OR REPLACE FUNCTION` in 0002.
- Keep all 28 current transitions.
- Add `failed -> reconciling`, `parked -> reconciling`, and `parked -> skipped`.
- When `OLD.commit_attempted` is true, reject `failed -> pending` and `parked -> pending` unless the same `UPDATE`
  sets `destination_checked_by` (a person confirmed the destination does not have the record). The normal retry path
  for such a record is `failed|parked -> reconciling -> pending`.
- Reject any change to `attempts` other than the trigger's own `+1` on `pending -> claimed`.
- Reject any change to `max_attempts` after insert.

**c. Insert and delete guards (G2).**
- A `BEFORE INSERT` trigger on `run_records` requires `state = 'pending'`, `attempts = 0`,
  `commit_attempted = false`, and a non-null `idempotency_key` (see e).
- A `BEFORE DELETE` trigger rejects every delete.

**d. Transition audit (G6).**
- New append-only table `run_record_transitions`: `id bigint identity`, `tenant_id`, `run_record_id`,
  `from_state`, `to_state`, `reason`, `actor text`, `at timestamptz default now()`.
- An `AFTER UPDATE OF state` trigger writes one row per actual change, including changes made by bulk statements.
- `actor` is `NEW.claimed_by`, falling back to `current_setting('processlens.actor', true)`.

**e. Idempotency key (G9).**
- Add `run_records.idempotency_key text`, nullable in the column so existing development rows survive. The insert
  guard requires it on every new row.
- Add an index on `(tenant_id, idempotency_key)`.
- The runner computes the key from the pinned recipe's `meta.idempotency_key` template when it creates the run's
  records.

**f. One active run per destination, and a run lease (G7, G8).**
- Add `runs.destination_key text`, copied from the workflow when the run is created. A `BEFORE INSERT` trigger on
  `runs` requires it.
- Add a partial unique index on `runs (tenant_id, destination_key) WHERE status IN ('running', 'paused')`.
- Add `runs.lease_epoch integer NOT NULL DEFAULT 0`. It is incremented every time a worker takes over a run.

**g. Approvals (G10).**
- New append-only table `approvals`: `id uuid`, `tenant_id`, `run_id`, `run_record_id` (nullable for run-level
  approvals), `step_id`, `kind` (enum: `first_commit`, `commit`, `ai_value`, `repair`, `requeue`), `shown jsonb`
  (the exact values the person saw), `decision` (enum: `approved`, `rejected`), `decided_by uuid NOT NULL REFERENCES
  users(id)`, `decided_at timestamptz NOT NULL default now()`.
- `UPDATE` and `DELETE` are rejected, as for the other append-only tables.

**h. TRUNCATE protection (G5).**
- A `BEFORE TRUNCATE` statement-level trigger rejects `TRUNCATE` on `recipe_versions`, `committed_keys`,
  `step_events`, `ai_calls`, `run_record_transitions`, `approvals`, and `run_records`.

### 2. `internal/docs/sql-patterns.md`
- **Change state.** Add `AND claimed_by = $worker` and a lease check to the conditional update. The lease check is
  `AND EXISTS (SELECT 1 FROM runs WHERE id = run_records.run_id AND lease_epoch = $epoch)`. Zero rows still means:
  stop and re-read.
- **New pattern: take over a run.** A run whose `heartbeat_at` is older than the timeout gets a new `worker_id` and
  `lease_epoch = lease_epoch + 1`. Recovery runs only after a successful takeover.
- **Verify transaction.** The `committed_keys` insert reports how many rows it wrote. Zero rows means another record
  already committed this key, so pause the run with `pause_reason = 'duplicate_detected'`. Never treat it as success.
- **Skip already committed.** Join on `r.idempotency_key = k.idempotency_key` (replacing the single bind parameter).
- **New pattern: re-queue.** One for a record with `commit_attempted = false` (`-> pending`), and one for a record
  with `commit_attempted = true` (`-> reconciling`, or `-> pending` with `destination_checked_by` set).

### 3. `internal/docs/LEDGER_SPEC.md`
- Update the transition table to the new list, and state the `commit_attempted` rule.
- Mark rules L1, L4, L5, and L6 as enforced by the database where 0002 enforces them.
- Update the invariant-to-test table to name the new tests.

## Decisions this ticket assumes (owner: confirm or change before T2 starts)
1. A record whose idempotency key is already in `committed_keys` ends `skipped` with reason "already committed in an
   earlier run". It never ends `verified`, because the database has no `pending -> verified` transition.
2. Rows with an empty record key, or a key repeated within the same file, never become ledger rows. Input review
   excludes them (`input_records.status = 'excluded'`, with the issue recorded), and the results screen shows them
   from `input_records`.
3. A person may re-queue a commit-attempted record directly to `pending` only by recording that they checked the
   destination (`destination_checked_by`). Otherwise it goes through `reconciling`.
