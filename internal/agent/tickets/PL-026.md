# PL-026: What the admin panel needs from ProcessLens

Owner: T2 · Reviewer: T1 · Depends on: PL-023 (merged) · Phase: D · **Critical (touches the runner): T1 writes
break-it tests before merge** · Decisions: D-023, D-025

## Description
The admin panel lives in its own repository (D-023) and is built from modules (D-025). A module that needs the
schema to change gets its migration here, in this repository, because this repository owns the schema and the
runner. This ticket adds the first admin module migration and the product behaviour behind it:

- the admin module registry;
- a log of admin actions;
- the database role the admin panel connects as;
- a "pause everything" switch the runner obeys;
- turning off a person's access;
- the Chrome extension version check.

## Requirements
1. **Migration `db/migrations/0004_admin_core.sql`**, the `core` admin module.
   - `admin_modules`: one row per admin module this schema supports. Columns: `id text PRIMARY KEY`,
     `migration text NOT NULL`, `added_at`. This migration inserts the row `('core', '0004_admin_core.sql')`.
     Every later admin-module migration inserts its own row in the same file. The admin panel reads this table
     to decide which modules to switch on (D-025).
   - New columns:
     - `tenants.runs_frozen_at timestamptz` and `tenants.runs_frozen_by uuid REFERENCES users(id)`;
     - `tenants.min_extension_version text` (null means any version);
     - `users.deactivated_at timestamptz`.
   - `extension_reports`: the version each person's extension last reported. Columns: `user_id` (primary key),
     `tenant_id`, `version`, `reported_at`.
   - `admin_audit`, append-only through the `forbid_mutation()` trigger, like `approvals`:
     - columns: `id`, `tenant_id`, `actor_user_id`, `module` (text), `action` (text), `target` (text), `detail`
       (jsonb), `at`;
     - actions in this migration: `freeze_runs`, `unfreeze_runs`, `change_role`, `deactivate_user`,
       `reactivate_user`, `pause_run`, `cancel_run`, `set_min_extension_version`.
   - The role `processlens_admin` (NOLOGIN; the deploy creates a login that inherits it):
     - `SELECT` on every table;
     - `INSERT` on `admin_audit`;
     - `UPDATE (role, deactivated_at)` on `users`;
     - `UPDATE (min_extension_version)` on `tenants`;
     - **nothing else.** It cannot touch `runs`, `run_records`, `committed_keys` or `jobs`.
     - Every later admin-module migration grants only the columns its module writes, in the same file.
2. **The freeze switch: the API and the runner.**
   - `POST /api/v1/admin/freeze` and `POST /api/v1/admin/unfreeze` set and clear `runs_frozen_at`. Each writes an
     `admin_audit` row in the same transaction.
   - When frozen:
     - `POST /runs` and `/runs/{id}/resume` return 409 with "Runs are paused by an admin".
     - The runner checks the flag **at the same step boundary where it checks `cancel_requested_at`**. It pauses
       the run there with `pause_reason = 'admin_freeze'`, after reconciling any record in the commit window.
       **Never stop between `submitting` and `verified`.**
   - Unfreeze does not resume runs. Each run is resumed by a person.
3. **The extension version check.** No change to the hub protocol or its frames.
   - The extension reports its manifest version to a new `POST /api/v1/executor/version`:
     - each time the command session reaches `ready`;
     - the API stores it in `extension_reports` against the operator.
     - The extension change is this one call in the service worker, plus its unit test. Nothing else in the
       extension changes.
   - `POST /api/v1/admin/min-extension-version` sets or clears the minimum, with an audit row.
   - While the reported version is below the minimum:
     - `POST /runs` and `/runs/{id}/resume` return 409 with "Update the ProcessLens Chrome extension to version X
       or newer";
     - **runs already going are not interrupted.**
   - Compare versions numerically, part by part: `1.10.0` is newer than `1.9.2`.
4. **A deactivated user** can't start, resume or approve anything (403). Their open runs keep their state.
5. **The web app** (PL-023) shows banners:
   - when frozen: "An admin paused all runs. Nothing new will start." The Run buttons are disabled.
   - when the extension is too old: "Your Chrome extension is out of date. Update it to keep running tasks."
6. **The admin endpoints.** These, plus the existing pause and cancel, are the **only** write paths the admin
   panel uses for anything that affects runs. Until sign-in lands with the Railway ticket, they accept requests
   only from `127.0.0.1`, with a shared `PROCESSLENS_ADMIN_TOKEN` header (read from the environment, never
   committed).
7. **`internal/docs/ADMIN-MODULES.md`**, one page, explaining how to add an admin module that needs schema:
   - the PL migration: its tables or columns, its `admin_modules` row, and its grants;
   - the ADM ticket: the module folder and its manifest, naming that migration.

## Out of scope
The admin panel itself (ADM-001, in `process-lens-admin`), sign-in and SSO, and Railway.
