# PL-004: Recipe specification and JSON Schema v1

Owner: T1 Claude · Critical: no · Depends on: PL-001 · Phase: 1

## Goal
The recipe contract exists as a machine-checkable JSON Schema plus a short spec, so the compiler,
executor, and editor can all be built against it.

## Read first
- internal/AGENTS.md, internal/docs/SYSTEM_DESIGN.md (the recipe section), internal/docs/ARCHITECTURE.md, internal/docs/AI_BOUNDARIES.md

## Scope
- internal/docs/RECIPE_SPEC.md
- packages/recipe/schema/recipe.schema.json (JSON Schema 2020-12)
- packages/recipe/examples/create-lead.recipe.json
- internal/agent/reports/PL-004.md

## Git
The RECIPE_SPEC is private: commit it with `git -C internal`. The schema and example are public: write them in
the T1 worktree (`git worktree add ../process-lens-t1 -b pl-004`), push, and open a draft pull request titled
"Recipe schema v1".

## Out of scope
- Generated types and validation tests (a later DeepSeek ticket). Executor or compiler code.

## Requirements
1. Meta: name, when to use, input schema, record key template, idempotency key template (D-012),
   approval policy, allowed origins.
2. Every step type in the design doc, each with its own required fields.
3. Target bundles: ordered strategies, container scope, frame path.
4. Value sources per field: input column, constant, rule table, read from page, extracted from a document,
   AI-generated text (always requires approval).
5. Constitution 6 in the schema itself: `commit: true` requires `assert_after`.
6. `format_version` field; RECIPE_SPEC explains how future versions migrate.
7. Anything not already decided (for example a bounded agent step) goes into a proposal, not the schema.

## Acceptance criteria
- [ ] The example validates against the schema (paste the validator output).
- [ ] A commit step without `assert_after` fails validation (paste the output).
- [ ] RECIPE_SPEC is under about three pages and links to the schema rather than restating it.
