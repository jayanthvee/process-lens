# PL-016b: Prove record → compile → run in a real browser

Owner: T2 · Reviewer: T1 · Depends on: PL-016 (merged) · Phase: C

## Description
The e2e suite still proves the runner with a hand-written recipe (`fixtures/sites/lead-crm/recipe.json`). This
ticket proves the chain a person actually uses: the **real recorder** records a demonstration, the **compile
route** turns it into a recipe, and the **real runner** executes a batch from it.

The chain is proved on both fixtures:
- `lead-crm`, which is tidy;
- `messy-crm`, which has generated ids, recipient chips, rich text, a full-page save and a back navigation.

It also adds the `allowed_origins` confirmation T1 carried over from the PL-016 review, and a visible mode for
demos.

## Scope
- `tests/e2e/`: new test files, `conftest.py` helpers, and `README.md`
- `apps/extension/src/popup/` and `apps/extension/tests/` (requirement 3 only)
- `internal/agent/reports/PL-016b.md`

Do not change product code to make an e2e test pass. If a test exposes a product bug, stop, report it with its
evidence, and wait for T1.

## Requirements

1. **The golden test on `lead-crm`: `tests/e2e/test_record_compile_run.py`.**
   - **Record:** the test starts recording through the popup, as a person would. Playwright then performs the flow
     in the page: New lead → Email → Interest → Company → Save, until "Lead created" shows. Then it stops
     recording.
   - **Compile:** the test reads the recorded events from the extension and sends them to
     `POST /api/v1/recipes/compile`, choosing the record key and the commit step the way the **Make recipe** form
     does. It stores the result through `POST /api/v1/recipes`.
   - **Run:** the stored recipe runs the existing 5-row batch.
   - **Pass condition:** the batch ends with 3 `verified`, 1 `skipped` and 1 `parked`, and the fixture's test API
     shows each email exactly once.
   - The hand-written `recipe.json` is not used anywhere in this test.

2. **The golden test on `messy-crm`.**
   - **Record:** the flow is:
     - add two recipients and remove one with its ✕;
     - type into the rich-text notes;
     - visit the second page and come back with Back;
     - Save. "Saved" appears on the next page.
   - **Compile, then run 3 rows.**
   - **Pass condition:**
     - all 3 rows are `verified`;
     - the fixture's state shows each saved record with exactly the recipients the row named, never the removed
       one;
     - the notes text is the row's text;
     - the compiled recipe contains a `navigate` step for the Back.
   - If a step cannot be recorded or replayed, the test must fail with the reason, and the report must say which
     PL-016 item it traces to. Do not paper over it.

3. **Confirm the allowed origins in Make recipe** (carried from the PL-016 review).
   - Before storing, the form lists the origins the recipe will be allowed to act on, derived from the recording,
     each with a checkbox, all ticked by default.
   - The person can untick an origin. The form then sends the pinned list as `allowed_origins`, so a recorded
     navigation to an unticked origin becomes a 422.
   - **Tests (vitest):**
     - the derived origins are listed;
     - unticking one sends the pinned list;
     - a 422 is shown in plain words.

4. **Visible mode for demos.**
   - `PROCESSLENS_E2E_HEADED=1` opens the browser visibly, and `PROCESSLENS_E2E_SLOWMO_MS` (default 0) slows each
     Playwright action.
   - Both default off, so the suite and CI are unchanged.
   - Document both in `tests/e2e/README.md`.

5. **README clean-up.**
   - Remove the stale "Known blocker against a green run (2026-10-12)" section from `tests/e2e/README.md`. PL-014
     fixed that bug.
   - Add the two new tests to the table.
