# PL-121: a sign-in run notices the code page at once, and carries on after the code

Owner: T2 (DeepSeek) · Branch `pl-121` (from `main` at 4e08cdf) · Reviewer: T1
Read `internal/docs/WORKING-RULES.md` first.

## Why (owner's Goodlabs run 67a019d5, 2026-10-28)

The fixture is `tests/runner/fixtures/pl121_goodlabs_sign_in.json`. It holds the owner's saved
recipe (email scrubbed) and the run's timeline. The recipe:

1. navigate /login
2. fill the email
3. click Continue
4. `sign-in-finished`: `wait_for` url `/home/dashboard`, 90 s

What happened (UTC):

- 06:07:07: the steps begin. The email is typed and Continue is clicked.
- About 06:07:10: the code page shows. About 06:07:12: Goodlabs' code email arrives.
- Nothing types the code. `sign-in-finished` is a single 90 s check (`run_loop.py`, the `wait_for`
  block, ~line 814). The extension only looks for a code page *after* a check has failed
  (`checkCommandCondition` → `probeWallForCheck` in `service-worker.ts`). So the code page was
  first noticed when the wait ended, about 06:08:42.
- The code look then starts from that moment, minus 10 s (PL-119). The email from 06:07:12 is 90 s
  older, so it doesn't count. At 06:09:44 the run paused with `code_required` / `none`.

Teaching worked because the recorder's own watch looks for a code page right after each action
(`content/code-watch.ts`). The run has nothing like it while it waits.

**The next break, behind this one.** When a code from email is typed, `_apply_event` calls
`_stop_record_for_event`. That releases the record to `pending`, and it is claimed again from step
1. That is right for PL-102's case: a code page in the middle of a task, before anything was done.
For a sign-in, the code page is part of the task. Starting over means opening /login while already
signed in and looking for an email box that isn't there, so the row parks.

## Change

1. **The sign-in wait notices a code page within 5 seconds.**
   - While a `wait_for` step waits, the code page is looked for again and again, not only when the wait ends.
   - Do it either way:
     - the runner checks in slices of 3 s or less until the step's own deadline, and each failed slice gets the extension's existing wall probe;
     - or the extension's wait poll also probes for a code page and answers early with the `code_required` event.
   - Say which you chose and why.
   - The step's total wait stays its own `timeout_ms`. No new constant for the person to set.
2. **A code typed during a wait doesn't restart the row.**
   - When `code_required` arrives during a `wait_for` step and the code from email is typed and the code page goes away (`entered` and `cleared`), the record stays `filling` and the same wait goes on.
   - If less than 30 s of the wait is left at that point, it gets 30 s more.
   - Steps 1–3 are not sent again.
   - When the code is not typed, the run pauses exactly as today.
   - A code page during any other step keeps PL-102's behaviour: release, then claim again.
3. **The panel's "no code" sentence matches PL-119.** `apps/web/src/panel/PanelTasks.tsx` (~line 163) still says "No code arrived at … Check that this inbox is signed in…". Use PL-119's sentence: "No new code email arrived. If you already opened it in Gmail, ProcessLens can't see it — type the code here."
