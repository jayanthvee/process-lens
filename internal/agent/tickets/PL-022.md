# PL-022: Real test apps (Odoo and Twenty CRM) running locally

Owner: T2 · Reviewer: T1 · Depends on: PL-018 (merged) · Phase: C

## Description
Our test sites are pages we wrote ourselves, so they contain only the bugs we already thought of. From now on,
recording and replay are tested against **real open-source business apps** running locally in Docker:
- **Odoo 18 Community** covers the brief's CRM, accounting, shop/inventory, sales and calendar.
- **Twenty CRM** is a modern React CRM, with autocompletes, inline editing and command menus.

These count as the brief's "demonstration websites". They are real software, and they are safe: they run
locally, can be reset, and send no external email.

This ticket only stands the apps up with seed data and reset scripts. **T1 runs all browser testing against
them.** T2 runs no e2e in this ticket.

## Requirements
1. **`infra/test-apps/docker-compose.yml`** runs both apps, separate from the root `docker-compose.yml`
   (never edit the root file).
   - **Odoo:** pin an exact `odoo:18` tag plus its own Postgres, on `localhost:8069`.
   - **Twenty:** use Twenty's documented self-host images, pinned to exact tags, with its server, worker,
     Postgres and Redis, on `localhost:3000` (move ProcessLens's own services if they collide).
   - All data goes in named volumes. Nothing listens beyond `127.0.0.1`.
   - **Outgoing mail is disabled** in both apps: no SMTP, or a null mail server.
2. **Seed scripts,** in Python under `infra/test-apps/`, idempotent:
   - **Odoo** (through XML-RPC). Create the database. Install `crm`, `sale_management`, `stock`, `account`
     and `calendar`. Create:
     - 3 salespeople;
     - 10 existing leads, so the duplicate checks have something to find;
     - 20 products with codes, prices and stock;
     - 5 customers with open invoices.
   - **Twenty** (through its API). Create the workspace and a login. Create 10 people and 5 companies.
     - If the first workspace needs one manual sign-up step, document it in the README in at most 3 lines,
       and script everything after it.
   - **Credentials:**
     - Test logins are written to `infra/test-apps/.env.example`, which is committed. They are test values
       only.
     - The real `.env` is gitignored.
     - Never put a password in a recipe or a recording.
3. **Reset.** `python infra/test-apps/reset.py odoo|twenty|all` drops the app's data and re-seeds it, in under 3
   minutes each. T1 uses it between test runs.
4. **Sample CSVs** in `infra/test-apps/samples/`, one per use case the apps cover:
   - use case 1, leads: 20 rows, including 3 duplicates of seeded leads and 2 rows with a missing email;
   - use case 4, product updates: 10 rows, including 1 unknown code;
   - use case 6, enrollment-style: on Odoo, using contacts and tags;
   - leads for Twenty: 10 rows.
5. **README** (`infra/test-apps/README.md`): start, seed, reset, the URLs and logins, and the RAM it needs. Odoo
   plus Twenty together must run on a 16 GB laptop.
6. **Decisions:** add two entries to `internal/docs/DECISIONS.md`.
   - **D-021, hosting:** Railway for the API, the workers, Postgres and the web app (the PM chose Vercel or
     Railway; Vercel can't hold the hub's WebSocket or run long workers).
   - **D-022, test targets:** real open-source apps (Odoo and Twenty) replace hand-built mocks as the main
     test targets. The mocks stay for unit-level fixture tests.

## Out of scope
- Any recorder, executor, runner or web-app change.
- Writing recipes or e2e tests against the apps. T1 does that.

## Acceptance criteria
- [ ] `docker compose -f infra/test-apps/docker-compose.yml up -d` followed by `python infra/test-apps/reset.py all`
  gives both apps seeded and logged-in-ready. Paste the real output in the report.
- [ ] A Python unit test checks the CSV samples' shape: row counts, and the duplicates and missing values listed
  above.
- [ ] Gates: `python -m pytest -q`, `ruff check .` and `ruff format --check .`.
- [ ] Report: `internal/agent/reports/PL-022.md`.

## T2 operating rules for this ticket
- **Sub-agents** run on deepseek-flash only. Builders use thinking high and `max_steps` 80; the coordinator stays
  on thinking low. Don't choose other models.
- **No e2e runs.** No plan stop. Stop only for:
  - a change outside this ticket's scope;
  - a Docker problem you can't fix in 3 attempts;
  - three identical failures.
- If Docker Desktop isn't running, say so and stop. Don't work around it.
- On Windows, never use `2>&1` or the PowerShell `&` call operator. Scratch files go only under `.cache/` or
  `.data/`.
- Use conventional commits with no AI attribution. Never commit `docker-compose.yml` or
  `internal/docs/TEST-MOCK/`. Push the branch and stop for T1.
