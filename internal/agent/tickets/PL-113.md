# PL-113: Sign-ins finish and say why they stop; a row is Done only when the change is really there; updates teach and repeat cleanly

Owner: T2 (DeepSeek) · Branch `pl-113` (from `pl-112` at bbf77d8) · Reviewer: T1

## Why

On 2026-10-26 the owner taught a price update in Odoo Sales from the side panel (open a product,
change Sales Price) and ran a 5-row price list. The panel said **Done** for 3 rows and **Already
there** for 1. In Odoo, nothing changed: Webcam stayed $79, Oak Standing Desk $910, Mesh Task Chair
$329, and "Ceramic Coffee Mug", which does not exist, was also Done. A second run with new prices
said **Already there** for all four.

This breaks the core promise: every record ends with a true, explained outcome. Items S1–S3 come first, then item 1.
Every fix is a general rule; nothing may match Odoo's names, classes, or URLs.

## What went wrong (T1, from the owner's screenshots)

- The owner did not click a save button: Odoo saves the form by itself when you leave it. The
  recording had no save click, so the panel's default picked the last click, the **Sales** tab, as
  "The Sales click saves your work". Its inferred check (the tab is there) is true on every page, so
  every row passed.
- The recording held a fill for every field on the form, not just the one the person changed:
  `Typed the goods — "on"`, service, combo, track inventory, cost "455.00", category "All",
  reference "PL-DESK-1001", sales price "900.00", then "910", then "910.00".
- The preview in Try one row showed the value it meant to type (799), not what the page kept.
- The task's "already done" key was the product name, so a new price for the same product can never
  run again.
- A search that found nothing still went on to "Done".

## Change

Items S1–S3 come first. They are from the owner's Goodlabs sign-in test on 2026-10-27 (zip from
`pl-112` 2fc8e38, hosted API at main after PR #91). Run `7bad9d67…`: navigate → fill email → click
Continue parked twice, about 1 s after the steps began, with "Couldn't click “Continue”: something was
in front of it". The task was not marked a sign-in, and the panel never offered the Gmail code.
What T1 ruled out: the work window being hidden (that pauses with `window_hidden`, not this
sentence); the black/about:blank work window (that is the abandon guard retiring the tab *after* the
park); the Windows PIN prompt (that came from the owner's own autofill in their own tab, not the run).

### S1. Notice a code page that arrives late, while teaching

Cause (from the code): `recorder.ts` probes for a code page only 250 ms after a recorded action
(`TEACH_CODE_SETTLE_MS`), on attach, on `visibilitychange`, and on the panel's yes. Goodlabs answers
Continue with a loading state and a server call, so the code boxes render well after 250 ms. Typing or
pasting the code is never recorded (correctly), so no later action triggers another probe. Result: no
"Reading your code from Gmail…", and `status.signIn` is never set, so the task is saved as a
spreadsheet task with no email pick.

- Keep probing after an action for as long as the page is still changing: a `MutationObserver` on the
  document (debounced, e.g. 300 ms after the last change) plus a URL change (`popstate`, history API
  changes), for up to 15 s after the last recorded action. Stop at the first code page found.
- The Gmail lookup's `since` is the time of the last recorded action before the code page (minus
  30 s of slack), not the moment the probe fired, so a code email that arrived first is still found.
- Test: a fake page that shows the six "Digit N of 6" boxes 1.5 s after the Continue click, with no
  further action → the probe finds it, `signIn` is set, and the ask goes out once.

### S2. A sign-in run is Done only when the person is signed in

Cause: the saved recipe is `navigate /login → fill email → click Continue` and nothing after it. The
code page is not a step, so a run that clicks Continue would be marked Done straight away, before the
code page even loads. Nothing checks that the sign-in finished.

- A sign-in recipe ends with a wait step: wait until the page that came after the code while teaching
  is reached (its path pattern, e.g. `/home/*`), or at least until the code page is gone and no
  login/code prompt is showing. Up to 90 s, so the code email has time to arrive.
- While waiting, a code page triggers the existing PL-102 code read from Gmail.
- Done only when that check passes. Otherwise the row parks with "Sign-in didn't finish: <what the
  page shows>".
- Record the after-sign-in path while teaching (the first page after the code page) into the recipe.
- Test: a recipe compiled from a sign-in recording ends with that wait. A fake run that never leaves
  the code page parks. One that reaches the dashboard after the code is filled ends Done.

### S3. Say exactly what blocked a click, and stop mistaking a busy button for a covered one

The parked sentence says "something was in front of it" for every hit-test miss, including "the hit
test found no element at the box center" (the point is outside the window). The step's real error is
only in `step_events`, which no screen and no API shows. T1 could not tell which case this was.

- Reason in plain words per case: "…covered by <the covering element's own name/text, or its kind>",
  "…the button is outside the window and the page didn't scroll to it", "…the button was busy".
- Show the step's raw error detail on the run page under the row (small, for support), and return it
  from `GET /runs/{id}/records` as `last_step_error`. No values from the row in it.
- Two likely causes here; cover both with a real-DOM test:
  1. A button that goes `disabled`/`aria-busy` with `pointer-events: none` (a common button style)
     right as it is clicked: `elementFromPoint` passes through it and returns the card behind it, which
     reads as "covered". Before calling a target covered, check whether the target itself is
     disabled/busy/`pointer-events: none`. If it is, treat it as busy: wait as for item 11 of PL-107,
     then succeed via S2's check if the site moved on by itself.
  2. A full-height layout (`height: 100vh; overflow: hidden`) whose own inner panel scrolls: the
     button sits below the window, `scrollIntoView` on the document does nothing, and the hit test
     finds nothing. Scroll the nearest scrollable ancestor, then measure again.
- The work window is half the person's window wide. Note in the report whether Goodlabs-like
  layouts change at that width (no site names in code).

### 1. Done means the change is on the page (blocking)

- A commit step's check must prove the row's own values, not the page's chrome. An assertion that is
  true before the step ran (a tab label, a heading, a menu) is not a check: the compiler refuses it
  as a commit assertion, and the runner treats a check that already held before the step as "not
  proven" (park, never verify).
- For an edit (a field changed, then saved or left), the check is: the field shows the row's value
  after the save, read back from the page (or the record's saved view). Typed 799 → the page must
  show 799.
- If no check can prove it, the row parks with "ProcessLens couldn't confirm the change was saved."
  It is never Done.

### 2. Never take a tab, a heading or a menu as the save

- The default "save" is the last click that changes data (a button whose name or role reads as
  save/create/add/submit/confirm/apply/update, or a form submit). Tabs (`role=tab`), breadcrumbs,
  menu items and links that only move around never count.
- If no such click exists, the panel says plainly: "We didn't see a Save click. Some apps save by
  themselves. Click Save while teaching, or choose how your work is saved." With choices: one per
  recorded click, **The app saves by itself when I leave the page**, and **Nothing gets saved**.
- "Saves by itself" compiles a commit that leaves the form the way the person did (or uses the
  app's save shortcut, if recorded), then runs the item 1 read-back check.

### 3. Record only the fields the person changed

- A fill is recorded only when the person changed the value (input after focus, value differs from
  the value the field had when the page loaded or when focus arrived). Fields that the page filled by
  itself, or that were only tabbed through, record nothing.
- Checkboxes and radios record a click/check, not `Typed … "on"`.
- Several fills into the same field fold into one line with the final value
  ("Typed the sales price — 910").

### 4. Try one row shows what the page kept

- After the try, read the changed fields back and show "Sales price: now 799" (or "still 910 — not
  saved"). Never show only the value from the file as if it were the result.

### 5. An update's "already done" includes the new value

- When a task changes an existing item (it finds a row, then edits a field) rather than adding one,
  the key that prevents doing it twice is **the item + the new values**: Oak Standing Desk → 799 runs
  once; Oak Standing Desk → 850 runs again later.
- Plain words on the key line: "We'll skip a row if this product already got this exact change."

### 6. A search that finds nothing skips the row

- If the find step finds no match, the row is **Skipped: "No product called ‘Ceramic Coffee Mug’ was
  found."** (the column's plain name and the row's value). PL-106 started this for find-then-update;
  make sure it fires whenever the next steps depend on what the search found.

### 7. Teaching: fix a mistake without losing the recording

- Each line has its ✕ while recording too, not only after Stop.
- After Stop: **Continue teaching** (adds to the same recording) and **Start over** (clears, after a
  "Throw away these N steps?" confirm on the same screen). **Start teaching** no longer clears a
  recording silently.
- The step count and the list always match ("6 steps recorded" shows 6 lines; hidden code steps say
  "+1 hidden code step").
- The name box is empty, or suggests the site and task (e.g. "Update price on localhost"), never a
  previous recording's name ("Recorded on goodlabs.com").
- The key line names the column in the person's words ("Product"), not the field's hint text
  ("Search…").

## Tests (write first, failing, then fix)

- Compiler: a recording whose only click after the fills is a tab gets no commit on that tab; the
  panel's default is "no Save click seen".
- Compiler/runner: an assertion already true before the commit step never verifies a row (park with
  the item 1 sentence).
- Runner (unit, fake page): typed 799, page still shows 910 after save → parked, not Done.
- Recorder: a form with 10 fields where the person changes one records exactly one fill; checkbox
  records a click; three fills into one field fold into one line with the last value.
- Key: an update task with rows (Desk, 799) then (Desk, 850) runs both; (Desk, 799) twice runs once.
- Search that matches nothing → Skipped with the item 6 sentence.
- Panel: ✕ while recording; Continue teaching keeps steps; Start over asks first; count matches
  lines; name box never carries another site's name.
