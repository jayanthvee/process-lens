# PL-068: A verification-code page pauses the run, the person types the code on the same screen, and it carries on

Owner: T2 (DeepSeek) · Reviewer: T1 · Size: **medium, 3 parts** · Branch `pl-068` · Worktree: whichever DeepSeek
folder is free (`.worktrees\deepseek` or `.worktrees\deepseek2`) · Extension, API and web.

## Why
Sites like LinkedIn, Indeed and Workday ask for a one-time code, by email or SMS, when you sign in or when they want
to check it's you. Today a run hits that page and pauses as `login_required` or `challenge`, and the person has to
find the work window and type the code there.

The owner wants this instead: the run pauses, **the run page shows "Enter the code the site sent you" with a box,
right on that screen**, the person types it, ProcessLens types it into the site's code field and presses continue,
and the task carries on.

Rules that don't change:
- ProcessLens never stores, logs or records the code.
- It never types a password.
- It never reads anyone's inbox or SMS. The person supplies the code.
- No LLM calls (D-017).

## The fix
1. **Detect a code page** (`apps/extension/src/executor/guards.ts`, beside `challengeOrLoginInPage`). A page asks for
   a code when a visible, enabled input has any of:
   - `autocomplete="one-time-code"`;
   - `inputmode="numeric"` with a `maxlength` of 4–8 and a label, placeholder or nearby heading containing "code",
     "verification" or "one-time";
   - or the page is one of the known split-digit layouts (4–8 single-character inputs side by side).

   There must be **no password field**: a password page stays `login_required`. Raise a new event `code_required`,
   with the page's own heading as the detail (never the URL's query string). Add the kind to `shared/events.ts` and to
   the runner's `PAUSE_EVENTS`, so the run pauses with `pause_reason = 'code_required'` and the record is released
   before any commit, exactly like `login_required`.
2. **Send the code from the web app** (`services/api`, hub).
   - **The route:** `POST /api/v1/runs/{run_id}/code` with `{code}`, which is 4–10 characters of `[0-9A-Za-z]`.
   - **The check:** it's accepted only while that run is paused with `code_required`, and only from a person in the
     run's tenant.
   - **Delivery:** the hub forwards it once, over the session's socket, as a new command type `enter_code` (add it to
     `shared/command-protocol.ts` with the protocol's existing versioning). The code is held in memory only for that
     send. Never write it to the database, to `step_events`, to logs or to the response; a test asserts it appears
     nowhere in the database after the flow.
   - **The extension:** on `enter_code`, finds the code field(s) with the same detector, types the code (split digits
     one per box), then presses the page's single primary submit button (a `button[type=submit]` or the only enabled
     button inside the form whose text is "Verify", "Continue", "Submit" or "Next"; if it can't find exactly one,
     it presses Enter in the last box).
   - **The result:** it reports `entered` or `not_found` and never echoes the code. On `entered`, the run resumes as
     a normal Resume does. The released record is claimed again (and with migration 0009, the pause doesn't burn an
     attempt).
3. **The screen** (`apps/web/src/pages/RunDetail.tsx` and the waiting-run component). When `pause_reason` is
   `code_required`, the paused banner becomes:
   - "The site is asking for a verification code (<page heading>). Enter the code it sent you."
   - a one-time-code input (`autocomplete="one-time-code"`, `inputmode` numeric where the code is numeric) and a
     **Continue** button, on that same screen;
   - while it sends: "Entering the code…". On `not_found`: "ProcessLens couldn't find where to type the code. Type it
     in the work window, then press Resume." Resume stays available as the fallback.
   - the input is cleared after sending and never kept in state longer than the send.

## Tests first (red before the fix)
- **vitest, detector:** `one-time-code` input, numeric with a "Verification code" label, six split boxes, and a
  password page (stays `login_required`); a normal form with a "Promo code" field must **not** trigger (it needs the
  verification wording or the `one-time-code` hint, plus being the page's only visible input group).
- **vitest, `enter_code`:** single box and split boxes get typed and the submit pressed; no submit found means Enter;
  the result never contains the code.
- **pytest, API:** 409 unless the run is paused with `code_required`; another tenant gets 404; a bad code shape is 422;
  the code is in no table afterwards (scan every text and jsonb column of the touched tables for it).
- **pytest, runner:** a `code_required` event pauses the run with that reason and releases the pre-commit record.
- **vitest, web:** the banner, input, Continue, the sending and not-found sentences, and Resume still shown.
- **e2e, new local fixture:** `fixtures/sites/code-login/` is a tiny page served by the e2e fixture server. It shows
  "Enter the 6-digit code we emailed you" with split boxes; the correct code is fixed in the fixture (`246810`); then
  it shows a form the recipe fills. One test: the run pauses on the code page, the test posts the code through the
  API exactly as the web app does, and the row ends `verified`.
