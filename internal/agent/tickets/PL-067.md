# PL-067: Runs go at a person's pace, stay under a daily cap per site, and stop at a warning page

Owner: T2 (GLM Flash) · Reviewer: T1 · Size: **medium, 3 parts** · Branch `pl-067` · Worktree
`C:\Users\vasup\process-lens\.worktrees\glm` · Runner, API, ledger reads, one extension guard.

## Why
People will run ProcessLens on sites like LinkedIn, Indeed and Workday under their own accounts. A run must look after
those accounts:
- it never hammers a site;
- it stays under a daily number the company sets;
- it stops the moment the site shows an "unusual activity" or "are you a robot" page.

The person deals with that page. ProcessLens never pushes past it. No LLM calls anywhere (D-017).

## The fix
1. **Pacing** (`services/runner/run_loop.py`).
   - **Settings:** a run gets `min_seconds_between_rows` (default 0, which is today's behaviour) and
     `min_seconds_between_steps` (default 0).
   - **Where they live:** in the run's own settings if `runs` already has a settings JSON (check
     `db/migrations/0001_init.sql` and later). Otherwise add migration `0010_run_pacing.sql`: two nullable integer
     columns on `runs`, with a CHECK of `0..3600`, and no change to the ledger guard.
   - **Behaviour:** the runner waits at least that long before claiming the next row, or before sending the next step
     command, adding a jitter of 0–25% of the gap. Use the existing `Clock` (`services/runner/clock.py`) so tests
     don't sleep.
   - **Pause and cancel still win:** a pause or cancel during a wait is noticed within one second.
2. **A daily cap per site** (`packages/ledger/reads.py`, append only; the runner).
   - **The setting:** a tenant setting `site_daily_caps: {origin: number}`. Look for a tenant settings column first,
     and add it to the same migration if there isn't one.
   - **The check:** before claiming a row, the runner counts this tenant's rows that entered `submitting` today (UTC)
     on runs whose recipe's `meta.allowed_origins` include that origin.
   - **At the cap:** the run pauses with `pause_reason = 'site_daily_cap'` before claiming, and the record stays
     `pending`. Nothing reaches the commit window, so the ledger invariants are untouched.
   - **The run page:** says "Paused: today's limit for linkedin.com (25 rows) is reached. It can continue tomorrow."
     The action sits on the same screen (the owner's rule): a Resume button that is disabled with that sentence until
     the count allows it.
3. **Stop at a warning page** (`apps/extension/src/executor/guards.ts`, `challengeOrLoginInPage`). Add markers for
   rate-limit and unusual-activity pages:
   - visible text such as "unusual activity", "we've restricted", "too many requests", "verify you're human",
     "temporarily blocked", or "security check";
   - a page title like "Security Verification".

   These raise the existing `challenge` event, so the run pauses and nothing is clicked or solved. Keep the list in
   one constant, matched case-insensitively and only on visible text, and never on input values. The pause sentence
   names the page: "The site showed a warning page ('unusual activity'). Check it yourself, then Resume."

## Tests first (red before the fix)
- **pytest, runner (`tests/runner`):**
  - with a fake clock, a 30-second row gap makes the second claim wait 30–37.5 seconds;
  - a pause during the wait stops the run without claiming;
  - the cap pauses with `site_daily_cap` and leaves the record `pending`;
  - another tenant's rows don't count towards the cap;
  - at zero settings, the behaviour is exactly today's.
- **pytest, db:** the migration applies, and the CHECK refuses -1 and 3601.
- **vitest:** each warning marker raises `challenge`; a normal LinkedIn-like page with the word "security" in a job
  description does **not** (only page-level markers count: title, a heading, or a dialog's text); and the existing
  challenge and login tests pass.
- **vitest, web:** the cap pause sentence and the disabled Resume.

  pause_reason), your report.

  identical failures.

- **Git:** conventional commits, no AI attribution, never push to `main`.
