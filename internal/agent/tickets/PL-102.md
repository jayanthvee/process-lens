# PL-102: Codes from email are fetched and typed by ProcessLens, and never recorded

Owner: T1 · Branch `pl-102` (from `main`)

## Why

Many sites send a one-time code by email at sign-in. Today a run pauses on that page and the person
has to open their inbox, copy six digits and paste them into the run page (PL-068). The owner's bar
is that nobody does this by hand: if the code is in the person's email, ProcessLens reads it and types
it, on any site.

On the pilot call the recorder also took the code down: six single-digit boxes became six
"Typed the fill input" steps, and a click in Gmail was named with the email's text, code included.
That is a privacy bug.

## Change

### 1. Reading the code (`apps/extension/src/shared/email-code.ts`, new)

- `parseGmailFeed(xml)`: Gmail's inbox feed (`https://mail.google.com/mail/u/<n>/feed/atom`) as
  `{ from, subject, snippet, receivedAt }`. Plain string parsing: a service worker has no DOMParser.
- `findCode(messages, { since, site })`: `found` with one code, `none`, or `ambiguous`.
  - Only messages received no earlier than one minute before the code page appeared.
  - Only messages that talk about a code (verification, one-time, passcode, security/login code, OTP).
  - A code is 4–8 digits (or Google's `G-123456`); dates, times, prices and phone numbers are not.
  - A sender or subject that names the site wins. Otherwise the only code there is wins (white-label
    logins such as "NCPL One" do not name GoHighLevel). Two different codes and no way to tell: `ambiguous`.
  - Newest wins among messages from the same sender (the person asked twice).
- `scrubCodes(text)`: text that talks about a code loses its 4–8 digit runs.

### 2. Using it during a run (service worker + hub)

- When the guard reports `code_required`, the run pauses on the code page as today. The extension then
  looks for the code: the feed for each signed-in Gmail account (`u/0` to `u/4`, credentials included),
  every 5 seconds for up to 2 minutes. If the feed does not answer, it reads the inbox list of a Gmail
  tab already open in this Chrome through the debugger, without opening or marking any email.
- `found`: the code is typed with `enterCodeInPage` and the page's own continue is pressed. The
  extension reports `code_entered` (source `email`), never the code.
- `ambiguous`, `none` after 2 minutes, or no Gmail: the run page asks the person as today, with a
  plain reason ("Two codes arrived and we can't tell which is this site's. Type the right one.").
- After a code is entered (from email or by the person) and the code page is gone, the run resumes
  by itself. No second click.
- The first time, the run page asks once, right where the code box is: "This site emailed you a code.
  Let ProcessLens read sign-in codes from your Gmail? [Yes, always] [I'll type it]". The answer is
  kept in the extension. It can be turned off in the same place.

### 3. The code never leaves the computer

The code is not stored, logged, sent to the hub, or written to the ledger, in either direction. Email
text other than the one code is not kept anywhere. Nothing calls an LLM (D-017).

### 4. The recorder never takes a code down (`content/recorder.ts`, `shared/fingerprint.ts`)

- Nothing typed into a code field is recorded: 4–8 single-character boxes in a row,
  `autocomplete="one-time-code"`, or a numeric field whose own words ask for a code. A short number
  field that is not a code (a quantity) is still recorded.
- Every name and text rung goes through `scrubCodes` before it leaves the page.

## What it cannot do

Codes sent by text message, and codes from an authenticator app on a phone. Those still ask the
person, as today. Outlook is a follow-up if a pilot company uses it.
