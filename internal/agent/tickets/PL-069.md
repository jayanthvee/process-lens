# PL-069: OrangeHRM as the Workday stand-in, and a weekly timesheet filled from a sheet

Owner: T2 (DeepSeek) · Reviewer: T1 · Size: **large, 3 parts** · Branch `pl-069` · Worktree
`C:\Users\vasup\process-lens\.worktrees\deepseek2` · Test infrastructure and one e2e golden.

## Why
ProcessLens is for a consulting company. Its people's most repetitive weekly job is the **timesheet**: hours per
project per day, in Workday or a tool like it. Workday has no public sandbox. **OrangeHRM** (open source) is real HR
software with timesheets, projects, employees and approvals, and it runs in Docker. Real software beats a look-alike
(D-022), so it joins Odoo and Twenty as a test app.

## Part 1: OrangeHRM in the test apps
- **Containers:** add OrangeHRM 5.x to `infra/test-apps/docker-compose.yml`, following that file's conventions:
  - the official `orangehrm/orangehrm` image, pinned to an exact 5.x tag;
  - a MariaDB/MySQL container;
  - the port bound to `127.0.0.1` only (pick a free one, for example 8070);
  - named volumes, outgoing mail off, and env vars namespaced `ORANGEHRM_*` with working test defaults.
- **Never touch the root `docker-compose.yml`.**
- **First-run install:** OrangeHRM's installer runs in a browser the first time. Find its unattended install (an env
  var or CLI the image supports; read the image docs) so a fresh `up` gets a ready app with a test admin login. Put
  the test login in `infra/test-apps/.env.example` as a committed test value, like Odoo's `ProcessLensTest18`.
- **`infra/test-apps/seed_orangehrm.py`:** through OrangeHRM's own REST API (v2) where possible:
  - 3 fake employees, each with an ESS (employee) login;
  - 2 customers and 4 projects with activities ("Development", "Meetings");
  - one employee assigned to the projects;
  - and remove any timesheet that employee already has for the test week.
  - Add `orangehrm` to `TARGETS` in `reset.py`, and include it in `all`.
- **Helpers in `tests/e2e/real_apps.py`:** `orangehrm_base`, `login_orangehrm(page, env)`, and
  `orangehrm_timesheet_rows(env, employee, week_start)` (read through the API) returning
  `[(project, activity, {day: hours})]`.
- **Docs:** update `infra/test-apps/README.md` with how to start it and how to reset it.

## Part 2: `tests/e2e/test_orangehrm_timesheet_golden.py`
Model it on `tests/e2e/test_odoo_lead_golden.py`: the same fixtures and marks, reset (`reset.py orangehrm`), popup
form, harness calls, and a trace under `.cache/pl069/`.
- **Demonstration**, as the test employee: Time → My Timesheets → the test week → Edit → add a row (pick the project,
  pick the activity) → type hours for Mon–Fri → **Save**. Don't Submit: a saved draft is the commit, and submitting
  is a separate approval step.
- **The sheet:** `fixtures/demo/orangehrm-timesheet.csv` with `project, activity, mon, tue, wed, thu, fri`. Three
  rows, three different projects. The record key is project + activity (a template joining both).
- **Assertions over the API:**
  - the week's timesheet has exactly those three rows, with those hours;
  - each record is `verified`;
  - a second run of the same sheet adds no duplicate rows: rows end `skipped`, or `verified` without a new row,
    whichever the ledger gives. Quote it.

## Part 3: what was hard
OrangeHRM's timesheet is a grid of inputs in a table: the same shape the PL-048 column-header naming solved for
Odoo. In the report, say:

- how the project autocomplete behaved;

These findings tell us what Workday will need.

## When something fails
Run the golden at most **3 times**. A product bug (recorder, compiler or runner) is a finding: mark the test
`xfail(strict=True)` with the exact parked reason and failing step, and write the smallest product change that would
fix it. Your own harness mistakes are yours to fix.
