# PL-049: No false duplicate check on a product picker, no save check pinned to the demo's own number

Owner: T2 (DeepSeek Flash) · Reviewer: T1 · Size: **small, 2 parts** · Branch `pl-049` · Worktree
`C:\Users\vasup\process-lens\.worktrees\deepseek` · **Compiler only.**

## Why
PL-046 recorded an Odoo sales quotation. The compiled recipe has two defects (see
`git show origin/pl-046:internal/agent/reports/PL-046.md`, "Two more compiled defects"):
1. **A false duplicate check.** The product field's placeholder is "Search a product". `_looks_like_a_search` in
   `packages/compiler/compiler.py` sees the word "search" in a rung and adds "Skip a record if the search finds it".
   Nobody searched for anything: the person typed a product name and picked it from the dropdown. With that branch,
   rows would be skipped as duplicates.
2. **A save check pinned to the demo's number.** The save's observation was the new quotation's number, `S00001`, and
   it was compiled verbatim into `"assert_after": {"text_visible": "S00001"}`. Odoo gives every new quotation a new
   number, so no replay can ever pass this check.

## The fix
1. **A pick is not a search.** In `_looks_like_a_search` / `detect_duplicate_search`, a fill followed by a click on a
   dropdown option is a pick, not a search. The click counts as an option pick when any of its rungs has role
   `option`, or its `within` names a `listbox` or an autocomplete dropdown. Also, the word "search" found only in a
   `text_fuzzy` rung (that's a placeholder) is not enough on its own.

   Keep every existing case that is a search: role `searchbox`, a `within` that names a search container, a button
   named "Search", and Odoo's search view (Enter in the search box). The existing PL-017 tests must pass unchanged.
2. **Don't pin a number the app made.** Where the commit's `assert_after` is built (`_resolve_commit_assertion` in
   `compiler.py`, `packages/compiler/assertions.py`), a `text_visible` value doesn't pin when **both** of these are
   true:
   - it is not one of the sample row's values (so it wasn't typed by the person);
   - it looks like a generated reference: letters and digits with at least 3 digits, optionally with `/` or `-`
     separators, for example `S00001`, `INV/2026/00012`, `PO-0042`, `SO123`.

   Instead, use the same fallback the compiler already uses for a weak observation: the URL shape, or the next
   assertion the existing code would pick. Never leave a commit step with no `assert_after`.

## Tests first (pytest, red before the fix)
Build the candidates from the recipe JSON in the PL-046 report: the fill of "Search a product", the click on the
option `[PL-CHR-2001] Mesh Task Chair` (role `option`), and the save, whose observation is `text_visible: "S00001"` on
a URL like `http://127.0.0.1:8069/odoo/sales/12`. Put the fixture in `packages/compiler/tests/fixtures/`, as a new
`test_pl049.py`.
- **No branch:** fill plus option pick gives no duplicate branch.
- **Real searches still branch:** the existing searchbox, search-button and Enter-in-search cases still get one.
- **A placeholder isn't a search:** "search" in only a `text_fuzzy` rung gives no branch.
- **Generated numbers don't pin:** `S00001`, `INV/2026/00012` and `PO-0042` aren't pinned, and the save gets the URL
  shape (or the existing fallback) instead.
- **Typed values still pin:** a `text_visible` that equals a sample row value (for example a lead name) is still
  pinned as today.
- **Ordinary words still pin:** a `text_visible` like "Quotation saved" is unchanged.
