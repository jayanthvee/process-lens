# PL-112: "Nothing gets saved" saves nothing; plain finished-row words; sign-in tasks run from an email pick

Owner: T2 (DeepSeek) · Branch `pl-112` (from `pl-111` at 0e5c2b3) · Reviewer: T1

## Why

On 2026-10-26 the owner taught a sign-in with an emailed code from the side panel (zip from
`pl-111` 0e5c2b3). The recording was right: typed the email, clicked Continue, and nothing from the
Gmail tab or the code. The owner chose **Nothing gets saved** and pressed **Save as task**. It was
refused with:

> ProcessLens couldn't see anything change after "Continue", so it can't check that click worked.
> Pick a different answer for "Which click saves your work?", or choose "Nothing gets saved".

They had already chosen "Nothing gets saved", so the sentence tells them to do what they did. A
sign-in can't be saved as a task at all.

In the same session the 7-row Odoo run passed, but every finished row's reason read
**Assertion passed**, which is engine wording.

Every fix is a general rule. Nothing may match Goodlabs' names, classes, or URLs.

## Cause (T1, from the code)

- The panel sends `commit_step_ids: []` for "Nothing gets saved" (`PanelTeach.tsx` →
  `makeRecipeRequest`). That part is right.
- `packages/compiler/coalesce.py` `collapse_submits` sets `commit=True` on every click+submit pair,
  and on a lone submit, whatever the person chose. Continue sits in a form, so it becomes a commit
  step anyway, the compiler finds no assertion for it, and refuses.
- `compiler.py:259` ORs `event.commit` with `commit_ids`, so the choice cannot turn it off.

## Change

### 1. The person's choice decides which step saves

- When the request names commit steps (`commit_step_ids` was sent, even empty), only those steps are
  commits. A submit still folds into its click (one step), but it is not a commit unless chosen.
- When `commit_step_ids` is not sent at all (older callers), keep today's behaviour.
  The API model must tell "sent []" from "not sent" (`services/api/compile.py` defaults it to `[]`
  today; make the default `None`).
- With no commit steps the recipe is read-only (`filling → verified`), as PL-107 item 6 intended.
- If the chosen click is a submit and has no assertion, the PL-107 sentence still applies.

### 2. The refusal sentence never contradicts the choice

- If the person chose "Nothing gets saved" and the compile is still refused, do not tell them to
  choose "Nothing gets saved". Use the "This recording can't be saved yet: …" shape.
- The old error clears as soon as the save choice changes.

### 3. A finished row says what happened, in plain words

- Replace "Assertion passed" wherever a person sees it. Default reason for a verified row:
  - a row that saved something: **Added and checked**
  - a read-only row (no commit step): **Done**
- Fix it at the source (`packages/ledger/commits.py` `verify_commit` default, and any runner caller
  that passes its own engine wording), and in `plainReason` for rows already stored with the old
  words.
- Search for other engine words that reach the reason column (assertion, assert_after, commit,
  precheck, reconcile) and give each a plain sentence.

### 4. A sign-in task runs without a spreadsheet: pick an email, press Run

Owner's request, 2026-10-26. A task taught once that signs in with an emailed code should not ask for
a CSV.

- A task whose recording reaches a code page (the recorder already knows: `codePromptInPage` /
  the hidden code step) is a **sign-in task**. Say so in the task's own data (a flag in the recipe
  or the task record; your choice, explain it in the report). General rule; no site names.
- In Tasks, a sign-in task shows **Run** with a dropdown of emails instead of "Run with a
  spreadsheet". The dropdown holds the email used while teaching, plus any typed before for this
  task, plus "Another email…" (a text box). Remember the list per task in the extension's storage,
  not on the server.
- Run makes a one-row run from the picked email (the column the email was typed into while teaching,
  e.g. "Email or phone number"), reusing the existing one-row path (`Try one row` / run-once).
- During that run the code page is filled from Gmail exactly as PL-102 does today.
- Plain words on the same row when it can't:
  - no code email found: "No code arrived at <email>. Check that this inbox is signed in to Gmail in
    this Chrome, then press Try again."
  - more than one possible code: the PL-102 wording.
  - Gmail not allowed yet: the PL-102 offer with its **Read it from my Gmail** button.
- Zero LLM calls; the code is never stored, logged, or shown in the panel.

## Tests (write first, failing, then fix)

- Compiler: a recording of fill → click Continue → submit of the same form, with
  `commit_step_ids=[]`, compiles to a recipe with no commit step and no refusal.
- Compiler: the same recording with `commit_step_ids` omitted behaves as today.
- Compiler: with `commit_step_ids=["<continue id>"]` it is a commit step (today's refusal when no
  assertion can be inferred is kept).
- API: `POST /compile` with `"commit_step_ids": []` vs. the field missing.
- Web: choosing "Nothing gets saved" after a refusal clears the error; a refusal under "Nothing gets
  saved" never says "choose “Nothing gets saved”".
- Web/ledger: a verified row's reason shows "Added and checked" or "Done", never "Assertion passed",
  including a row stored with the old text.
- Web/extension (item 4): a recording with a code page is marked a sign-in task; its Tasks row shows
  Run with the email dropdown (taught email first) and no spreadsheet button; Run sends one row with
  the picked email in the taught column; "Another email…" adds to the list; the three plain sentences
  appear on the row.
