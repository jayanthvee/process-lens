# PL-013: Run orchestrator and runs API

Owner: T2 · Reviewer: T1 (plan review, then code review and break-it tests before merge) · Depends on: PL-012 (merged) · Phase: C

## Description
Make the backend own runs. A run executes one pinned recipe version against one input batch, record by record. Every
ledger write goes through `packages/ledger`, which implements `internal/docs/sql-patterns.md` exactly. The browser
side stays behind an `Executor` interface. This ticket ships a scripted fake executor and fake destination, and
PL-014 connects the real extension over the WebSocket hub.

Constitution rules this ticket must hold: deterministic execution with zero model calls (D-017); the database ledger
is the only workflow state (D-004); write-ahead before every commit; reconcile before any retry of a record that
reached `submitting`; waits are conditions with timeouts, never fixed sleeps.

## Requirements

### 1. `packages/ledger`: the only place ledger SQL lives
One typed function per pattern in `sql-patterns.md`:
- claim run, take over run, heartbeat;
- claim record, change state;
- write-ahead `submitting`, mark `submitted_unverified`;
- verify (one transaction with `committed_keys` and the zero-row incident);
- recover run, close out exhausted records, skip already-committed records;
- both re-queue variants;
- record an approval.

Rules for every function:
- **Fencing.** Every state change is conditional on the expected state, `claimed_by`, and the `lease_epoch` check with
  `FOR SHARE`. Zero rows raises a typed `StaleLease` or `StateConflict`. It never fails silently.
- **Reason.** Every state change sets `reason`, even when it's unchanged, so audit rows never carry a stale reason
  (PL-012 follow-up 2).
- **Separation.** No other module may contain SQL that touches `runs`, `run_records`, `committed_keys`, or `jobs`.
  Add a test that greps for it.

### 2. Migration `0003_run_orchestration.sql`
- **Fresh destination check** (PL-012 follow-up 1). In the guard's re-queue path, require
  `destination_checked_at >= now() - interval '5 minutes'` and `<= now()`, so a check can't be backdated.
- **`approval_requests` table**: `id`, `tenant_id`, `run_id`, `run_record_id`, `step_id`, `kind` (`approval_kind`),
  `shown jsonb`, `created_at`, `resolved_by_approval_id` (nullable, references `approvals`). The only update allowed
  is setting `resolved_by_approval_id` once; the trigger rejects anything else. Deletes and TRUNCATE are rejected.
- Add `approvals.request_id` (nullable, references `approval_requests`), so a decision points at the exact request
  and values it approved.

### 3. `services/runner`: the orchestrator

**Template rendering** (`templates.py`):
- Render `{{row.<column>}}` and `{{<variable>}}` with the filters `lower`, `upper`, `trim`.
- An unknown filter, a missing column, or a missing variable is an error. It is never an empty string.

**Run creation** (called by the API):
- Validate the recipe against the schema and against the supported step set:
  `navigate`, `fill`, `select`, `click`, `wait_for`, `assert` (executor); `branch`, `end_record`, `approval_gate`
  (runner).
- Refuse any other action at creation. Fail closed, as the PL-010 executor does.
- Copy `destination_key` from the workflow.
- Create one `run_records` row per `input_records` row with `status = 'ready'`, with the `record_key` and
  `idempotency_key` rendered from the pinned recipe. Excluded and `needs_review` rows never become ledger rows.
- Rendering failures refuse the run, listing each failing row. They are not skipped silently.

**Worker loop** (`python -m services.runner --worker-id <id>`):
- Claim a queued run, or take over one whose heartbeat is stale.
- After a takeover, run recovery: reconcile every commit-window record **before** claiming any `pending` one.
- Before the first claim, skip already-committed keys.
- Heartbeat on a timer.
- Pause and cancel are read from `runs.status` between steps.
- Cancel never abandons a commit-window record: it reconciles it, then stops.

**Record processing:**
1. **Prechecks.** Apply `meta.input_schema.rules`. `skip`/`park`/`fail` map to the matching transitions, each with
   its reason.
2. **Steps in order.**
   - Runner steps (`branch`, `end_record`, `approval_gate`) are evaluated by the runner.
   - Executor steps are sent as commands. Each command carries `command_id`, `run_id`, `run_record_id`, `lease_epoch`,
     the step with values already rendered, `commit`, and `expires_at`.
   - `branch.when` and `wait_for`/`assert` conditions are executor checks.
   - `end_record` may end `verified`, `skipped`, or `parked`, never `failed` (D-017).
3. **Commit step.**
   - Write `submitting` (commit transaction) → send the command.
   - On the executor's dispatch acknowledgement → `submitted_unverified`.
   - When `assert_after` passes → verify transaction.
   - Assertion timeout, lost executor, or any result short of proof → `reconciling`.
   - `failed` only when the executor reports a positive rejection. The attended executor cannot do that yet, so in
     this ticket a commit that doesn't verify always goes to `reconciling`.
   - Zero rows from the `committed_keys` insert → pause the run with `duplicate_detected`.
4. **Approvals.**
   - Apply `meta.approval_policy`: `first_record` gates the first commit of **every** run, including batches
     started without a preview. `every_record`, `first_n`, and `none` behave as named. Preview mode always gates.
   - At a gate, write an `approval_requests` row with the exact values about to be submitted, leave the record in
     `filling`, and pause the run with `awaiting_approval`. An approved decision resumes it. A rejected one parks the
     record with the reviewer's reason.
5. **Canary.** The first record of a run that reaches a commit step is the canary. If it does not end `verified`
   because of a locator, assertion, or reconcile failure, pause the run with `canary_failed` before any other
   record is claimed.
6. **Non-commit failures** use the step's `on_failure` (`park` by default). An unresolvable or ambiguous locator
   parks the record.

**Reconcile** (`reconcile.py`):
- Behind a `Reconciler` interface, because the recipe schema has no reconcile definition yet (see the open decision
  below).
- Outcomes: exactly one match → `verified` plus `committed_keys`; none → `pending` (the next claim uses an attempt);
  several, or an error → `parked`.

**Executor interface** (`executor.py`):
- A Python `Protocol` covering perform a step, check a condition, and the dispatch-acknowledgement callback.
- `FakeExecutor` and `FakeDestination` in `services/runner/testing.py`:
  - **Scriptable.** Create, duplicate, slow save, validation rejection, and locator failure can each be scripted.
  - **Crash hooks.** Optional crash hooks fire at each write-ahead point.
  - **Production builds** never import the testing module.

### 4. Runs API (`services/api/runs.py`, `approvals.py`)
- `POST /api/v1/runs` (`workflow_id`, `recipe_version_id`, `input_batch_id`, `mode`): creates the run (queued) or
  returns 422 with every problem.
- `GET /api/v1/runs/{id}`: status, pause reason, counts (`run_summary`), and any open approval request with its
  values.
- `GET /api/v1/runs/{id}/records`: per-record state, reason, attempts, `commit_attempted`.
- `GET /api/v1/runs/{id}/transitions?after=<id>`: the audit feed the dashboard polls, until streaming arrives in PL-014.
- `POST /api/v1/runs/{id}/pause`, `/resume`, `/cancel`.
- `POST /api/v1/approvals` (`request_id`, `decision`, `decided_by`, `reason`).
- `POST /api/v1/records/{id}/requeue` (optional `destination_checked_by`): picks the correct PL-012 pattern. A
  commit-attempted record with no check goes to `reconciling`.
- `GET /api/v1/runs/{id}/results.csv`: one row per ledger record, plus the excluded input rows with their issues.

There is no authentication yet. Every query is still scoped by `tenant_id` taken from the run, workflow, or record.
Never trust a client-supplied tenant id.

## Open decision (owner, before Step 1)
**How a recipe says "check whether this record already reached the destination".** The schema has no `reconcile`
definition and no `reject_when` (provable rejection) condition.

Options:
1. A schema v1.1 change adding `meta.reconcile` (a condition plus steps) and `reject_when` on commit steps. This
   requires a decision and touches the protected schema path.
2. Reuse the recipe's own duplicate-search `branch`.

T1 recommends option 1 and will draft the proposal. PL-013 does not wait for it: it builds against the `Reconciler`
interface, and its tests use the fake.

## Acceptance criteria
- [ ] Step 0 plan committed and approved by T1 before any implementation commit.
- [ ] `packages/ledger` has a function for every pattern in `sql-patterns.md`. A test fails if ledger-table SQL
      appears anywhere else.
- [ ] Happy path: a 20-record batch on the fake destination ends with every record `verified`, `skipped`, or
      `parked` with a reason. Each verified key exists exactly once in the fake destination.
- [ ] **Kill test, deterministic.** A crash at each write-ahead point (after `submitting` commits; after dispatch;
      after the acknowledgement; after the assertion passes, before verify) × 4 repetitions. Then a new worker takes
      over and recovers. Zero duplicates in the fake destination, and every record ends in an exit state.
- [ ] Re-running the same batch as a new run creates nothing new: every key ends `skipped`, "already committed".
- [ ] Two workers racing for one run: exactly one holds it. A stale worker's state change raises `StaleLease`.
- [ ] Canary: a locator failure on the first commit pauses the run `canary_failed`, and no other record is claimed.
- [ ] Approval: under `first_record`, a batch with no preview still stops at the first commit; approval resumes it,
      rejection parks it. The approval row references its request.
- [ ] A commit whose assertion times out ends `reconciling`, never `failed`. Each reconcile outcome (one, none,
      several, error) is tested.
- [ ] Cancel during a commit-window record reconciles that record before the run stops.
- [ ] Run creation refuses an unsupported action, an unknown template filter, and a missing column. Each is tested.
- [ ] Every API endpoint is tested, including tenant scoping (one tenant's ids never reach another tenant's data).
- [ ] Migration 0003: a backdated or future `destination_checked_at` is rejected. `approval_requests` resolves once,
      and any other change is rejected.
- [ ] No fixed sleeps in `services/runner` (waits are conditions or timer events). No model SDK imported anywhere
      under `services/runner` or `packages/ledger`.
- [ ] Gates: `python -m pytest -q`, `ruff check .`, `ruff format --check .`, and `python -m db.migrate` twice.
- [ ] Report written to `internal/agent/reports/PL-013.md` with real command output.
