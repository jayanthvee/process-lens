# PL-080: set a run's pace and a site's daily limit on screen

Owner: T2 (DeepSeek) · Reviewer: T1 · Branch `pl-080` (from `main`)
Time box: 90 minutes

## Why

PL-067 built pacing (`runs.min_seconds_between_rows` / `min_seconds_between_steps`) and the
per-site daily cap (`tenants.settings.site_daily_caps`), but nothing on screen sets them. Today
they can only be changed in the database. The LinkedIn pilot needs both, set by the person
running it. The owner's rule is no manual juggling, so this belongs in the app.

## Scope

1. **Pace on the run's start screen** (`apps/web/src/pages/TaskRun.tsx`, the step where the run
   is started).
   - Add one "Pace" choice: **As fast as the site allows** (both 0, today's behaviour, the
     default), **Steady** (10 s between rows, 2 s between steps), and **Careful** (30 s between
     rows, 5 s between steps).
   - Send it with the run's create call. `POST /api/v1/runs` in `services/api/runs.py` accepts two
     optional integers, validated to 0–3600, and stores them on the run.
   - Put the three labels and their one-line explanations in `lib/words.ts`.
   - The run page shows the pace that's set, in one short line.
2. **Daily limits per site**: replace the `/settings` `ComingSoon` route with a real Settings page
   holding one section, "Daily limits per site". Each row is a site (origin) and a number of rows
   per day, with add, edit and remove.
   - Add `GET` and `PUT /api/v1/settings/site-limits`. They read and write
     `tenants.settings->'site_daily_caps'` for the signed-in person's tenant, using one `jsonb_set`
     that leaves the other settings keys alone.
   - Validate the input: an origin must be `https://host` or `http://host[:port]` with no path, and
     a limit must be a whole number from 1 to 10,000.
   - Only an admin can change the limits; everyone else sees them read-only. Use whatever role
     check the existing admin routes use.
   - Store the origin exactly as a recipe's `allowed_origins` writes it, because PL-067's count
     matches on exact text. Check how recipes write it: with or without `www.`, and with or without
     a trailing slash. Normalise both sides the same way, and test that a cap set here is the one
     the runner counts.
3. **The cap sentence links here.** PL-067's "today's limit for linkedin.com (25 rows) is reached"
   on the run page gets a "Change the limit" link to the Settings section, shown to admins only.

## Out of scope

Anything about how pacing or caps behave in the runner; PL-067 owns that. No test apps and no
e2e: other agents are using Odoo and OrangeHRM.

## Gates

- Tests first:
  - API tests for the run create with pace (valid, out of range, missing);
  - site-limits GET and PUT (admin, non-admin, invalid origin, invalid number, other settings
    keys kept);
  - a test that a limit saved through the API is the one `site_rows_submitted_today` and the
    runner's cap check use, for a recipe whose `allowed_origins` names the same site;
  - web tests for the pace choice being sent, the Settings section, and the admin-only link.
- `npm --prefix apps/web run check`, full `python -m pytest -q`, `ruff check .`,
  `ruff format --check .`.
