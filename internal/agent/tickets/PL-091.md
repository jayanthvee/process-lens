# PL-091: Read a text PDF of invoices into rows

Owner: T2 (DeepSeek) · Review: T1 · Branch `pl-091` (from `main`)

## Why

Brief use case 3 starts from invoices people receive as PDFs. Today ProcessLens reads `.csv`, `.tsv`, `.xlsx` and Word `.docx` only, so a PDF invoice has to be retyped into a spreadsheet first. This ticket reads a PDF that contains real text: one exported from accounting software, not a scan. Its rows then go through the same review screen, mapping and run as a spreadsheet's. OCR for scanned PDFs is out of scope; a scan is refused in one sentence that says so.

T1 has committed the ticket, the fixtures and the failing tests on this branch. Make them pass **without editing them**.

## Scope

1. **Dependency.** Add `pdfplumber==0.11.10` to `[project] dependencies` in `pyproject.toml` (MIT; it brings `pdfminer.six` and `pypdfium2`). No other new dependency.

2. **`packages/documents/pdf_document.py`** with `read_pdf(content: bytes) -> tuple[list[str], list[dict[str, str]]]`, the same shape `read_docx` returns. Export the following from `packages/documents/__init__.py`:
   - `read_pdf`;
   - `NotAPdf(DocumentRefused)`;
   - `NOT_A_PDF = "This file is not a PDF."`;
   - `NO_PDF_TEXT = "This PDF has no text ProcessLens can read; a scanned PDF needs OCR, which ProcessLens does not do yet."`;
   - `NO_PDF_FIELDS = "This PDF has no labelled fields or table ProcessLens can read."`.

   A scan and a text-only PDF both raise the existing `NoReadableContent`, with `NO_PDF_TEXT` or `NO_PDF_FIELDS` as the message.

3. **What a page holds.** Each page is read as lines of words, using pdfplumber's word positions. Words whose tops are within about 2 pt of each other are one line.
   - **A label line** is a line whose text contains a colon. The label is the text before the first colon (`Customer`) and the value is everything after it, trimmed (`Pinewood Preschool: Main Campus`).
   - **A table** is a header line made of two or more word groups. A group is a run of words separated by gaps smaller than about 2 space widths, so `Unit Price` is one header. The header is followed by lines whose words fall under those columns. A word belongs to the header column whose left edge it is at or right of, and left of the next column's left edge. The table ends at a label line or at a line whose words do not fall under the columns.
   - **Anything else is ignored:** a title such as `INVOICE`, or a footer sentence.

4. **What becomes a row.**
   - A page with label lines and a table gives one row per table row. Each row carries the page's label values plus that table row's cells.
   - A page with label lines but no table gives one row.
   - A page with a table but no labels gives one row per table row.
   - Pages are read in order, so one invoice per page is one row per page.
   - Columns are in the order they are first seen across the whole document.
   - Values are kept as text exactly as printed (`€1,299.00` stays `€1,299.00`); the existing `clean` step does any tidying.

5. **Refusals.** None of these may let a library error reach the person:
   - bytes that are not a PDF (they don't start with `%PDF-`, or pdfplumber cannot open them) raise `NotAPdf`;
   - a PDF with no text on any page raises `NO_PDF_TEXT`;
   - text with no label lines and no table raises `NO_PDF_FIELDS`;
   - a truncated or damaged PDF either reads what it can or raises a `DocumentRefused`.

   Encrypted PDFs: refuse with `NotAPdf`'s sentence or read them if pdfplumber can without a password. Never prompt and never guess one.

6. **API wiring.**
   - `services/api/documents.py`: `.pdf` is accepted next to `.docx`, and the suffix refusal becomes `"Only a .docx or .pdf file can be added here."`. A `.pdf` goes to `read_pdf`, a `.docx` to `read_docx`, and both then go through `clean` as today.
   - `services/api/batches.py`: `.pdf` is accepted. The suffix refusal becomes `"Only a .csv, .tsv, .xlsx, .docx or .pdf file can be added here."`. A PDF batch is stored the way a `.docx` one is (`kind` `csv`, the cleaned rows, the cleaner's notes).
   - Keep the 5 MB limit and the existing size checks.

7. **Web:** the two upload inputs accept `.pdf`:
   - `apps/web/src/pages/Spreadsheets.tsx` changes from `accept=".docx"` to `accept=".docx,.pdf"`;
   - `apps/web/src/pages/TaskRun.tsx` changes from `accept=".csv,.tsv,.xlsx"` to `accept=".csv,.tsv,.xlsx,.docx,.pdf"`.

   Update any visible wording there that lists file types. No other web changes.

## Out of scope

- OCR, scanned PDFs, and PDFs where the text is drawn as curves.
- Several PDFs in one upload (one file per invoice). For now, people combine their invoices into one PDF, one invoice per page. A later ticket covers this.
- Any change to the runner, the recipe, the compiler or the ledger.
