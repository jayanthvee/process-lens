# PL-018b: Replay and verify inside open shadow roots and same-origin frames

Owner: T2 · Reviewer: T1 · Depends on: PL-018 (merged) · Phase: C

## Description
PL-018 records forms inside open shadow roots and same-origin iframes. Its widget corpus proved that two of
the six widget types do not replay. The final e2e round left both open:

- **Shadow form.** The record parks with "could not verify the save automatically; check the destination"
  (`services/runner/reconcile.py:46`).
  - The recorder now witnesses the confirmation inside the shadow root (PL-018 `56214a9`), so the recipe's
    `assert_after` names the right text.
  - But the executor's text predicates read only `document.body.innerText`
    (`apps/extension/src/executor/assertions.ts:59` and `:64`), and that never includes text inside a
    shadow root. So the confirmation is never seen, and the commit goes to reconcile.
- **The same blindness is a safety bug for `text_absent`.** An error message rendered inside a shadow root
  reads as absent, so a `text_absent` check can **pass on a page that is showing the error**. The commit is
  then verified when it should not be. Fix both predicates together.
- **Iframe form.** The record parks with "step fill-1 targets a frame, but no frame contexts are available"
  (`apps/extension/src/executor/step-runner.ts:182`).
  - `executor/frames.ts` already tracks frame execution contexts (`Runtime.executionContextCreated`) for
    attended runs.
  - The command-mode path (`runCommandStep` in `background/service-worker.ts`) never supplies them, so every
    step with a `frame` path is refused.
  - PL-017b kept clicks inside subframes refused on purpose. This ticket lifts that, for same-origin frames
    only, through the same guarded click.

Real CRMs use both: web-component design systems (Salesforce Lightning, Shoelace) and embedded same-origin
iframes (legacy editors, admin panels).

4. **Assertions for a step in a frame.** Which document `assert_after` reads.
5. **Risks,** the tests per item, and the e2e budget.

## Requirements (after T1 approves the plan)
1. **Shadow-aware text predicates.**
   - `text_visible` and `text_absent` include text inside open shadow roots.
   - Closed shadow roots stay unreadable, as today.
   - **Tests (vitest):**
     - a confirmation inside an open shadow root satisfies `text_visible`;
     - an error inside an open shadow root makes `text_absent` false;
     - the same text inside a closed root is not seen.
2. **Frame contexts in command mode.**
   - Commands for a step with a `frame` path run in that same-origin frame's execution context.
   - A cross-origin frame, or a frame whose context cannot be found, **parks** with a clear reason and sends no
     input.
   - **Tests:**
     - a fill and a click in a same-origin frame resolve in the frame;
     - a cross-origin frame parks with zero `Input.*` calls;
     - a frame that reloaded between steps re-resolves its context.
3. **The guarded click inside a frame.**
   - Coordinates are translated by the frame's offset.
   - The hit test and the landing check run in the frame's document.
   - A press that lands elsewhere on a commit step reports `lost`, never `rejected`.
   - Tests mirror PL-017b's.
4. **The corpus goes green.**
   - The shadow-form and iframe-form corpus tests pass.
   - The coverage table reads **6 of 6**.
5. **No change for top-level pages.**
   - The lead-crm, messy and Gmail-style golden tests still pass.
   - Record the click overhead for a top-level click (the PL-017b median) and show it is unchanged.

## Out of scope
- Cross-origin frames and closed shadow roots. They stay refused, with their existing messages.
- Recorder changes. PL-018 already records both widgets. If the recording turns out to be wrong, stop and ask
  T1.
- Runner and protocol changes. If the frame path needs one, stop and ask T1.
- Payload-level verification (checking *who* a message went to). That is PL-020.
