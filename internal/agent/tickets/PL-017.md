# PL-017: Built-in recipe rules, claim order, and the chip replay gap

Owner: T2 · Reviewer: T1 · Depends on: PL-016b (merged) · Phase: C

## Description
A compiled recipe is a straight copy of the demonstration. It has no "skip if this record already exists" and no
"park if a required field is empty", so an existing lead parks where it should be skipped.

This is the first step of the recipe-building approach the owner chose: **built-in rules → AI suggestions →
questions → verification → self-healing.** The approach is recorded as decision D-019 below. This ticket builds the
deterministic layer, with no model calls. It also fixes the two defects PL-016b carried over.

## Requirements

1. **Record the decision.** Add this row to `internal/docs/DECISIONS.md`:
   - **ID:** D-019.
   - **Decision:** Recipes are built in layers. The compiler's built-in rules come first. AI suggestions (PL-018)
     fill what the rules miss, and each suggestion carries its reason. Where the rules and the AI are unsure or
     disagree, the person is asked. The person confirms every rule. Every new or changed recipe is verified by
     preview and canary before a batch (PL-019). Locator repair is proposed from parked records and approved by a
     person (PL-020). AI never runs inside a batch (D-017 stands).
   - **Reason:** Rules are free and deterministic, AI generalizes across sites, and questions capture nuance only
     the person knows. Verification makes a wrong suggestion safe, and human approval keeps every run auditable.
   - **Status:** Accepted (owner). **Date:** 2026-10-13.

2. **Claim records in row order.**
   - The claim query in `packages/ledger/records.py` orders by the input row
     (`JOIN input_records … ORDER BY input_records.row_index, run_records.id`), not by `created_at, id`. The
     `created_at` values tie, so the uuid broke the tie and the canary was effectively random.
   - Update the matching pattern in `sql-patterns.md`.
   - **Test:** a 5-row run whose records share one `created_at` is claimed in row order, 0 to 4, so row 0 is the
     canary.

3. **The messy chip-removal replay gap.**
   - **Diagnose first.** Run the messy golden test once in visible mode (`PROCESSLENS_E2E_HEADED=1`) and record, in
     the report, what the page shows at `click-3`: are the row's two chips present, and what are their ✕ accessible
     names?
   - **Then fix the real cause:**
     - If it's the recorder or compiler (for example, the chip only appears after an autocomplete pick, which was
       not recorded), fix that.
     - If the fixture behaves unlike a real site, fix the fixture and say why.
   - Remove the test's `xfail` marker in the same commit as the fix. The marker is `strict`, so the test fails if it
     passes while still marked.
   - **Test:** the messy golden test passes as written in PL-016b requirement 2.

4. **Duplicate check, from a recorded search.**
   - **Detection:** the compiler detects a search for the record key before the create step: a `fill` whose value
     is the record key's sample value, followed by a click or submit that runs it.
   - **What it proposes:** a `branch` straight after the search.
     - The `when` is: the results show the record key (`text_visible` of the rendered key, scoped to the results
       region if one was recorded).
     - If the key is shown, `end_record` `skipped`, with reason "duplicate".
     - Otherwise, continue with the create steps.
   - **In Make recipe:** a **"Skip a record if the search finds it"** checkbox, pre-ticked when a search was
     detected. Unticked, there is no branch.
   - **With no search recorded:** the checkbox is disabled, with the hint "Record a search for the key first to turn
     on the duplicate check". The compiler never invents a search.
   - **Safety:** an unanswered check parks the record and never takes either branch. R1 from PL-014 stands; do not
     change it.
   - **Tests:**
     - a compiler unit test: the branch is produced from a recording with a search, and none without one;
     - vitest: the checkbox is pre-ticked, unticking removes the branch, and it is disabled with no search.

5. **Required fields.**
   - **Recorder:** the recorder notes whether each filled field is `required` or `aria-required="true"`.
   - **In Make recipe:**
     - Each input field gets a **"Park the record if this is empty"** checkbox.
     - It is pre-ticked for required fields and for the record key.
     - Ticked fields become `input_schema` rules, so the record parks before any input with the reason
       "missing <field>".
   - **Tests:**
     - a compiler unit test: the rule is produced, and a row missing that field parks before the first fill;
     - vitest: pre-ticked for a required field and for the record key, and unticked for an optional one.

6. **The lead-crm golden test returns to 3/1/1.**
   - The recorded flow now starts with a search for the email (a miss: "No leads found"), then New lead → fill →
     Save.
   - Make recipe keeps the defaults: the duplicate check is on, and Company is marked required.
   - The 5-row batch must end with:
     - 3 `verified`;
     - `ana` (who already exists) `skipped`, with reason "duplicate";
     - the no-company row `parked`, with reason "missing company";
     - nothing `failed`;
     - each email exactly once.
   - Row 0 is a new lead, so the canary is deterministic (requirement 2).
   - Remove `settle_run`'s automatic `canary_failed` resume if this flow no longer needs it. Keep the first-record
     approval.
