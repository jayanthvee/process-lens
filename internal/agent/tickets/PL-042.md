# PL-042: A recording that saves twice — the popup says so and keeps the first entry

Owner: T2 (GLM Flash) · Reviewer: T1 · Size: **small, 1 part** · Branch `pl-042` · Worktree
`C:\Users\vasup\process-lens\.worktrees\pl-042` · **Popup only:** `apps/extension/src/popup/`

## The bug, from the owner's recording
`packages/compiler/tests/fixtures/odoo_two_saves_owner.json` is the owner's real recording, sanitized. In it:
1. The owner started a lead (`New`), picked a contact, and opened the contact's page (`Internal link`).
2. They came back and started a second lead. They typed a contact, email, phone and revenue, and clicked **Add** (seq 24).
3. Then they filled a **third** lead and clicked **Add** again (seq 33).

`recordedValues(events)` currently offers `contact, email, phone, expected_revenue, expected_revenue_2`. The `_2` column is the repeat entry, and on the dashboard it reads as "Expected revenue 2" (and "Contact 2"), which confused the owner.

## The fix
1. **Find the repeat.** A recording **saves twice** when the click chosen as the save step (`defaultCommitStepId` / `commitChoices` in `make-recipe.ts`) has the same target as a later click in the recording. Compare the steps' `targets` ladders, using the role/name rung or the first css rung.
2. **Keep only the first entry.** Every popup function that reads the events (`recordedValues`, `recordedWarnings`, `defaultRecordKeyColumn`, `parkFieldDefaults`, `searchDetected`, and the events `makeRecipeRequest` sends) uses the events **up to and including the first save click**. Everything after it is dropped.
   - Add one exported helper, `firstEntryEvents(events, commitStepId)`, and use it in each of those.
   - **Do not change the compiler or the recorder.**
3. **Say so in plain words.** `recordedWarnings` adds:
   "This recording saves twice. ProcessLens kept the first entry and ignored the repeat after it."
   The popup shows it where it shows the other warnings. No new button.
4. **Leave a single-save recording alone.** A recording that saves once is unchanged in every function. The PL-037 fixture `odoo_quick_create_owner_pick.json` must give exactly what it gives today.

## Tests first (`apps/extension/tests/popup-make-recipe.test.ts`, red before the fix)
- On the two-saves fixture:
  - `recordedValues(...).map(v => v.column)` has no `_2` column;
  - the warning is present;
  - the events sent in `makeRecipeRequest` end at the first Add.
- On `odoo_quick_create_owner_pick.json`: values and warnings are unchanged. Assert today's exact output.
- A recording whose two Adds have **different** targets is not treated as a repeat.

Load the fixtures the way the existing test does:
