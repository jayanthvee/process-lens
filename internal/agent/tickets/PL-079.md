# PL-079: updates are keyed by what they change, and a row that already matches is skipped

Owner: T2 (DeepSeek) · Reviewer: T1 · Branch `pl-079` (built on `pl-075`, which carries PL-075 and PL-077 together)
Time box: 120 minutes

## Why

PL-075 lets an in-place update compile and replay: three Odoo product prices verified. PL-077
knows when a recording is a find-then-update (`search_kind == "update"`). Two gaps remain, both
seen in the price golden:

1. **The key is wrong for updates.** The compiled `idempotency_key` is the record key alone
   (the SKU). For a create that's right: one lead per email. For an update it means "this product
   was changed once, ever", so next week's new price for the same SKU is skipped as "already
   committed in an earlier run". An update must be keyed by the record **and the values it
   writes**: `{{row.sku}}:{{row.new_price}}`. Running the same sheet twice still skips every row
   (it does today), and a new price is new work.
2. **A row whose value is already there parks.** When the page already shows the row's values,
   Odoo keeps Save hidden. The commit click can't be prepared, so the canary parks and the run
   pauses `canary_failed`. This happens whenever someone fixed a row by hand, or the sheet repeats
   a value. Nothing needs writing, so the row should end `skipped` with the reason "Already had
   these values, so nothing was changed."

## Scope

1. **Compiler** (`packages/compiler/`): when `search_kind == "update"`, `meta.idempotency_key`
   becomes the record key's template, then `:`, then every column a fill in the update writes, in
   step order (for the golden, `{{row.<sku>}}:{{row.<new_price>}}`). A create's key is unchanged,
   byte for byte. The key template must use only columns the sample row has.
2. **The "already matches" outcome.** Before the update's commit click, if every fill the update
   made left the field holding the value it already had, **and** the commit control isn't on show,
   end the record `skipped` with the reason above.
   - Do this in the recipe, with a compiled `branch` whose condition is the same `element_absent`
     on the commit control that PL-075 uses as proof. If it's absent before the click, the page
     has nothing to save.
   - Put the branch right before the commit click, only for update recipes whose commit
     assertion is PL-075's `element_absent` shape.
   - **Never** in the runner or executor as a special case: D-017, and the branch is visible in
     the recipe.
   - Check that the extension's fill doesn't itself mark the form dirty when the value is
     unchanged. If it does, Save shows, the branch won't fire, and the click saves the same value.
     That's harmless but worth knowing. Say which happens, with evidence from Odoo.
3. **The price golden** (`tests/e2e/test_odoo_product_price_golden.py`).
   - Run 1: three rows `verified`.
   - Run 2 of the same sheet (same tenant, already wired): all three `skipped` as already
     committed.
   - Run 3, one row changed to a new price and the other two the same as Odoo already has, in a
     fresh tenant so no committed keys apply: the changed row `verified`, the other two `skipped`
     by the new branch.
   - Assert the key template. The golden passes today with runs 1 and 2, so it has no `xfail`
     marker. If run 3 can't pass, add `xfail(strict=True)` around run 3 only, with the reason.
