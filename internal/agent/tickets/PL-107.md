# PL-107: A real sign-in with an emailed code, taught and run from the side panel

Owner: T2 (DeepSeek) · Branch `pl-107` (from `main` at c79c901) · Reviewer: T1

## Why

On 2026-10-26 the owner taught and ran a sign-in on a real site (email, then a six-digit code sent
by email, then one click inside) using the tester zip built from main c79c901. It never reached the
code. Everything below is what broke, read from the owner's screenshots, the hosted run records, and
T1 driving the same build against the same site in a test Chrome.

Every fix is a general rule. The site only showed us the problem; nothing may match its names,
classes, or URLs.

The failing tests are on this branch. Make them pass. Do not change what they assert. Items 8–11
have no test yet: write one per item, failing first, then the fix.

Tests:

- `apps/extension/tests/pl107-recorder.test.ts` (items 1, 2, 3, 4)
- `apps/web/tests/pl107Panel.test.tsx` (items 5, 6, 7)
- `tests/api/test_pl107_try_again_reopens.py` (item 8)

## Change

### 1. A button's name leaves out what the page hides

The site's Continue button holds two labels, `Continue` and an `aria-hidden="true"`, `opacity:0`
`Continuing` shown while it loads. The recorder named the step "Clicked ContinueContinuing".

- `apps/extension/src/shared/fingerprint.ts`, `nodeTextExcludingHelp`: skip a subtree that is
  `aria-hidden="true"`, `hidden`, or `display:none` / `visibility:hidden` (computed style when
  available). Opacity alone does not hide a name.
- The resolver must compute the name the same way: `accessibleNameOf` in
  `apps/extension/src/executor/ladder.ts`. A recipe saved with the old doubled name must still
  resolve: accept the old full-text name as a fallback match.

### 2. Every box of a split code is a code field

Boxes 2–6 were recorded as "Typed the digit 2 of 6" … "6 of 6", with their digits. A code must never
be in a recording (constitution §3.2).

- `isSplitCodeBox` only knows `maxlength="1"`. Add: a box whose label matches
  `/\bdigit \d+ of \d+\b/i`; and any input in a row of 4–8 sibling inputs (same parent within three
  levels, same `type`/`inputmode`) where one of them is a code field by any existing rule.
- An ordinary six-field form (First, Last, Email…) stays an ordinary form.

### 3. One click on a submit button is one line

A submit button outside its form (`<button form="login-form">`) records a `click` and a `submit` on
the same control. The compiler's `collapse_submits` already folds them, but the step list showed two
"Clicked …" lines, and the person deleted one by hand.

- `apps/extension/src/popup/flow.ts`, `stepLines`: a `submit` right after a `click` with the same
  first target is folded into that click's line. Removing the line removes both events.

### 4. Teaching never records the email tab

The person went to Gmail for the code while teaching. "Clicked Inbox", "Clicked <the email's
subject and text>" and "Clicked Copy code" became steps, and the last one was taken as the save.

- `apps/extension/src/shared/email-code.ts`: export `isEmailHost(url)` for Gmail, Outlook (live and
  office), Yahoo Mail. Plain google.com is not mail.
- `RecorderSession.append` drops an event whose `url` is an email host (return `null`; update the
  callers).

### 5. Start over is always there, and Start teaching starts empty

The panel had no Clear. Start teaching added to the previous steps.

- `apps/web/src/panel/PanelTeach.tsx`: a **Start over** button beside Start/Stop whenever there are
  steps and it is not recording (it sends `record:clear`).
- **Start teaching** sends `record:clear` before `record:start`.

### 6. Ask which click saves; "Nothing gets saved" is an answer

The panel always sent the last click as the commit step. Here that was "Copy code" in Gmail, which
changes nothing visible, so the compile was refused. A sign-in saves nothing at all.

- A select labelled **Which click saves your work?** under the step list: one option per recorded
  click (its line's sentence, value = step id), then **Nothing gets saved** (value `""`).
- Default: the last click, as today.
- `""` sends `commit_step_ids: []`, which compiles a read-only recipe (`filling → verified`).

### 7. A refused save says why, on the same screen

The compiler's refusals use engine words, `plainSentences` hid all of them, and the panel showed
"Could not save this as a task."

- Map the known refusals to one plain sentence each, in `apps/extension/src/popup/words.ts`:
  - no assertion could be inferred → `ProcessLens couldn't see anything change after “<click>”, so it
    can't check that click worked. Pick a different answer for “Which click saves your work?”, or
    choose “Nothing gets saved”.`
  - schema / step-name refusals already have PL-103's plain sentences; keep them.
  - anything else → `This recording can't be saved yet: <the first plain problem, or "something in
    it can't be repeated">. Start over and teach it again.`
- The popup uses the same mapping.

### 8. Try again on a finished run puts it back to work

Both runs ended `completed` with their row parked. Try again set the row `pending`; the run stayed
`completed`; the supervisor only starts `queued` runs; the row said "Waiting" forever.

- `requeue_record` (or the endpoint, same transaction): if the run is `completed`, set it `queued`
  and clear its worker/lease fields the way a fresh run has them. `running`/`paused` stay as they
  are. `cancelled`: refuse with 409 and the words "This run was stopped. Start a new run to try
  this row again."
- SQL goes in `packages/ledger` (sql-patterns.md), not in `services/api`.

### 9. The panel tells the truth about the row it tried

"Try one row" showed **Finished** for a row that was parked, with no reason and no button.

- `apps/web/src/pages/TaskRun.tsx`: the Try-one-row badge comes from the row's own state
  (`rowOutcome`), not the run's status. A parked or failed row shows its plain reason and its
  **Try again** / **Skip it** buttons right there (same `sendRecordAction` as RunDetail).
- The Runs progress card: a finished run with rows that need a person says so (PL-106 item 4 words);
  it never reads "Finished" alone.

### 10. A cookie notice in the way is answered, not reported as "something in front"

On a fresh page the site's cookie notice covered Continue. The row parked: "Couldn't click
“ContinueContinuing”: something was in front of it".

- When the click's hit-test finds a covering element, check whether it is a consent notice (a
  dialog/region/banner whose text mentions cookies/consent/privacy and that has buttons).
- Answer it the most private way it offers: Reject all / Decline / Necessary only / Only essential.
  Then retry the click once.
- If it offers only Accept/Allow (and Customize), do not accept for the person: park with
  `A cookie notice is covering the page. Answer it in the work window, then press Try again.` and
  the Show it button (PL-104) on the same row.
- Never click anything in a notice the person did not see unless it is a reject-style button.
- Test: a local page with a covering notice (one with Reject, one Accept-only). A local page is fine
  here because it locks in a fix for a bug a real site showed.

### 11. A click the site already did by itself counts as done

The site moves on once a valid email is in: the button turns into its loading state while the run
is about to click it. A busy or disabled button then fails the click.

- Before a click: if the target is `aria-busy="true"`, `disabled` or `aria-disabled="true"`, wait for
  it as today (PL-048). If, while waiting, the step's own `assert_after` becomes true, the click is
  done: record the step as passed with evidence "the page moved on by itself" and carry on.
- Only when `assert_after` is true. A step with no assertion keeps today's behaviour. Never skip a
  commit without its assertion holding (no double entry is possible: the check proves the result is
  there).

### 12. Codes are filled from email while teaching too (stretch, same branch)

The person had to fetch the code somewhere else to finish teaching. PL-102 fills a code during a
run.

- While recording, when the recorded tab reaches a code page (`codePromptInPage`), and the person has
  allowed codes from email (`processlens.codesFromEmail`), look up and type the code exactly as a run
  does. The typed code is never recorded (item 2 already guarantees that).
- The panel shows "Reading your code from Gmail…" while it looks, and the PL-102 offer if consent was
  never given.
- If it cannot find exactly one code, the panel says so and the person types it.
