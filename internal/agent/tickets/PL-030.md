# PL-030: Run ProcessLens yourself, from one command: a saved task appears on the dashboard and runs

Owner: T2 (GLM) · Reviewer: T1 · Size: medium · Depends on: PL-024, PL-027 (merged)

## Goal
The owner can do the whole loop alone, with no test harness:
1. run one command;
2. teach a task in their own Chrome and press **Save as task**;
3. see the task on the dashboard, upload a spreadsheet, **Try one row**, approve, and **Run** the rest;
4. watch the leads appear in Odoo.

Today two things stop this:
- **Save as task saves nothing.** The popup compiles the recipe and keeps it in extension storage. No route creates
  a task in the database, so the dashboard never sees it. The tests insert tasks with SQL.
- **Nothing starts the server, or a runner for each run.** Only `tests/e2e/conftest.py` does that.

## Requirements
1. **`POST /api/v1/tasks`** (`services/api/tasks.py`, new).
   - Body: `{ "name": str, "recipe": object }`.
   - The tenant and the person are the configured operator: use `require_operator_user` from
     `services/api/operator.py`, as `workspace.py` does.
   - In one transaction:
     - insert a `workflows` row: name; `destination_key` set to the host of the recipe's first
       `meta.allowed_origins` entry; `allowed_origins` from the recipe;
     - store the recipe as version 1 with the same validation and storage code `POST /api/v1/recipes` uses. Reuse
       it; do not copy it.
   - Return `{ workflow_id, recipe_version_id }`, status 201.
   - An invalid recipe gets a 422 with the same problems list `/recipes` gives.
   - The front door's JSON-only and origin rules apply unchanged. The popup's origin must already be allowed: check
     how `/recipes/compile` is allowed for the popup, and do the same.
2. **The popup saves the task** (`apps/extension/src/popup/make-recipe.ts`).
   - After a successful compile, POST the recipe to `/api/v1/tasks` on the same ProcessLens address.
   - On success, `#make-result` says "<name> is ready. Open it in ProcessLens." and links to
     `<address>/tasks/<workflow_id>`.
   - On failure, it says "Could not save the task: <plain reason>".
   - **The frozen e2e contract stays:** every id listed in `internal/agent/reports/PL-025.md`, the words
     `is ready` and `Could not`, and the session storage keys. The new link sits inside `#make-result`.
3. **`scripts/demo.py`**, one command: `python scripts/demo.py --extension-id <id>`.
   - Apply migrations (`db/migrate.py`).
   - Make sure one operator user exists (owner role) in one tenant. Store its id and a generated runner secret in
     `.data/demo.env`, which is gitignored, and reuse them on later starts.
   - Build `apps/web` if `apps/web/dist` is missing.
   - Start the API on `127.0.0.1:8000` with `PROCESSLENS_EXTENSION_ID`, `PROCESSLENS_OPERATOR_ID` and
     `PROCESSLENS_RUNNER_SECRET` set. Copy exactly how `tests/e2e/conftest.py` (`api_server`, `start_worker`) does
     it.
   - **The runner supervisor:**
     - every 2 s, check for a run in `queued`, or in `running` with no live worker, and for a connected extension
       session (`GET /api/v1/executor/session`);
     - when both exist, start `python -m services.runner --executor browser --session <id> --hub-url
       ws://127.0.0.1:8000 --runner-secret <secret>`, with the same arguments the harness uses;
     - only one worker at a time.
   - Print, in plain words:
     1. Open `chrome://extensions`, turn on Developer mode, and choose **Load unpacked** with
        `apps/extension/dist` (built if missing).
     2. Copy the extension's ID, and start again with `--extension-id` (when it was not given).
     3. In the popup, set the address to `http://127.0.0.1:8000` and press **Connect**.
     4. Open `http://127.0.0.1:8000`.
   - Ctrl+C stops the API and any worker cleanly.
   - Add a `demo` target to the `Makefile` that calls it.
4. **The demo spreadsheet** `fixtures/demo/odoo-inquiries.csv` is already added: 8 rows.
   - Its salespeople are the seeded ones (Priya Raman, Marcus Bell, Sofia Duarte).
   - Two rows (Elena Petrova, Omar Haddad) are leads already seeded in Odoo, and one row has no email.
   - Mention it in the printed steps.

## Tests (write them first)
- **API:**
  - `POST /api/v1/tasks` creates one workflow and one version, under the operator's tenant, and `GET
    /api/v1/tasks` lists it;
  - a recipe with no commit assertion gets a 422;
  - with no operator configured, it gets a 503.
- **Extension (vitest):** a successful compile then save shows "is ready" with a link to `/tasks/<id>`; a failed save
  shows "Could not save the task". The frozen-id test still passes.
- **The supervisor's decision as a pure function:** `(runs, session, worker_alive) -> start | wait`, unit-tested.
  No process spawning in the tests.

## Not in scope
Auth beyond the operator id; Railway; changes to the runner or the hub protocol.

## Gates
`python -m pytest -q --ignore=tests/e2e`, ruff, `npm --prefix apps/web run check` and
`npm --prefix apps/extension run check`. No e2e. **T1 runs the real demo end to end** before approving.
