# PL-105: Everything an employee does, in a Chrome side panel

Owner: T2 (DeepSeek) · Branch `pl-105` (from `main`) · Reviewer: T1

## Why

Employees should never need the website. Today they switch between a popup that closes on every
click and a website with eleven places, half of them "Coming soon". The owner: "I don't even have a
clue what half the features are doing." So everything an employee does moves into one Chrome side
panel that stays open beside the page they work in, and it shows only what an employee needs.

The cheapest path: build the web app a second time, as the extension's panel page. Same React
pages, no second UI.

## Change

1. **Manifest** (`apps/extension/manifest.json`). Add the `"sidePanel"` permission and
   `"side_panel": { "default_path": "panel/panel.html" }`. Remove `action.default_popup`. The
   service worker calls `chrome.sidePanel.setPanelBehavior({ openPanelOnActionClick: true })` on
   install and on startup, so a click on the toolbar icon opens the panel. Minimum Chrome stays 116.
   The popup goes away: `popup.html`, `popup.ts` and `popup.css` leave the build. The logic in
   `make-recipe.ts`, `flow.ts` and `words.ts` stays and is imported by the panel; its tests stay.
2. **The panel page.** `apps/web/src/panel/PanelApp.tsx` exports `PanelApp`: the routes and a narrow
   shell (360-420px), with no `Router` inside, so the tests wrap it in a `MemoryRouter` and
   `apps/web/src/panel/main.tsx` wraps it in a `MemoryRouter` too (an extension page has no server
   behind deep links). Four things only:
   - **A connection line at the top.** "Connected", or "Not connected" with a **Connect** button
     right there. It reads `/api/v1/executor/session?browser=<id>`; Connect sends the worker
     `executor:connect` with the hub address and access code.
   - **Teach.** What the popup does today: start and stop teaching (`record:start`, `record:stop`),
     the recorded steps with remove (`record:get`, `record:remove`), and **Save as task** (the same
     compile and save calls `make-recipe.ts` makes). This replaces the website's Teach page in the
     panel.
   - **Tasks.** Each task shows **Run with a spreadsheet** (a link to the existing
     `/tasks/:id/run` flow), or **Run once** for a task with no spreadsheet columns (point 5).
   - **Runs.** The existing Runs and run detail pages: live progress, and every row that needs the
     person has its fix buttons on the same row. Actions sit where the problem shows.
3. **Hidden from employees.** The panel has no Home, Needs help, Saved answers, Documents, Apps,
   Spreadsheets, Settings, Help, no "Coming soon" page and no Notes for support. The website keeps
   working at its address for us and is not deleted here, but its sidebar drops Saved answers,
   Documents, Settings and Help (all Coming soon). Their routes may stay; nothing links to them.
   Update `apps/web/tests/shell.test.tsx`, which lists those four today.
4. **No access-code page in the panel.** `apps/web/src/lib/api.ts` gains
   `configureApi({ base, headers })`. With a base, every call goes to `${base}${path}` (one slash,
   never two) and carries the headers; unconfigured, paths stay relative as today. The panel's
   `main.tsx` configures it before the first render with the hub address and
   `Authorization: Bearer <access code>`. That is the header `services/api/access.py`
   (`has_credential`, `_bearer`) already accepts from the extension; the website's `pl_access`
   cookie is never sent from an extension page. The hub address and code come from the same two
   build values the popup uses today (`__PROCESSLENS_HUB_URL__`, `__PROCESSLENS_ACCESS_CODE__`); the
   last hub the person connected to (`LAST_HUB_KEY` in `chrome.storage.local`) wins over the baked
   one. `AccessGate` is not used in the panel. Never log or print the code.
   - The browser id comes from the worker (`executor:whoami`) through `chrome.runtime.sendMessage`,
     not the `postMessage` bridge in `lib/browser.ts`. Add a setter there the panel calls, so
     `useSessionPath` and run creation read it unchanged.
   - **API change in scope.** `services/api/middleware.py` refuses a state-changing request from
     `chrome-extension://<id>` on every path but four (`EXTENSION_ORIGIN_PATHS`). The panel posts
     runs, uploads, mappings, pause, resume, cancel, requeue and dismiss from that origin. Accept
     the pinned extension origin (`origin_is_extension`) on every `/api/v1/` state-changing path.
     The credential check is unchanged, and an unset `PROCESSLENS_EXTENSION_ID` still accepts none.
5. **Run once.** Runs are created by `POST /api/v1/runs`, which requires an `input_batch_id`, and a
   batch comes only from `POST /api/v1/batches` with an uploaded file of at least one row. A task's
   keys are row templates (`{{row.<col> | lower}}`), so one constant empty row would render an empty
   key, or the same key every time and be skipped as already done. **API change in scope:**
   - `GET /api/v1/tasks` adds `inputs: string[]` to each task: the field names of the pinned recipe
     version's `input_schema`, minus `run_once_id`. Empty means no spreadsheet columns.
   - `POST /api/v1/tasks/{workflow_id}/run-once`, body `{ browser_id?: string }`, answers 201
     `{ run_id, status }` like `POST /api/v1/runs`. It refuses with 422 a task whose `inputs` is not
     empty ("This task needs a spreadsheet."). Otherwise, in one transaction, it writes a one-row
     batch whose row is `{ "run_once_id": <fresh uuid> }` and creates the run on it through
     `create_run`, with the same `require_runs_allowed` check, mode `batch`, limit 1.
   - Saving a task with no recorded inputs compiles with `record_key` `{{row.run_once_id}}` and a
     sample row `{ "run_once_id": "x" }`, so each Run once is new work and the ledger rules are
     untouched. Today such a recording cannot be saved at all (the form demands a key column).
6. **Build.** `buildExtension` (`apps/extension/scripts/release-lib.mjs`) also builds the web app's
   panel entry (`apps/web` `vite build` with a `panel.html` input and `base: "./"`) into
   `dist/panel/`, so `dist/panel/panel.html` loads its script by a relative path. The website build
   is unchanged. `validate-package.mjs` checks the panel page is in the zip.

Add: API tests for the origin change (a panel `POST /api/v1/runs` from the pinned id passes, another

## Out of scope

- Deleting the website, its access gate or its Coming soon pages.
- Saved answers, Documents, Apps, Spreadsheets, Settings, Help in the panel.
- A new design system: the panel reuses the web app's styles, narrowed.
- Any change to the ledger, the runner or the recipe schema.
