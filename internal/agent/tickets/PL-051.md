# PL-051: Ready to deploy on Railway (API, web, workers, Postgres, migrations)

Owner: T2 (GLM Flash) · Reviewer: T1 · Size: **medium, 3 parts** · Branch `pl-051` · Worktree
`C:\Users\vasup\process-lens\.worktrees\glm` · Decisions: D-021 (Railway), D-024 (SaaS-ready)

## Why
Coworkers have to use ProcessLens from their own machines by 2026-10-31. Today it runs only through
`scripts/demo.py` on the owner's laptop. That one process applies migrations, ensures an operator, builds the web
app, starts the API, and runs a supervisor that starts a worker when a run is waiting and a Chrome session is
attached. Railway needs the same thing split into long-running services and configured by environment variables.
**This ticket makes the repo deployable. It does not deploy:** the owner creates the Railway project and presses
deploy.

## The fix
1. **One image.** Add a root `Dockerfile`:
   - a multi-stage build: a Node stage builds `apps/web` (so `apps/web/dist` exists, which
     `services/api/main.py` serves at `WEB_DIST`), then a Python 3.12 slim stage installs the project from
     `pyproject.toml` (no dev extras, no Playwright, no browsers);
   - copies only what runs: `services/`, `packages/`, `db/`, `scripts/`, `apps/web/dist`;
   - a non-root user, and `PORT` honoured.

   Also a `.dockerignore` that leaves out `.venv`, `node_modules`, `.cache`, `.worktrees`, `.data`, `private/`,
   `internal/`, `tests/`, `fixtures/` and `.env*`.
2. **Two start commands, no demo script.** Move the reusable parts out of `scripts/demo.py` into
   `services/deploy.py` (or a small package). `demo.py` keeps working and imports them; its tests must still pass.
   - **`python -m services.deploy api`:** apply migrations (`db.migrate`, idempotent), ensure the operator, then run
     uvicorn on `0.0.0.0:$PORT`. Nothing is built at start-up, since the image already has `dist`.
   - **`python -m services.deploy supervisor`:** the same watch loop the demo runs (start a worker for a waiting run
     when a Chrome session is attached, and stop it when that session goes). It reads the database and the API's
     address (`PROCESSLENS_API_URL`) from the environment and never binds a port.
   - Every setting comes from the environment: `DATABASE_URL`, `PROCESSLENS_EXTENSION_ID`, the runner secret,
     `PROCESSLENS_PUBLIC_URL`. A missing required one stops start-up with one plain line naming it. No defaults
     that point at localhost in deploy mode.
   - **Secrets:** the runner secret comes from `PROCESSLENS_RUNNER_SECRET` when set. Don't generate and print one in
     deploy mode.
3. **Railway config and the runbook.**
   - `railway.json` (or `railway.toml`) for the API service: builder Dockerfile, start command, healthcheck `/health`.
   - A second service, "supervisor", uses the same image with the other start command. Document it if Railway's
     config file can't declare two services.
   - `internal/docs/DEPLOY.md`: one page, numbered steps for the owner. Create the project, add Postgres, add the
     two services from this repo, set these variables (a table: name, what it is, example, required yes/no), deploy,
     open `/health`, and point the extension at the public URL. Note that WebSockets go through Railway's public
     domain with `wss://`, and check `socketBase` in the extension handles `https://` giving `wss://` (read it, and
     say in the report what you found).
