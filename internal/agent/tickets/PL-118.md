# PL-118: price updates in Odoo Sales can be taught and run honestly (PL-113 leftovers)

Owner: T2 (DeepSeek) · Branch `pl-118` (from `main` at a8cc554) · Reviewer: T1

## Why

Owner's use case #4: change product prices in Odoo Sales from a spreadsheet (Product, New Price).
Odoo saves a form by itself when you leave it, so there is no Save click. On 2026-10-26 the task
picked the Sales tab as "the save" and reported Done without the price changing. PL-113 fixed the
junk fills, the update key, and refused a tab as the save. These parts weren't built (see
`internal/agent/reports/PL-113.md`, "Not done"), so the use case is still blocked.

## Change

1. **Infer a read-back for an edit.** When a recording changes a field on an existing item (a
   find, then fills), the commit's `assert_after` is a `value_equals` read-back of each changed
   field against the row's value (e.g. Sales Price shows 799), read after the save or the leave.
   Odoo formats numbers ("799.00", "$ 799.00"), so compare numbers as numbers (strip currency,
   spaces and thousands separators; 799 = 799.00), and compare text trimmed and
   case-insensitive. The compiler refuses as a commit assertion a check that would already hold
   before the step (a tab, heading or menu label). If no read-back can be built, the compile says
   so and the row can never be Done.
2. **"The app saves by itself when I leave the page."** Add it as the third choice on the teaching
   save screen, next to the recorded clicks and "Nothing gets saved". It is offered whenever the
   recording has no Save click, and is the default when the recording ends with a field change
   followed by a navigation or the page's own save indicator. It compiles a commit that leaves the
   form the way the person did:
   - the recorded navigation, a breadcrumb click or the next item. If none was recorded, use the
     app's save shortcut only if one was recorded.
   - Then item 1's read-back runs on the item's saved view (re-open it if needed).

   It is a `click`, `fill` or `select` commit step under the existing rules: write-ahead, reconcile,
   then `verify_commit`. No new commit-capable action.
3. **Try one row shows what the page kept.** After a try, the panel shows each changed field read
   back from the page: "Sales price: now 799", or "Sales price: still 910, not saved". It never
   shows the file's value as if it were the result. The executor returns the read-back values
   through the try path. No row values go into logs or step events.
4. **Key line words for an update:** "We'll skip a row if this product already got this exact
   change." (with the key column's plain name instead of "product"). Adding tasks keep today's
   line.
5. **Teaching edits (PL-113 item 7, the rest):**
   - After Stop: **Continue teaching** adds to the same recording.
   - **Start over** clears only after "Throw away these N steps?" on the same screen, with Yes /
     Keep them. Start teaching no longer clears silently.
   - The "N steps recorded" count equals the lines shown. A hidden code step says "+1 hidden code
     step".
   - The name box starts empty or as "<site> task", never a previous recording's name.
