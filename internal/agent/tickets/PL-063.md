# PL-063: Two more use cases on real Odoo, a customer invoice and a product price update

## Why
The brief has 10 use cases, and 2 pass end to end on real Odoo: customer inquiries (CRM leads) and sales quotations.
Invoices use the same editable order-line table the quotation fixes made work. Product updates are the brief's "update
workflow" case, where the idempotency key carries the new value (`internal/docs/RECIPE_SPEC.md`). Each new golden is
one more use case the PM can see working.

## Part 1: `tests/e2e/test_odoo_invoice_golden.py`
Model it on `tests/e2e/test_odoo_quote_golden.py`: the same fixtures, reset, popup form, trace file (under
`.cache/pl063/`) and harness calls.
- **Demonstration:** Accounting (Invoicing) → Customers → Invoices → New → pick the Customer → "Add a line" →
  Product (picked from the row's autocomplete) → Quantity → Unit price → **Save**. Don't confirm or post: a draft
  invoice is the commit. Posting is a second, separate decision and stays out of scope.
- **Three replay rows:** each with a different seeded customer, product, quantity and unit price.
- **Assertions over XML-RPC** (add helpers to `tests/e2e/real_apps.py`, the way PL-046 added `orders_by_partner` and
  `order_lines`):
  - exactly one draft `account.move` of type `out_invoice` per customer;
  - with exactly one line of its product at its quantity and price;
  - every record `verified`.

## Part 2: `tests/e2e/test_odoo_product_price_golden.py`
- **Demonstration:** Sales (or Inventory) → Products → search for one product by its internal reference → open it →
  change **Sales Price** → Save.
- **The sheet:** `sku` and `new_price` columns. The record key is the sku. The test asserts the compiled recipe's
  `idempotency_key` contains both the sku and the new price; if the compiler doesn't produce that, it's a finding
  (see below).
- **Three replay rows:** three seeded products, each with a new price.
- **Assertions:** each product's `list_price` equals its row's price over XML-RPC, all rows `verified`, and a second
  run of the same sheet changes nothing (each row ends `skipped` or `verified` without a second write, whichever the
  ledger's rule gives; quote what happened in the report).
- **The search here is real.** The duplicate-search heuristic may add a branch. Say in the report whether it did, and
  whether that is right for an update.

## When something fails
Run each test at most **3 times**. If a failure is a product bug (recorder, compiler or runner), don't fix it here.
Mark that test `xfail(strict=True)` with the exact parked reason and the failing step (as PL-046 did), and write in
the report the smallest product change that would make it pass. A test-harness mistake (your own helper or
selector) is yours to fix.
