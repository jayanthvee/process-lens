# PL-041: The run setup stops being janky — say what a waiting row is waiting for, one run per click, flag a task that keeps failing

All three parts come from the owner's runs on 2026-10-17. **The owner's rule:** every action sits on the screen where the problem shows, in plain words, and never sends the person to hunt on another page.

## Part 1: a queued run says what it is waiting for
**What the owner saw.** "3. Try one row" sat on "Queued" forever. The cause was another task's paused run on the same app: the database allows one running-or-paused run per app (`runs_one_active_per_destination`, statuses `running` and `paused`). Nothing on screen said so.

1. **The API.** `RunDetail` (`services/api/runs.py`) gets `waiting_behind: {run_id, task_name, status} | null`.
   - It is set only when this run is `queued` and another run of the same tenant and `destination_key` is `running` or `paused`.
   - Add the read to `packages/ledger/reads.py` as `run_blocking(conn, run_id)`, next to the other reads. **No SQL in `services/`:** `tests/runner/test_sql_separation.py` enforces this.
   - **Tests in `tests/api/`:**
     - a queued run behind a paused run of another task names it;
     - behind a running run, likewise;
     - a queued run with nothing ahead gives `null`;
     - another tenant's run never shows.
2. **The page.** In the "3. Try one row" card (`pages/TaskRun.tsx`) and at the top of the run page (`pages/RunDetail.tsx`), when `waiting_behind` is set, show:
   "Waiting: your **{task_name}** run on this app is paused. Only one run per app can go at a time."
   - **Cancel that run** button: POST `/api/v1/runs/{id}/cancel`, then reload.
   - **Open it** link: `/runs/{id}`.
   - For a `running` blocker: "Waiting for your **{task_name}** run on this app to finish." with the Open it link only.
   - **Tests (vitest):**
     - both sentences render;
     - Cancel posts to the blocker's id;
     - nothing shows when `waiting_behind` is null;
     - `engineWordsIn` is empty.
- **Commit and push.**

## Part 2: one click, one run
**What the owner saw.** A double click on **Try it** created two preview runs. **Run the other N rows** and **Try all N again** can do the same.

- Guard each of the three with a `useRef` in-flight flag, set before the request and cleared in `finally`. `busy` state alone is too late: a second click lands before React re-renders.
- **Tests:** two synchronous clicks POST exactly once, for each of the three buttons.
- **Commit and push.**

## Part 3: a task that keeps failing says so, with the fix
**What the owner saw.** The old task "New CRM Lead" looked healthy in the task list, but every run parked its rows with the same reason ("the confirmation was already on the page before saving"). It had been recorded before a fix, and saved tasks never change.

1. **The API.** `GET /api/v1/tasks` rows get `keeps_failing: {reason} | null`.
   - It is set when the task's **two most recent finished runs** both ended with no verified row, and at least one parked or failed row each, with the same reason.
   - The read goes in `packages/ledger/reads.py`, extending `_LIST_TASKS` or as a second read that the route joins in Python.
   - **Tests:**
     - two failing runs with the same reason flag it;
     - one good run among the last two clears it;
     - different reasons don't flag;
     - a task with no runs gives `null`.
2. **The page.** On the task row in `pages/Tasks.tsx` and at the top of `pages/TaskRun.tsx`:
   "This task stopped working the last two times ({plainReason}). Record it again in the extension to fix it."
   - Use `plainReason` from `lib/words.ts`.
   - Add one **How to record it again** button, linking to `/teach`.
   - Muted warning tone, using the existing tokens. **Tests:** the sentence renders when flagged and is absent when not; `engineWordsIn` is empty.
- **Commit and push.**
