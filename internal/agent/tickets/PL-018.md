# PL-018: A recorder that captures what changed, not just the events it hears

Owner: T2 · Reviewer: T1 · Depends on: PL-017b (merged) · Phase: C

## Description
The owner recorded the same Gmail task three times (Compose → To → body → Send) on the current build, with the tab
refreshed. Each time the recorder missed two of the four actions:
- **The message body was never recorded.** Gmail's editor is a `contenteditable` that changes without the events
  the recorder listens for.
- **The recipient accepted with the keyboard (Tab or Enter on a suggestion) was recorded as the typed prefix
  "ma".** Key presses are not recorded, and the chip that appeared was never read.
- **When the suggestion was clicked instead,** the click was recorded *before* the typing that produced it, so a
  replay would click a suggestion that does not exist yet.

A replay of any of these would send a wrong or half-written email, and the final "Undo" check could still pass.

**The root cause is the recording model.** The recorder trusts specific DOM events. Real sites change values through
editors, autofill, keyboard selection, paste, IME and password managers, which fire events we will never enumerate.

This ticket changes the model to **state-diff recording**: before every recorded click, navigation, key press and
stop, snapshot every visible editable element, diff it against the previous snapshot, and record what changed. Events
become hints about intent, not the source of truth.

It is the first item of the owner's priority: **the recorder comes first, before AI.** It renumbers the D-019 tickets
accordingly.

## Step 0: plan, then stop for T1 (required)
Write `internal/agent/proposals/PL-018-plan.md` and stop. Do not write any implementation before T1 approves it. The
plan must answer each of these:
1. **The snapshot.** Exactly which elements it reads:
   - inputs, textareas and selects;
   - `contenteditable` roots, and `role=textbox` with `aria-multiline`;
   - **chip / token lists**: how a chip is recognised generically, by ARIA (`role=option`/`listitem` inside a
     labelled container, a remove button) and by structure, not by a Gmail selector;
   - Shadow DOM: open roots, which are reachable;
   - same-origin iframes.

   What it never reads: passwords and credential contexts, reusing the existing rules. And how it stays fast on
   large pages.
2. **The diff → steps.**
   - How a changed field becomes a `fill`, a changed select a `select`, and an added or removed chip a "set the
     recipients" step.
   - **Ordering:** the snapshot is flushed *before* the triggering click or press is emitted, which fixes the order
     bug.
   - How a field that changed and then changed back produces no step.
3. **The `press` action.** The schema change for keys that matter: Enter, Tab, Escape, Backspace, Delete, and
   Ctrl/Cmd+Enter.
   - It needs `targets` and `key`, it is never commit-capable on its own, and it is not recorded for keys inside a
     text field that only typed characters.
   - The executor half: `Input.dispatchKeyEvent`, through the PL-017b input gate.
   - The compiler and recipe-schema changes, with schema tests.
4. **Autocomplete / chip folding.**
   - "Typed a prefix, then a chip appeared (by click, key or paste)" compiles to one step: set that field to the
     chip's value. The chip's value is its email or text, never the display name.
   - On replay: type the row's value, then accept the suggestion whose text **contains** the row's value. If no
     single suggestion matches, park.
   - The row value becomes the record key's sample value ("mailjaitu@gmail.com", not "ma").
5. **The widget corpus.** A new fixture page set, `fixtures/sites/widget-corpus/`, with:
   - a Gmail-style compose: chip recipients with keyboard autofill, a `contenteditable` body, Send, and an "Undo"
     toast;
   - a plain `contenteditable` editor and a framework-style editor that mutates the DOM without `input` events;
   - a React-style autocomplete;
   - an open Shadow DOM form;
   - a same-origin iframe form.

   For each, the plan lists what is recorded and how it replays.
6. **What stays out:** canvas apps, cross-origin iframes and closed shadow roots. Each is listed with the message a
   person sees when recording on one.
7. **Risks,** the tests per item, and the e2e budget.

## Requirements (after T1 approves the plan)
1. **State-diff recording,** as approved. The order bug is fixed by construction.
2. **The `press` action:** schema, recorder, compiler and executor, with schema tests and vitest.
3. **Autocomplete / chip folding,** with containment matching on replay.
4. **Reset the step-id counter** when a recording starts or is cleared.
5. **Weak observations are dropped as assertions.** "Loading…", "Saving…", and spinner or progress text are not
   proposed as `assert_after`.
6. **The widget corpus,** with a selftest, and **the golden test: Gmail-style compose.**
   - Record: Compose, To via keyboard autofill, body text, Send.
   - Compile, then run 3 rows.
   - **Pass condition:** each row's message is sent exactly once, to that row's address only, with that row's body,
     and the fixture's state proves it.
   - Real Gmail is never touched.
7. **Corpus e2e:** each corpus widget records and replays one value correctly.
   - The report gives the coverage table, "N of M widget types".
   - Any widget that fails is reported with its cause, not hidden.
8. **D-019 renumbering:** update the D-019 row so the layers read "AI suggestions and summary (PL-019),
   verification (PL-020), self-healing (PL-021)".

## Out of scope
- AI or model calls, and the plain-language summary in Make recipe. That is PL-019.
- Canvas apps, cross-origin iframes, and closed shadow roots.
- Runner and protocol changes, except what the `press` executor half needs. If more seems needed, stop and ask T1.
- Real third-party sites in any automated test.
