# PL-040 report (T1): a hidden work window no longer fails rows, and "Run the rest" doesn't re-ask

**Status:** done. Both changes come from the owner's runs on 2026-10-17.

## 1. A hidden work window
**The bug.** Chrome stops drawing a background tab, or a minimized or fully covered window. A step there failed with "19 element(s)" or "no animation frame arrived". Those messages hide the real cause, and each failure spent one of the row's tries.

**The fix.**
- **Extension (`executor/visibility.ts`, `command-step.ts`, `service-worker.ts`).**
  - Before each step's guards, the session reads `document.visibilityState` through the debugger.
  - A hidden page gets its tab activated and its window focused (restored first if it is minimized), then polled for up to 2 s.
  - A page that stays hidden refuses the step with the new `window_hidden` event, and no input is sent.
  - A step that fails while the page is hidden is reported as `window_hidden` too, rather than as the target error.
- **Protocol.** `window_hidden` is now an `EventKind`.
- **Runner.** `window_hidden` is in `PAUSE_EVENTS`. The record is released to `pending` before the commit, as for `challenge`, and the run pauses with `window_hidden`.
- **Dashboard (`lib/words.ts`).**
  - `window_hidden` reads: "The ProcessLens window was hidden behind other windows, so the site stopped drawing. Press Resume and it will come to the front."
  - The reasons that used to read "Paused: Canary failed. Sort that out, then resume." now have their own sentences: `canary_failed`, `executor_disconnected`, `policy_blocked`, `duplicate_detected`, `records_not_exit` and `internal_error`.
  - "bound tab" became "the ProcessLens window".

**In the owner's Chrome:**
- One row paused with `window_hidden`, with no failure and nothing typed. After Resume it verified.
- The bring-forward didn't take on that first try, and the cause isn't known yet. The pause is what kept the row safe.

## 2. "Run the rest" doesn't ask for approval again
**The bug.** "Try one row" is a preview, and a preview always gates. "Run the other N rows" then created a batch run, and the default `first_record` policy gated its first row again: the same question twice.

**The fix (`services/runner/creation.py`, `packages/ledger/reads.py`).**
- A batch run whose recipe policy is `first_record` gets `{"commit": "none", "approved_in_preview": <run>}` when a preview of the **same batch on the same recipe version** has a verified row.
- `every_record` and `first_n` are unchanged.

## Tests
- **Extension:** `tests/window-hidden.test.ts`, 10 tests. They cover `ensureVisible`, `pageIsHidden`, the prepare and dispatch refusals with no `Input.*` sent, and the protocol. The extension check passed 459.
- **Runner:**
  - `test_a_window_hidden_event_pauses_the_run_and_releases_the_row`;
  - 4 creation tests: a verified preview waives the gate; an unverified preview doesn't; another recipe version doesn't; `every_record` still gates.

  Runner, DB, API and packages: 883 passed.
- **Web:** words tests. The web check passed 139.
- **e2e:** the new `test_hidden_work_window.py` covers the work tab twice, before the run and mid-run, and every row must save. Full suite: **23 of 23 passed** (16 min 37 s).

**Limit.** Playwright keeps every page it controls drawing, headless and headed alike. So that e2e test passes even with the check switched off: it proves the bring-forward never breaks a run, not the hidden case itself. The hidden case rests on the unit tests and the owner's Chrome. Removing Playwright's `--disable-renderer-backgrounding` family of flags didn't change this.

## Known gaps

- **A `window_hidden` release still spends one of the row's attempts,** as every event release does. That is the same gap as "disconnects burn attempts", and it needs a ledger change.
