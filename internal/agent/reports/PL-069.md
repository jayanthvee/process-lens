## 2. The golden — what happened

`tests/e2e/test_orangehrm_timesheet_golden.py`, modelled on the Odoo lead golden: same marks, its
own session fixtures, `reset.py orangehrm` before it runs, the popup's Make recipe form, and the
harness's own calls. Sheet: `fixtures/demo/orangehrm-timesheet.csv`, three rows, three different
projects, Monday to Friday in `H:MM`.

**It gets a long way.** Three runs were spent:

1. The first stopped on a wrong button selector (the grid has no "Add" — an empty week already
   offers one blank row). My harness mistake, fixed.
2. The second stopped on my own bug: I passed an already-formatted `"2:00"` through `float()`.
   Fixed.
3. The third ran the whole chain: recorded through the real extension, compiled through the popup,
   created the run, and started the replay. It then **parked the canary at the save step**:

   > the page never showed "SuccessSuccessfully Saved…" within 8 seconds; check lead-crm: if the
   > row is there, Dismiss it, otherwise Try again

   The other two rows stayed `pending`, and the run paused `canary_failed`. Nothing was written to
   OrangeHRM.

So the test is marked `xfail(strict=True)` with that exact reason, as the ticket asks for a product
finding. The worker also logged a `keepalive ping failed … keepalive ping timeout` on its websocket
at the end; it is the hub dropping an idle connection after the run had already paused, and it is
not what stopped the run.

**The product finding, and the smallest fix.** The compiler's `assert_after` synthesis walks the
observed element *and its children* and joins their text, which doubles a Vue `oxd-toast` into
`"Success"` + `"Successfully Saved…"` → **`text_visible: "SuccessSuccessfully Saved…"`**. No page
ever shows that string, so a commit recorded after such a toast can never verify — on OrangeHRM,
and on any app whose toast nests its text. The fix belongs in `packages/compiler/compiler.py` where
the commit assertion is built: take the toast's **own** text node (trimmed) once, not a
concatenation of every descendant's text. With that, the same recording's check becomes
`text_visible: "Successfully Saved…"`, which the page does show, and this golden should pass with no
other change. `strict=True` means the fix turns the xfail into an XPASS failure, which is the
signal we want.

**Caveat, stated plainly:** because the xfail is on the whole test, it would also swallow an early
infrastructure failure. The finding above is from a run that reached the commit step (15m42s); the
xfail's own last execution only proves the test collects and runs under `xfail`.

## 3. What was hard (the part that tells us what Workday will need)

- **The grid.** OrangeHRM's timesheet is a plain HTML table of `input.oxd-input--active` cells: one
  project/activity row (a type-ahead plus a dropdown) and **seven day cells per row**, Monday first.
  The demonstration fills the first five. There are no column-header names to read — unlike PL-048's
  Odoo table — so the day cells are addressed **by position in the row**, which is what a person
  does and what the recorder captured. A Workday grid that is virtualised or reordered would need
  the header-name rung instead.
- **The project is an autocomplete**, not a `<select>`: typing narrows it and the option is clicked
  (`Type for hints...` → `option`). The activity is an `oxd-select` dropdown that only fills in
  after a project is chosen. Both behaved predictably and were recorded as clicks.
- **The save check came out wrong** (`text_visible` with the text doubled) — see part 2. That is
  the one thing standing between this golden and green.
- **Timesheet semantics.** Saving is the commit; submitting for approval is separate, and the draft
  is what a person's week looks like. Deleting a timesheet has no API call; deleting its rows does.
