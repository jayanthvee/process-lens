## 1. The origin rule I found, and how both sides normalise

A recipe's `meta.allowed_origins` is compiled by `packages/compiler/compiler.py:derive_origins`,
which calls `packages/compiler/assertions.py:origin_of`:

```python
parts = urlsplit(url)
return f"{parts.scheme}://{parts.netloc}"
```

So a recipe writes **`scheme://host[:port]`**, and specifically:

- **no trailing slash** and **no path**: `https://www.linkedin.com/feed/` is recorded as
  `https://www.linkedin.com`;
- **`www.` is kept** when the site's own URL has it, and never added or removed — it is part of the
  host, not a formatting choice;
- the port is kept when the URL named one (`http://localhost:5173`);
- the scheme and host are whatever the browser reported, which is lower case; the recipe schema
  (`packages/recipe/schema/recipe.schema.json`) enforces `^https?://[^/?#]+$`.

PL-067 counts with exact text on both sides: the recipe side is
`rv.recipe->'meta'->'allowed_origins' ? origin` and the cap side is `caps.get(origin)`. So a cap
keyed by anything else counts zero rows and never pauses.

`services/api/settings.py:normalise_origin` therefore stores exactly that shape: it strips
whitespace, requires `http`/`https` and a host, lower-cases the scheme and host (the browser already
does, so this matches the recipe), drops one bare trailing slash, keeps the port and `www.`, and
**refuses** anything that is not a bare site — a path, a query, a fragment, a name and password, or
a non-numeric port. It never guesses: a wrong origin gets a 422 sentence, not a silent rewrite.

`tests/api/test_pl080_site_limits_api.py::test_the_origin_is_stored_the_way_a_recipe_writes_it`
asserts the stored key equals `origin_of("https://www.linkedin.com/feed/")` for input
`HTTPS://WWW.LinkedIn.com/`, and that a port survives. The cross-check test below proves the cap
the API stores is the cap the runner counts.

## 2. Pace (scope 1)

- `POST /api/v1/runs` accepts two optional integers, each validated `0..3600`
  (`Annotated[int, Field(ge=0, le=3600)]`); the database CHECK is the same range. Missing means
  unset, which the runner already reads as 0 — today's behaviour.
- `packages/ledger/create.py:insert_run` writes both columns; `services/runner/creation.py:create_run`
  passes them through; the API route forwards them.
- `GET /api/v1/runs/{id}` now also answers `min_seconds_between_rows` / `min_seconds_between_steps`
  (0 when unset, read through the existing `reads.run_pacing_settings`).
- `apps/web/src/pages/TaskRun.tsx`: one **Pace** radio group in step 3 ("Try one row"), the step where
  a run is started — *As fast as the site allows* (default, 0/0), *Steady* (10 s / 2 s), *Careful*

  cannot go at different speeds; the radios lock once a run exists. Nothing extra is sent for the
  default, so the request for "as fast as the site allows" is byte-for-byte what this page always
  sent (an existing test asserts that exact body and still passes).
- The three labels and their one-line explanations live in `lib/words.ts` (`PACE_CHOICES`), with
  `paceWords(rows, steps)` for the run page's one short line.

## 3. Daily limits per site (scope 2)

- **API.** `services/api/settings.py` adds `GET` and `PUT /api/v1/settings/site-limits`, both scoped
  to the signed-in operator's tenant (`require_operator_user`; a client-supplied tenant is never
  trusted). The answer is `{tenant_id, sites: [{origin, limit}] (sorted by origin), can_change}`.
- **The write.** `packages/ledger/admin.py:set_site_daily_caps` — one statement:
  `SET settings = jsonb_set(settings, '{site_daily_caps}', $caps::jsonb, true)`. `create_if_missing`
  makes the first save work on a tenant with no caps; every other settings key is untouched
  (`test_other_settings_keys_are_left_alone`). PUT replaces the whole map because the page saves one
  list: a per-row write would leave removed caps standing. Documented in
  `internal/docs/sql-patterns.md`.
- **Validation.** An origin per the rule above; a limit is a **strict** integer `1..10,000`
  (`Field(strict=True)`), so `0`, `10_001`, `3.5`, `"twenty"` and `true` are 422. Two rows that
  normalise to the same origin are 422, not a silent last-one-wins.
- **Who may change them.** Everyone reads them; a change needs an admin. The check is
  `may_change_site_limits`: a valid `PROCESSLENS_ADMIN_TOKEN` header (the shared-token check every
  existing admin route uses, refactored into a non-raising `admin_token_matches` so the same
  comparison answers `can_change` too) **or** the tenant's `owner`. The owner branch is a deliberate
  decision, explained under "Decisions". A turned-off owner is refused like anyone else.
- **The page.** `apps/web/src/pages/Settings.tsx` replaces the `/settings` `ComingSoon` route with
  one section, "Daily limits per site" (`id="daily-limits"`): a row per site (origin, rows per day),
  Add a site, Remove, and Save changes — add/edit/remove are local until Save, which sends the whole
  list in one PUT. A non-admin sees the same rows read-only with "Only an admin can change the daily
  limits."
- **The link (scope 3).** `GET /api/v1/runs/{id}` adds `site_cap.can_change` (the same predicate), so
  the run page needs no second request. When a `site_daily_cap` pause stands *and* `can_change` is
  true, the run page shows **Change the limit** → `/settings#daily-limits`; otherwise it does not.

## Decisions

1. **An owner counts as an admin for this page.** The ticket says to use the role check the existing
   admin routes use, which is the shared admin token. The web page cannot hold that token (it is
   served by the same API and carries no admin session), so a token-only rule would make the page's
   add/edit/remove unreachable and the ticket's own "why" — the pilot's operator sets both — fail.
   The owner branch mirrors ADM-001's sign-in rule ("refuses anyone whose role is not `owner`"), which
   is this product's existing definition of an admin person. The token still works, so the admin
   panel's callers are unaffected. If the reviewer prefers token-only, the change is one line in
   `may_change_site_limits` (the page then reads only).
2. **The page saves the whole list at once.** Add/edit/remove are local until Save, matching the
   API's one-`jsonb_set` write and making removal unambiguous.
