## Part 1 — the API (`GET /api/v1/apps`)

Commit `333e1c7` — `feat(api): the apps read and GET /api/v1/apps`.

- **`list_apps(conn, *, tenant_id)`** in `packages/ledger/reads.py`, with `_LIST_APPS` beside the
  other reads and a paragraph of comment saying why. It copies `_LIST_TASKS`' shape: the latest
  recipe version per workflow (so a task is named as its recipe is, with the workflow name as the
  fallback), `w.archived_at IS NULL` and the `%(tenant)s::uuid IS NULL OR …` filter.
  - `per_origin` unnests `workflows.allowed_origins`, so **one row per origin**, and a task allowed
    on two sites appears on both. Empty and null origins are dropped.
  - `tasks` is a `jsonb_agg` ordered by name, so the contract's order is the SQL's, not a second
    sort in Python.
  - `last_run` ranks every run of the origin's tasks with `row_number() … ORDER BY created_at DESC,
    id` and keeps `place = 1`, so the app shows the newest run of *any* of its tasks. Runs are
    joined on `ru.tenant_id = per_origin.tenant_id` as well, so a cross-tenant run cannot leak in.
- **`services/api/apps.py`**, mounted in `main.py` next to `home_router`, taking the same optional
  `tenant_id` query parameter as `/tasks`. `app_host` strips the scheme exactly as `_LIST_TASKS`
  does with `regexp_replace`, and `app_name` applies the ticket's rules: `odoo` in the host or port
  8069 → "Odoo", `twenty` or port 3000 → "Twenty", otherwise the host without its port. The
  response is `AppEntry` with exactly `{name, host, origin, tasks: [{id, name}], last_run_at,
  last_run_status}`, sorted by `name` with `host` as the tie-break (two Odoo hosts can share a
  name). No row contents.
- Rows are frozen dataclasses (`AppRow`, `AppTaskRow`) in `packages/ledger/models.py`, exported
  from `packages/ledger/__init__.py` — the convention every other read follows. The `id` in the
  JSON aggregate comes back as a string, so `list_apps` builds the `uuid.UUID` explicitly rather
  than relying on Pydantic coercion.

### Tests (`tests/api/test_apps_api.py`, 9 tests, red first)

The `ledger` fixture and `add_task` helper follow `tests/api/test_home_api.py`. Covered: two tasks
on one origin make one app with both tasks (and one row only); one task on two sites appears on
both; an archived task's site is left out; another tenant's site never appears; no runs gives
`last_run_at: null` and `last_run_status: null`; the newest run of either task wins (with the
timestamp compared to the run row itself, not to "some time"); the two response shapes are asserted
key-for-key; the order is by name; and `app_name` / `app_host` have their own unit test with no
database.

## Part 2 — the page (`apps/web/src/pages/Apps.tsx`)

Commit `c328064` — `feat(web): the apps page`.

- `/apps` now renders `Apps` instead of `<ComingSoon />` (`App.tsx`). `apps/web/tests/router.test.tsx`
  lost `/apps` from its `COMING_SOON` list, which is the one place that asserted the old
  placeholder, and its stub gained `/api/v1/apps`.
- **Fetch:** one `useJson<AppRow[]>("/api/v1/apps")`, as `Tasks.tsx` does, with the same
  `Array.isArray(data) ? data : null` guard so a refusal is one sentence, never a throw.
- **Chrome status:** one line above the cards — "Chrome is connected", or "Chrome isn't connected —
  open the ProcessLens extension and press Connect". While the session is not known yet the line is
  absent rather than claiming "not connected". See the deviation note below about its source.
- **One card per app:** the name with the host in `--muted` under it; "Used by" and each task's
  name as a link to `/tasks/<id>` (the workflow id the Tasks page already links with); then
  `Last run ${relativeTime(...)} · ${runStatusWords(...).label}` or "Not run yet". No new mapping:
  both words come from `lib/words.ts`.
- **Empty state:** "Apps appear here once you teach a task on one." with one quiet button,
  "Teach a task", to `/teach` — the same `.empty` primitive `tasks.css` uses.
- **Styling (`apps.css`):** only existing tokens (`--ink`, `--ink-2`, `--muted`, `--hair`), no new
  font or colour, following `tasks.css`'s placement-only style over the shared `.panel`, `.empty`
  and `.btn` primitives. Two cards side by side at most, one column under 780 px, and the host
  breaks with `overflow-wrap: anywhere` rather than widening the page.
- **Type:** `AppRow` / `AppTask` were added to `apps/web/src/types.ts`, which is where every other
  API shape lives ("if a value is not here, the API does not send it yet"). This is the one file
  the ticket did not name; the alternative was a page-local interface, which nothing else in
  `apps/web` does.

## Deviations, and two calls for T1

1. **The Chrome line's source.** The ticket says "from what `lib/workspace.ts` already gives", but
   `lib/workspace.ts` has no connection read — it carries `useWorkspaceState` (`runs_frozen`,
   `extension_*`) and `runsBlocked`. Using `extension_version != null` would have answered a
   different question ("has this extension ever reported?") and could have shown "connected" for a
   closed browser. The page therefore reads the existing `GET /api/v1/executor/session` with
   `useJson`, exactly as the sidebar's status line does. **No new route was added**, and
   `lib/workspace.ts` was not touched.
2. **"One card per app" against DESIGN.md §4's ban on card grids.** The ticket asks for cards and
   for them to stack under 780 px; DESIGN.md §4 bans "card grids". The compromise: cards that reuse
   the `.panel` surface, **at most two side by side** (§5's own limit on panels), one column on a
   phone. If T1 reads §4 strictly, changing `.app-cards` to a single column is a one-line change in
   `apps.css`.

Not verified: the page in a browser (ticket says not to), and the endpoint against a live server —
only through `TestClient` and vitest stubs.
