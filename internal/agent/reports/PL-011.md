## Summary

The API now stores, lists, and retrieves compiled recipes. `services/api/recipes.py`
adds three endpoints under `/api/v1`: `POST /recipes` validates a recipe document
against the recipe JSON Schema and stores it, `GET /recipes` lists the active
recipes, and `GET /recipes/{id}` returns one pinned version. Ingest is fail-closed:
a document that fails the schema, or a commit step without an `assert_after`, is
rejected with every problem listed and nothing is written.

**One thing the ticket assumed does not exist.** The ticket says the recipe is
persisted "to the `recipes` table". There is no `recipes` table. The schema
(`db/migrations/0001_init.sql`) models a recipe as a row in **`recipe_versions`** —
an immutable, versioned recipe under a `workflows` row, with a trigger that rejects
`UPDATE` and `DELETE`, and `internal/docs/sql-patterns.md` states the rule: "Never
`UPDATE` or `DELETE` on `recipe_versions`". Adding a separate `recipes` table would
create a second source of truth and contradict that invariant, so these endpoints
read and write `recipe_versions`. The mapping, and the question it raises for the
owner, are under "Deviations" below.

## Endpoint contract

```
POST /api/v1/recipes?workflow_id=<uuid>&change_reason=<text>
  body:  the compiled recipe document (format_version, meta, steps, ...)
  201:   the stored version: id, tenant_id, workflow_id, workflow_name, version,
         format_version, name, record_key, idempotency_key, change_reason,
         created_at, recipe
  404:   the workflow does not exist or is archived
  422:   {"message": "...", "problems": [...]} — schema or commit-assertion failure

GET /api/v1/recipes?tenant_id=<uuid>&workflow_id=<uuid>
  200:   the latest version of every non-archived workflow (summaries, no document)

GET /api/v1/recipes/{id}
  200:   one recipe version, with its pinned version number and the document
  404:   no such version
```

The tenant is derived from the workflow, so a caller names the workflow and nothing
else. `name`, `record_key`, and `idempotency_key` are extracted from the recipe's
`meta` for the response; the whole document (including `meta`) is stored in the
`recipe` jsonb column, so those fields persist with it.

## Deviations from the ticket, and why

- **No `recipes` table: the endpoints use `recipe_versions`.** This is the significant one. The ticket names a `recipes` table that the schema does not have; the schema's own model is `workflows` + immutable `recipe_versions`. Writing to a new mutable table would duplicate the recipe jsonb, add a second source of truth, and sit beside a trigger whose whole purpose is that stored recipes never change. So `POST` inserts the next `version` for the workflow, `GET` lists the latest version per non-archived workflow, and `GET /{id}` is one `recipe_versions` row. The alternative — a new migration adding `recipes` — is a schema change outside this ticket's scope and against the immutable-recipes invariant, so it was not made. **This is the first thing to confirm or redirect.**
- **The endpoint names a `workflow_id`, not a `tenant_id`.** `recipe_versions.tenant_id` and `workflow_id` are `NOT NULL`; the tenant is derivable from the workflow, so the caller supplies only `workflow_id` and a missing/archived workflow is a 404. There is no tenant middleware or auth yet, so nothing else could supply it.
- **`GET /recipes/{id}` returns a recipe *version*.** With `recipe_versions`, an id is a version, and "with version pinned" is exactly its `version` column. A "recipe id that groups versions" would be the `workflow_id`.
- **Commit-assertion checking is defence in depth.** The schema's `commit_assertion_rule` already forbids a commit without `assert_after`; the explicit walk exists because (a) the ticket asks for it and (b) the schema's `oneOf` produces a generic message ("is not valid under any of the given schemas"), whereas the walk names the offending step id and says what is missing. `test_ingest_finds_an_unasserted_commit_inside_a_branch` shows the difference.
- **The validator is reused from `packages/compiler/validation.py`.** It is the one implementation of "validate against `recipe.schema.json`", so reusing it guarantees the API and the compiler agree. It does couple `services/api` to `packages.compiler`; if the recipe package should own validation outright, that is a small move.
- **`services/api/db.py` and the `main.py` mount were added.** The endpoints need a connection helper and a router; the ticket's scope is "in `services/runner/` or `services/api/`", and a router must be mounted to be reachable.

## Open questions for the owner or T1

1. **The `recipes` table (the one real decision).** Should recipe storage be served from `recipe_versions` (what this branch does, respecting the immutable-versions invariant), or does the owner want a dedicated `recipes` table added by a new migration? If the latter, it needs a decision row first, because it would duplicate `recipe_versions` and the immutability trigger.
2. **Workflow creation.** `POST` requires an existing `workflow_id`. Should there be a `POST /workflows` (or find-or-create by name) so a recipe can be ingested without a pre-made workflow? That needs `destination_key`, which is not in the recipe.
3. **`GET /recipes` shape.** It currently returns the latest version per active workflow. If the list should return every version, or a workflow-level record, the query changes.
4. **Schema `oneOf` diagnostics.** A schema violation reports a generic message at the offending path. Would a decoder that surfaces the best branch's error be worth adding to `packages/compiler/validation.py` (and the compiler's tests)?
5. **Auth and tenancy.** Every endpoint trusts the caller. That is fine while there is no auth layer, but recipe storage is where tenancy enforcement will land.
