# PL-077 report (T2): a search that finds the record to change is not a duplicate check

**Status:** done, gates green. The quotation golden could not be run: Odoo's reset was being raced by
another process (evidence below), and the stop rule applies. Branch pushed.

## The rule, as written in the code

`detect_find_then_update` in `packages/compiler/compiler.py`, whose docstring carries the rule:

> After the step that runs the search, and before the first commit that follows it, a click
> navigates to a **record page** — a page on the same origin whose last path segment is all digits,
> different from the page the click ran on — and there is a commit after that click.
>
> Then the search finds the record the run is about to change: the duplicate check must not skip it,
> and a search that finds nothing must park the row instead. Everything else is a create: no search,
> a click to a page whose last segment is a word (`.../new`), a click that does not navigate, or a
> commit before any such click.

Decided from the recorded steps and their URLs only (`candidate.url`, `candidate.after_url`, the
action, and where the commits are) — never from an app's name, version or page text. The helper that
implements the single judgement, `_opens_a_record`, states it once: `/odoo/products/17` is a record
page, `/odoo/products/new` is a create page, and a click that leaves the URL alone is neither.

## The change

1. **`CompileResult.search_kind`** — `"update"`, `"create"`, or `None` for no search. Computed from
   the recording, not from the checkbox: with the person's rule unticked the shape is still
   reported, because the form has to word the rule it is showing either way.
2. **`_not_found_branch(value_template, key_column)`** — the mirror of `_duplicate_branch`, same
   machinery: the schema's own `element_absent` condition over the same results cell, and inside it
   one `end_record` with outcome `parked` (never `failed`, D-017) and the reason
   `No record matched {{row.<key column>}}, so there was nothing to change.` No new schema keys.
3. **Placement** — the branch goes straight after the step that runs the search, exactly where the
   skip branch went: after the results settle and before the click that opens a result. A create's
   steps are unchanged.
4. **A warning** says which rule was applied: "the search finds the record to change, so a row is
   parked when the search finds nothing".
5. **`POST /api/v1/recipes/compile`** carries `search_kind` in its answer (`services/api/compile.py`).
6. **The popup** (`make-recipe.ts`) words its checkbox from that answer:
   - create (or no answer): **"If this row is already there, skip it"** — today's words;
   - update: **"Park a row when the search finds nothing"**, still ticked.
   The sentence is set on the label beside `#make-duplicate` after a successful compile, and reset to
   the create wording whenever a fresh recording is mirrored into the form, so a stale wording can
   never describe a different recording. `SKIP_IF_THERE`, `PARK_WHEN_NOTHING_FOUND` and
   `duplicateLabelFor()` are exported so the tests and the form cannot drift.

## Tests (written first)

  nothing" — and **no** skip branch;

  commit;
