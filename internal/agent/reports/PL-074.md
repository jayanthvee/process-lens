# PL-074 — The code page is still open when the person's code arrives

Branch `pl-074`, built on `pl-068` (merged `origin/pl-068` first). Code commit `19c346f`; this
report is the second commit.

## The cause

**The runner armed the abandon guard on the `code_required` pause, and the guard retired the bound
tab to `about:blank`.**

The chain, in `services/runner/run_loop.py`:

1. The extension's guard raises `code_required` while the bound tab shows the fixture's code page;
2. `_apply_event` → `_stop_record_for_event` releases the record (`filling` → `pending`, attempt
   refunded) and pauses the run with `pause_reason = "code_required"`; `_process_record` returns
   `"paused"`;
3. back in `process_run`, `_ABANDONED_OUTCOMES` contains `"paused"`, and the record had touched the
   browser (`self._browser_touched` is set before the steps run), so `_arm_guard()` was called;
4. the extension's `armAbandonGuard` blocks every request and calls `Page.navigate about:blank` —
   the guard's designed retirement for a released record;
5. when the person's code arrived, `enter_code` evaluated on `about:blank`, found no code field,
   and answered `not_found`.

T1's probe (`not_found:probe@blank:0`) was right about the tab's state; the runner *did* arm the
guard on an event pause, because a run-level pause is reported as the record outcome `"paused"` and
`"paused"` is one of the abandoned outcomes.

## Evidence

Instrumentation (temporary, removed before the commit; the code was never logged): the service
worker wrote a session-scoped ring buffer of the bound tab's history — `bind`, every
`chrome.webNavigation.onCommitted` for the bound tab, every step/check, guard arm/disarm failable
tab id and URL, and `enter_code` with the tab's URL — read by the e2e through the popup into
`.cache/pl074/`.

**Before the fix** (run 1, failing at `assert sent.get("entered") is True`):

```
18:07:02.623  nav          .../form            (the run's navigate lands on the code page)
18:07:02.712  guard-arm    .../form            (the runner arms the guard on the same tab)
18:07:02.749  nav          about:blank         (the guard's retirement)
18:07:02.766  guard-armed  url ""              (the tab is blank)
18:07:03.073  enter-code   about:blank / ""
18:07:03.075  enter-code-answer  entered=false, reason "not_found"
```

**After the fix** (run 2, same test, `entered` passed):

```
18:08:40.130  nav          http://127.0.0.1:54189/form
18:08:40.399  enter-code   http://127.0.0.1:54189/form
18:08:40.505  enter-code-answer  entered=true, reason "submitted"
```

No `guard-arm` appears between the navigate and the code. The code page was in front of the run's
first step: the fixture serves the code page at **both** `/` and `/form` while the cookie is absent
(`fixtures/sites/code-login/server.py`, `do_GET`), so the recorded navigate to `/form` lands on it —
the fixture had no bug. There was no new `bindActiveTab` or `restoreBoundTab` between the page and
the blank; the only navigation was the guard's own `Page.navigate`.

## The fix

`services/runner/run_loop.py`:

- `PAGE_KEEPING_PAUSES = frozenset({"code_required"})` — a pause whose page the person still has to
  answer in the bound tab;
- `_keeps_the_page(conn, run)` reads the run's own `pause_reason` (the row the pause just wrote, and
  what the run page shows) — a resumed run has `pause_reason = NULL`, so a later record's outcome
  is judged on that record's own pause, not on an old one;
- the arm at the record boundary now requires `not self._keeps_the_page(conn, run)`.

Everything else arms exactly as before: a park, a failure, a cancel (`_finalise_cancel` still arms
unconditionally), a timed-out approval gate, an `internal_error`, `canary_failed`,
`records_not_exit`, `duplicate_detected`, `admin_freeze`, `login_required`, `challenge`,
`policy_blocked`, `window_hidden`, and a disconnect. The guard still retires a released record's
half-filled form in every one of those cases.

## Tests first

Added to `tests/runner/test_abandon_guard.py` (red before the fix):

- `test_a_code_prompt_pause_keeps_the_page_open` — queues `code_required` **during** the fill
  step's prepare (so the record is `filling` and the browser is touched, the real path), then
  asserts the run is `("paused", "code_required")`, the record is `pending`, and
  `"arm" not in guard_calls`. Red before the fix: `assert 'arm' not in ['arm']`.
- `test_a_login_pause_still_arms_the_guard` — the same delivery with `login_required`; asserts the
  guard is still armed, so the change is demonstrably one pause wide.

A shared `_queue_during` helper queues the event the moment the named executor call returns; an
event pushed before the run starts is consumed between records, where nothing is armed, and would
not exercise the path.

## The golden

`tests/e2e/test_code_login.py` now also **approves the task's first save** after the resume. The
compiled task carries `approval_policy: {commit: first_record}` (PL-027), and with the code finally
entered the row reached its commit gate and paused `awaiting_approval` — the golden had never got
that far. The loop polls `/api/v1/runs/{id}/approvals` and approves each open request with
`harness.operator_id()`, exactly as `Harness.settle_run` does in every other golden, then asserts
`["verified"]` and that the site received the candidate. No assertion was weakened, and the code is
still never recorded, logged or echoed: the test keeps its `CODE not in ...` checks.
