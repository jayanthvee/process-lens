# PL-101: a record key picked from a list is warned about before it skips real work

Owner: T2 (DeepSeek) · Reviewer: T1 · Branch `pl-101` (from `main`)

## Status: done — all required gates green

## The change

### Compiler (`packages/compiler/compiler.py`)

- `CompileResult.key_warning: str | None`, default `None`.
- After the steps are folded and parameterized (and after the create-option expansion), the compiler
  collects the columns that feed a list:
  - every column templated into a rung whose `role` is `option` (`role option "{{row.salesperson_2}}"`);
  - the column typed into the fill immediately before an option click (the search text that opened
    the list).
- The key column is `CompileOptions.record_key_column` when it is set, otherwise the first
  `{{row.<column>}}` in `CompileOptions.record_key`. When that column is one of the list-fed
  columns, `key_warning` is set and the same sentence is appended to `warnings`.
- The sentence uses the column label with a trailing `_<number>` removed, underscores turned into
  spaces, and the first letter capitalized (`salesperson_2` → `Salesperson`). It is exactly the
  ticket's wording:

  > Salesperson is picked from a list, so many rows can share it. ProcessLens does each key once,
  > ever: a later row with the same salesperson would be skipped. Pick a column that is different
  > on every row, like an email or a reference.

- A typed key with no option click (the safe case) leaves both `key_warning` and the extra warning
  unset.

### Compile API (`services/api/compile.py`)

`CompileResponse` now carries `key_warning: str | None = None`, filled from the compiler result. The
route still stores nothing and needs no database.

### Popup (Make recipe form)

- `apps/extension/src/popup/popup.html`: a `#make-key-warning` block sits directly above
  `#make-result`, in the popup's warning style (`panel__note--warning`), holding the compiler's
  sentence and a **Change the key** button (`#make-change-key`).
- `apps/extension/src/popup/make-recipe.ts`:
  - `compileRecording` parses `key_warning` into `CompileOutcome.keyWarning`.
  - On a compile that carries the warning, the form does not save yet: it shows the warning above
    the result and relabels the primary button **Save anyway**.
  - Pressing that button again with the same key saves anyway; this is the explicit override, so the
    warning informs rather than blocks.
  - **Change the key** hides the warning, restores **Save as task**, and focuses `#make-key`, which
    is the key picker.
  - Choosing a different key, refreshing the recording, or a successful save clears the warning.
- `apps/extension/src/popup/popup.css`: the small grid that holds the warning and its button; the
  `[hidden]` rule keeps it out of the layout when there is no warning.

## Notes and risks

- The list detection runs on the parameterized steps, so it sees the same `{{row.<column>}}`
  templates the recipe will carry. It deliberately uses the ticket's two signals only: a `role:
  option` rung and the fill immediately before an option click. Anything the recorder reports as a
  listbox option counts (`role: option` is the ARIA role for a listbox choice); a dropdown that
  reports `menuitem` is not one of these and is not judged. A native `select` and a value the page
  set itself are likewise left alone.
- **Known boundary:** when a suggestion becomes a chip, `_fold_chip_fills` drops the option click
  (and the typed prefix) before this check runs, so a key column whose only list evidence was that
  chip is not warned about. The ticket defines the two signals as the option rung and the search
  text, and the chip fold removes both, so this is a follow-up decision for T1 rather than a rule I
  invented here. Verified with a one-off chip recording: `key_warning` is `None`.
- The `record_key` fallback was verified with a one-off `compile_recording` run using
  `record_key="{{row.salesperson_2 | lower}}"`; it produces the same warning as
  `record_key_column="salesperson_2"`. A constant `record_key` has no column to judge and gets no
  warning. Those checks are not separate tests.
- The popup now needs two presses to save a task whose key is warned about (the first shows the
  warning, the second is the override). `tests/e2e/conftest.py`'s `compile_via_popup` clicks
  `#make-go` once and then waits for "is ready" or "Could not"; an e2e golden that keys on a
  customer or salesperson column (the quotation golden does) would therefore need that second
  press. The e2e suite is opt-in (`PROCESSLENS_E2E=1`) and is outside this ticket's scope, so no
  e2e file was changed; this is flagged for the owner/T1.
- No runner, schema, migration, or ledger change. Existing compiled recipes are untouched.
