## What changed

### 1. A pick is not a search

`packages/compiler/compiler.py`

- New `_is_option_pick(candidate)`: a click is a suggestion pick when any rung has role `option`,
  or any rung's `within` names a `listbox` or an `autocomplete` container.
- `_looks_like_a_search` returns `False` when the runner is an option pick, before scanning the
  field's name. The product field's placeholder, "Search a product", can no longer turn the pick
  that follows it into a duplicate-search branch.
- The same scan now skips `text_fuzzy` rungs. That rung is the recorder's placeholder fallback,
  so a "search" found only there is not durable enough on its own to switch the branch on.
- Every real search signal still branches: role `searchbox`, a `within` naming a search container,
  a button named "Search", and Enter in the search box (Odoo's search view). The PL-017 tests run
  unchanged.

Result on the PL-046 quotation fixture: `navigate, fill, click, click(save), navigate` — **no
branch**, and no "the search step is not a commit step" warning.

### 2. A generated number is not a save check

`packages/compiler/assertions.py`

- `GENERATED_REFERENCE_PATTERN`: letters and digits, at least three digits, optionally separated
  by `/` or `-`. It matches `S00001`, `INV/2026/00012`, `PO-0042` and `SO123`; it does not match
  "Quotation saved", "Summit Climbing Gym", or a value without letters.
- `looks_like_generated_reference(text)` and `observation_is_generated_reference(observation,
  sample_values)` expose the check.
- `condition_from_observation(..., sample_values=...)` drops a `text_visible` that is a generated
  reference **unless** it is one of the sample row's values (the person typed it). Other
  observation predicates are still tried.
- `infer_assertion(..., sample_values=...)` forwards the sample row's cells.

`packages/compiler/compiler.py`

- `_resolve_commit_assertion` passes `options.sample_row.values()` to the inference.
- When inference yields nothing and the observation was a generated reference,
  `compile_recording` retries `_infer_assertion_from_fills` with the observation cleared. So the
  save gets the next assertion the compiler already knows how to pick: the navigation's URL
  shape, or the new record's name appearing (`text_count_increases`). A commit is never left
  with an empty `assert_after`; if no fallback exists the existing refusal still fires.
- The warning now says where the assertion actually came from (the recorded observation vs the
  navigation) instead of claiming a rejected observation was used.

A supplied `commit_assertions` entry is still authoritative, as the compiler's own docstring
says: a person's explicit decision outranks inference. The fix targets the number the
demonstration produced, not a value a reviewer deliberately supplied.

## Residual risks

- The generated-reference rule is deliberately narrow. A confirmation whose text happens to look
  like a reference (`ISO9001`, say) is treated as generated unless it is a sample-row value. That
  is the ticket's rule and errs toward a weaker but replayable check over an impossible pin.
- A supplied `commit_assertions` value is not filtered. That keeps the existing authority order
  (a person's decision over inference); filtering it would be a separate product decision.
- No real browser replay was run here. The unit-level evidence is that the PL-046 fixture's
  recipe now has no duplicate branch and a replayable save check; T1's e2e run is the proof on
  the live app.
