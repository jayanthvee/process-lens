# PL-041 report (T2): what a waiting run waits for, one run per click, a task that keeps failing

**Status:** done. All three parts, plus the extra on the Spreadsheets page. Branch `pl-041`, four
commits, pushed. T1 runs the browser check.

## 1. A queued run says what it is waiting for

**The bug.** "3. Try one row" could sit on "Queued" forever. The cause was another task's paused run
on the same app: `runs_one_active_per_destination` allows one `running` or `paused` run per tenant
and destination. Nothing on screen said so.

**The API.**
- `packages/ledger/reads.py`: `run_blocking(conn, run_id)`, with `_RUN_BLOCKING`. It takes the
  tenant and the destination from the run's own row (never from the client), matches another run on
  the same tenant and `destination_key` that is `running` or `paused`, and answers only while this
  run is `queued`. The task's name is the recipe's own `meta.name`, with the workflow name as the
  fallback -- the same rule the runs list uses. `BlockingRunRow` is in `models.py`.
- `services/api/runs.py`: `GET /api/v1/runs/{id}` carries `waiting_behind: {run_id, task_name,
  status} | null`. No SQL in `services/`; `tests/runner/test_sql_separation.py` still passes.

**The page.** One shared `components/WaitingRun.tsx`, used by the run page's first panel (above the
progress bar) and by the "3. Try one row" card, so the two cannot drift apart.
- A paused blocker: "Waiting: your **{task_name}** run on this app is paused. Only one run per app
  can go at a time." with **Open it** and **Cancel that run** (POST `/api/v1/runs/{blocker}/cancel`,
  then reload).
- A running blocker: "Waiting for your **{task_name}** run on this app to finish." with **Open it**
  only -- a running run is not something to stop from here.
- Once the cancel is sent the blocker is still `paused` until a worker finishes stopping it, so that
  reload still reports it; the block then says "Stopping that run. This one starts when it has."
  instead of offering the button a second time.

**Tests.** `tests/api/test_run_waiting_api.py`, 5: behind a paused run of another task names it;
behind a running run likewise; nothing ahead gives `null`; a finished run is never shown as waiting;
another tenant's paused run on the same app never shows. `apps/web/tests/waitingRun.test.tsx`, 5:
both sentences, the cancel posting to the blocker's id and reloading, nothing when `waiting_behind`
is `null`, the same in the card that started the row, and no engine word.

## 2. One click, one run

**The bug.** A double click on **Try it** created two preview runs; **Run the other N rows** and
**Try all N again** could do the same. `busy` state is set, but it only reaches the button after
React re-renders, and the second click lands before that.

**The fix.** Each of the three carries a `useRef` in-flight flag, set before the request and cleared
in `finally`: `tryingIt` and `runningRest` in `TaskRun.tsx`, `tryingAll` in `RunDetail.tsx`.

**Tests.** `apps/web/tests/oneClickOneRun.test.tsx`, 3 -- two clicks with no render between them (the
DOM's own `click()` twice inside one `act`) send exactly one request, for each button. All three
failed with two requests before the guard and pass with one after it.

## 3. A task that keeps failing says so

**The bug.** The owner's "New CRM Lead" looked healthy in the task list while every run needed a
person for the same reason. It had been recorded before a fix, and a saved task never changes.

**The API.**
- `packages/ledger/reads.py`: `keeps_failing_tasks(conn, tenant_id=...)`, a second read (the route
  joins it in Python; `_LIST_TASKS` is untouched). It takes each task's two most recent **finished**
  runs (`status` not `queued`/`running`/`paused`), counts the rows each added and the rows that need
  a person, and flags the task when both added nothing, both have at least one such row, and the two
  share a reason. `min` picks one reason when two runs have more than one in common, so the answer
  is stable.
- `services/api/home.py`: `GET /api/v1/tasks` rows carry `keeps_failing: {reason} | null`. See
  "Decisions" for why this file and not `tasks.py`.
- A cancelled run's unreached rows become `skipped`, not `parked`/`failed`, so two cancelled runs do
  not produce the warning.

**The page.** One shared `components/KeepsFailingWarning.tsx`: "This task stopped working the last
two times ({plainReason}). Record it again in the extension to fix it." with one **How to record it
again** link to `/teach`. It sits on the task's row in `Tasks.tsx` and under the task's name at the
top of `TaskRun.tsx`. Muted warning tone: `--gold-soft` on `--gold-line`, `--ink-2` text, no new
token.

**Tests.** `tests/api/test_task_keeps_failing_api.py`, 6: two failing runs with the same reason flag
it; one good run among the last two clears it; different reasons do not flag it; a task with no runs
gives `null`; only the two most recent finished runs count; a queued run neither earns nor clears
it. `apps/web/tests/keepsFailing.test.tsx`, 4: the sentence and the link on the task row and at the
top of the run page, absent when the task is working, and no engine word in either.

## Decisions worth knowing

- **`GET /api/v1/tasks` lives in `services/api/home.py`**, not in `services/api/tasks.py` (which is
  the `POST` route only). The ticket's file list named `tasks.py`; the route's owner is `home.py`,
  so the field was added there. `TaskEntry` is shared with `/home`, whose keys are frozen by
  `tests/api/test_home_api.py`, so `/tasks` answers with a `TaskListEntry` subclass that adds
  `keeps_failing`. The Home glance is unchanged.
- **The aside in the warning sentence has no closing full stop.** `plainReason` always ends with
  one, and the template puts the value in parentheses, so keeping it verbatim would read
  "...saving.). Record it again...". The component strips that one character.
- **`waiting_behind` is a read, not a lock.** It says what the database says now; a run that becomes
  free is not pushed to the page, which finds out on its next poll.
- **Cancel requests a stop; it does not stop the run itself.** That is the existing API contract,
  and the block says so rather than pretending the wait is over.

## Known gaps

- **`keeps_failing` reads the reason from the rows, so two runs that failed for the same reason in
  different words do not flag.** The reasons are the runner's own sentences, which are stable for
  the same failure, so this is deliberate rather than an oversight -- but it means a task whose
  failure message changed between runs stays unflagged.
- **A task flagged on the Tasks page, whose newest run has since worked, clears on the next
  request** -- there is no acknowledgement state, and nothing on screen says "this was flagged
  before".
- **The Cancel that run button speaks for a paused blocker only.** A queued run behind a *running*
  one has no action but to wait, which is what the API allows.
