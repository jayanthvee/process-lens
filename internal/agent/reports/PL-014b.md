## Adversarial review, and the one defect it found

Before hand-off an independent reviewer (read-only, its own sub-agent) was asked to refute the branch.
It upheld every requirement but one, and it was right about that one:

**Requirement 2 defect (found, fixed here).** The claimed-session rule was implemented only as a
*renewal* in `_retire` (when both peers have already gone), while the clock was still read on every
attach. So a claimed session whose runner was **still attached** kept its creation-time `expires_at`,
and `_match_token` refused the extension's re-attach with 4401 after ten minutes — exactly the
long-run case requirement 2 exists to allow, and the session was simultaneously unpurgeable because a
socket held it. The old `test_a_claimed_session_expires_only_after_the_last_peer_leaves` had encoded
that reading (it asserted the stale clock was kept).

Fix: `services/api/hub.py` now has `_is_expired(session, now)`, which answers "live" for a claimed
session while either peer is attached, and reads the clock only for an unclaimed session or one whose
peers have both gone. `_match_token`, the runner attach check and `_purge_expired` all go through it.
Tests: `test_a_claimed_session_with_a_peer_attached_is_not_expired` (new; the extension drops and
re-attaches with its resume token while the runner is still attached, and must be accepted), and the
existing lifetime test gained one assertion that the session is not expired while a peer is present.
Both fail with the hub reverted (`2 failed, 27 passed`) and pass with it (`29 passed`).

The reviewer's other notes, not fixed and disclosed rather than hidden: a navigate **prepare** now runs
no origin guard at all (its justification — the URL is checked in `performStep` — only applies to a
dispatch, so this is a small loosening that is harmless today because a prepare sends no input); the
transient-error regex is broader than the two strings the ticket names; the `watchCommandDebugger`
wiring in `service-worker.ts` is covered only by inspection (no test imports that module); and a
`_send_frame` that closes a peer on queue overflow can leave `attached` true. None of those changes
behaviour the ticket's requirements state.

### What the three failures are

All three are the same thing. Every fixture recipe's first step is `open-crm`, a `navigate` to
`{{crm_base}}/`. Each of these three tests leaves the bound tab on a wall or off-origin page and then
expects that **first navigate** to be refused because of the page the tab is *currently* on:

```
test_a_challenge_page_pauses_the_run_with_challenge   expected pause_reason=challenge
    got: status=paused pause_reason='canary_failed'
         records=[bo@example.test=parked(could not verify the save automatically; ...)]
test_a_login_page_pauses_the_run_with_login_required  expected pause_reason=login_required
    got: status=paused pause_reason='canary_failed'
         records=[bo@example.test=parked(could not verify the save automatically; ...)]
test_an_off_origin_page_parks_the_record               expected state=parked
    got: assert 'verified' == 'parked'
```

That is exactly the behaviour item 5 asks for. The navigate's URL is checked against `allowed_origins`
and it lands on the CRM, so the guards then run on the CRM (where there is no wall and the origin is
allowed) and the record proceeds. The three tests encode the pre-item-5 contract:
`test_off_origin_and_destructive.py` says so in its own comment — *"the recipe's first command is
guarded there"* — and `test_challenge_and_login.py`'s module docstring says *"The guards run before
every command against the page the extension is bound to, so the deterministic trigger is to leave the
bound tab on the wall page."*

Nothing is duplicated and nothing is `failed`: the two wall cases park the record (with a
save-verification reason) and the off-origin case completes correctly. The guard itself is not
loosened — a step that acts on an off-origin page, and a navigate that **lands** off-origin, are both
still refused; the unit tests in `command-prepare.test.ts` prove the landing case.

- **Item 2's `_purge_expired` is conservative**: it only removes a session with no attached peer, so a

- **Item 10 moved the step body out of `service-worker.ts` into `command-step.ts`.** That is the seam

## C1 — the previous resume token died before the extension had the new one

`services/api/hub.py`: `Session.used_token` records **the token the last completed attach presented**,
and it is committed in the same promotion block that publishes the newly issued token. `_match_token`
accepts the last-issued token, the last-used token and (only while an attach is in flight) the pending
one. At most two committed resume tokens are live — last used and last issued — and a used token a
later attach supersedes is refused 4401. On a first attach the spent session token plays the "used"
role, so a lost first `session` frame does not lock the extension out either.

Tests: `test_the_token_the_extension_holds_survives_an_unread_session_frame` (attach with A, drop
without reading the frame, re-attach with A → accepted), `test_a_superseded_used_token_is_refused`
(re-attach with B → accepted, then A → 4401), `test_a_lost_first_session_frame_keeps_the_session_token_valid`.
Negative check: with `hub.py` reverted, **4 failed** (`test_a_resume_token_is_single_use` and the three
above).

## C2 — a poll that never evaluated cleanly ended as a real "no"

`apps/extension/src/executor/assertions.ts`: `isTransientEvaluateError` is narrowed to the three real
messages ("Execution context was destroyed", "Cannot find context with specified id", "Inspected target
navigated or closed"); the bare `was destroyed` is gone. `waitForCondition` records whether the LAST
attempt before the timeout evaluated cleanly, and only then returns a real `passed: false`; when the
last attempt threw transiently the result carries `unanswered: true`.
`apps/extension/src/background/service-worker.ts`: `checkCommandCondition` turns `unanswered` into
`{ok: false, reason}`, which the session sends as `result refused` — never as an answered "no".

Tests: `a poll that only ever threw a transient error is unanswered, never a clean false`,
`transient errors followed by a clean false are a clean false`, `retries 'Inspected target navigated or
closed'`, plus the narrowed-regex cases. Negative check: part of the **7 failed** with the extension
sources reverted.

## C3 — a wall that appears after a save must pause the run with its reason

`apps/extension/src/background/service-worker.ts`: new `probeWallForCheck` runs `checkChallengeOrLogin`
on the bound tab (a `check` carries no step, so the guard gets a minimal one; a probe that throws
changes nothing). On a clean `passed: false` the answer carries the wall's `event`.
`apps/extension/src/background/command-session.ts`: the check branch sends that
`event <challenge|login_required>` **before** the `condition` reply, gated by `current()`, and sends the
`condition` reply unchanged.

Tests: `a wall under a failed check is sent as an event BEFORE the condition reply` (asserts the
event index is before the condition index, `passed` is still false), the login-wall twin,
`a clean false on a clean page sends no event`, `a check that could not be evaluated sends no wall
event, only the refusal`. Negative check: part of the **7 failed** above.

**Runner half.** `tests/runner/test_event_draining.py::test_a_challenge_during_the_commit_assertion_
parks_the_record` pins the runner side T1 asked for: the event arrives while the commit's `assert_after`
check runs, the record ends `parked` and the run pauses `challenge`. Two honest notes on it. (a) It is a
**regression guard, not a new-behaviour test**: the drain after the assert check predates this round
(`9fa625b`), so it passes with `run_loop.py` unchanged — C3's actual change is extension-side, and the
runner test proves the runner half was already right and stays covered. Reverting `run_loop.py`
entirely does not fail it, which is how that was checked. (b) A commit-window event is decided by
`_stop_record_for_event` → reconcile, so the record parks **only when the destination check cannot
answer cleanly** — the real `ParkingReconciler` always parks (which is why the e2e case parks), while a
reconciler that answers a clean zero-match would release the record to `pending`. The test encodes the
real path (`errors=("row-0001",)`) and documents the clean-miss case in its docstring rather than
bending either the test or the runner.
