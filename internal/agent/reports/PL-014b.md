every non-e2e gate is green, and the one full e2e run is reported below exactly as it showed. Branch

The three e2e failures are **all one cause, and it is item 5 working as the ticket specifies**:
item 5 moves the origin and challenge/login guards for a `navigate` from *before* the command to *after*
it lands, and three existing e2e cases are built on the old ordering (they leave the bound tab on a
wall or off-origin page and expect the recipe's **first step, a `navigate`**, to be refused for the page
the tab is leaving — which is the bug item 5 exists to fix). Those cases live in
`tests/e2e/test_challenge_and_login.py` and `tests/e2e/test_off_origin_and_destructive.py`, neither of
which is in this ticket's Scope (only `test_disconnect_mid_save.py`, for item 9). So they are reported,
not edited, and not re-run.

### What the three failures are

All three are the same thing. Every fixture recipe's first step is `open-crm`, a `navigate` to
`{{crm_base}}/`. Each of these three tests leaves the bound tab on a wall or off-origin page and then
expects that **first navigate** to be refused because of the page the tab is *currently* on:

```
test_a_challenge_page_pauses_the_run_with_challenge   expected pause_reason=challenge
    got: status=paused pause_reason='canary_failed'
         records=[bo@example.test=parked(could not verify the save automatically; ...)]
test_a_login_page_pauses_the_run_with_login_required  expected pause_reason=login_required
    got: status=paused pause_reason='canary_failed'
         records=[bo@example.test=parked(could not verify the save automatically; ...)]
test_an_off_origin_page_parks_the_record               expected state=parked
    got: assert 'verified' == 'parked'
```

That is exactly the behaviour item 5 asks for. The navigate's URL is checked against `allowed_origins`
and it lands on the CRM, so the guards then run on the CRM (where there is no wall and the origin is
allowed) and the record proceeds. The three tests encode the pre-item-5 contract:
`test_off_origin_and_destructive.py` says so in its own comment — *"the recipe's first command is
guarded there"* — and `test_challenge_and_login.py`'s module docstring says *"The guards run before
every command against the page the extension is bound to, so the deterministic trigger is to leave the
bound tab on the wall page."*

Nothing is duplicated and nothing is `failed`: the two wall cases park the record (with a
save-verification reason) and the off-origin case completes correctly. The guard itself is not
loosened — a step that acts on an off-origin page, and a navigate that **lands** off-origin, are both
still refused; the unit tests in `command-prepare.test.ts` prove the landing case.

### What T1 needs to decide

The ticket's Scope allows editing only `tests/e2e/test_disconnect_mid_save.py` in the e2e harness
("(item 9 only)"), so those three cases cannot be brought up to date here. Either:

- those two files are updated to the item-5 contract (a wall/off-origin detection that survives a
  navigate — e.g. point the recipe's first step at the wall page, or assert on the landing-page guard),
  or
- item 5 is narrowed (keep the challenge/login guard pre-command for a `navigate`, skip only the origin
  guard).

I did neither: it is a scope call, and the ticket says to report the e2e run as it showed. For the
record, the narrow variant would still leave `test_an_off_origin_page_parks_the_record` failing, since
its failure *is* the origin guard being skipped for a navigate.

## Things T1 should look at

- **Item 3's "non-loopback client" test** changes how the app is constructed in that one test
  (`TestClient(app, client=("203.0.113.10", 1))`); the loopback front door itself is unchanged.
- **Item 2's `_purge_expired` is conservative**: it only removes a session with no attached peer, so a
  session whose clock runs out while a socket is attached survives until that socket leaves. That is
  deliberate — dropping a live session would strand an attached peer — but it is a reading of
  "expired sessions are removed", not a literal one.
- **Item 5 changes when the guards run for a navigate**, which is a real behaviour change rather than a
  refactor: a navigate now runs the origin and challenge guards *after* it lands. That is the whole
  point of the requirement and it is what the unit tests pin (a navigate is not refused against an
off-origin page; a click still is; a navigate whose *landed* page is off-origin is refused after the
  navigate). Its cost is the three stale e2e cases described above, which are outside this ticket's
  Scope to update.
- **Item 6 emits no event when no command is in flight.** A detach between commands is silent; the next
  command's attach failure is what reports it. That follows item 7's "only while it is `current()`".
- **Item 10 moved the step body out of `service-worker.ts` into `command-step.ts`.** That is the seam
  the ticket asks for (so the prepare path is testable at all), not a rewrite: the service worker
  keeps the bound tab, the debugger, the error classification and the `attached` flag.
