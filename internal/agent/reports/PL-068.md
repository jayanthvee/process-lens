# PL-068: A verification-code page pauses the run, the person types the code, it carries on

Owner: T2 (DeepSeek) · Reviewer: T1 · Branch `pl-068`

## Status: **all unit and API gates green; the new e2e golden pauses correctly but its code POST is refused for a harness reason (below), so it is red**

Commit `2ceee6c`. Extension, API, hub, runner, web and the SECURITY_MODEL note all pass their
gates. The new golden `tests/e2e/test_code_login.py` is written and its fixture is in, but it does

## What changed

### 1. Detecting a code page — `apps/extension/src/executor/guards.ts`

`codePromptInPage` runs in the page, beside `challengeOrLoginInPage`. A page asks for a code when a
visible, enabled text field matches any of:

- `autocomplete="one-time-code"` (the standard hint);
- `inputmode="numeric"` with `maxlength` 4–8 **and** a label / placeholder / nearby heading saying
  code, verification or one-time;
- 4–8 single-character boxes on one row (the split layout).

A visible password field wins: the probe answers "not a code page", so `checkChallengeOrLogin`
still says `login_required`, and ProcessLens never types a password. A "Promo code" field carries
neither signal and does not trigger. The detail is the page's own heading (nearest `h1–h3`, else
the field's words, else the title); the URL is never read.

`checkChallengeOrLogin` now returns `event: "code_required"` with that heading.

Both page-side functions are evaluated through `new Function(...)`, so they cannot reference
module-level helpers: the caller embeds `codePromptInPage.toString()` inside a one-expression IIFE
before the probe. (The first e2e attempt failed precisely because of the missing binding; that is
fixed and covered indirectly by the restored guard tests.)

### 2. `enter_code` end to end

- `shared/command-protocol.ts`: `EventKind` gains `code_required` (also in `EVENT_KINDS`);
  `CommandKind` gains `enter_code`, with an `EnterCodeCommandMessage`, and `parseIncoming` refuses
  a code that is not 4–10 letters/digits. The protocol version is unchanged: both ends ship
  together, and the message carries the same `protocol` field and the same fail-closed check.
  (The ticket says "add the kind to `shared/events.ts`"; that file carries `RecordedKind` for the
  recorder, while the run-level `EventKind` lives in `command-protocol.ts`, which is where it was
  added — the recorder's own event list is untouched.)
- `background/command-session.ts`: handles `enter_code` before the step commands, reports the
  extension's own `ok` / `locator_failed` plus `observed.entered`, and never includes the code in
  the reply. The service worker wires `deps.enterCode` to `enterCodeInPage` over the bound tab's
  debugger.
- `enterCodeInPage`: fills one box with the whole code, or one digit per split box (native setter +
  `input`/`change`), then presses the page's single primary control — `button[type=submit]`, or the
  only enabled in-form button whose words are Verify / Continue / Submit / Next — else Enter in the
  last box. Its answer is `entered`/`not_found` and never carries the code.
- `services/api/runs.py`: `POST /api/v1/runs/{run_id}/code` with `{code}` matching
  `^[0-9A-Za-z]{4,10}$` (422 otherwise). 409 unless the run is `paused` with
  `reason == "code_required"`; 404 when the configured person is in another tenant; 503 when no
  extension is attached. Nothing is written.
- `services/api/hub.py`: `send_enter_code` enqueues one frame to the attached extension and awaits
  the reply, resolving it in memory (the paused run has no runner peer to relay to). Pending
  callers are keyed by command id and dropped on timeout.
- `services/runner/run_loop.py`: `PAUSE_EVENTS` gains `code_required`, so the run pauses with that
  reason and `_stop_record_for_event` releases the pre-commit record exactly as for a login wall.

### 3. The screen — `apps/web/src/pages/RunDetail.tsx`, `lib/words.ts`

When `pause_reason` is `code_required`, the progress panel shows the sentence, a labelled
`Verification code` input (`autocomplete="one-time-code"`, `inputmode="numeric"`) and **Continue**,
in the same panel as the run's outcome. While sending: "Entering the code…". On `not_found` or a
refusal: the sentence that says to type it in the work window and press Resume. The input is
cleared in `finally`, so the code is never kept in state after the send. Resume remains in the
actions row. The words live in `words.ts` (`codePromptWords`, `ENTERING_CODE`, `CODE_NOT_FOUND`)
and carry no engine vocabulary.

`WaitingRun.tsx` is unchanged: it describes a *different* run ahead of this one, and the ticket's
sentence belongs to the paused run's own page. Noted rather than edited.

## Residual risks

- **The recorder still records a code if a person types one while recording.** The invariant "never
  records the code" holds for the run (nothing stores it) but not for a demonstration that includes
  the code page. Compiling such a recording would put the code in a sample row. This needs a
  recorder exclusion, which the ticket's file list does not allow.
- **`enter_code` shares protocol version 1.** Old extensions will refuse an unknown type (they
  send `refused`), which is the fail-closed behaviour, but a version bump may be wanted when a
  released extension and a new hub must coexist.
- **Split-box layouts vary**: one row within 40 px is assumed; a two-row or widely spaced layout
  falls back to "no code page" and the run parks as before.
- **The hub sends to the most recently attached extension**, not to the one bound to that run. With
  several sessions open, a code could be typed into the wrong tab. The route checks the run's
  state, but not the session's binding.
