## 2. API

**Before.** There was no delete, hide or restore route. The only task writes were create and
run-once.

**After** (`services/api/tasks.py`, `packages/ledger/reads.py`):

- `POST /api/v1/tasks/{workflow_id}/remove` sets `removed_at` once and answers 200 with
  `{workflow_id, removed: true}`. A second remove is a no-op 200 that leaves the first stamp alone.
- `POST /api/v1/tasks/{workflow_id}/restore` clears it and answers 200 with `removed: false`;
  restoring a task that is listed is a no-op.
- An id that names no task is 404 with `task <id> does not exist`.
- A task whose run is `queued`, `running` or `paused` is refused with 409 and the detail
  `Stop its run first.` The run's own rows are the authority (`workflow_has_open_run`, a new read in
  `packages/ledger/reads.py`, so the separation rule still holds).
- Every task list skips a removed task: `_LIST_TASKS` (which serves `GET /api/v1/tasks` and Home's
  five-task glance), `_KEEPS_FAILING` and `_LIST_APPS` each gained `AND w.removed_at IS NULL`.
  Removing a task therefore also takes its "keeps failing" warning and its Apps entry with it.
- Runs are untouched: `_LIST_RUNS` never filters by workflow and already names a run by its pinned
  recipe's `meta.name` with the workflow name as the fallback, so a removed task's past runs still
  list under its name.

**Test.** `tests/api/test_pl120_remove_api.py` (8). One test removes a task and asserts, in the same
run: it is gone from `GET /api/v1/tasks` and from `GET /api/v1/home`, its workflow row still carries
its name, and its `recipe_versions`, `input_batches` and `runs` counts are unchanged; the run still
appears in `GET /api/v1/runs` with `recipe_name == "Inquiries"` and `GET /api/v1/runs/{id}` still
answers. Others cover restore, the second-remove no-op (the stamp is asserted *equal*, not merely
non-null), the three open statuses parametrised into 409 with `Stop its run first.` in the detail
and the task still listed, and 404 for both routes on an unknown id.

## 3. Panel Tasks tab and web Tasks page

**Before.** A task row offered one quiet action ("Try one row" / "Run again" / "Open" /
"Run with a spreadsheet"). There was no way to take a task off the list from either surface.

**After** (`apps/web/src/pages/Tasks.tsx`, `apps/web/src/panel/PanelTasks.tsx`, and their CSS):

- Every task row and every panel card gained **Remove**.
- Pressing it opens the question on that same row/card: `Remove "<name>" from the list? Its past
  runs stay.` with **Remove** and **Keep it**. Keep it closes the question and sends nothing.
- Remove posts to the endpoint, the row/card goes away at once, and the surface shows
  `Removed "<name>". Undo` -- a `role="status"` line above the list -- for 10 s
  (`UNDO_MS = 10_000`, a `setTimeout` cleared on unmount). Undo posts to `/restore`, the row comes
  back and the line goes.
- A refused remove (409) leaves the task on screen and shows the API's own sentence on that row or
  card. No sentence is invented on the client.
- On the panel, the row's problem line was moved below the confirm block so a 409 and the question
  are not both printed mid-card; sign-in cards are unaffected and their existing tests still pass.

**Test.** `apps/web/tests/pl120Remove.test.tsx` (6), three per surface: asks first and Keep it
neither posts nor hides; Remove posts, the card goes, `Removed "<name>"` appears, Undo posts to
`/restore`, the card returns and the line goes; and a 409 shows `Stop its run first.` with the task
still present. The 10 s expiry is not asserted -- a fake-timer test would pin the number without
pinning the behaviour, and the ticket asks for "about 10 seconds".
