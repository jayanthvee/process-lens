## Summary
The browser recorder now exists as a Manifest V3 extension in `apps/extension/`. A content script captures
clicks, typing, dropdown selections, and form submits, and describes each element with the recipe's ordered target
ladder: accessible role and name inside a named container, then `data-testid`/`data-test`, then the label, then a
stable CSS selector that skips generated class hashes, then fuzzy text. Typing is coalesced into one `fill` per
field. A password field is never read, buffered, or sent. The service worker owns the recording state
(start/stop/clear), stamps every event with its order, keeps the session history, badges the toolbar action, and can
stream events as JSON lines over a WebSocket with reconnect; the popup drives it and exports the recording as JSON.
Forty-seven tests cover the fingerprints, the capture rules, event ordering, and password omission, and every
emitted step is validated against the recipe JSON Schema. The built extension was loaded into a real Chromium
browser, recorded a live demonstration, and returned the events.

  `npm run validate` confirms every path the manifest references exists and is non-empty. It was then loaded into
  a real Chromium browser (`npm run e2e`): the service worker started and the popup rendered. Google Chrome
  (branded) ignores command-line unpacked-extension loading — a platform restriction, quoted above — so the smoke

  the same for every emitted step in a scripted session.

  password field, fires input, focusout, and change, and asserts no event is produced and the secret is absent
  from the whole payload; the live smoke asserts the same in a real browser.
- [x] **Report written to `internal/agent/reports/PL-007.md`.** This file.

## Deviations from the ticket, and why
- **Tests, tooling, and the README were added, though the ticket lists only the extension structure.** Three of the
  four acceptance criteria are verification criteria ("generates ordered semantic event objects matching recipe step
  schemas", "password inputs are strictly omitted"), which cannot be demonstrated without tests and a build. All of
  it lives under `apps/extension/`.
- **The report is a commit on `pl-007`, not `git -C internal`.** The two repositories were consolidated into one
  (`internal/` is now tracked in the root repository and `internal/.git` no longer exists), so the private-repo
  command in the ticket's Git section no longer applies; the branch is pushed as usual.
- **D-017 was recorded as a separate commit (`193e4a5`) on this branch.** Recording the owner's PL-004 decisions in
  `internal/docs/DECISIONS.md` is outside this ticket's Scope but was explicitly instructed this session; it is kept
  as its own commit so it can be moved if the owner prefers.
- **`make up`-style local services were not touched.** The extension needs no database or object storage, so the
  Postgres/MinIO stack was left alone.
- **A button that submits a form yields two events** (`click`, then `submit`), because the browser really does both.
  This is deliberate: the recorder records what happened and the compiler folds them into one step. Documented in
  the README.
- **`debugger` and `webNavigation` are declared but unused.** The ticket lists them and the executor will need
  `debugger` (decision D-006); the recorder itself does not call either. Flagged as a question below.
- **`dist/` and `node_modules/` are gitignored** (root `.gitignore`), so the package is built from source with
  `npm run build`; the loadable artifact is `apps/extension/dist`.
- **`apps/extension/.gitkeep` was removed** now that the directory holds real content.
- **Not attempted:** the executor, the compiler, and any WebSocket *server*. The recorder's stream is a client only.

## New dependencies, and why
- `esbuild` (dev) — bundles the content script as a classic script and the worker and popup as modules; content
  scripts cannot be ES modules.
- `typescript` (dev) — the language, `strict`, with `tsc --noEmit` as the type gate.
- `vitest` + `jsdom` (dev) — the test runner and a real DOM to exercise the recorder in.
- `@types/chrome`, `@types/node` (dev) — types for the extension APIs and for the Node-side scripts.
- `ajv` (dev) — validates every emitted step against the recipe JSON Schema in the conformance tests.
- No runtime dependencies: the extension ships only its own bundled code.

### The questions as they were raised

1. **CI does not run the extension.** The workflow has Python and gitleaks jobs; there is no Node job, so
   `npm run check` runs only on a developer's machine. Should a job be added (typecheck, tests, build, validate)?
   The browser smoke test needs a Chromium install, so it probably stays local or nightly.
2. **`internal/` is tracked in a public repository.** Commit 2104c3f moved the whole `internal/` tree into the
   public `process-lens` repo (the repository reports `visibility: PUBLIC`), which contradicts D-014 ("`internal/`
   private") and AGENTS.md, and means tickets, decisions, reports, and the constitution are public. This report is
   therefore public too. I did not change it — it looked like a decision to confirm or reverse.
3. **Chrome vs Chromium for the smoke test.** Edge is used because branded Chrome refuses command-line extension
   loading. Is that acceptable, or should the check be documented as manual-only for Chrome?
4. **The click-then-submit pair.** Keep both events and let the compiler merge them, or suppress the `submit` when
   its submitter was the element just clicked?
5. **Permissions.** `debugger` and `webNavigation` are declared now for the coming executor; leaving them declared
   on a recorder-only build adds an install warning. Narrow them until the executor lands, or keep them?
6. **Icons.** No icon is declared, so Chrome shows a default. A brand icon is a small follow-up if wanted.
