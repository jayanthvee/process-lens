## What works, verified on the real app

The demonstration (the ticket's requirement 1 fields) is recorded through the built extension in a
real Chromium, compiled through the popup, and the compile succeeds. The compiled recipe, dumped
from the run (`PROCESSLENS_E2E_DUMP_RECIPE=1`), is the demonstration the ticket asks for:

* `navigate` to `http://127.0.0.1:8069/odoo/crm?view_type=list`;
* `fill` the search view with `{{row.search}}` (Odoo's query box), `press` Enter;
* `branch` — "Skip a record if the search finds it" — on `element_present` with the rung
  `role=cell name={{row.search | lower}}`;
* `click` New, `fill` Name/Email/Phone, `click` the Extra Information tab, `fill` Company Name;
* `click` + `fill` the salesperson many2one autocomplete, its `option` click templated to
  `{{row.salesperson_2}}`;
* the tags many2many the same way;
* `click` Save as the commit, carrying `assert_after: {url_matches: "/odoo/crm/\\d+"}`;
* `meta.input_schema.rules`: `missing search -> park`.

On replay, the fifth row (no email) parks exactly as designed, with reason `missing search`, and
the ledger records it through `prechecked`. The other four park at `fill-1`.

## Bugs found on the real apps, and their fixes

Every one of these was invisible on the fixture sites the earlier tickets used, and each is
reproduced by a test that fails if the fix is undone.

1. **A value the page set itself was recorded as an action.** Odoo renders computed defaults into
   the lead form (Expected Revenue `0.00`, Probability `0.00`, Salesperson `Administrator`, Sales
   Team `Sales`). The state-diff recorder witnessed them and emitted a `fill` for each, so the
   recipe would type the page's own arithmetic back into fields nobody touched — and would type
   `Administrator` over the salesperson a row asked for. The envelope carried only a human sentence
   ("this field changed without any typing: the page set it").
   *Fix:* the recorder states the fact structurally (`page_set` on the event envelope), the popup's
   form no longer offers such a value as a column, and the compiler drops the step with a warning
   naming the event. `apps/extension/src/content/recorder.ts`,
   `apps/extension/src/shared/recipe-types.ts`, `apps/extension/src/popup/make-recipe.ts`,
   `packages/compiler/{model,normalize,compiler}.py`.
   *Tests:* `apps/extension/tests/recorder-snapshot.test.ts`,
   `apps/extension/tests/popup-make-recipe.test.ts`,
   `packages/compiler/tests/test_pl027_real_apps.py`.

2. **The new envelope field was silently dropped by its own allow-list.** `makeEvent` and
   `annotatedStepEvent` copy a fixed set of keys, so `page_set` was set on the way in and absent on
   the way out. Found by the unit test for fix 1, not by reading the code.
   *Fix:* both allow-lists carry it. `apps/extension/src/shared/events.ts`,
   `apps/extension/src/content/recorder.ts`.

3. **The duplicate check was tied to the ledger's record key.** Odoo's duplicate is an email while
   this workflow is keyed on the lead's name (the row with no email must still have a key). The
   popup therefore left the "check for duplicates" box unticked — `searchDetected` only looked at
   the key column — and the compiler emitted no branch, so a duplicate would have been created.
   *Fix:* both the popup and the compiler now key the check on **the column the destination was
   actually searched by**, preferring the record key when it is that column (so a workflow keyed on
   the email is unchanged). `apps/extension/src/popup/make-recipe.ts`,
   `packages/compiler/compiler.py`.
   *Tests:* `apps/extension/tests/popup-make-recipe.test.ts`,
   `packages/compiler/tests/test_pl027_real_apps.py`.

4. **A search run with Enter was not recognised as a search.** Odoo's search view has no button; the
   demonstration types the query and presses Enter. The compiler only accepted a *click* as running
   the search, so every Odoo workflow would silently lose its duplicate check.
   *Fix:* a press of Enter runs a search too, in both the popup and the compiler.
   `packages/compiler/compiler.py`, `apps/extension/src/popup/make-recipe.ts`.

5. **The duplicate branch's condition was page-wide text.** `text_visible: {{row.<key>}}` is true
   whether or not the record exists on Odoo, because the search view renders the query back onto the
   page as a facet — so the branch would have skipped *every* row of the batch, the three new leads
   included.
   *Fix:* the condition is `element_present` on a result cell (`role=cell` with the searched value's
   accessible name), which is rung 1 of the ladder and true only when the destination's own results
   table holds the value. `packages/compiler/compiler.py`.

6. **A table cell could not be named by the ladder at all.** `roleOf` had no implicit role for
   `<td>`, `<th>` or `<tr>`, so `role=cell` resolved against `generic` and a result cell could only
   be targeted by a CSS selector into someone else's markup — exactly the durability the ladder
   exists to avoid. This is what fix 5 depends on.
   *Fix:* TD→`cell`, TH→`columnheader`, TR→`row` in both the executor's ladder and the recorder's
   role map (the two sides must agree or a compiled rung can never match).
   `apps/extension/src/executor/ladder.ts`, `apps/extension/src/shared/fingerprint.ts`.
   *Tests:* `apps/extension/tests/executor-ladder.test.ts`, `apps/extension/tests/fingerprint.test.ts`.

7. **A commit's navigation assertion could not tell a save from a refusal.** `path_pattern` drops the
   last path segment, so `/odoo/crm/new` (the form the save was sent from) and `/odoo/crm/12` (the
   saved record) both collapse to `/odoo/crm/`, and the assertion was already true *before* the
   click. A refused save would have verified. The compiler's own docstring called this looseness
   out; on a real app it decides the golden.
   *Fix:* the pattern keeps the observed page's shape with digit runs generalised (`/odoo/crm/\d+`),
   and when no pattern can tell the two pages apart the compiler now says so in a warning rather
   than pretending the assertion is evidence. `packages/compiler/assertions.py`,
   `packages/compiler/compiler.py`.
   *Tests:* `packages/compiler/tests/test_assertions.py` (one expectation updated deliberately, with
   the reason in the test), `packages/compiler/tests/test_pl027_real_apps.py`.

8. **A save that moved the page produced no evidence at all.** Verified on Odoo: the save is a
   client-side route change (`performance.timeOrigin` unchanged, so the document survives), and the
   move landed after the observation window's debounce had been armed and cleared by its own cap. The
   recording's last event was the Save click with no evidence, so the compile refused with "a commit
   step must carry an assertion" — a workflow that had just worked, refused.
   *Fix (two, both in the content recorder):* the observation window reads the live URL when it
   closes, not only what the URL watch recorded; and a window that closes while it is watching a page
   it landed on reports that move. `apps/extension/src/content/recorder.ts`.
   *Tests:* `apps/extension/tests/observation.test.ts`,
   `apps/extension/tests/observation-arrival.test.ts` (two expectations updated deliberately: an
   arrival with no confirmation is no longer silence, and the URL pattern keeps the record id's
   shape).

9. **The recorder could not see how `reset.py` and a replay interact.** Not a bug in the product but
   a gap in the harness that hid one: `wait_for_observation` returned the *first* observation in the
   recording, and the click that opened the form already had one — so a test that waited before Stop
   cut the recording off before the *save's* evidence arrived, and the compile failed for a reason
   that had nothing to do with the app.
   *Fix:* `wait_for_observation_after(seq)`. Also `make_run(key_column=...)`, so a row whose email is
   empty (the one a precheck rule parks) still has an input key of its own, and the `real_apps`
   marker with a lazily-built `_clean_fixture`, so a real-app test does not start the fixture site
   and its warm-up run against the one extension session it needs.
   `tests/e2e/conftest.py`.

## What is not done

### The approval hold and the abandon guard: built, unit-tested, and stopping here

`approval_policy: first_record` no longer releases the record. The record holds the tab **at** the
commit step: `RunLoop._await_decision` waits on the injected clock for a decision, the approvals
API's `resume_run` puts the run back in `running` for the worker that already holds it, and
approving executes the commit that is prepared. The proof in the unit tests is `attempts == 1` for
every row — the database raises `attempts` only on `pending -> claimed`, so one attempt means the
record was never re-queued and re-run from step 1. No new ledger transition was needed:
`filling -> pending` is legal, but the hold simply never makes it; a timeout parks the record and
leaves the run paused on the still-open request.

The abandon guard is `apps/extension/src/executor/abandon-guard.ts`: `Fetch.enable` on the bound
tab pauses requests at the request stage, every non-GET/HEAD is answered `BlockedByClient`, and the
guard is released by the next navigate's arrival (its `disarm` reports what it refused, which the
runner writes to `step_events` as `blocked an unsaved change from leaving the page`). It is armed
when a record leaves the tab without committing and the browser was actually touched — a precheck
park never opened a page, so nothing is armed for it.

### The failing step: the extension disconnects during the guard step — UNPROVEN, T1's

Two golden runs on this step, two different traces.

**Run A (`.cache/run/g1.txt`): the guard call was never answered, and the run paused
`executor_disconnected`.**

```
AssertionError: the run never settled: status=paused pause_reason='executor_disconnected'
records=[golden no email=pending(None); golden new three=pending(None);
golden new one=verified(assertion passed);
golden bad salesperson=parked(the click target could not be resolved: the target is not clickable:
the box center is covered by <div>);
golden existing lead=pending(None); golden new two=pending(the extension disconnected from the hub)]
```

worker log (`.cache/e2e/worker-logs/e2e-worker-471ca873.log`):

```
run 567090f4-c28f-4b90-9720-b2ee4d847e86 paused on a detached event: the extension disconnected from the hub
the abandon guard arm was not answered (peer_gone)
services.runner: processed 2 run(s)
```

What that trace does show: the approval hold and the mid-form park both worked (`golden new one`
verified *before* any approval was needed for it — it is not the canary — and `golden bad
salesperson` parked with the form half filled), and the disconnect lands on the guard arm that
follows that park, which is exactly when a full `Fetch.enable` starts pausing every request the page
makes.

**Hypothesis, UNPROVEN: request flood.** With the first pattern set (`urlPattern: "*"` for every
resource type) the guard pauses — and must continue — the whole of a real page's request traffic,
including every stylesheet, image and script on the way out of a page load. The extension's one
service-worker thread would then be too busy to answer its own hub keepalive, and the socket would
be closed under it. This fits the shape of Run A (the disconnect begins at the arm, not before it)
but **nothing here proves it**: no request counts were measured, and the narrowed pattern set below
was written from that reasoning rather than validated against it. T1 should treat the flood as a
candidate, not a finding.

**Run B (`.cache/run/g2.txt`): the guard arm was refused outright, for a definite reason.**

```
AssertionError: the run never settled: status=paused pause_reason='canary_failed'
records=[golden existing lead=pending(None);
golden bad salesperson=parked(the click target could not be resolved: the target is not clickable:
the box center is covered by <div>); golden new three=pending(None); golden new two=pending(None);
golden new one=skipped(duplicate); golden no email=pending(None)]
```

worker log:

```
the abandon guard arm was refused: Fetch.enable failed: {"code":-32602,"message":"Unknown resource type in fetch filter: 'Preflight'"}
keepalive ping failed
TimeoutError: timed out while closing connection
websockets.exceptions.ConnectionClosedError: sent 1011 (internal error) keepalive ping timeout; no close frame received
```

This one is **not** the flood and is **not** unproven: `Preflight` is not a valid CDP `resourceType`
in this Chromium, so `Fetch.enable` was rejected and the guard was never armed at all (which is why
`guard()` logs rather than raising — the record was then unguarded, and the run continued on the
old behaviour). The socket keepalive timeout follows that. The definite fix is one line: drop
`Preflight` from `WRITE_RESOURCE_TYPES` in `apps/extension/src/executor/abandon-guard.ts` (the list
is `Document, XHR, Fetch, Ping, Preflight, Other`, and its unit test asserts that exact list).

Both traces share one more thing worth T1's attention: `golden bad salesperson` parked **not** where
it was designed to. It was meant to fail at the salesperson autocomplete step; it failed earlier,
at a click whose box centre was covered by a `<div>` — a transient of a live page, and the row's
park is legitimate either way (the row must not reach Odoo, and does not).

Also note: Run B ran with `PROCESSLENS_E2E_SKIP_RESET=1`, so Odoo still held the leads an earlier
passing run created; that is why `golden new one` was reported `skipped(duplicate)` there. A real
golden run resets first, and the six rows are chosen so five of them are new.

```
navigate-1  ok      rung=null  error=null
fill-1      failed  rung=null  error=the fill target could not be resolved:
                                  no rung of the target ladder resolved to exactly one element
```

…for all four records that were not parked by the precheck rule. Immediately after the run the bound
tab was at `http://127.0.0.1:8069/odoo/crm/17` — the record page the *demonstration* saved, not the
`/odoo/crm?view_type=list` the recipe navigates to — while `input.o_searchview_input` matched once
and `#name_0` not at all. So the tab kept the previous view, and `fill-1` looked for the search view
on a record form.

Root cause not established within this sitting. The next thing to test, and the reason the code
points there: `dispatchNavigate` treats a `Page.navigate` reply with **no `loaderId`** as a
same-document navigation with "no load to await" and returns success
(`apps/extension/src/executor/dispatch.ts`, the `loaderId === ""` branch). A same-document reply
leaves the previous document in place, so a step that follows runs against the wrong page and the
navigate still reports `ok`. The honest fix is for the step to verify it *arrived* — the tab's URL
must be the one asked for — and to refuse when it is not; a stronger version reloads so a fresh
document arrives. Neither is written, because neither could be verified in the time left.

**The two acceptance criteria are therefore unmet:** neither golden passes, let alone three times in
a row. Nothing in the repository claims otherwise.

### What the Odoo golden asserts once the guard step holds

the second parks mid-form, and two more rows follow it — their navigate is what would unload the
abandoned form. Expected outcome: 3 `verified`, 1 `skipped` (`duplicate`), 2 `parked` (the row with
no email, reason `missing <email column>`; and the abandoned row), nothing `failed`.

Three assertions carry the invariant:

1. exactly one commit gate is approved, and it is approved *after* the golden has checked that the

   carries at least one `blocked an unsaved change from leaving the page` step event as the reason
