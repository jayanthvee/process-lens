## The evidence (what the page showed at the save)

The golden was instrumented in the file itself (screenshots, every input's value, every
`.oxd-input-group__message`, every toast, and a page-side witness of clicks whose control says
"save"), polling the same tab the replay drives every 200 ms, and the run's `step_events` were
dumped. All of it was written under `.cache/pl078/` and **removed from the test file before this
commit**.

- **The replay never left the timesheet view.** Every snapshot during the canary's run shows
  `…/time/viewMyTimesheet?startDate=2026-10-19`: the grid was never open at a snapshot. The
  canary went `filling` → `submitted_unverified` → `parked` in about ten seconds, and the tab
  never showed a toast or a validation message. `step_events` says every step returned `ok` and
  `click-3` (Save) failed its assertion.
- **The compiled recipe had no activity step at all.** Its steps were: navigate → click *Edit* →
  fill *Project* → **click "-- Select --"** (with no value) → fills 19Mon…23Fri → click *Save*.
  OrangeHRM requires a project *and* an activity for a row with hours; the save was refused, so no
  confirmation could appear. That is why the 8-second check timed out — not because the toast was
  late.
- **The recorder never saw the activity click.** `recording.json` (the raw events) is click *Edit*,
  fill *Project*, a page-set fill of the project, click "-- Select --", the five day fills, click
  *Save*, submit, observation `text_visible: "Successfully Saved"`. The click on the **option
  "Development"** is missing.
- **Why it is missing — the DOM, from the live page.** OrangeHRM 5.7's OXD select is
  `.oxd-select-wrapper > .oxd-select-text > .oxd-select-text-input[tabindex=0]` plus a
  `[role=listbox]` sibling. There is **no `role=combobox`** and no `aria-controls`. The options are
  `div[role=option]`.
- **Why it is missing — the events, from the live page.** A capture listener attached the way the
  recorder attaches its own, then a click on the option, recorded:
  `pointerdown` on the option, `mousedown` on the option, `mouseup` on the **table** — and **no
  `click` event at all**. The widget selects on `mousedown` and removes the list before the
  release, so the browser dispatches no click. A recorder that listens for clicks loses the whole
  choice, silently.
- **The day-cell targets.** The compiled fills are `role: textbox, name: "19Mon"` plus
  `css: input.oxd-input.oxd-input--focus`. They do **not** depend on `oxd-input--active` (the
  ticket's guess); they depend on `oxd-input--focus`, which — like `--active` — is a state class
  that only exists while a cell has focus. The role rung is also date-derived ("19Mon" is this
  week's Monday), so the ladder is only as durable as the week it was taught in. Both are reported
  as follow-ups, not fixed here: the role rung resolved on every replayed fill (rung 1), so neither
  is what parked the run.
- **A second, independent defect.** The popup offered one column per *distinct value*
  (`seenValues`), so Monday's and Tuesday's `2:00` collapsed into one column (`f_19mon`), and the
  compiler then bound both fills to it. A row whose Tuesday is `1:00` would have replayed Monday's
  hours into it.

## The fix (where the cause lives)

- **Recorder** (`apps/extension/src/content/recorder.ts`): a press on a `role=option` inside an
  open `role=listbox` whose control is not an input/combobox is recorded as a **select of that
  control**, once the list leaves the document with the press. That is the honest reading of a
  widget that acts on `mousedown`; a list of already-chosen values (a chip list) stays open and
  records nothing, and a press the person drags away from records nothing either. A click on the
  same option is suppressed so one choice is one step.
- **Executor** (`apps/extension/src/executor/step-runner.ts`): `resolveListboxDescriptor` used to
  refuse an open list without an id ("the open listbox has no id to scope the option search to").
  OXD's list has none. The single open list is the one the caller's click just opened, so it is
  given an id of our own and the option search stays scoped to it.
- **Popup** (`apps/extension/src/popup/make-recipe.ts`): `recordedValues` keys its dedupe by the
  field's targets *and* the value, not the value alone. Two fields taught the same value get two
  columns; the same field recorded twice with one value is still one.
- **Compiler** (`packages/compiler/parameterize.py`, `packages/compiler/compiler.py`):
  - `match_column` takes the step's own field names as a preference, so a value held by two columns
    binds to the column this step names (falling back to the first match, as before, for a step
    that names none).
  - `_fold_select_control_clicks` drops a click on the control a select of the same control opens
    by itself. Without it the replay clicked the dropdown open and the select's own click closed it
    again — the last run's failure.
- **Golden** (`tests/e2e/test_orangehrm_timesheet_golden.py`): the sheet's `mon`…`fri` hours are
  mapped to the compiled columns by the column's label (`f_19mon` is this week's Monday), the
  activity column is read from the compiled select step instead of guessed from the form's last
  option, and the project/activity cells are set explicitly.

## Tests (product tests, written before the fix)

- `apps/extension/tests/recorder-capture.test.ts` — three cases: no click ever fires and the press
  is the select; a click that does follow the same press is not recorded twice; a chip list is not
  a choice.
- `apps/extension/tests/executor-run.test.ts` — a custom combobox whose open list has **no id**:
  the control is clicked, the one list is scoped to, and its option is clicked.
- `apps/extension/tests/popup-make-recipe.test.ts` — two fields taught `2:00` offer `f_19mon` and
  `f_20tue`, not one column.
- `packages/compiler/tests/test_pl078_input_columns.py` — equal values keep their own columns by
  field name; a step that names no field keeps the old first-match behaviour.
- `packages/compiler/tests/test_pl078_select_control_click.py` — the click that opened a dropdown
  is folded into its select; a click on another control is kept.

## The golden: three runs, all spent

1. **Run 1** (with the capture, `--runxfail`): the canary parked at the save with
   `the page never showed "Successfully Saved" within 8 seconds`; the evidence above is from it.
2. **Run 2** (after the recorder, executor, popup and column fixes): the compiled recipe now had
   the activity select, but its value bound to the *project* column (the popup's value dedupe), and
   every row parked at `select-1` with `found no option matching … inside its listbox` or
   `could not find the listbox`.
3. **Run 3** (after the popup dedupe fix): the recipe is now right — `development`, `f_19mon` …
   `f_23fri`, `project`, record key `{{row.project}}:{{row.development}}` — but every row parked at
   `select-1` with `the combobox has no listbox to search`: the recorded `click-2` on the dropdown
   opened the list and the select step's own click closed it before the option search. That is the
   `_fold_select_control_clicks` fold, written **after** run 3.

**What is therefore still unproven:** the fold and the golden's explicit activity mapping have unit
tests and pass the gates, but no end-to-end run has exercised them. `xfail(strict=True)` stays with
that reason in the file, so the run that passes fails as XPASS — the signal to remove the marker.
