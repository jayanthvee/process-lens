# PL-079: updates are keyed by what they change, and a row that already matches is skipped

Owner: T2 (DeepSeek) · Reviewer: T1 · Branch `pl-079` (built on `pl-075`, merged with `origin/main`)

## Status: done — all gates green, both goldens passed on the first real attempt

Two gaps closed, both in the compiler. No change to the runner, the executor, the extension or the
schema.

1. **The key.** When the recording is a find-then-update (PL-077), `meta.idempotency_key` is now the
   record key's own template, then `:`, then every column the update's fills write, in step order.
   For the price golden that is `{{row.search | lower}}:{{row.sales_price}}`. A create's key is
   unchanged, byte for byte: the record key alone.
2. **The row that is already right.** An update whose commit assertion is PL-075's `element_absent`
   proof now carries a compiled `branch` **immediately before the commit click**. Its condition is
   the same `element_absent` on the commit control; if it holds, the record ends `skipped` with
   "Already had these values, so nothing was changed." The branch is a step in the recipe — nothing
   in the runner knows about it (D-017).

## The change

`packages/compiler/compiler.py` only.

- `_update_columns(candidates, search_run)` — the columns the update's own fills write: every `fill`
  after the step that ran the search and before the commit, whose value the sample row bound to an
  input column, de-duplicated, in step order. A fill whose value stayed a literal (a column the
  sample row does not carry) is left out rather than guessed at, so **the key template uses only
  columns the sample row has**, as the ticket requires.
- `_resolve_meta(..., update_columns=...)` — appends `:{{row.<column>}}` for each of those columns to
  the record key template. An `options.idempotency_key` supplied by a caller still wins outright.
  The decision is `search_kind == "update"`, i.e. the recording's shape, not whether the person left
  the search rule ticked.
- `_already_matches_branch(commit_control)` — builds the branch from the commit's own
  `assert_after.element_absent.targets`, so the condition and the proof cannot drift apart.
- `_already_matches_placement(candidates, search_kind)` — the branch only exists for an update, and
  only immediately before the first commit whose assertion is the disappearing-control shape. A
  commit that proves itself with text or a URL gets no branch, because it cannot say whether there
  was anything to save.
- `_render_steps(..., already_branch_before=..., already_branch=...)` — inserts it at that index.

The detection order moved: the search shape is now decided before `_resolve_meta` runs, so the key
can be resolved in the same pass. Nothing else about the search handling changed.

Compiled shape of the golden's recipe (from its trace):

```
navigate-1  fill-1(search)  press-1(Enter)  branch-1(park when the search finds nothing)
click-1(row)  fill-2(price)  branch-2(skip when Save is already gone)  click-2(commit)
```

## What Odoo does on an unchanged fill

**It does not mark the form dirty, and Save stays hidden.** The extension's fill is select-all, one
`Backspace`, then one `Input.insertText` (`apps/extension/src/executor/dispatch.ts`), so the field
briefly goes empty before it holds the same value again. Odoo compares the value, not the editing
history, so the form is clean when the fill finishes.

The evidence is run 3 below, and it is Odoo's own answer rather than ours: the two rows whose price
equals the stored one have step events ending at `fill-2:ok` and then the record ends
`skipped:Already had these values, so nothing was changed.` — the branch, whose condition is
"the Save control is not on show", held within the same second as the fill. The changed row in the
same run has `fill-2:ok -> click-2:ok` (the branch polled its full timeout because Save *was* shown)
and Odoo's `list_price` is the new value afterwards.

So the "harmless but worth knowing" case the ticket names does not arise on Odoo 18: a same-value
fill never shows Save, the branch always fires, and the same value is never saved again.

## Known trade-off

The branch inherits the runner's condition timeout, as PL-075's assertion and PL-077's park branch
do, so a row that *does* have work pays that wait once (8 s by default) before the commit click.
The skip path costs nothing: `element_absent` holds at its first poll. Pinning a shorter timeout on
the branch was considered and rejected — it would only shorten the wait when Save is present, and it
would add a second number to a condition the ticket asks to keep identical to PL-075's proof.
