## Part 1: why the recorded `combobox` rung matched 0 on replay

**The ticket's hypothesis — recorder/resolver role disagreement — is not what happened.**
Verified against the live Odoo 18 test app: the many2one autocomplete input carries
`role="combobox"` statically in Odoo's own template
(`web/static/src/core/autocomplete/autocomplete.xml`) and its placeholder "Search a product"
comes from the account module (`product_label_section_and_note_field.js:208` sets it for the
order-line product cell). Both `semanticRole` (fingerprint.ts) and `roleOf` (ladder.ts) honor
an explicit role, and a faithful replica of the resolver's role+name computation run against
the live page at click-5 state matched **exactly one element** — the row's product input.

**The actual cause is a resolution-time race, and the resolver's patience gives up one step
too early.** Clicking "Add a product" does not render the editable row instantly: measured on
the live app three times, the row's inputs appear **156–187 ms** after the click (the row's
onchange round trip). PL-046's parked page stats — `4 input(s), 340 element(s)`, rung 4 css
`input.o-autocomplete--input.o_input` matched **2** — are exactly the page *before* the row
renders: my reproduction of that state gives `4 inputs, 340 elements, 2 autocomplete inputs`
(customer + payment terms). The row contributed zero inputs. So at the moment click-5's ladder
climbed, the element the recording named did not exist yet, and no rung could match.

Why the replay did not wait it out: `resolveWhenReady` (executor/step-runner.ts) re-climbs the
ladder while **nothing at all** matched (`nothingMatched` = every attempt found 0). Here rung 4
(css) matched the two *other* autocomplete inputs — ambiguous, found=2 — so the retry loop
exited on the first attempt and the step parked, ~170 ms before the row's input ever appeared.
Every rung's counts fit: role 0 (no combobox named "Search a product" exists yet), css 2
(the two form autocompletes), text_fuzzy 0 (no "Search a product" text anywhere — the row is
not rendered readonly first; it just isn't there).

**Fix within this ticket's files:** what could be fixed was fixed —
`roleOf` now agrees with `semanticRole` exactly (skip `role="label"`, validate the recipe role
pattern and fall back to the implicit role, `LABEL` → `generic`), pinned by tests that run the
same element through both sides. **The race's fix does not fit this ticket's file list**: the
retry patience lives in `executor/step-runner.ts` (`resolveWhenReady`/`nothingMatched`), which
the ticket forbids. Recommended for T1: treat "no unique match yet" as still-waiting until the
ready-wait deadline (not just all-zero attempts), or wait out the quiet window before the next
step's prepare. With the row present, this ticket's header naming makes rung 1 resolve
(`combobox` + "Product" — see part 2).

## Part 2: column-header names, both sides, one rule

- **Recorder** (`accessibleName` in `shared/fingerprint.ts`): a field control (`input`,
  `select`, `textarea`) inside a `td` / `role=cell` / `role=gridcell` with no
  `aria-labelledby`/`aria-label`/`<label>` is named by its column header **before the
  placeholder**: the product cell records as role `combobox`, name **"Product"**; the quantity
  as **"Quantity"**. Field controls only — a read-only cell's span is still named by its own
  text, and the customer many2one above the table keeps its label name.
- **The header rule** (`columnHeaderName`, exported from fingerprint.ts): the `th` (or
  `role=columnheader`) at the cell's column position — the cell's `aria-colindex` when present,
  else its position among the row's cells; header `colspan`/`aria-colspan` counts, and a
  header's own `aria-colindex` is honored — text trimmed, sort arrows and icon glyphs left out
  (`i`, `svg`, `aria-hidden`, Odoo's `o_list_sortable_caret`/`o_resize`).
- **Resolver** (`resolveTargetInPage` in `executor/ladder.ts`): a role rung's name matches the
  element's accessible name **or** its column-header name, so **recipes pinned with placeholder
  names keep resolving** (the old "Search a product" rung still matches — the placeholder is
  still the accessible name). The resolver is serialized into the page and cannot import the
  recorder's code, so the rule is mirrored; `tests/order-line-names.test.ts` runs the same
  elements through both sides to pin the agreement ("agrees with the recorder's header name"
  test).
- **Part 3 — ties stay refusals:** two editing rows both named "Product" fail with
  `more than one match` at rung 1 and the step refuses; nothing picks the first. Odoo renders
  inputs only in the row being edited, so one match is the normal case.

## The golden: two attempts, no replay verdict

Both runs of `tests/e2e/test_odoo_quote_golden.py` (reset done before each, per the ticket)
reported `1 xfailed` — but **the test body never executed in either run**:

1. **Run 1, 168 s**: fixture setup ran (scratch DB, extension build, API server log created
   16:45:42, the Odoo reset's 127 s), then failed ~30 s later — around the extension/browser
   binding. No trace file (the test's own `_trace` never ran), no API traffic, no browser
   profile content.
2. **Run 2, 2 h 46 m**: same failure point, after a ~2.6 h hang following the API server
   startup (16:50:50). Same silence: no trace, no traffic, empty profile.

Why "xfailed" instead of an error: **pytest (9.1.1) reports a fixture-setup failure of a
strictly-xfail-marked test as xfailed** — verified with a two-line probe test (a fixture that
raises under `xfail(strict=True)` reports `XFAIL`, not `ERROR`). So the strict xfail masked a
harness failure. The marker's stated reason (PL-046's park) is what pytest prints; it is not
what happened.

Environment notes for whoever picks this up: the worktree was fresh — `.venv` and Playwright
browsers had to be installed (playwright 1.64.0, chromium-1248, both under the repo's
`.cache/`), whereas PL-046's run used the main checkout's older install. A standalone probe of
the harness's own `_launch_with_install` (persistent Chromium, `channel="chromium"`, built
extension loaded) **launches fine** in this worktree, so the failure sits further up the
binding chain — the popup/service-worker handshake (`bind_extension_to`) or the API/DB health
wait are the suspects. Suggested next step for T1: run the golden once outside the xfail (or
add a `--setup-show` pass) to surface the real fixture error; the replay itself is untested
territory for PL-048's change, and the race fix in `step-runner.ts` (part 1 above) decides
whether click-5 resolves at all.

Odoo is left reset and seeded (the second run's `odoo_reset` fixture re-reset it; the test body
never touched it).
