## Changes

All in `services/runner/browser_executor.py`.

- **Constant and constructor (items 1).** `DEFAULT_LATE_REPLY_GRACE_SECONDS = 45.0`, and
  `BrowserExecutor.__init__` takes `late_reply_grace_seconds: float = DEFAULT_LATE_REPLY_GRACE_SECONDS`
  and stores it as `self.late_reply_grace_seconds`.
- **One grace read (item 2).** A new `_read_with_grace(deadline, *, command_id)` reads once as before;
  only when that read returns `timeout`, the executor is not `disconnected`, and `self._socket` is not
  `None` does it read once more for the same `command_id`, ending at `deadline + grace`. A reply in
  that window is returned as if it had come in time. A second timeout is returned unchanged and the
  caller's existing lost path runs, so silence past the grace still detaches.
  - The second wait is anchored to the caller's absolute `deadline`, not `self._now()`, so repeated
    entries (an ack inside the grace followed by `_step_result`) cannot extend the total wait beyond
    one grace. There is exactly one extra read, never a loop of grace windows.
- **The three waits (item 2).**
  - `_step_result` (which serves `prepare`, `dispatch`'s reply and `perform`) now calls
    `_read_with_grace`;
  - the ack loop in `dispatch` calls `_read_with_grace` with the same `ack_deadline`;
  - the reply wait in `check_condition` calls `_read_with_grace` with its existing deadline.
  Nothing else in the reader changed: `await_peer`, `guard`, `_read`, `_read_once` and `_route` are
  untouched, so `peer_gone`/`closed` still short-circuit before any grace and R3's `command_id`
  filter still drops a stale reply.
- **Wire deadline untouched (item 3).** `_send_command` and every `ttl` argument are unchanged, so
  `expires_at` still carries the original budget. The extension still refuses a dispatch that
  expired before any input was sent; the grace only governs how long the runner keeps reading for a
  step that already started.
- **`_lost` docstring (item 4).** It now says the late-reply grace comes first: `_step_result` gives
  the command one more wait past its deadline while the socket is up, and only silence past that
  grace reaches the detach path.

Diff: 32 insertions, 7 deletions in one file.

## Notes for T1

- **No change beyond the three waits was needed.** Every other reader call site keeps its old
  deadline, and no wire field moved.
- **`dispatch` can now block for two graces.** It already had two independently-deadlined phases
  (the ack, then the reply); each now has its own grace, so the worst case is
  `2 x (budget + grace)` instead of `2 x budget`. `probe_confirmation`'s 100 ms poll can likewise
  wait about 50 s (5.1 s budget + 45 s grace) on silence before it detaches.
- **Heartbeat headroom is unchanged and now conservative.** `services/runner/run_loop.py:591` still
  requires `3 x max_step + DISPATCH_BUDGET_SECONDS`, and `services/runner/worker.py:33-36` documents
  365 s as the largest a legal recipe can demand. With the schema's 120 s maximum step, the true
  worst case is `3 x 120 + 5 + 2 x 45 = 455 s`. The heartbeat beats on its own thread
  (`services/runner/worker.py:82`), so a lease does not lapse while the executor blocks; the guard
  check is only conservative. Updating that formula is outside this ticket's scope, so it is
  reported here rather than changed.
- **A late reply past the wire `expires_at` is accepted by design** (ticket item 3). The extension
  refuses to *begin* input past expiry, but a step that already started can finish and report late;
  that result is used. A hosted-smoke rerun should read a long gap before a result as the grace
  working, not as a hang.
