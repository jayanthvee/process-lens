## Built (behind a flag, off by default)

### The flag
`apps/extension/src/executor/flags.ts` — `IN_PAGE_DISPATCH_KEY` (`processlens.inPageDispatch`),
`dispatchPathFrom`, `inPageDispatchEnabled`. Only an explicit yes (`true`, `"in-page"`, `"on"`,
`"true"`, `"1"`) turns it on; anything else is the debugger. `RunDeps.inPage` carries it into a run;
`performStep` reads `StepRunDeps.inPage`.
Proves: `apps/extension/tests/pl108-flags.test.ts`.

### The in-page dispatcher
`apps/extension/src/executor/inpage.ts` — the same callable interface as `executor/dispatch.ts`, each
action one self-contained page expression:
- `inPageClick`: scroll into view, hit-test the centre, then
  `pointerdown/mousedown/pointerup/mouseup/click` on the element the hit test found.
- `inPageFill`: focus, clear, write through the element's own native `value` setter (React's value
  tracker sees it), then `input`/`change`; contenteditable takes `execCommand("insertText")` with a
  textContent fallback; a password field is refused.
- `inPagePress`: `keydown/keypress/keyup`, and `form.requestSubmit()` for Enter in a field.
- `inPageSelect`: a native `<select>` is set React-safe and fires `input`/`change`; a custom
  combobox answers `custom` for the caller to click.
- `inPageUpload`: a `DataTransfer` built from base64 files on the file input.
- `dialogOverrideExpression()`: a main-world `alert/confirm/prompt` override that records the last
  dialog on `window.__plDialogs` and never answers for the person.
Proves: `apps/extension/tests/pl108-inpage.test.ts` (the click sequence and a covered target; a
React-safe fill and a refused password; a contenteditable fill; a Enter press with `requestSubmit`;
a native select and a custom combobox; upload's graceful refusal when the page cannot build a file
list; the dialog override).

### The per-step fallback
`apps/extension/src/executor/executor.ts` — in the run loop, an in-page step whose own `assert_after`
does not hold is retried **once** through the debugger, and `StepReport.via` records which path
worked (`"in-page"` or `"debugger"`). A step with no assertion has no effect to check and stays on
its in-page result. **A commit step is never retried**: a failed commit check may already have saved,
so it parks rather than risk a double entry.
`apps/extension/src/executor/step-runner.ts` — every action dispatches through the in-page path when
`deps.inPage` is set, and the owner's `beforeInput`/`onFirstInput` policing runs once immediately
before the page call, exactly as it runs before the debugger's first input.
Proves: `apps/extension/tests/pl108-fallback.test.ts` (in-page reported when its check passes;
fallback to the debugger when the in-page action shows no effect, with a trusted press really sent;
a commit parks with no retry; a debugger-only run carries no `via`).

## Not built this push

- **Page loads via `chrome.tabs.update` / `chrome.webNavigation`** — the run loop still navigates
  through the debugger (`Page.navigate`). Wiring `chrome.tabs.update` and the load event is
  service-worker code that the unit tests cannot exercise, and the measurement is out of scope
  tonight.
- **Network evidence via `chrome.webRequest`** — not wired; it is observe-only and belongs with the
  page-load work above.
- **A normal background tab instead of a separate window** — not changed; that is the measurement
  half, left for the owner. The `debugger` permission is still needed for the navigation and the
  fallback.
- **Upload dispatch** — `inPageUpload` exists, but the executor's actions are
  `navigate/fill/select/click/press`; a recipe has no upload action to route to it yet.

## Recommendation (one paragraph)

Ship nothing yet: the pieces exist and are unit-proven, but the question — is the in-page path good
enough to be the default? — is answered by the table, not by this code. The design is sound and
conservative: off by default, per-step fallback to the debugger, and no commit ever retried, so
turning it on for a test run cannot silently double-save a record. What remains before the owner can
judge it is the parts unit tests cannot cover — `chrome.tabs.update` page loads, the dialog override
installed at document start, `chrome.webRequest` evidence, and a background tab — plus the three-way
(and background/minimized) e2e run that fills the table above. My expectation, not a measurement: the
in-page path will carry ordinary fields, buttons and native selects, and the fallback will earn its
keep on rich-text editors, custom dropdowns and uploads — the exact list the table should name.
