## What Odoo's Save button does after a save (real page, evidence)

Probe: `.cache/pl075/probe_save.py` (scratch, not committed) logged into Odoo 18, opened
`PL-DESK-1002`, changed Sales Price, clicked Save, and read the control every 250 ms:
`.cache/pl075/save-button.json`.

- **before the edit** (clean form): the button exists, `disabled=false`, **`visibility: hidden`**;
- **after the edit** (dirty): `visibility: visible`;
- **+265 ms after Save**: `disabled=true` (the in-flight save);
- **+593 ms and every sample to +7.7 s**: `disabled=false`, **`visibility: hidden`** — still in the
  DOM, hidden by CSS.

So the answer is **hidden**, not removed and not merely disabled. Per the ticket that selects
option **(b)**: the recorder emits the evidence only when the clicked control is really gone or
hidden. A control that is only disabled proves nothing and is not reported; `isGoneOrHidden` walks
`hidden` attributes and `display: none` ancestors and reads the element's own computed
`visibility`, which is exactly Odoo's mechanism. The executor's resolver already treats a hidden or
disabled element as "not usable", so `element_absent` means "no visible, enabled element resolves"
there, and the evidence agrees with it.

Also confirmed: the page's URL stays `/odoo/products/2` and no toast appears.

## The change

**Executor — `apps/extension/src/executor/assertions.ts`.** `conditionExpression` used to return at
the first predicate key it recognised. It now collects every predicate key (`text_visible`,
`text_absent`, `text_count_increases`, `url_matches`, `element_present`, `element_absent`,
`value_equals`) and joins their expressions with `&&`; a single-key condition produces exactly the
same expression as before, and `timeout_ms` is not a predicate.

**Recorder — `apps/extension/src/content/recorder.ts`.** The observation window remembers the
control the action was performed with (`click`, a checkbox/radio click, or a submit's control) and
whether it was on show when the window opened. When a window ends with no confirmation and no
navigation, and that control is now gone or hidden, the recorder emits
`{ element_absent: { targets: <the control's ladder> }, url_matches: <navigationPattern(url)> }`.
`navigationPattern` is the same function the URL evidence uses. Nothing is emitted for a control
that was already hidden when the window opened, for one that is merely disabled, or for a click
that already produced a toast or a navigation.

**Compiler — `packages/compiler/assertions.py`, `compiler.py`.** `condition_from_observation` keeps
both halves of that observation as the commit's `assert_after` (`element_absent` is the proof,
`url_matches` pins the record page), and the "also true on the page the step ran on" warning does not
fire when the condition carries `element_absent`. The refusal for a click with no evidence at all is
unchanged. One more compiler fix was needed for the golden: `_drop_container_clicks` dropped Odoo's
product-list row click ("dropped container click at event 4: it has no role, label or test id"), so
the replay filled the price field on the *list* page and every row parked. A css-only click that
carried its own `url_matches` observation is now kept; a css-only click with no evidence is still
dropped. (`after_url` deliberately does not count: it is the next action's page, not this click's
evidence, and using it broke PL-031's container rule.)

## Goldens

**Price golden — 2 runs, as allowed, each after `reset.py odoo` and a rebuilt `dist`.**

- Run 1 failed at the replay's second fill: the row click had been dropped (above), so the recipe
  filled the price on the list page; all three rows parked. Trace: `.cache/pl063/price-golden-trace.log`.
- Run 2 got through the whole first pass: the compile succeeded from
  `{"element_absent": {"targets": [{"by": "role", "role": "button", "name": "Save manually"},
  {"by": "css", "selector": "button.o_form_button_save.btn.btn-light"}]}, "url_matches":
  "/odoo/products/\\d+"}`, **all three rows verified**, and Odoo's `list_price` equalled the sheet
  for all three. It then failed at the **second run of the same sheet**: the first row's commit
  click could not be prepared ("1 matched, 0 usable — no visible, enabled match") because the
  product's price already equals the row, so Odoo keeps Save hidden; the record parked and the run
  paused `canary_failed`, with the other two rows `pending`. The ledger did not skip the
  already-committed keys before driving the browser.

  The `xfail(strict=True)` marker is therefore **kept, with this new reason**. PL-063's cause (the
  compile refusal) is fixed; what fails now is a repeat run of an update, which is a separate
  ticket. The golden's final assertion used to read a top-level `idempotency_key`, which never
  exists (the key lives in `meta`); it now reads `meta.idempotency_key` and asserts the record key
  is in it. The trace records, and the report repeats, that the compiled key is the record key
  alone, so PL-063's "a later change to the same product is still a new key" is **not** satisfied —
  an open finding, deliberately not hidden.

- **Quotation golden — 1 run: passed** (168.95 s, after its own reset).
- **Invoice golden — 1 run: passed** (170.67 s, after its own reset).

A note on the reset: three early `reset.py odoo` attempts failed at `seed_odoo` because Odoo
answers 500 while it is still installing the fresh database's base modules (the create call returns
