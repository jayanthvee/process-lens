## 1. A code ProcessLens typed is never typed again

**Before.** There was no memory of a typed code anywhere. `findCode` chose a code purely from the
messages in the inbox, and `codeForTeaching` handed its code to the page and forgot it. The
teaching code A and the run's code A were two unrelated facts, so the run found A again.

**After.**

- `apps/extension/src/background/used-codes.ts` (new) — `SaltedCodeMemory`: one salt per service
  worker, from `crypto.getRandomValues(16)` at module load, never written anywhere; each typed code
  is remembered as `SHA-256(salt + "\0" + code)` with a 15-minute expiry (`USED_CODE_TTL_MS`),
  swept on each read and write. `digestCode(salt, code)` is exported so a test can search for the
  hash itself. A worker restart re-evaluates the module, which makes a new salt and remembers
  nothing — the memory is in memory only. Chrome's service worker always has `crypto.subtle`, so
  SHA-256 is the real path; a 64-bit FNV-1a salted digest is used only where `subtle` is missing
  (the jsdom test environment).
- `apps/extension/src/background/code-lookup.ts` — `LookupDeps.isUsed?: (code) => boolean | Promise<boolean>`.
  `withoutUsed()` drops every message whose code matches before `findCode` chooses, so a used code
  is not merely deprioritised: it is not a candidate. It is applied on every poll of the look.
- `apps/extension/src/background/teach-code.ts` — `used?: CodeMemory`; the code it hands to the
  page is remembered before the page types it.
- `apps/extension/src/background/service-worker.ts` — one `typedCodes` instance shared by the
  teaching path and both run paths. `enterCode` (the person typed the code on the run page)
  remembers it on a successful entry; `codeFromEmail` goes through `typeEmailedCode` below.

**Test.** `apps/extension/tests/pl119-new-code.test.ts` (5).

- *types only the new code in the run, not the teaching code* — the owner's shape: `Goodlabs
  <team@…>`, "Your Login Code", A at 28 s before the code page taught and typed, B arriving 8 s
  after it. Teaching returns A; the run types only B.
- *skips a code typed a moment earlier even inside the ten seconds* — the discriminating one:
  A arrived 5 s before the page, so the 10 s window alone would accept it. **Before the fix this
  typed A**; now A is skipped and the look waits for B.
- *waits for the new email because the old one is outside the ten seconds* — a restarted worker
  remembers nothing, A is stale by time alone, and the look polls more than once before B.
- *forgets an entry after fifteen minutes* — `USED_CODE_TTL_MS` boundaries.

## 2. Only a code that arrived after the code page counts

**Before.** `CLOCK_SLACK_MS = 60_000` in `apps/extension/src/shared/email-code.ts`, so a message
received up to a minute *before* the page counted. With no code page seen by the session,
`CommandSession` looked back `CODE_PAGE_FALLBACK_MS = 3 * 60_000` from `Date.now()` (the wall clock,
not the session's injected clock).

**After.**

- `CLOCK_SLACK_MS = 10_000`, with the reason in the comment.
- `CODE_PAGE_FALLBACK_MS = 10_000`, and both it and the `code_required` stamp now use
  `this.deps.now()` instead of `Date.now()`, so the session clock is the only clock involved.
- The teaching watch is untouched: `CODE_EMAIL_SLACK_MS = 30_000` in
  `apps/extension/src/content/code-watch.ts` still starts its look 30 s before the last action.
  Nothing in that file changed.

**Tests.** `pl119-new-code.test.ts` *allows ten seconds of clock difference, and no more*
(9 s found, 11 s not); `pl119-code-window.test.ts` *looks back ten seconds, not three minutes*
(**before: the value was `Date.now() - 3 min`**) and *does not use an email that arrived two minutes
earlier* (**before: `['111111']` was typed**). The existing
`apps/extension/tests/email-code.test.ts` case *allows a minute of clock difference…* asserted the
old constant, so it now reads *ten seconds* with a 9 s message; that file is the only pre-existing
test changed.

## 3. A refused code gets one more look

**Before.** `codeFromEmail` in the service worker did one `lookForCode`, one `typeCodeInBoundTab`,
and answered with `cleared`. A code the site refused ended the attempt.

**After.** `apps/extension/src/background/code-entry.ts` (new) — `typeEmailedCode(deps, ask)`:

- at most `MAX_CODES_PER_PAGE = 2` codes for one code page;
- every code that was actually typed (`entered: true`) is remembered, so the second look cannot
  pick it up again;
- the second look uses whatever is left of the *same* `lookMs` deadline, so a refusing site cannot
  hold the run longer than the look it asked for;
- a typing with `cleared !== false` ends it (including an older caller that reports no `cleared`);
- if nothing newer arrives, it returns the first typing's answer, so the run pauses exactly as it
  did before this ticket — no new pause reason, no third code.

`service-worker.ts`'s `codeFromEmail` now returns `typeEmailedCode(...)` with `enter: typeCodeInBoundTab`
and `used: typedCodes`.

**Test.** `apps/extension/tests/pl119-refused-code.test.ts` (4).

- *types the newer code once after the first is refused, and no third* — typed `['111111', '222222']`,
  the third email never typed, answer `cleared: true`. **Before: `['111111','111111']`.**
- *stops after two codes when the second is refused too* — typed exactly two, answer `cleared: false`.
- *keeps today's pause when no newer code arrives* — typed once, answer `cleared: false`.
- *does not type the same code again on a later look* — a second entry for the same page answers
  `{entered: false, reason: "none"}` instead of re-typing. **Before: `['111111','111111']`.**

## Not done, plainly

- **The owner's use case is not re-proven on the real site.** The ticket forbids e2e and browsers,
  so this is unit work against the fixture shape. Per WORKING-RULES 1 the Goodlabs run still needs
  a real pass from the side panel before the use case is closed.
- **Teaching remembers at hand-off, not at confirmation.** `codeForTeaching` remembers the code
  when it returns it to the page, because the worker never learns the code again afterwards (by
  design). If the page then fails to type it, that code is remembered although nothing was typed.
  The failure mode is "skips a code that was never typed", never "types a used one twice".
- **The memory dies with the worker.** An MV3 restart forgets every typed code and makes a new
  salt. Within 15 minutes and within one worker life the rule holds; across a restart only the
  10 s window protects the run. That is what item 1 asked for ("a random salt made when the worker
  starts, kept in memory only"), and the restarted-worker test asserts the intended behaviour.
