# Report PL-009

Status: done · Agent: T2 DeepSeek · Commit: 99bf29c (branch `pl-009`)

## Summary

The recorder now watches the page for a short window after every click and submit
and reports what changed — a confirmation element appearing, or the URL moving —
on its own `observation` event. The compiler folds each observation onto the
action it followed, so a commit step gets its `assert_after` from the recording
itself instead of a hand-supplied override. `fuzzyText` no longer returns a text
field's value, so a typed buffer (and a password) never enters a target ladder.
Both halves are covered by tests and proven end to end: a real browser recording
with no manual assertion compiles into a schema-valid recipe.

## Files changed

- `apps/extension/src/content/recorder.ts`: a post-action observation window (MutationObserver + debounced timer, capped at 2× the window) that emits a confirmation or a URL change on an `observation` event; `pushState`/`replaceState`/`hashchange`/`popstate` are watched for URL moves.
- `apps/extension/src/shared/recipe-types.ts`: `RecordedKind` gains `observation`; `RecordedEvent` gains the optional `observation` payload.
- `apps/extension/src/shared/events.ts`: `makeEvent` carries an observation payload.
- `apps/extension/src/shared/fingerprint.ts`: `fuzzyText` never returns an input/textarea value (placeholder and aria-label stay); a select still reports its selection.
- `apps/extension/tests/observation.test.ts`: 8 tests for the observation window.
- `packages/compiler/assertions.py`: documents that an observation arrives either inline or as its own event, and defines `OBSERVATION_EVENT_KIND` (the contract the recorder conforms to).
- `packages/compiler/normalize.py`: keeps `observation` events and folds each onto the most recent click/submit, instead of dropping them as noise.
- `packages/compiler/tests/test_observations.py`: 6 tests for the compiler half.

## Deviations from the ticket, and why

- **The compiler change is in `normalize.py`, not `assertions.py`.** The ticket's scope item 3 says "matching compiler expectation in `packages/compiler/assertions.py`". The *expectation* is there (the predicate keys, and now `OBSERVATION_EVENT_KIND`), and the recorder conforms to it; but accepting the recorder's own `observation` event needs a reader, and the reader is `normalize.parse_events`, which is where the envelope is parsed. `assertions.py` gains the contract constant and the documentation; `normalize.py` gains ~40 lines that keep and fold those events. Without the `normalize.py` change the recorder's observation events would be dropped as noise and criterion 2 could not hold.
- **The observation event is a new kind, and it attaches to the most recent click/submit, not the immediately preceding event.** A click and a submit both open a window, and the user may type again inside the window; attaching to "the previous event" would put the confirmation on the wrong step. The fold therefore walks back to the last click or submit.
- **The fingerprint rule is "never an input value", slightly wider than "when the value matches the typed buffer".** The recorder cannot see the buffer at fingerprint time, and never using the value also keeps a password out of the ladder as a matter of course. `placeholder` and `aria-label` are kept.
- **A `<select>`'s fuzzy rung still reports its selection.** The ticket names input/textarea; a select is a combobox, and the compiler's existing `exclude_text` guard covers the select echo. Noted as an open question rather than changed.
- **The observation window is capped at 2× the debounce (3s).** A debounce that only re-arms could otherwise never fire on a page that mutates continuously.
- **Tests and the two scratch harnesses were added.** The harnesses (`pl009_capture.mjs`, `compile_pl009_recording.py`) live in gitignored `.data/` and are not part of the deliverable; the tests are committed.

## Open questions for the owner or T1

1. **PR #4 (PL-008) is still open and unmerged**, and `pl-009` is branched from its
   tip (`ebdbf43`). When PR #4 merges, `pl-009` becomes a diff against the
   compiler; if it is merged first, its reviewer needs the compiler too.
2. **Should a select's fuzzy rung also drop the chosen option?** Same class of
   echo as the input value; left unchanged to stay inside the ticket.
3. **A confirmation that appears and then disappears inside the window** is
   missed if it is gone by the time the debounce fires. Longer-lived evidence
   (the URL, or a persistent banner) covers most Save flows; a transient toast
   that vanishes in under 1.5s would not be captured.
4. **Cross-origin navigation after an action** is deliberately not encoded
   (`sameOrigin` guard, mirroring the compiler). If a workflow lands on another
   host, its assertion must come from a confirmation element or a manual override.
