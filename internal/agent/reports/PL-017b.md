# PL-017b: A click lands only on the element the guards approved

Owner: T2 · Reviewer: T1 · Depends on: PL-017 (merged) · Phase: C · Branch `pl-017b`

## Summary

`dispatchClick` measured a click target once and then pressed at that point. If the page reflowed
between the measure and the press, the press landed on whatever had moved there — the defect PL-017
diagnosed on the messy fixture and then hid by making the fixture's listbox an overlay.

This ticket closes the gap in the executor and restores a genuinely reflowing fixture to prove it:

1. **Wait for the target to stop moving** (`settleTargetInPage`, `apps/extension/src/executor/ladder.ts`):
   the box is measured on a `requestAnimationFrame` pair inside one `Runtime.evaluate` with
   `awaitPromise`; stable when x/y/width/height each differ by ≤ 1 px across the pair. It re-measures
   until stable within the step's deadline, else the step **parks** ("the target kept moving") with no
   input sent.
2. **Hit-test the point again immediately before the press** (`hitTestTargetInPage`): re-measures the
   box and runs `elementFromPoint` at its center; the point must be the target or a descendant. A
   covered point re-measures within the deadline, else **parks** ("the target is covered by another
   element") with no input sent.
3. **Check where the press actually landed**: a one-shot capture-phase `mousedown` listener records
   whether the event target is the approved element or a descendant. On the target → success.
   Elsewhere on a non-commit step → park. Elsewhere after input → `lost` through the existing F2
   path (never `rejected`/`not_dispatched`). A missing result counts as landed only when a
   `Page.frameNavigated` arrived (the click's own navigation).
4. **Prove it on a reflowing page**: `messy-crm` gains a `listbox_in_flow` switch (default off) that
   puts the listbox back in normal flow so opening it pushes Add down; the messy golden runs with it
   on and passes, and a second messy case checks nothing extra is added and nothing is created twice.
5. **Keep the existing behaviour**: the added per-click page-side work on a still page is a
   `requestAnimationFrame` pair plus one `elementFromPoint`. Measured on the lead-crm golden:
   **median 33.2 ms**.

All six quality gates are green, each requirement has a test that fails without its change, the
reviewer passed, and the final full-suite e2e run is **15 passed** — reported below exactly as it showed.

## Requirement 1 — wait for the target to stop moving

`settleTargetInPage(query: { token, deadline_ms })` in `ladder.ts`, serialized and evaluated with
`awaitPromise`. It scrolls the target into view once, rejects a zero-area box, then loops: measure the
box on animation frame A, measure again on the next frame B; a stable pair (≤ 1 px on left/top/width/
height) resolves the settled box (frame B's). It loops until `deadline_ms`, then fails with "the
target kept moving". A frame that never arrives resolves `null` at the deadline, so the wait cannot
hang. `dispatch.ts` `settleTarget(...)`; default deadline `DEFAULT_CLICK_SETTLE_MS = 2000`.

**Tests** (`apps/extension/tests/executor-click-landing.test.ts`):
- *clicks a box that moves once, then settles, at the SETTLED point* — the box moves for several
  frames, then holds at y=100; the press lands at the settled y=112, not at any mid-motion point.
- *parks with zero Input.\* calls when the box never settles* — an alternating box parks with reason
  /kept moving/ and no `Input.*` at all.

## Requirement 2 — hit-test the point again immediately before the press

`hitTestTargetInPage(query)` in `ladder.ts`: re-measures the box and runs `elementFromPoint` at its
center; only the element itself or a descendant is a hit (never an ancestor). In `dispatchClick` the
hit test runs **before** `mouseMoved` (the first `Input.*`), so a covered target sends nothing; a miss
re-settles and re-measures until the step deadline, then parks.

**Tests:** *parks with zero Input.\* calls when the point is covered by an overlay*, and *re-measures
and clicks at the target's new position when an overlay opens under the old point* (the reflow race:
the old point is covered, the target has moved down, the click lands at the new position).

## Requirement 3 — check where the press actually landed

A one-shot capture-phase `mousedown` listener is installed immediately before the input (after the
settle/hit-test loop, so its window is not spent waiting for the box), sets
`window.__plClickLanding.result` to `"target"`/`"other"`, and removes itself after one event or a
timeout. After `mouseReleased`, `dispatchClick` reads it:

- `"target"` → success.
- `"other"` → `throw new ExecutorError("the click landed on a different element", undefined, "park")`.
- `null` → landed only if a bounded `Page.frameNavigated` wait sees the click's own navigation;
  otherwise the "elsewhere" rules.

`dispatchClick` has **no commit/isCommit flag and needs none.** The commit-vs-non-commit distinction
is the existing F2 rule: the throw happens only **after** the first `Input.*` event, which fires
`hooks.onFirstInput` (= `opts.sentInput`); `command-session.ts` then classifies
`status = sent ? "lost" : (gateRefusal ? "refused" : "not_dispatched")`. A commit landing elsewhere
therefore reports `lost`, and the runner reconciles.

**Tests:**
- *succeeds when the press lands on the target*.
- *parks when a non-commit click lands elsewhere, only after input was sent* — asserts 3
  `Input.dispatchMouseEvent` calls and that `onFirstInput` fired before the throw.
- *treats a click that navigated, with no listener result, as landed* — the navigation null case.
- *reports lost (not rejected) when a commit dispatch lands elsewhere* — drives the **real**
  `CommandSession` with the **real** `dispatchCommandStep` against a fake CDP whose press lands on a
  stranger, and asserts the socket result status is `"lost"` (and not `"rejected"`).

## The reviewer pass

One reviewer pass (`reviewer`, Sonnet 5.5, thinking high, `max_steps` 30) ran before hand-off,
focused on requirement 3's commit path.

**Verdict: PASS** — no blocking defect on the commit path. The reviewer confirmed, by reading the
code with line references:

- `onFirstInput` is `opts.sentInput` and fires before `mouseMoved` (the first `Input.*`); every throw
  that can follow input (the landing read, the `whenNavigated` wait, the park) comes after it.
- `command-session.ts` classifies `sent ? "lost" : gateRefusal !== null ? "refused" : "not_dispatched"`
  — a commit landing elsewhere reports `lost`; nothing on the path can report `rejected`.
- A `beforeInput` throw before the press yields `refused` (nothing sent), which is correct.

Two non-blocking findings were folded in:

1. *The landing-listener timer could expire during the settle loop*, recording a false "elsewhere"
   after a click that landed. **Fixed**: the listener is now installed immediately before the input
   (after the settle/hit-test loop), with a window floored at `DEFAULT_LANDING_WINDOW_MS` (2000 ms)
   so the settle wait never spends it.
2. *The stability pair was one `requestAnimationFrame`, not the pair the ticket names.* **Fixed**:
   `settleTargetInPage` now compares the box on two consecutive animation frames (frame A vs frame B).

Out-of-scope working-tree churn the reviewer flagged (`docker-compose.yml`, an untracked
`internal/docs/TEST-MOCK/`) was already dirty at session start and is left uncommitted.
