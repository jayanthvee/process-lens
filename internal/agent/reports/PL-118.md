## 1. Infer a read-back for an edit

**Before.** A find-then-update commit got its assertion from what the recording observed (the
`/new` landing, or the disappeared Save control). The compiler never wrote a `value_equals`
read-back for a changed field, so an in-place edit could compile with a weaker check than the
ticket asks for -- PL-113's report names this as its largest gap.

**After** (`packages/compiler/compiler.py`; `apps/extension/src/executor/assertions.ts`):

- `_edit_shape` reads the shape from the recording and its URLs only: the last click that landed on
  a **record page** (a numeric id or a UUID, the same rule `detect_find_then_update` uses), the
  parameterized fills that ran on that page, and the first thing that took the person off it (a
  click that moved the page, a navigation, or a recorded save shortcut). A create never has this
  shape, because `/new` is not a record page -- today's create rules are untouched.
- `_read_back_assertion` turns the changed field into
  `value_equals: { selector: { targets: <the field's own ladder>, description: <the field's name> },
  value: { kind: "input", column: <the row's column> }, case_insensitive: true }`. The value is the
  row's column, never the taught literal: a second batch row has a different price. A literal the
  sample row does not carry cannot be read back for every row, so no assertion is built for it.
- `_read_back_for_commit` gives that assertion to **any** commit that saves an edit, unless the
  caller supplied one -- a person's decision still outranks inference.
- The comparison itself is in the executor: `PAGE_NUMBER_SOURCE` reads the number a formatted value
  carries (`"$ 799.00"`, `"1,299.00"`, `"799"` are one number), and text is compared trimmed and,
  when the recipe says `case_insensitive`, without case. Anything that is not a number falls back to
  the text comparison, so a word never matches a number.
- A tab, a heading or a menu is still refused as a commit assertion (`_is_chrome_assertion`); the
  ticket's "a tab-only check is refused" holds and is pinned.
- If no read-back can be built (a literal, or no changed field on a record page) and the person
  chose "saves by itself", the compile says so in its warnings and appends an `end_record` that
  parks every row with `ProcessLens couldn't confirm the change was saved.` -- the row can never be
  Done.

**Tests.**
- `packages/compiler/tests/test_pl118_compiler_read_back.py` -- the owner's shape (search, open the
  product, change Sales Price, press Save) gets `value_equals` on the price with the row's column;
  the tab-only check is refused; a literal price compiles to a parked `end_record` with the
  sentence; a recording that never leaves the form does the same and its warning says so. Written
  first; the first run failed with `CompileOptions.__init__() got an unexpected keyword argument
  'save_by_itself'` and, after that was added, on the missing assertion.
- `apps/extension/tests/pl118-value-read-back.test.ts` -- 799 vs `$ 799.00`, thousands separators,
  trimmed/case-insensitive text, two different amounts not equal, and `readValueEquals` returning
  the page's value and the field's name. Written first; it failed with both numeric cases returning
  `false` and `readValueEquals is not a function`.
- `tests/api/test_compile_api.py::test_a_price_edit_compiles_with_a_read_back` -- the same shape
  through the route, with `save_by_itself: true`.

## 2. "The app saves by itself when I leave the page"

**Before.** The panel offered the recorded clicks and "Nothing gets saved"; there was no third
answer, and no compile mode behind it. PL-113's report records it as not built.

**After** (`apps/web/src/panel/PanelTeach.tsx`, `apps/extension/src/popup/make-recipe.ts`,
`packages/compiler/compiler.py`, `services/api/compile.py`):

- **The choice.** `SAVE_BY_ITSELF_CHOICE` is the third option, offered whenever the recording holds
  no click that reads as a save (`hasSaveClick`: a button whose name says
  save/create/add/submit/confirm/apply/update, or a form submit) and it is not a sign-in. It is the
  default when the recording ends a field change with a page move or the page's own save message
  (`selfSaveIsDefault`). The panel and the popup show the same decision line and the same select.
- **The request.** The sentinel `__self_save__` sends `commit_step_ids: []` and
  `save_by_itself: true`; no click is named as the save, and the capture is not trimmed to a save
  click (the leave is the last thing the person did and the compiler needs it).
- **The compile** (`_self_save_commit`). The person's own leave stays a step. The commit is the
  click that opened the item during teaching, replayed after the leave to re-open the item's saved
  page, carrying the item 1 read-back. It is a `click` commit under the existing rules -- write
  ahead, reconcile, `verify_commit` -- so no new commit-capable action exists. When the person
  already re-opened the item after leaving, that click is marked instead of adding a duplicate. The
  search detector reads a copy of the steps with a commit at the end, so the search branch and the
  `update` shape are still recognised; the real steps are untouched.
- Because the leave and the re-open both stay in the recipe, the compiled recipe is schema-valid
  and `search_kind` is `"update"`.

**Tests.**
- `apps/web/tests/pl118Teach.test.tsx` -- the third choice is present and preselected for the
  owner's shape, and the compile request carries `save_by_itself: true` with no commit click. Its
  first run failed looking for the update key line that did not exist yet.
- `packages/compiler/tests/test_pl118_compiler_read_back.py::test_the_saves_by_itself_mode_reads_the_value_back_on_the_saved_page`
  -- the recipe keeps the breadcrumb and the navigation, and the commit is the re-open click with
  the read-back on Sales Price.
- `tests/api/test_compile_api.py::test_a_price_edit_compiles_with_a_read_back` -- the route plumbs
  `save_by_itself`, and the recipe passes `recipe_problems`.

**Not done.** "Use the app's save shortcut only if one was recorded" runs into PL-018's existing
rule: a recording whose last action is a committing key is refused (`The save or send was done with
a key.`), because a press is not commit-capable (AGENTS.md section 4). A shortcut followed by other
steps is accepted as the leave, but a shortcut on its own is refused exactly as before; the ticket's
clause cannot be satisfied without weakening that refusal. The test that pins this is
`test_a_save_shortcut_alone_is_still_refused`.

## 3. Try one row shows what the page kept

**Before.** The card showed the file's values under "About to add:" and nothing after the try. The
executor had no way to hand a read-back back, and no API field carried one.

**After** (extension check command, `BrowserExecutor.check_condition`, `RunLoop`, `reads`,
`GET /runs/{id}/records`, `TaskRun.tsx`):

- after a check whose condition is a `value_equals`, the worker reads the field's **actual** value
  and sends `observed.read_back = [{ label, value, matched }]` with the answer, whether it passed or
  failed (`assertions.ts::readValueEquals`, `service-worker.ts`, `command-session.ts`);
- `BrowserExecutor.check_condition` keeps the answer's `observed`; the runner writes it onto the
  commit step's event, next to the destination ref, for a verified row and for a parked one;
- `GET /runs/{id}/records` returns `read_back` (the latest one, so a retried row shows its last
  answer); `TaskRun.tsx` renders `Sales price: now $ 799.00` or
  `Sales price: still 910, not saved` above the row's controls;
- a read-back the page answers "no" never verifies the row: it parks with
  `ProcessLens couldn't confirm the change was saved.` A check the page could not answer still
  reconciles, exactly as before, so a lost executor is never read as a failed save.

**Tests.**
- `apps/extension/tests/pl118-value-read-back.test.ts` -- the read-back reads the page's own value,
  and returns `null` when the field is not on the page.
- `tests/runner/test_pl118_read_back_runner.py` -- a read-back that holds is `verified` with one
  `committed_keys` row and the page's value on the step event; a read-back that still shows 910
  parks with the sentence and keeps `matched: false`; a check that held before the step parks with
  the freshness reason. Written first; the fake had no way to answer with an observation, and the
  parked sentence did not exist.
- `tests/api/test_pl118_try_read_back.py` -- the record returns the read-back, an empty list when
  there is none, and the latest wins.
- `apps/web/tests/pl118ReadBack.test.tsx` -- the card says both sentences. Written first; it failed
  with the card's text containing only "About to add: …".

**Note on a conflict inside the ticket.** Item 3 says both "the panel shows each changed field read
back from the page" and "no row values go into logs or step events". The value has to reach the
panel from a run the runner owns, so it is stored on the commit step's `observed` payload -- the
column the ledger already describes as "what the page showed: value read back, text seen, URL". It
is the page's own reading, never the row's input from the spreadsheet, it is never logged, and only
`{label, value, matched}` is kept. If T1 reads the sentence as "nothing of the page's either", the
display requirement has to give: there is no other durable path from the runner to the panel.

## 4. Key line words for an update

**Before.** "We'll use **Product** so nothing gets added twice." for every shape.

**After.** `updateDetected` decides the shape from the recording (a search for the key, a click that
opens a record page, a fill on that page), and both the panel and the popup then say

**After.**

## Not done, and limits worth knowing

1. **A save shortcut on its own** is refused by PL-018's "done with a key" rule, so item 2's clause
   is only half reachable: a shortcut followed by other steps counts as the leave, a shortcut alone
   is refused exactly as before.
2. **A recording that never leaves the form** proves nothing about a save. "Saves by itself"
   compiles it with an `end_record` that parks every row and says so in the warnings, rather than
   committing the fill (which would check the value the run just typed).
3. **An edit opened by a typed URL** (no click on a list) has no opener for `_edit_shape`, so it
   gets no inferred read-back and keeps the older rules (PL-075's disappeared control, or the
   navigation). Only the ticket's search→open shape gets the read-back.
4. **A failed read-back parks directly** (`submitted_unverified → reconciling → parked`) rather than
   searching the destination first; the ticket asks for the park and its sentence, and a person
   checks the row. A check the page could not answer still reconciles as before.
5. **Live acceptance is not done**: no real site, no browser. The rules are proved with fakes, a
   real DOM and the database.
6. The read-back is stored on `step_events.observed`; see item 3's note on the ticket's conflicting
   sentence.
