## 1. The read (`packages/ledger/reads.py`, appended)

`record_steps(conn, record_id, tenant_id) -> list[StepEventRow]`, plus `pinned_recipe_steps(conn,
recipe_version_id)` for naming a step from the version the run is pinned to.

- **Order** is `started_at, id`, so a step's attempts come back in the order they ran whatever order
  they were inserted in.
- **`observed` is not selected at all**, not filtered later: it can hold the values a row showed, and
  the results page never shows them. There is a test that puts `SECRET-PRICE-42` in it and asserts
  the string appears nowhere in the returned row.
- **The error is one string, cut to 200 characters**, chosen from the JSON in SQL: the `message`,
  else the `reason`, else the value itself when the column holds a bare string
  (`jsonb_typeof(error) = 'string'`). An error that is only `{"code": 42}` gives `None` rather than
  an empty sentence. `STEP_ERROR_CHARACTERS` holds the 200.
- **Tenant-filtered**: another tenant's record returns `[]`, not a row.
- The rows come back as a `StepEventRow` dataclass (frozen: `step_id`, `attempt`, `started_at`,
  `ended_at`, `outcome`, `error`), defined at the end of `reads.py` because `models.py` was out of
  the ticket's file list. `packages/ledger/__init__.py` exports both functions and the type.

Both edits to `reads.py` are additions: 77 lines added, 0 removed (`git diff --numstat`).

## 2. The route

`GET /api/v1/runs/{run_id}/records/{record_id}/steps` answers:

```json
[{"step_id": "type-email", "step_name": "Email", "attempt": 1, "outcome": "ok",
  "seconds": 0.4, "error": null}]
```

- **`step_name`** comes from the run's pinned recipe version: `_step_names` walks `steps` and every
  `then` / `else` / `steps` list (the same keys `services/api/recipes.py` already uses), so a step
  inside a branch is named too. A step with no `name` of its own falls back to its id.
- **`seconds`** is `ended - started` rounded to a tenth, or `null` while the step has no end.
- **404** when the run does not exist, when the record does not exist, when the record is not in
  that run, or when the record's tenant is not the run's. A row with no steps is `200 []`, which is
  different from "no such row" on purpose.

## 3. The page (`RunDetail.tsx`)

Every row gets a **Show steps** button under it (a `tr.row-steps` with `colSpan={4}`, so the table's
shape and the 400 px layout are unchanged). It is closed by default, and the request happens only
while it is open: `useJson(open ? path : null, open ? pollMs : null)`.

Each step is one line: its name, its outcome in a plain word (`done`, `skipped`, `stopped here`,
`tried again`), its time (`0.4 s`, or `going` while it has no end), and `tried 2 times` when the
attempt is more than one. The step that stopped the row shows the sentence the runner gave it, on
its own line.

Because the interval is the page's own, an expanded row on a running run refreshes every two
seconds -- which is the execution monitor's live view, with no second polling scheme.

`apps/web/src/lib/words.ts` gained `stepOutcomeWords`, `stepSecondsWords` and `stepAttemptsWords`,
appended at the end (28 lines added, 0 removed). The styling is in `runs.css` only.

## Notes for T1

- **The `reads.py` import block.** `reads.py` did not import `dataclass` or `datetime`, and the
  file is append-only for this ticket, so the two imports sit at the end of the file with
  `# noqa: E402`. `ruff` accepts it; if you would rather have them at the top after the merge, it
  is a two-line move.
- **`StepEventRow` lives in `reads.py`** for the same reason (`models.py` was not in the file
  list). Moving it to `models.py` later changes one import.
- **A row's steps and its state can disagree**, by design: `step_events` is what the executor did,
  and a row that was re-queued keeps the steps of its earlier attempt. That is what a person
  debugging the row needs to see.
- **Screenshots** were out of scope, as the ticket says; `screenshot_key` is not read.
- **Not verified by me:** no browser. The 400 px layout is CSS plus the testing-library pass, not a
