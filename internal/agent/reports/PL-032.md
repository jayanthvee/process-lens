# PL-032 report (T1): the owner's Odoo quick-create replays

**Status:** done.

## The problem

The owner's second recording (`odoo_quick_create_owner_tab.json`, sanitized) did not replay. It made a lead from
the CRM kanban's quick-create card. Three things went wrong:

1. **The contact was never filled.** The owner typed the contact and pressed Tab, and Odoo's suggestion box
   committed the match. The replay sent Tab before any suggestions had loaded.
2. **Two steps were noise.** A "Start typing…" hint option was clicked before anything was typed, and a Tab only
   moved focus.
3. **The save check could never pass.** A quick-create save changes no URL and shows no message.
   - The first attempt waited for the email, which the card never shows.
   - The second attempt waited for the contact's name, which is already on screen in the form being filled. The
     runner's pre-commit probe then parked the row as "already present".

## The changes

1. **A compiler pass, `_settle_suggestion_boxes`**, runs right after `_fold_retried_fills`. It has three rules:
   - **Hint options are dropped.** An option click with no fill since the last pick is a hint.
   - **A Tab after a typed entry becomes a pick.** When a combobox fill is followed by Tab and no option click, the
     Tab becomes a click on an option, with two rungs: the exact name `{{row.col}}`, then `Create "{{row.col}}"`. An
     existing record is picked, and a new one is created.
   - **Focus-only Tabs are dropped.** A Tab whose element has no role, or a generic one, is dropped.
2. **A new condition, `text_count_increases`.**
   - **In the extension** (`assertions.ts`), the condition counts the text in `innerText`:
     - the first evaluation stores a baseline in `window.__processLensCounts`;
     - a lower count lowers the baseline;
     - the condition passes once the count rises above the baseline, then forgets it;
     - a reload loses the baseline, so the check fails closed.
   - **No runner or protocol change.** The pre-commit probe sets the baseline, and the post-commit check sees the
     new card.
   - **Wired through:** the schema, `OBSERVATION_KEYS`, `_render_condition`, and the dashboard's step text ("the
     new item appears").
3. **The save check picks the new condition.** When a commit has no other evidence, `_infer_assertion_from_fills`
   now gives `text_count_increases` on the first templated fill.

## Verified

- **Unit tests:**
  - compiler and API: 178 passed;

- **Real Odoo:** the owner's Tab recording replayed on two rows.
  - The new contact, "Probe Fresh Contact", was created through `Create "…"`.
  - The existing contact, "Probe Known Contact", picked the partner that was already there; no duplicate was made.
  - Both rows were verified by the count check. In Odoo, each lead has the right partner, email, phone and
    revenue, and the opportunity name auto-filled.
- **The full e2e suite:** 20 passed. Only the 2 known widget tests failed, `test_widget_shadow_form` and
  `test_widget_iframe_form` (PL-018b).

## Known limits

- **The exact-name rung** picks the first option whose name matches. Two partners with the same name are
  ambiguous.
- **`text_count_increases` counts text anywhere on the page.** An unrelated element changing the count at the same
  moment could pass the check falsely. That would take a concurrent change during the commit window, which is
  unlikely on a single-user form.
