## What landed

1. **One image** — root `Dockerfile`, multi-stage:
   - a Node 22 slim stage runs `npm ci` + `vite build` for `apps/web` (so `apps/web/dist`
     exists, which `services/api/main.py` mounts at `WEB_DIST` — the layout `/app/apps/web/dist`
     matches its `parents[2]` lookup);
   - a Python 3.12 slim stage installs the project from `pyproject.toml` (no dev extras — no
     Playwright, no browsers), copies only what runs (`services/`, `packages/`, `db/`,
     `scripts/`, `apps/web/dist`), runs as non-root user `processlens` (uid 10001), and honours
     `PORT` (Railway sets it; the image defaults to 8000). `PYTHONPATH=/app` carries the
     `packages/` tree, which setuptools does not package but the services import.
   - `.dockerignore` leaves out `.venv`, `node_modules`, `.cache`, `.worktrees`, `.data`,
     `private/`, `internal/`, `tests/`, `fixtures/`, `.env*` (plus `.git`, `__pycache__`,
     `apps/extension`, `apps/demo-crm`, `infra`, `tools`, egg-info). The root
     `docker-compose.yml` was not touched, and is excluded from the build context.
2. **Two start commands, no demo script** — `services/deploy.py` (new):
   - `python -m services.deploy api`: `DATABASE_URL` + `PROCESSLENS_RUNNER_SECRET` +
     `PROCESSLENS_EXTENSION_ID` required (an unset extension id accepts no extension origin —
     `services/api/middleware.py` refuses every request), then `db.migrate.apply_migrations`
     (idempotent), then the operator row, then `uvicorn` on `0.0.0.0:$PORT`. Nothing is built.
   - `python -m services.deploy supervisor`: the demo's watch loop, moved: the pure decision
     (`worker_decision`, `status_lines`, `State`, `START`/`WAIT`, `waiting_run_id`) and the loop
     helpers (`open_runs`, `stop_process`) live here now, and `scripts/demo.py` imports them —
     `demo.worker_decision is deploy.worker_decision` is asserted in the new tests, and
     tests/demo passes unchanged (34/34 across both files). The supervisor reads
     `DATABASE_URL` and `PROCESSLENS_API_URL` (new, required) and **never binds a port** (asserted).
   - A missing required setting stops start-up with one plain line naming the variable, exit 1.
     No defaults point at localhost: the API binds `0.0.0.0`, and there is no localhost URL
     anywhere in deploy mode.
   - **Secrets:** the runner secret comes only from `PROCESSLENS_RUNNER_SECRET`; deploy.py does
     not import `secrets` at all (asserted), generates nothing, writes no files. The demo keeps
     its local `secrets.token_urlsafe` path in `scripts/demo.py`.
   - The worker subprocess gets the hub address via `hub_ws_url` (`https://`→`wss://`,
     `http://`→`ws://`), the same rewrite the extension's `socketBase` does.
   - One behavioural note: the deploy operator row is created idempotently (reuse by tenant name
     + email), and the demo's `ensure_operator` now calls the same row function — its stored-
     operator semantics (reuse only while the `users` row exists) are unchanged.
3. **Railway config and runbook** — `railway.json` for the **api** service (Dockerfile builder,
   start command `python -m services.deploy api`, healthcheck `/health`, ON_FAILURE restart).
   Railway's per-service config file cannot declare a second service, so the **supervisor**
   service is documented in `internal/docs/DEPLOY.md` (same repo, same image, custom start
   command `python -m services.deploy supervisor`, no public domain). The runbook is one page,
   numbered: project → Postgres (`DATABASE_URL` as a reference to the plugin variable) → both
   services → variables table (name, what it is, example, required, which service) → deploy →
   `/health` → pointing the extension at the public URL.

## The socketBase finding (asked for in the ticket)

`socketBase` (`apps/extension/src/background/command-session.ts:148-149`) is
`trimBase(hubUrl).replace(/^http:/i, "ws:").replace(/^https:/i, "wss:")`, applied before dialing
`/api/v1/executor/ws` (line 367). So an `https://` public domain yields `wss://` automatically;
**nothing needs to change** for WebSockets through Railway. The supervisor's worker starts use
the same rewrite (`services.deploy.hub_ws_url`), so the runner and the popup agree.
