## S1. A code page that arrives late is noticed while teaching

**Changed.** New `apps/extension/src/content/code-watch.ts`: `watchCodePage` looks for a code page
a settle (300 ms) after the page's last change, keeps looking while the page keeps changing, gives
up 15 s after the last recorded action, and stops at the first code page found (`teachCode.attempted`
is the stop signal, so one page is asked about once). The Gmail lookup's `since` is now
`lastActionAt() - 30 s`, not the moment of the probe: a code email that arrived before the site
finished rendering is still found. `recorder.ts` replaces the single 250 ms probe
(`TEACH_CODE_SETTLE_MS` is gone) with `watchCode()` on every recorded action, on attach, on
`visibilitychange`, and on the panel's yes.

**Proved by** `apps/extension/tests/pl113-late-code-page.test.ts` (written first; it failed on
`Failed to resolve import "../src/content/code-watch"`):
- `is found 1.5 s later, and the code is asked for once` -- six "Digit N of 6" boxes rendered
  1.5 s after the click, no further action: the probe finds them and `ask` is called once with
  `since: T0 - 30_000`.
- `keeps looking while the page is still changing, and stops after 15 s` -- five changes over 10 s,
  then the boxes: found; a change after the 15 s window is not probed.
- `does not ask twice for the same code page`.
- `is what the recorder runs after an action` -- the recorder contains `watchCodePage(` and no
  longer contains `TEACH_CODE_SETTLE_MS`.

## S2. A sign-in is Done only when the person is signed in

**Changed.**
- `packages/compiler`: `CompileOptions.sign_in` / `sign_in_after_path`, and a last step
  `{"id": "sign-in-finished", "action": "wait_for", "condition": {"url_matches": <landing>},
  "timeout_ms": 90000}`. `assertions.sign_in_landing_pattern` builds the pattern from the landing
  page's own path (`/home` matches `/home` and `/home/inbox`, not `/login` or `/homework`). A
  sign-in with no landing page compiles no wait and says so in the warnings.
- `services/runner/run_loop.py`: `wait_for` is a real step. It enters `filling`, renders and checks
  its condition with the step's own timeout, drains events (so a code page raises PL-102's
  `code_required` and the code is read from email exactly as before), records the step event, and
  on a failed check parks with `describe_wait_failure` -- `Sign-in didn't finish: <what the check
  never saw>`. It never verifies a row.
- `apps/extension/src/background/sign-in.ts`: `noteSignInPage` records the page the code was asked
  on and then the first *different* page -- the landing page. `service-worker.ts` calls it on
  `record:code-from-email`, on `record:event` and on `record:pending-observation`, so a page loaded
  right after the code is caught even when the person stops immediately. Both are page addresses;
  no code is stored.
- `services/api/compile.py` + `apps/web/src/panel/PanelTeach.tsx`: the compile request carries
  `sign_in` and `sign_in_after_path`.

**Proved by**
- `packages/compiler/tests/test_pl113_sign_in_wait.py` -- the last step is the wait, with 90 s and
  the landing pattern; the pattern matches the landing page and not the sign-in page; a sign-in
  with no landing page adds no wait and warns; a non-sign-in recording gets no wait.
- `tests/runner/test_pl113_sign_in_runner.py` -- a row that reaches the landing page is `verified`
  with reason `done`; a row that never leaves the code page **parks** with a reason starting
  `Sign-in didn't finish:`; a `code_required` event raised while the wait is being checked is
  answered by exactly one `code_from_email` call and the row still ends `verified`.
- `apps/extension/tests/pl113-sign-in-landing.test.ts` -- the landing page is recorded once, stays
  put on later pages, is not the code page, is cleared with the recording, and the worker is wired
  to it.
- `apps/web/tests/pl113SignInWait.test.tsx` -- the panel's compile request carries
  `sign_in: true` and `sign_in_after_path: "https://app.example.test/home"`. This test was written
  after the panel edit; run against the stashed panel it fails with `expected { recording: [...] }
  to match object { sign_in: true }`, which is the failure recorded here.

## S3. A blocked click says what blocked it; a busy button is not a covered one

**Changed.**
- `apps/extension/src/executor/ladder.ts` (`measureTargetInPage`):
  - a target that is `disabled`, `aria-disabled`, `aria-busy`, or `pointer-events: none` is reported
    as `the target is busy (<why>)` -- checked *before* the coverage sentence, because the point
    passes through such a control and lands on the card behind it;
  - a hit test that finds nothing scrolls the nearest scrollable ancestor and measures again;
    still nothing gives `the target is outside the window and the page didn't scroll to it`;
  - a covered target is described by the covering element's own name/text (`<button "Sign up">`) or
    its kind (`<div>`).
- `services/runner/step_words.py`: the click sentence now names each case --
  `Couldn't click “X”: it was covered by “Sign up”` / `… it was covered by a div` /
  `… the button is outside the window and the page didn't scroll to it` / `… the button was busy`.
- `services/runner/run_loop.py`: a busy prepare whose step's own `assert_after` passes ends the row
  `verified` with reason `the page did it by itself` instead of parking. **Limit:** nothing was
  pressed, so this path writes no `committed_keys` row; a later identical row is not skipped as a
  duplicate. Flagged for T1.
- `packages/ledger/reads.py` + `services/api/runs.py`: `GET /runs/{id}/records` returns
  `last_step_error`, the latest step event's own error for that record.

**Proved by**
- `apps/extension/tests/pl113-click-blockers.test.ts` (real DOM, `installLayout`) -- the two causes
  of the ticket:
  1. a button that goes `disabled` + `aria-busy` + `pointer-events: none` and whose point lands on
     the card behind it: **reported `covered by <div>` before the fix**, `busy` after;
  2. a `height: 100vh; overflow: hidden` shell with its own scrolling panel and the button below the
     window: **`ok: false` before the fix** (hit test found nothing), `ok: true` after, and the panel
     actually scrolled.
  A third test pins the outside-the-window sentence when there is nothing to scroll.
- `tests/runner/test_pl113_click_words.py` -- the four sentences.
- `tests/runner/test_pl113_busy_click.py` -- a busy save whose check passes is `verified` ("the page
  did it by itself"); one whose check fails parks with
  `Couldn't click “Save”: the button was busy`; the raw error is kept on the step event.
- `tests/api/test_pl113_step_error.py` -- `last_step_error` is returned, is `null` with no failed
  step, and the latest error wins.

**Both** of the ticket's two likely causes are reproduced by these tests; cause 1 was the one that
produced the "something was in front of it" sentence with an element that was not covering anything.

**Half-width window (asked for in the ticket).** No site-name check was possible without a browser,
which the ticket forbids, and the fixtures are synthetic. What the code does about width is
geometric and width-independent: the hit test is at the box centre, and the new ancestor scroll
handles a target outside the *window* whatever the window's width. A layout that reflows at half
width into a single column and pushes a button below the fold is exactly the case cause 2 fixes; a
layout whose own panel scrolls instead is also cause 2. Nothing here was checked against a live
`height: 100vh` app.

## 1. Done means the change is on the page (blocking)

**Changed.** `packages/compiler/compiler.py` gains `_chrome_names` / `_is_chrome_assertion`: a
commit assertion of `text_visible` whose text is the recorded name of a tab, link, menu item or tree
node in the same recording is refused, in plain words ("… it is there whether or not the change was
saved … re-record the save with a check that shows the change"). The runner's existing guarantees
were pinned rather than changed: a confirmation already on the page parks
(`the confirmation was already on the page before saving`), and a read-back that does not hold is
never verified. The recipe schema already refuses a commit with no `assert_after` at run creation
(`CreationError`), so a commit with no proof cannot reach a run.

**Proved by**
- `packages/compiler/tests/test_pl113_true_done.py` -- a save whose only "confirmation" is the Sales
  tab's own label is refused, with the frame sentence and a re-record instruction.
- `tests/runner/test_pl113_done_runner.py` -- typed 799 with the page still showing 910 after the
  save: never `verified`, and the `save` step event is `failed`; a read-back that holds is
  `verified`; a check that already held before the step parks with the freshness reason.

**Not done.** The compiler does not yet *infer* a `value_equals` read-back for an edit (field
changed, then saved or left). The runner honours `value_equals` when a recipe carries it and the
extension evaluates it, but a recording of an in-place edit still gets its assertion from the
observation/navigation rules, so an edit with no confirmation can still compile with a weaker check
than the ticket asks for. This is the largest gap in item 1.

## 2. Never take a tab, a heading or a menu as the save

**Changed.** `apps/extension/src/popup/make-recipe.ts`: `CHROME_ROLES` (tab, link, menuitem,

**Proved by** `apps/extension/tests/pl113-save-default.test.ts` (written first; it failed with the

choices; a real Save click still is the default.

**Not done.** The ticket's third choice, **"The app saves by itself when I leave the page"**, and

item 1 read-back) are not implemented. The panel says the sentence and offers the recorded clicks
and "Nothing gets saved"; it does not yet offer that third answer.
