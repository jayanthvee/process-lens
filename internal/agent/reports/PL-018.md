## 1. What was built (the ticket's requirements)

1. **State-diff recording.** `apps/extension/src/content/snapshot.ts` (new) takes one bounded pass
   over the page's editable state (inputs, textareas, selects, contenteditable roots, `role=textbox`
   with `aria-multiline`, labelled chip lists, open shadow roots, same-origin iframes), never reads
   a password or credential context, and `diffSnapshot` reports what changed. The recorder
   checkpoints before every recorded click (pointerdown + click, one checkpoint per gesture), key
   press, submit, navigation and stop, and emits the diff first, so the order bug — a click recorded
   before the typing that produced it — cannot occur. The first checkpoint is the baseline; a field
   that changed and changed back emits nothing.
2. **The `press` action.** `packages/recipe/schema/recipe.schema.json` gains `$defs/step_press`
   (`key` ∈ Enter, Tab, Escape, Backspace, Delete, Control+Enter, Meta+Enter; `commit` and
   `assert_after` absent by construction); the recorder listens on `keydown` and emits press steps
   for keys that are not mere typing; the compiler's `ACTIONABLE_KINDS`/`STEP_ACTIONS` learn `press`;
   the executor performs it through CDP (`Input.dispatchKeyEvent`, keyDown + keyUp, through the
   PL-017b input gate); `EXECUTOR_ACTIONS` in `services/runner/creation.py` gains `"press"` (the one
   runner touch, approved by T1).
3. **Autocomplete / chip folding.** The recorder witnesses the relationship and carries it on the
   envelope (`chip`, `autocomplete`, `supersedes`); the compiler folds the typed prefix and the accept
   into one `fill` of the chip's value (the address, never the display name); the popup's
   `recordedValues` applies the same rule, so the sample row and record key offer the address. On
   replay, a fill the recorder witnessed as an autocomplete is completed by containment: type the
   value, find the single suggestion whose text contains it, accept it. The accept is a click through
   the PL-017b guarded path; `Enter` is allowed only when the widget's `aria-activedescendant` is
   that single option; otherwise the step parks.
4. **Step-id reset.** `shouldResetStepIds` (recorder.ts) restarts the counter when the worker says a
   new recording started, and when a clear empties the recording; covered by `recorder-session.test.ts`.
5. **Weak observations dropped.** `packages/compiler/assertions.py` refuses "Loading…", "Saving…",
   ellipsis-only text and any observation read while the node was busy as commit evidence; covered by
   `packages/compiler/tests/test_pl018.py`.
6. **The widget corpus.** `fixtures/sites/widget-corpus/` — eight pages (Gmail-style compose, plain
   editor, framework editor, React-style autocomplete, open shadow form, same-origin iframe form,
   chip-removal + Ctrl+Enter refusal page, 1000-field perf page), a handshake server, a store, and a
   standalone `selftest.py`.
7. **R1 (key-commit refusal).** The compiler refuses a recording whose last actionable event is
   `press(Enter|Control+Enter|Meta+Enter)`, or whose named commit step is a press, with the message
   "The save or send was done with a key. Re-record it by clicking the button (for example Send)."
8. **R2 (unreplayable chip removal).** A chip that vanished with no remove control clicked since the
   previous checkpoint is marked `unrecordable`; the compile refuses with "A recipient was removed in
   a way that can't be replayed (no remove button). Re-record it using the ✕, or don't remove
   recipients during the recording."
9. **D-020.** A new entry in `internal/docs/DECISIONS.md` records the recording-first order and
   restates the layer numbering (AI suggestions and summary PL-019, verification PL-020, self-healing
   PL-021), superseding that part of D-019; D-019 itself is untouched.

### The e2e budget, spent in full, reported as it shows

Four scoped runs and the one full suite were used. **All five failed, and the failures drove the last
four commits.** No further e2e run was made: the ticket's budget is exhausted, so the remaining
checks stop here for T1.

**Golden run 1 (of 2).** Recorded the ticket's demonstration; the recording was right — the typed
prefix, the `press(Enter)`, the chip's address and the body's text were all in it — but
`wait_for_observation` returned `None`:

```
E       AssertionError: the Send's confirmation was never recorded
E       assert None
```

Cause: the toast is pre-rendered (`hidden`) in the page's markup, and the observation window skipped
every confirmation node that was already in the document. **Fix (committed):** `isShown` — a node is
"already showing" only when its text is non-empty and nothing on its ancestor chain hides it, so a
pre-rendered status element's reveal (or its first text) is evidence. Unit tests added.

**Golden run 2 (of 2).** The compile refused to fold the accept:

```
E       AssertionError: an autocomplete accept must fold away, not stay a press:
E       [{'action': 'press', 'id': 'press-1', 'key': 'Enter', ...}]
```

Cause: the recorder mints the superseded fill's id from the page's own counter (`fill-2`) and the
worker re-stamps every stored step per action (`fill-1`), so the envelope's `supersedes` pointed at
an id no stored event carried. **Fix (committed):** `RecorderSession` keeps the provisional→stored id
map and translates `supersedes` on append; the chip fill also carries `autocomplete` onto the
rendered step so the executor completes it. Unit test added.

**Corpus run 1 (of 2).** The Make recipe button stayed disabled:

```
E           playwright._impl._errors.TimeoutError: Page.click: Timeout 30000ms exceeded.
E             - locator resolved to <button disabled id="make-go" ...>
```

Cause: a free-text widget's value is not email-shaped, so the popup chose no record key and the form
refused to submit. **Fix (test-side):** the corpus test picks the first key column, as a person would.

**Corpus run 2 (of 2).** Five failures, every widget refused at compile time with the same class of
problem:

```
E       AssertionError: Plain editor: the Make recipe form could not compile the recording:
E       result='Could not make a recipe (1 problem).'
E       warnings='commit step click-1 has no assert_after: ...'
... (the same for framework-editor, react-autocomplete, shadow-form)
```

Causes, each fixed after the run and verified offline (unit tests only — the budget was gone):

1. Every corpus widget keeps its confirmation pre-rendered (`hidden`), so no observation was
   recorded and the commit click had nothing to assert. Fixed by the same `isShown` rule as above.
2. The React-style widget accepts **by click**, and the recorded option click was never folded into
   the chip, so the accept stood as its own click (and a replay would accept twice). **Fix

   ticket's "by click, key or paste" — with a negative test that an ordinary click is not consumed.
3. Shadow form: a key/input event inside a shadow root is retargeted to the host, so the person's
   typing was credited to the host (and the click on the host was recorded as a step). **Fix

4. Iframe form: the test waited on the parent's status element, which the framed page's save does not
