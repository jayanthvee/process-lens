# PL-072 — A Word document becomes a clean CSV (and a run's input)

Code commit `dec6d52`; this report is the second commit.

## What was built

**Reader — `packages/documents/docx_table.py` (new).** `read_docx(bytes)` turns a `.docx` into
`(columns, rows)` and tries three shapes in the ticket's order:

- a table: the largest table that has a non-empty first row and at least one row under it (equal
  sizes keep the first), with merged cells repeated into every grid cell they cover and a header
  split across two rows joined (`Contact` + `Name` → `Contact Name`);
- repeated `Label: value` blocks, separated by blank paragraphs or headings; each block is one row,
  labels in first-appearance order, missing labels become empty strings;
- the longest bulleted/numbered list, one column named from the nearest heading above it, or
  `Item` when there is none.

Anything else raises `NoReadableContent("This document has no table or list ProcessLens can read.")`.
A non-`.docx` upload raises `NotAWordDocument("This file is not a Word document.")`. The file is
opened only after checking that it is a zip containing `word/document.xml`; python-docx reads the
package's own parts, and no macro, external link or embedded object is executed or followed.

**Cleaner — `packages/documents/clean.py` (new).** `clean(columns, rows) -> (columns, rows, notes)`
is pure and deterministic:

- headers trimmed, empty ones named `Column N`, duplicates numbered (`Email`, `Email 2`);
- cells: whitespace collapsed, NBSP / zero-width removed, smart quotes made plain, emails
  lower-cased, phones trimmed but not reformatted, ISO and unambiguous written dates
  (`12 March 2026`, `March 12, 2026`, `12 Mar 2026`) written `YYYY-MM-DD`, ambiguous
  slash/dash dates left as typed and counted, numbers with thousands separators untouched;
- fully empty rows dropped and counted, exact duplicate rows (after cleaning) dropped and counted;
- notes are the plain sentences `Removed 2 empty rows`, `Removed 1 duplicate row`,
  `3 dates were ambiguous and left as typed`.

`csv_bytes(columns, rows)` writes the full table with `csv.writer`, UTF-8 with a BOM.

**API — `services/api/documents.py` (new), registered in `services/api/main.py`.**

- `POST /api/v1/documents/to-csv` reads a `.docx` (5 MB limit), answers
  `{columns, rows (first 50), notes, csv_token}`.
- `GET /api/v1/documents/to-csv/{token}.csv` answers the full cleaned CSV (UTF-8 BOM), or 404 once
  the hour-long token has expired. Tokens live only in memory and are never logged by this code.
- `services/api/batches.py`: `POST /api/v1/batches` now also accepts `.docx`, runs the same reader
  and cleaner, stores the batch as `kind = "csv"` with the cleaned rows, and returns the notes in
  the upload response. CSV/XLSX behaviour is unchanged; the response gains `notes: []`.

**Web — `apps/web/src/pages/Spreadsheets.tsx`, `spreadsheets.css`, `words.ts`.** The page gains an
"Add a Word document" panel: choose a `.docx`, see the first rows and the notes, then
**Download CSV** (the token's full file) or **Use for a task** (the existing `/tasks` pick-a-task
screen). The panel is shown on the empty, loading and populated page, so a document can be added
before any spreadsheet exists. Copy lives in `words.ts`; the panel uses the existing light theme,
gold primary button and quiet secondary button, and the existing table styles.

**Fixtures — `fixtures/documents/`.** `make_fixtures.py` generates five committed documents:
`clean-table.docx`, `merged-header.docx`, `label-blocks.docx`, `bulleted-list.docx`,
`no-table.docx`.

## Decisions and deviations

- **The preview upload is JSON with base64, not multipart.** The front door
  (`services/api/middleware.py`) accepts `multipart/form-data` only on `POST /api/v1/batches`, and
  this ticket's file list does not include `middleware.py`. The new route therefore takes
  `{file_name, content_base64}`; the page reads the chosen file with `FileReader`. The batch route
  keeps its normal multipart upload because that path is already allowed.
- **`Use for a task` opens `/tasks` rather than carrying the file.** The existing run flow lives in
  `apps/web/src/pages/TaskRun.tsx`, which is outside the ticket's file list and starts by asking
  for a file. The person downloads the cleaned CSV and adds it on the task's run page; the button is
  the ticket's "continues into the existing pick-a-task flow" and nothing more.
- **The Spreadsheets page had no add area on this branch,** so the ticket's "takes `.docx` as well"
  is a new area that takes `.docx`; CSV/XLSX uploads still start from a task's run page.
- **Two-row header detection is a heuristic:** a horizontal merge in the first row, or a first row
  with an empty cell whose second row is fully filled. A normal data table whose first row has one
  blank cell and whose second row is full could be read as a two-row header.
- **Dates are rewritten only when the whole cell is a date.** A date embedded in a sentence is left
  as typed. This is deliberate: rewriting text around a date risks corrupting it.
- **The token is in the download URL, as the ticket specifies.** Application code never logs it,
  but a deployment's access log (e.g. uvicorn's) records request paths, so the token can appear
  there. The token is single-purpose, expires in an hour, and gives access to a cleaned CSV only.

## Residual risks

- The one-hour token store is per process; a restart loses un-downloaded CSVs (accepted by the
  ticket's "in memory or in `.data/`").
- The base64 request body is decoded only after a length check, but the JSON body itself is read by
  the framework before the route; a very large request is bounded by the 5 MB decoded check, not by
  a request-body limit.
- `TaskRun.tsx`'s picker still lists `.csv`/`.xlsx` only; changing it was out of scope.
- The cleaner's duplicate check is exact after normalisation, so rows differing only in a phone
  number's formatting or an ambiguous date are kept, not merged.
