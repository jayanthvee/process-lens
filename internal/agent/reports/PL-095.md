## Interpretation notes (not deviations from the ticket's scope)

- **When the file's column name is kept as the task's wording.** `_duplicate_label` uses the
  mapped spreadsheet column unless its normalised name equals the task column's own name; then it
  falls back to the task column's label. Without that carve-out, a file header `Email` for task
  column `email` would read `Same Email as row 1`, and the frozen
  `tests/api/test_batches_api.py:762` expects `Same email as row 1`. The ticket's own example
  (`search` → `SKU`) is a genuinely different name, so the carve-out does not touch it. The "No …"
  reason is untouched and still names the task column (`No sku`, `No email`).
- **One definition of a number, used twice.** `_number_value` is the single definition for both
  "is this example a number" and "is this value a number", so a value like `+5.00` in a number
  column is flagged (`isn't a number`) exactly as the ticket's kind rule excludes a leading `+`.
- **Shape matching ranks as `close` (2),** the same rank a synonym or token-overlap match gets.
  On a tie, file order decides, as it already did before this change.

## Known limits of the heuristic (ticket-scoped, none exercised by the tests)

- A number column whose value has more than 6 digits and no decimal point is flagged
  (`1,232,000` → `isn't a number`), because the ticket makes such a run a phone or an ID. The
  same rule keeps a real phone column from being judged.
- Shape matching is coarse by design: `192.00` and `349.00` are both `9.9`, so a number column can
  match another number column when no name or value settles it. A text example like `Ruiz Hermanos`
  is `A A`, the same shape as `Sam Lee`, so when two file columns are name-close and shape-close to
  different task columns the tie is broken by file order — the ticket puts the shape rule before
  the synonym and token rules, so it ranks at the same `close` (2). The guess is only a starting
  point: the person sees it on the check page, and a saved mapping always wins.
- A price column taught with `349.00` flags a value like `1 232` (internal space) or `+5`; both
  are the ticket's own exclusions.

## Independent review

An adversarial read-only review (Claude Sonnet, fresh context) returned **BLOCK** on one claimed
MAJOR: that `_number_value` raises `decimal.InvalidOperation` on Unicode decimal digits
(Arabic-Indic `٣٤٥`, Devanagari `१२३`, Thai `๑๒๓`) because `_NUMBER` is compiled without `re.ASCII`
while `\d` matches every Unicode decimal character, and so a non-Latin spreadsheet would 500 at
`GET /batches/{id}/check`.

The finding did not survive checking. CPython's `Decimal` converts Unicode decimal digits to ASCII
before parsing (`PyUnicode_TransformDecimalAndSpaceToASCII`), so the call returns a value rather
than raising. Run directly against the module:

```
'٣٤٥' -> 345
'१२३' -> 123
'๑๒๓' -> 123
_number_value('٣٤٥') -> 345        # no exception
_kind_reasons(number column, '٣٤٥') -> []
```

That is the right behaviour for the ticket: a price written in Arabic-Indic numerals is a number,
not a value to flag. `tests/api/test_batches_check_helpers.py` now pins it, so a later change
cannot turn it into a crash or a false flag. The reviewer's own caveat explains the miss — its
shell could not run `python.exe`, so its findings were trace-only and it labelled this one
"traced, not reproduced". Its secondary note (that `_shape` maps such digits to `9`, the same class
as ASCII digits) is accurate and harmless: it makes a numeric column match a numeric column, which
is the point of the shape rule.

The review found nothing else: it traced the six-digit boundary, internal spaces, a leading `+`,
`.5`/`5.`/`--5`, malformed comma grouping, `€1.234,56`, the shape-rule regression path, the
`Same email as row 1` wording, blank-value skipping, unmapped columns, and double-reporting as
clean.
