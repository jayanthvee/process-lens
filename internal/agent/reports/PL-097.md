# Report PL-097

Status: done (T2) · Branch `pl-097` · Reviewer: T1

## Summary

A row that stops on a step now says why in words a person can act on, instead of showing the
extension's own diagnosis. `services/runner/step_words.py` turns the step, the row and the raw
error into one sentence in `check_words.py`'s style: pure, no database, no browser. The run loop
uses it for a simple step that failed and for a commit whose target could not be resolved; the
step event keeps the extension's raw `error` unchanged, so debugging loses nothing.

The pilot's three cases now read:

- `“Priya Ramen” isn't in the Salesperson list`
- `No salesperson in this row`
- `The page changed the name as it was typed; check the row's name`

## Files changed

- `services/runner/step_words.py` (new): `describe_step_failure(step, row, variables, error)`.
  Situation order is most specific first:

  | Situation | Sentence |
  |---|---|
  | a fill whose value rendered empty | `No <column> in this row` |
  | a fill that did not stick | `The page changed the <column> as it was typed; check the row's <column>` |
  | a click on a `role: option` rung templated from a row column, failed to resolve or covered | `“<value>” isn't in the <Column> list` |
  | any other click that was covered / not clickable | `Couldn't click “<element>”: something was in front of it` |
  | any other target not found | `Couldn't find “<element>” on the page` |
  | anything else | `Step “<name>” didn't finish: <error>` |
  | no error | `Step “<name>” didn't finish` |

  Every sentence is clipped to `check_words.MAX_SENTENCE` (160) with `…`. Where a row's own value
  is in the sentence (the option's value, the element's name), the value is cut and the
  finding is kept whole, as `check_words._with_value` does: a 300-character salesperson still
  reads `“PPPPP…” isn't in the Salesperson list` rather than losing the list's name.
  `<column>` is `step["value"]["column"]` through the same
  `_label` spelling `services/api/batches.py` uses (`salesperson` → `Salesperson`), lower-cased in
  the middle of a sentence. `<element>` is the first `role` rung's `name`, else the step's `name`
  with its leading `Click `/`Fill ` removed. Templates are rendered with
  `services.runner.templates.render`; one that does not render stays literal, as
  `check_words._text` does.
- `services/runner/run_loop.py`: `_simple_step`'s failed path and `_commit_step`'s
  `prepared.status != "ok"` path pass the record's **reason** through `describe_step_failure(...)`.
  Both still pass `error=result.error` / `error=prepared.error` to `_transition`, so the step event
  keeps the raw diagnostic. The `refused` path is untouched: a guard's own words still say what it
  refused, which is a different fact from "the step tried and failed".
- `services/runner/testing.py`: one new `FakeExecutor` plan behavior, `not_clickable`, returning
  `status="locator_failed"` with the extension's real covered-target message (exported as
  `NOT_CLICKABLE_ERROR`), so a run-loop test can reproduce the pilot's failure exactly. Existing
  behaviors are unchanged.
- `tests/runner/test_step_failure_words.py` (new): the run-loop test the ticket asks for.
- `internal/agent/reports/PL-097.md`: this report.

`tests/runner/test_step_words.py` was not touched.

## Review

An independent reviewer was given the ticket, the committed spec tests and the diff, and asked to
refute the change: every row of the ticket's table, the refused path, other dependants of the old
reason strings, the cap, runtime safety on a malformed step, and whether the new test proves what
the ticket asks. It returned **PASS** with one finding that was real and is now fixed: a very long
option value was clipped as a whole sentence, so the `isn't in the … list` tail disappeared. The
value is now cut instead of the sentence (`_with_value`), and the cap still holds at 160 with the
tail intact. Its second note — that `_commit_step`'s `prepared.status != "ok"` wiring has unit
coverage of the sentence but no run-loop test of its own — is recorded under "Notes for T1" rather
than expanded on, because the ticket asked for one run-loop test for the covered-option case.

## Notes for T1

- The check on the extension's phrases is a substring match, not a parse: the extension composes
  its message from a locator's own error (`step-runner.ts:955`), so there is no machine-readable
  code to switch on. A step whose error happens to contain "not clickable" gets the covered-target
  sentence. That is the same word-matching contract `check_words.py` already has.
- A commit step that fails to prepare with **no** error text now reads `Step “<name>” didn't
  finish`, where it used to read `the target could not be resolved`. That is the ticket's own
  "no error" row; the run loop no longer invents an error string for a `StepResult` that carries
  none.
- The `is covered` phrase is included beside `covered by` so a message that says "the box center
  is covered" (without "by") still lands on the covered-target sentence.
- Coverage gap, deliberately left: the `_commit_step` path (`prepared.status != "ok"`) is wired
the same way but has no run-loop test of its own. The sentence logic is covered by
  `test_step_words.py` and the wiring is a one-line, identical change to `_simple_step`'s, so it is
  verified by inspection rather than by a test. Say the word and I will add one.
