## Summary
The recipe contract now exists as JSON Schema 2020-12 (`packages/recipe/schema/recipe.schema.json`, format version 1):
meta with the record key, idempotency key, input schema, approval policy and allowed origins; variables; and all
eighteen step types from the design, each with its own required fields. An element is found through an ordered target
ladder (role + name, test id, label, stable CSS, fuzzy text) with container scope and an iframe path; values come from
one of six sources; and `commit: true` requires `assert_after`, so a commit without an assertion cannot be written at
all. A worked example (`create-lead.recipe.json`) validates against it, the specification is
`internal/docs/RECIPE_SPEC.md`, and 115 pytest tests read the shipped schema and example. The branch is pushed and
CI is green on it; the draft pull request "Recipe schema v1" is open as #2.

Requirements 1-7 of the ticket:
- 1 meta: name, when_to_use, input_schema, record_key, idempotency_key, approval_policy, allowed_origins - all seven
  required by the schema; the create/update idempotency split is in the `idempotency_key` description and the spec
  (decision D-012).
- 2 every step type in the design, with its own required fields - the 18 branches, `test_every_design_step_type_has_a_working_shape`
  and `test_the_action_list_matches_the_schema` (the latter reads the schema and fails if an action is added or lost
  without the test list changing).
- 3 target bundles: ordered strategies, container scope, frame path - `targets` (1-5 rungs, unique, ordered),
  `within` per bundle and per rung, `frame` as a path of index or URL steps.
- 4 value sources: input column, constant, rule table, read from page, extracted from a document, AI text (always
  approved) - the six `value_source` branches, with `requires_approval` pinned to `true` on the AI-text branch.
- 5 constitution rule 6 in the schema itself - `commit_assertion_rule` at the step level, plus per-branch
  `commit`/`assert_after` on the four steps that can write.
- 6 `format_version` and migration - `const: 1` at the top level, mapped to `recipe_versions.format_version`; the
  spec's "Versioning and migration" section says how a future version lands (a new schema file plus an explicit
  upcast, never an edit in place).
- 7 undecided things go to a proposal, not the schema - `internal/agent/proposals/P-002-recipe-open-items.md`, led by
  the bounded agent step, plus the AI-text call type, the transform vocabulary, and the `extract`/`classify`
  placement.

## Deviations from the ticket, and why
- **Validation tests were written, although the ticket defers them to a later ticket.** This session's objective names
  them ("write schema validation tests with pytest"), and the acceptance criteria require real validator output, which
  needs a validator. They went to `packages/recipe/tests/` because the project's own test plan puts unit tests next to
  the component they cover. Dropping them is one file plus one `pyproject.toml` line. Generated types (the other half
  of the deferred work) were **not** touched.
- **`pyproject.toml` changed** (outside the ticket's Scope): `jsonschema` in the dev extras and `packages` added to
  `testpaths`. Without the second line a test that is never collected is not a test.
- **The branch was cut from `origin/pl-003`, not from `main`.** `main` (4914d07) still holds only the initial six
  files: PL-002's work is unmerged in pull request #1, and `internal/` only became part of this repository in 2104c3f,
  which is on `pl-003`. RECIPE_SPEC cannot be committed to a tree that does not track `internal/`, so pl-004 stacks on
  the pushed state of pl-003. Consequence: the pull request to `main` shows the stack until #1 merges, and the branch
  carries `internal/agent/tickets/PL-003.md` rather than the renamed `PL-003-SCRAPPED.md` (that rename, bee7fdb, is
  only on the local `pl-003`).
- **Everything was committed on `pl-004` rather than "private, with `git -C internal`".** The two repositories were
  consolidated into one (2104c3f), `internal/.git` no longer exists, and agents must never push to `main`; so the
  specification, the proposal and this report are commits on the branch. Public-page housekeeping was still applied:
  no reference to `internal/`, a ticket id, or the constitution appears in the schema, the example, the tests or
  `pyproject.toml` (checked with a pattern search).
- **`commit` is available on `fill`, `select`, `click`, and `upload_file` only.** A download never changes the
  destination, so it is not a commit step; the choice is pinned by `test_a_step_that_writes_nothing_cannot_commit` and
  listed as an open question in the proposal.
- **Precheck rules live under `meta.input_schema.rules`.** The design demands the rule ("missing email → park") but
  does not say where it sits; the alternative is a top-level section, and it is in the proposal.
- **`transform.op` is not an enum.** The transform vocabulary is closed by decision but never enumerated in the design,
  so the schema constrains it to a name pattern and the vocabulary itself is an open question.
- **Proposal numbered P-002.** P-001 is already reserved for PL-001's architecture review, which is unwritten.
- **Local, gitignored, not part of the deliverable:** the worktree `../process-lens-t1`, `.data/` (bundled
  PostgreSQL 16.2, the gitleaks binary, and the harness scripts whose output is pasted above).
- **Left untouched, for the record:** the root working tree is on `pl-003` with one uncommitted change
  (`docker-compose.yml`: the MinIO image switched to a Chainguard build) that belongs to that thread, and the local
  `pl-003` is one commit ahead of its remote. Work happened in a separate worktree so none of it was disturbed.

## Open questions for the owner or T1
1. **The tests.** Keep `packages/recipe/tests/` here, or move the work to the deferred ticket that also owns generated
   types? If they are kept, `pyproject.toml`'s `testpaths` should stay as it is now.
2. **The commit-capable step set.** Confirm `fill`, `select`, `click`, `upload_file`, or widen it to `navigate` for a
   destination that creates through a URL.
3. **The proposal, item by item.** Especially the bounded agent step (recommended out of v1), whether AI-generated text
   may ever be the value of a commit step, and the initial transform vocabulary that should become an `enum`.
4. **`extract` and `classify` as runner steps.** The schema carries them because the design's step table does, but
   P-001's open question says nothing may call a model between `claimed` and `verified`. Should the validator reject
   them in a batch recipe until that is decided, rather than leaving it to the runner?
5. **`main` is far behind.** Should pull request #1 be merged before this one, so the recipe diff reads as six files
   rather than the whole stack? The draft pull request says plainly that it is stacked.
6. **`end_record` with `failed`.** A recipe step can end a record as `failed` today; the alternative is to leave
   `failed` to the runner's close-out and allow only `verified`, `skipped`, `parked` in a recipe.
