### 2. Re-check the rows the moment a column changes

`apps/web/src/pages/TaskRun.tsx`:

- The shared half of `continueOn()` is now `saveMappingAndCheck(from)`: PUT `/batches/{id}/mapping`,
  then GET the check. `continueOn()` calls it and keeps its old behaviour — save, ask, `setStep(3)`.
- The select's `onChange` records the pick (`editMapping`) and calls `recheckColumns()`, which sends
  the same save-and-ask immediately and stays on step 2. It writes the answer to `confirmed`, so the
  row problems and the "N rows ready · M rows need a look" line refresh under the dropdown.
- **Keeping the pick, and the latest answer only.** The picks live in a ref (`editsNow`) as well as
  in state, so a request started in the same tick as the click reads the pick the person just made,
  not the previous render's. Every save-and-ask — a column's and Continue's — goes through one
  chain (`inAskOrder`), and each step of the chain reads the picks **when it starts**. Two changes
  can therefore never race: the second ask runs after the first, sends the later mapping, and its
  answer lands last, so a slow earlier answer cannot replace a newer one. A failed ask rewinds the
  chain rather than wedging it.
- `asking` is a counter, so "Checking…" stays up until the last queued ask settles.

### 3. Do not guess a column whose values do not fit the field

`services/api/batches.py`:

- New `_fits_kind(kind, raw_rows, column)`: the column's non-blank values are counted against
  `kinds.is_email` / `kinds.number_value`; the column fits when **at most** half fail (so a tie, a
  1-of-2 column, keeps its place and its stray value is still flagged row by row, as the ticket's
  guard requires). Blank cells are ignored here — they belong to the task's own `missing` rule.
- `_match` takes the field's `kind` and the rows, and ranks only the offered columns.
- `_mapping_for` reads the kind from the field's example (`kinds.kind(spec["example"])`) and passes
  it down; `check_batch` passes `raw_rows = [row.raw for row in rows]`, so every row is read, not
  just `row_one`.
- A saved mapping is untouched: `_with_saved` still runs after the guess and still wins.

**One judgement call, flagged for T1.** An exactly-named column is exempt from the fit test: a
spreadsheet column whose normalised name equals the field's (`Email` for `email`) keeps its place
even when most of its values do not fit. Two reasons: the ticket's own example is a column matched
by a *shared word* ("Expected" for `expected_revenue`), not by its exact name; and
`tests/api/test_batches_value_checks.py::test_a_value_that_is_not_an_email_in_an_email_column_is_flagged`
— an existing test the ticket does not list for change — needs exactly that column chosen so its two
bad values are flagged "isn't an email". A literal reading of item 3 would unmap that column and the
existing test would fail, so the exemption is where the two requirements meet. If T1 prefers the
strict reading, the change is one clause in `_match` and that one existing test moves from "flags
two bad values" to "leaves the field Not found".

### 7. "Not found" is a skip, not "needs help"

- `packages/compiler/compiler.py`, `_not_found_branch(value_template, host)`: outcome `skipped`,
  name `Skip a record when the search finds nothing`, reason `Not found in <host>.` (falling back to
  `Not found.` if the URL has no host — no fixture produces that, but a recipe must never carry an
  empty site name). The host comes from `urlsplit(candidates[search_run].url).hostname`, i.e. the
  page the search ran on. The compile warning now says the row is skipped.
- **Ledger untouched.** I traced the claim path (`services/runner/run_loop.py`, `run_record`):
  the precheck moves `claimed → prechecked`, `_run_steps` moves `prechecked → filling` on the first
  executor step, and the search fill/press are executor steps, so the not-found branch can only run
  in `filling` (or `prechecked`, if the search were the first step — it is not, but `prechecked →
  skipped` is legal too). `commit_attempted` is false there, so `filling → skipped` is legal
  (migration 0003, `LEDGER_SPEC`), and `run_loop`'s `end_record` still turns a commit-attempted skip
  into a park (B2).

  I also chased the one shape that could put the record somewhere else: a recording whose
  `commit_step_ids` names a step **before** the search. Compiled, that recipe renders
  `fill(commit) → press → branch → …`, so the branch does sit after a commit. It is unreachable
  rather than illegal: every exit from `_commit_step` is terminal — `verified`, `failed`,
  `reconcile`, or a parked/stopped path, and the function has no `return None` — so a record that
  reaches that commit never goes on to the branch. The branch is dead code on that path, and the
  popup emits one commit step anyway. No ledger change, and nothing to report as a state violation.
- `apps/web/src/lib/words.ts`, `rowOutcome(state, reason?)`: a `skipped` row whose reason starts
  with `Not found in` reads `Skipped`; every other skip keeps `Already there`. Passed at both row
  tables that show a row's outcome — `RunDetail.tsx` and `NeedsHelp.tsx` (the latter is where a
  not-found row would otherwise have appeared). `plainReason` is unchanged and shows the reason as
  written.
- `apps/extension/src/popup/make-recipe.ts`: `PARK_WHEN_NOTHING_FOUND` now holds
  `Skip a row when the search finds nothing` (the constant keeps its name, which is how the ticket
  words the item and how the popup test imports it).
