The run paused on the canary after the first record, and four records never ran at all.

**Why the pass condition is unreachable from a compiled recording, and why the outcome varies.**
A compiled recipe is **linear**: no `input_schema.rules`, no duplicate-search `branch`, no conditional
`end_record`. Two consequences follow, and they are the same root cause:

- A `skipped` record can only be produced by a precheck rule (`then: skip`) or a duplicate-search
  branch reaching `end_record`; neither exists, so nothing can ever be `skipped` (0 in both runs).
- The ledger makes the **first record to reach a commit** the run's *canary*, and a canary that
  parks or fails pauses the whole run `canary_failed` (`run_loop.py:80` `_FAILURE_STATES`,
  `run_loop.py:519-520` the canary, `run_loop.py:229-235` the pause). With the hand-written recipe,
  the existing lead and the no-company row are diverted to `end_record` *before* any commit, so the
  canary is always a fresh lead and the batch reaches 3/1/1 deterministically. A compiled recipe has
  no such diversion: `ana` (the duplicate) and `el` (no company) both reach a commit and both park,
  so whether the run completes or halts at the canary depends on which record the ledger happens to
  claim first — which is **not deterministic** (the ready rows are ordered by `row_index`, but the
  runner's claim order is not). The same recording therefore yields 3/0/2 or a `canary_failed` halt
  with four pending, run to run.

**Traces to:** PL-016 requirement 1 (the compile route returns the compiler's raw output) and, behind
it, the compiler (PL-008), which synthesizes neither precheck rules nor branches. Nothing in PL-016
asked the compile route to synthesize rules, so this is a capability boundary the golden test makes
visible rather than a regression. Flagged for T1 to decide whether PL-016b's pass condition should be
restated, a follow-up ticket should teach the compiler the duplicate/incomplete handling, or both.

## Requirement 2 — the golden test on `messy-crm`

The test records the ticket's flow through the popup (two recipients, remove one with its ✕, type
into the rich-text notes, visit the second page and come back with Back, Save), then compiles
(`tests/e2e/test_record_compile_run_messy.py`).

The recording is the 10 events shown in the Summary. The compile **fails**, and the Make recipe form
shows the route's problems in plain words. The real output:

```
E  AssertionError: the Make recipe form could not compile the recording:
   result='Could not make a recipe (4 problems).'
   warnings='meta/input_schema/fields: 'add-recipient' does not match '^[a-z][a-z0-9_]{0,63}$'
             meta/input_schema/fields: 'add-recipient-2' does not match '^[a-z][a-z0-9_]{0,63}$'
             steps/1: {... 'value': {'kind': 'input', 'column': 'add-recipient'} ...} is not valid under any of the given schemas
             steps/3: {... 'value': {'kind': 'input', 'column': 'add-recipient-2'} ...} is not valid under any of the given schemas'
   assert None is not None
```

**Cause.** The messy fixture's recipient field is labelled "Add recipient". The popup's
`recordedValues`/`slug` (`apps/extension/src/popup/make-recipe.ts`) turns a field name into a column
by lower-casing and replacing runs of non-alphanumerics with `-`, giving `add-recipient`. The recipe
schema's field name is `^[a-z][a-z0-9_]{0,63}$` (`packages/recipe/schema/recipe.schema.json`,
`$defs/name`), which forbids the hyphen. So the compiled recipe is rejected (422), nothing is stored,
and the golden test cannot proceed to the run.

**Traces to:** PL-016 requirement 2 (the Make recipe form derives input columns from the recording's
field names). A multi-word accessible name — a normal thing on real pages, and every field on the
messy fixture's recipient/notes composer labels itself that way — produces a schema-invalid column.
This is the interaction of PL-016 requirement 2 with the schema (PL-008); the fix is a change to the
popup's slug (or the compiler's field-name normalization), i.e. product code, so it is left to T1.

Two further defects surfaced on the way to this outcome (both real, both fixed or avoided in the
harness, both worth T1's attention):

- **`POST /api/v1/runs` returns 500 on a duplicate `record_key` in a batch.** The form's record-key
  dropdown defaults to the *first recorded value*, which the recorder's buffering makes `interest`
  rather than `email` (the `select` fires immediately, the Email `fill` is flushed on the next
  blur). Every row then shares the key `data course`, and run creation hits
  `UniqueViolation: duplicate key value violates unique constraint "run_records_run_id_record_key_key"`
  and answers **500** instead of a 4xx naming the problem. The test chooses the `email` column, as a
  person would, and proceeds. The 500 is a robustness gap in the run-creation path (unhandled DB
  error), adjacent to PL-016 requirement 2 rather than inside it.
- **`POST /api/v1/runs` is the only path exercised for these rows.** With the key fixed, the run
  runs; the compiled recipe's default `approval_policy` is `first_record`, so the first commit opens
  an approval gate. The test approves it as the operator page would (`POST /api/v1/approvals`), which
  needs a real `users` row (`approvals.decided_by` is an FK); the harness creates one.
