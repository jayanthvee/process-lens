## The plain-words rule (requirement 7)

`apps/web/tests/engineWords.test.tsx` renders Home, Needs help, Tasks, Task detail, Runs, Run detail
and ComingSoon with sample data, asserts each really rendered its data (so a blank page cannot pass),
and fails if the visible text carries `recipe`, `ledger`, `parked`, `record key`, `verified`, `rung`,
`idempotency`, `v1`, `v2`, `step_`, `fill-` or `click-`. The list itself lives in
`apps/web/src/lib/words.ts` (`ENGINE_WORDS`) and the test imports it, so the rule the test enforces
and the rule the pages apply cannot drift apart. It also carries a case for the refusal state of both
actionable pages (see the review, MAJOR 1).

## The independent review, and what was done

A read-only reviewer was sent at the branch with one instruction: try to refute it. It found two
major defects, and both were real.

**MAJOR 1 — the API's own refusal text reached the screen.** `services/api/runs.py` answers a 409
with `str(exc)`, which is the ledger's own words: `run_record <id> is not parked`, or the database
trigger's `… was commit-attempted; parked -> skipped requires a fresh destination check`. Both
actionable pages printed it verbatim, so a person could read a table-row name, a state and a uuid —
and the branch's own `needsHelp.test.tsx` *asserted* that string was shown. Reproducible by two
clicks on the same row in two tabs.

Fixed: `lib/words.ts` now owns the translation (`refusalWords`). A refusal whose shape says the row
was already dealt with becomes "Someone else has already dealt with this row. Reload the page to see
where it stands."; anything else is measured against `ENGINE_WORDS` and replaced with a plain
sentence if it still carries an engine word. `engineWords.test.tsx` now renders both pages in their
refusal state with the ledger's real 409 bodies and fails on the same rule, and the two tests that
had asserted the raw text now assert that the raw text never reaches the person.

**MAJOR 2 — PL-015's approval decision was missing.** Nothing read `open_approval`, so a run paused
`awaiting_approval` told the person "An approval request is waiting for your decision, then resume."
and gave them a Resume button and no way to decide; the runner re-asks rather than proceeding, so
the pause could not be cleared from the UI at all.

Fixed: the run page renders the decision again. The request's values appear in plain words — the
value, then the row's own columns — and never the step id, the action name or the target ladder the
payload also carries (`lib/approvals.ts` drops them). One gold primary button ("Go ahead") and one
quiet one ("No, stop this row"), the operator id from `/api/v1/operator` in the body, and both
disabled with the API's own words when that route answers 503.

Also fixed from the review, each with a test:

- **The "next to the button" placement assertion for a run refusal** had been weakened to a
  presence check; the run actions now carry `.run-action-pause/resume/cancel` and the test asserts
  the shared container, as PL-015 did.
- **The `queued` status** was only asserted as a pure function; the page test now renders it.
- **`POLL_INTERVAL_MS`** was no longer asserted anywhere; now it is.
- **An already-finished run still polled once, 2 s after load** — a real regression, because
  `pollMs` started at 2000. It now starts at `null` and becomes 2000 only once the payload says the
  run is open.
- **The injection test** was deleted with the old page; a case for a hostile `record_key`/`reason`
  is back.
- **An unknown `/api/...` path answered the app shell at 200** instead of the API's own JSON 404,
  so a caller parsing JSON waited on a request that had failed. The SPA fallback now serves the page
  only for a path that is neither an asset nor under `api/`.
- **The fix for that also caught a Windows-only bug in itself**: Starlette normalises the mount's
  path with `os.path.normpath`, so on this machine the separators are backslashes and the `api/`
  prefix test silently never matched. It is normalised back, so it behaves the same here and on the
  deployment. This one is worth T1's attention precisely because it passed on neither side by
  accident: it was the test that caught it.

The reviewer's "checked and sound" list, which I re-verified: `counts.needs_help` really is the
length of the `/needs-help` response (one read, one filter, one order); the new SQL matches
`internal/docs/sql-patterns.md` and the real schema; every page guards division by zero; every
dependency in `apps/web/package.json` is an exact pin with no Tailwind and no component library; the
hub's new route changes no frame, socket, token check or protocol constant; and nothing touched the
ledger state machine, the runner, or the re-queue safety check.

## The safety rule (requirement 6)

Unchanged and enforced on this branch. `needsHelpActions.ts` is PL-015's gate plus a stricter
one: a `commit_attempted` row stays disabled until the box is ticked **and** the API has named an
operator, `actionBody` throws rather than ever omitting `destination_checked_by` for such a row, and
the page computes the gate and the body from the same `confirmed[record_id]` read in the same
render, so a tick cannot go stale between the two. The API and the database trigger remain the
backstop; no line of either changed.
