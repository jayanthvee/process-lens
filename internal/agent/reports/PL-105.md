# Report PL-105

Status: done · Agent: T2 (DeepSeek) · Commit: `6cf9313` · Branch `pl-105`

## Summary

Everything an employee does now lives in one Chrome side panel that stays open beside the page
they work in. The panel is the web app built a second time: the same React pages, a narrow shell,
and exactly three places — **Teach**, **Tasks**, **Runs** — with a connection line at the top that
reads this Chrome's session and offers **Connect** right there. There is no access-code page, no
Home, no Needs help, no Saved answers/Documents/Apps/Settings/Help, no "Coming soon" and no popup:
the manifest asks for `sidePanel` and points at `panel/panel.html`, the worker sets
`openPanelOnActionClick` on install and on startup, and the popup has left the build.

Three API changes carry it, each inside the ticket:

- **Front door.** The pinned `chrome-extension://<id>` origin is now accepted on every state-changing
  `/api/v1/` path, because the panel starts runs, uploads spreadsheets, saves mappings, pauses,
  resumes, cancels, re-queues and dismisses from that origin. The credential check is untouched and
  an unset `PROCESSLENS_EXTENSION_ID` still accepts no extension origin.
- **`GET /api/v1/tasks`** now carries `inputs`: the field names of the pinned recipe version's
  `input_schema`, minus `run_once_id`.
- **`POST /api/v1/tasks/{id}/run-once`** refuses a task with inputs (422, "This task needs a
  spreadsheet.") and otherwise writes a one-row batch whose row is `{"run_once_id": <fresh uuid>}`
  and creates the run on it through `create_run`, in one transaction, with `require_runs_allowed`,
  mode `batch`, limit 1. Saving a recording with no typed values compiles with
  `record_key {{row.run_once_id}}` and sample row `{ "run_once_id": "x" }`, so two Run onces are two
  pieces of work instead of a key skipped as already done.

The ticket's three written-first test files are unedited and pass:
`apps/extension/tests/side-panel.test.ts` (3), `apps/web/tests/panelNav.test.tsx` (7),
`apps/web/tests/panelApi.test.ts` (3).

## Review fixes

T1's review of PR #86 raised three items. All three are fixed on `pl-105`; `main` was not merged
in, as instructed.

### 1. The panel's Save sent no commit step (blocking)

`PanelTeach.tsx` called `makeRecipeRequest(events, { …, commitStepId: null })`, while the popup
passed the save click the form had preselected. With a null commit, `makeRecipeRequest` marks no
step as the commit, so the save click compiled as a plain click: no write-ahead record and no
save check, and a crash between the click and its confirmation could create the record twice.

`save()` now passes `defaultCommitStepId(events)` — the recording's last click, the same function
the popup used — so the panel and the popup compile the same recording the same way.

`apps/web/tests/panelTeach.test.tsx` (new) renders the real `PanelTeach`, lets the stubbed worker
answer with a two-click recording, presses **Save as task**, and asserts the compile request's
`commit_step_ids` is `["step-save"]` (the later click, not the earlier one, and not empty). It
also asserts the compile is followed by the `POST /api/v1/tasks` that makes the task real.

Re-adding `commitStepId: null` makes that test fail with `expected [] to deeply equal [ 'step-save' ]`,
so it pins the fix rather than describing it.

The recipe-level effect was checked against a real recording taken from the built extension in
Edge, compiled through `packages.compiler` both ways — a page whose Save is a plain button, which
is the case that has no `<form>` submit event to fall back on:

```
recording events: 4   (fill, fill, click, observation)
commit_step_ids as sent by the fixed panel: ['click-1']

=== after the fix: commit_step_ids=['click-1']
  click-1    click     commit=True  assert_after={"text_visible": "Saved ravi@example.com", "timeout_ms": 8000}

=== before the fix: commit_step_ids=[]
  click-1    click     commit=False assert_after=null
```

A note on why a form-based page does not show the difference: `packages/compiler/coalesce.py`
marks a click as a commit by itself when the browser follows it with a `submit` event for the same
control (`collapse_submits`). That is why the check above uses a plain button — with a `<form>
submit` the old code happened to produce a commit too, and the bug stayed invisible.

Consequence worth knowing: passing the recording's default commit also re-enables PL-042's
first-entry trim in the panel (`firstEntryEvents` returns the events unchanged when it has no
commit id). A recording that saves twice now compiles only its first entry, as it always did in
the popup. This removes an inconsistency rather than creating one: `recordedValues` — the source
of the column list and the record-key select — already trimmed by that same rule, so the panel
used to offer columns from the first entry and then compile the second one too. The panel has no
"Notes for support" area, so it does not print the popup's `REPEAT_SAVE_NOTE`; see Remaining risks.

### 2. A UTF-8 BOM at the start of `main.tsx`

The file began with `EF BB BF` before its first `/**`. It is now plain UTF-8 (`2F 2A 2A` at byte
zero), rewritten with `UTF8Encoding($false)`. The `git diff` shows the removed `\ufeff` on line 1,
so the fix is in the committed content and not only in the working copy.

### 3. A hosted build stayed on a stored 127.0.0.1

`main.tsx` booted with `(await lastHubUrl()) || BAKED_HUB_URL`: any non-empty stored address won,
including the `http://127.0.0.1:8000` an earlier local popup left in `chrome.storage.local`. A
tester handed a build with a hosted address baked in therefore talked to their own laptop.

`runtime.ts` now decides this in one tested place, `chooseHubUrl(baked, stored)`:

- nothing stored → the baked address;
- a stored loopback address and a hosted baked one → the baked (hosted) address;
- anything else → the stored address, so a person's own hub still wins, and a local build
  (`make demo`, the default `http://127.0.0.1:8000`) still follows the last hub it connected to.

`isLocalHub` names what counts as this machine: `127.0.0.1`, `localhost`, `[::1]`, `::1`, `0.0.0.0`.
`apps/web/tests/panelRuntime.test.ts` (new, 5 tests) pins all four branches plus the loopback names.
The decision is recorded at boot only; the worker still writes `processlens.lastHub` on
`executor:connect` (`apps/extension/src/background/service-worker.ts`), and that write is untouched.

Checked in the built extension in Edge, by storing a value and reloading the panel with network
capture on:

```
baked https://processlens.example.com, stored http://127.0.0.1:8000
  api requests after reload:
    https://processlens.example.com/api/v1/executor/session?browser=…

baked http://127.0.0.1:8000 (default build), stored https://team.example.net

    https://team.example.net/api/v1/executor/session?browser=…
```

The first is the reported bug and now goes to the hosted hub; the second is the local developer's
build still honouring the hub they connected to.

## Remaining risks

- **A real toolbar click is unverified** (see above): Chrome reports the behavior as set, which is
  the state a click reads.
- **The panel is the website's pages at 360–420 px.** Runs and the run page were narrowed with CSS
  and a prop; TaskRun's mapping table is the tightest screen at that width. It is usable in the
  Edge run above but has not been read by a person on a real screen.
- **`npm --prefix apps/web ci` is now a prerequisite of the extension build** (CI and the README
  both say so). A lone `apps/extension` checkout can no longer build a releasable zip; it fails with
  one sentence naming the command.
- **The panel does not say that a two-save recording was trimmed.** PL-042 has always compiled only
  the first entry, and the panel now does too, but `REPEAT_SAVE_NOTE` is shown by the popup's
  "Notes for support" and the panel has no such area, so a person who recorded two entries sees all
  of their steps listed and a task built from the first one only. Nothing is saved twice, which is
  the point; telling them what was left out is a UI slot this ticket did not add.
