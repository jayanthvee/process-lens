## 1. The person's choice decides which step saves

**Changed.** `packages/compiler/compiler.py`: `to_candidates` now checks whether the request
*named* the commit steps (`commit_step_ids is not None`). When it did, a candidate commits iff its
recorded id — or an id it absorbed — is in that list; the submit's own `commit` flag is ignored.
When the field is absent, the earlier rule stands unchanged. `services/api/compile.py`:
`commit_step_ids: list[str] | None = None`, so FastAPI tells "sent `[]`" from "not sent".

Two follow-on details the review found:

- `packages/compiler/coalesce.py` / `model.py`: a click and the submit it caused fold into one
  step. The submit's id is now kept on the folded event (`also_ids`), so a person who picks the
  submit's row (`Clicked Save` appears once per recorded click *and* once per recorded submit in the
  panel's list) still names that step. Without this, choosing the submit row silently compiled a
  read-only task — the old behaviour only seemed to work because the `event.commit` leak made it a
  commit.
- A choice that names no surviving step (e.g. a click the folds removed) still compiles read-only,
  but the warnings now say `the click chosen to save your work is not in the steps this recording
  compiles to, so nothing will be saved; record it again and pick that click`. A warning was chosen
  over a refusal because existing recordings legitimately name steps the folds keep, and a new
  refusal would be a bigger behaviour change than the ticket asks for.

**Proved by** `packages/compiler/tests/test_pl112_commit_choice.py`:
- `test_nothing_gets_saved_compiles_a_read_only_recipe` — fill → click Continue → submit of the same
  form with `commit_step_ids=[]` has no `commit` step and no `assert_after`. Before the fix:
  `CompileError: a commit step must carry an assertion` (the submit had marked Continue a commit).
- `test_an_omitted_choice_keeps_the_compilers_own_commit_rule` — the same recording with no field is
  still refused for the submit-derived commit, exactly as before.
- `test_a_named_click_is_the_commit_step_and_still_needs_an_assertion` — naming Continue keeps
  today's refusal.
- `test_a_named_click_with_evidence_is_the_one_commit_step` — the named click carries `commit` and
  its observation; there is one click step, not two.
- `test_the_submits_own_id_names_the_step_it_folded_into` — naming the submit's id commits the step
  it folded into.
- `test_a_choice_that_names_no_compiled_step_says_nothing_will_be_saved` — read-only plus the
  warning.

`tests/api/test_pl112_compile_choice.py` (`test_an_empty_commit_list_compiles_with_no_commit_step`,
`test_an_omitted_commit_list_keeps_the_older_behaviour`) proves the same split through
`POST /api/v1/recipes/compile`. Before the fix the `[]` request was a 422.

With no commit steps the recipe is read-only and the runner's existing `filling -> verified` path
(`services/runner/run_loop.py`) applies, which is PL-107 item 6's intent.

## 3. A finished row says what happened

**Changed at the source and in the words module.**
- `packages/ledger/commits.py`: defaults are now `added and checked` (`verify_commit`),
  `saving it now` (`begin_commit`), `sent it; checking it arrived` (`mark_submitted_unverified`).
- `services/runner/run_loop.py`: read-only finish `done`; reconcile success `added and checked`;
  precheck `checked the row`; the failure and pause reasons that a row can show are now sentences
  rather than engine phrases (`The click was never sent.`, `ProcessLens couldn't tell whether the
  click was sent`, `the page didn't show it saved`, `nobody decided whether to save this row in
  time`, `a reviewer turned this row down`, `the task ended without saying what happened`, `the site
  shows more than one match for this row`, `the site does not have it yet; trying again`).
- `apps/web/src/lib/words.ts`: `plainReason` maps the new strings and the old stored ones
  (`assertion passed`, `the destination has this commit`, `steps completed`, `precheck passed`,
  `commit write-ahead`, `no dispatch proof`, `the assertion did not pass`, …) to the same plain
  sentences, so rows already in the ledger read plainly too.

**Proved by**
- `tests/runner/test_pl112_reasons.py` — a commit-verified row's stored reason is `added and
  checked` (was `assertion passed`), and a read-only row's is `done` (was `steps completed`).
- `apps/web/tests/pl112Reasons.test.tsx` — `plainReason` for the old and new strings, and the run
  page rendering a row stored with `assertion passed` as "Added and checked." and one stored with

One engine-ish fallback is unchanged on purpose: `services/runner/check_words.py`'s `UNKNOWN_CHECK`
("the save's check did not pass") is what a *malformed* condition (a kind the schema forbids) parks

enumerated words (assertion, assert_after, commit, precheck, reconcile), so it was left alone rather
than editing an existing test the ticket did not name. Say the word and it becomes one more plain
sentence with that test updated.

## 4. A sign-in task runs without a spreadsheet

**Where the flag lives, and why.** On the **task**, not the recipe: `workflows.sign_in` and
`workflows.sign_in_column` (migration `0012_sign_in_tasks.sql`). A re-teach replaces the recipe
version, but the task keeps its identity and its list of emails, so the marker belongs beside it;
it is also what `GET /api/v1/tasks` already reads from. The **taught email** is not stored a second
time on the server — it is the recipe's own `input_schema.fields.<column>.example`, which the
compiler already writes. The **list** of emails typed since lives only in the extension's
`chrome.storage.local`, one key per task (`processlens.signInEmails.<workflowId>`).

**Teaching.** The recorder already probes `codePromptInPage` and sends `record:code-from-email` when
the recorded page asks for a code; the worker now marks the recorder status there (and on
`record:code-entered`), via the small `apps/extension/src/background/sign-in.ts`. `start` and `clear`
take the mark away again. `PanelTeach` reads `status.signIn` and, when saving, sends
`sign_in: true` plus `sign_in_column` (the column of the email-looking value, else the key column),
and remembers the taught address in this Chrome.

**Running.** `PanelTasks` gives a sign-in task **Run** and an email dropdown instead of "Run with a
spreadsheet": the taught email first, then every address typed before for this task, then
"Another email…" with a text box. Run calls the existing one-row path
(`POST /api/v1/tasks/{id}/run-once`) with `values: {<column>: <email>}`; the route writes that as the
run's one row, so the run fills the taught column and the code page is filled from Gmail exactly as
PL-102 does. `POST /run-once` still refuses a task that needs columns when no values are supplied
(`This task needs a spreadsheet.`), so the general rule is "a row is run once, either fresh or from
the values given".

**Plain words on the row.** The runner now writes `runs.pause_detail` when a code read fails
(`none`, `ambiguous`, `not_allowed`, …) while `pause_reason` stays `code_required` for every screen
that already reads it. The task list carries that detail, and the row says:
- `none`: "No code arrived at <email>. Check that this inbox is signed in to Gmail in this Chrome,
  then press Try again."
- `ambiguous`: PL-102's sentence ("Two codes arrived and ProcessLens can't tell which one is this
  site's. Type the right one here.").
- `not_allowed`: PL-102's offer and its **Read it from my Gmail** button, which posts
  `/api/v1/runs/{id}/code-from-email` with `remember: true`.
- anything else: `codeFromEmailWords`'s sentence for that reason.

The code is never stored, logged, recorded or shown: the runner still only ever sees
`entered`/`reason`/`cleared` (`BrowserExecutor.code_from_email`), and the panel never asks for one.

**Proved by**

- `tests/runner/test_pl112_code_detail.py` — a code read that found nothing pauses with

## Not done, and limits worth knowing

- **Live acceptance is not done**: a real teach against a site that emails a code, with Gmail signed
  in, and a Run from the email pick. The rules are proven with fakes and a real DOM, not a live
  inbox, and the ticket forbids browsers and e2e here.
- **A sign-in taught with no typed address is not marked as a sign-in task.** `taughtSignIn` needs a
  recorded value to know which column the address belongs in; with none, the task is saved as a
  normal no-input task and its row offers **Run once**. The run still meets the code page and the run
  page's PL-102 code box/offer handles it — but it is not the one-click email pick. Marking it
  without a column would type the address into `run_once_id`, which is worse.
- **The picked email is in that run's own input row** (as any run's row is; the runner reads it from
  `clean`). No *list* of addresses is kept on the server — only the one address in the run it was
  picked for, plus the recipe's original teaching example.
- **The popup's own form does not send the sign-in fields.** `saveTask` accepts them, but the panel
  is the shipped surface (PL-105 removed the popup from the build); the popup's DOM is only a test
  fixture now.
- **The extension marker depends on the recorder's code-page probe.** A code page the probe does not
  recognise (an unusual widget) is not marked, and the task falls back to the Run once path above.

## T1 review fix

T1 found one blocking issue: `run_task_once` accepted `values` for every task, and the row's record
key is always a fresh `run_once_id`. For a task that saves something (the CRM leads task, say) that
key never repeats, so `committed_keys` had nothing to compare and the "never add the same item
twice" guard was bypassed; it also took any column names and half a row.

**Fixed in `services/api/tasks.py`** (`sign_in_row`), with `latest_task_version`
(`services/api/task_columns.py`) now also selecting the workflow's `sign_in` and `sign_in_column`:

- `values` is accepted only when the workflow's `sign_in` is true. Any other task that sends values
  gets 422 "This task runs from a spreadsheet, not from one row."; a task with inputs and no values
  keeps today's `NEEDS_A_SPREADSHEET` 422.
- A sign-in task must send exactly one key, equal to its own `sign_in_column`, with a non-empty
  string value, trimmed and at most 320 characters. A wrong column or an extra key is 422 "Run this
  task with one email address, in its own field."; an empty or non-string value is 422 "Type the
  email this run should use."; a longer one is 422 "That email is too long to use here."
- Nothing is written for a refused request (the batch/run insert is still one transaction after
  the checks).

**Proved by `tests/api/test_pl112_sign_in_api.py`** (written first; 7 of them failed before the
fix, all 12 pass after):

- `test_run_once_refuses_a_row_for_a_task_that_saves` — a task with inputs and `values` is 422 and
  writes no batch.
- `test_run_once_refuses_a_row_for_a_task_that_saves_nothing_but_was_not_taught_as_a_sign_in` — the
  rule is the marker, not the shape of the task.
- `test_run_once_refuses_a_row_in_the_wrong_column`, `…_with_an_extra_column`,
  `…_an_empty_or_non_string_email` (empty, spaces, a number, null), and
  `…_an_email_longer_than_the_column_holds` — each 422 with its sentence.
- `test_run_once_trims_the_email_it_is_given` — the stored row carries the trimmed address (before
  the fix it stored the padding too).
- The existing `test_run_once_puts_the_picked_email_in_the_taught_column` and the
  `test_run_once_still_refuses_a_spreadsheet_task_with_no_values` still pass, unchanged.
