## Part 1 — the API (`GET /api/v1/spreadsheets`)

Commit `c5b6a79` — `feat(api): the spreadsheets read and GET /api/v1/spreadsheets`.

- **`list_spreadsheets(conn, *, tenant_id)`** in `packages/ledger/reads.py`, with `_LIST_SPREADSHEETS`
  beside `_LIST_APPS` and a paragraph of comment saying why.
  - One row per `input_batches` row whose `kind` is `csv`, `xlsx` or `manual` — never `documents` —
    newest first (`created_at DESC, id`), with the same
    `%(tenant)s::uuid IS NULL OR b.tenant_id = %(tenant)s` filter the other reads use.
  - `file_name` is `coalesce(files.original_name, 'Pasted rows')`, so a batch with no file reads as
    the rows a person pasted.
  - `task_id` is `input_batches.workflow_id`; `task_name` names the **latest** recipe version the way
    `_LIST_TASKS` does — `coalesce(rv.recipe -> 'meta' ->> 'name', w.name)` — through a lateral join
    on the highest version.
  - `row_count`, `uploaded_at` (`input_batches.created_at`), `uploaded_by` (`users.name`, joined on
    `input_batches.created_by`), `runs` (count of runs whose `input_batch_id` is this batch), and
    `last_run_id` (the newest of those, by `created_at DESC, id`). One lateral aggregate counts the
    runs and a scalar subquery keeps the newest id.
  - Nothing from `input_records` is read, and `raw` never appears: the page lists the upload, not its
    rows.
- **`SpreadsheetRow`** is a frozen dataclass in `packages/ledger/models.py`, exported together with
  `list_spreadsheets` from `packages/ledger/__init__.py` — the convention every other read follows.
- **`services/api/spreadsheets.py`** defines `SpreadsheetEntry` with exactly the nine frozen keys and
  `GET /api/v1/spreadsheets`, taking the same optional `tenant_id` query parameter as `/apps`. It is
  mounted in `main.py` next to `apps_router`.

### Tests (`tests/api/test_spreadsheets_api.py`, 9 tests, red first)

The fixtures follow `tests/api/test_apps_api.py` (fresh tenant via `ledger`, helpers that insert a
batch, a file, a user and runs). Covered: newest first; another tenant's batches never appear; a
batch with no file is "Pasted rows"; a file batch shows its original name; the run count and newest
run are right; no runs gives `runs = 0` and `last_run_id: null`; `uploaded_by` and `uploaded_at`
come from the batch row itself; `documents` batches are left out while `manual` and `xlsx` are in;
and the response keys are asserted exactly (`id`, `file_name`, `task_id`, `task_name`, `row_count`,
`uploaded_at`, `uploaded_by`, `runs`, `last_run_id`).

  ticket.

- **Styling (`spreadsheets.css`):** only existing tokens and the shared `.panel`, `.empty`, `.btn`

  the minor ones and hide under 780 px, so the file, the task and the run survive on a phone.
- **Type:** `SpreadsheetRow` was added to `apps/web/src/types.ts`, which is where every other API

## Deviations, and a call for T1

1. **`uploaded_by`'s source.** The ticket says `users.name` but names no foreign key. Because
   `uploaded_at` is explicitly `input_batches.created_at`, I treated the batch's own creator,
   `input_batches.created_by -> users.name`, as "uploaded by" — the same event and the same row. The
   other candidate is `files.uploaded_by`: the two agree in intent for a file batch, but a pasted
   batch has no file, and `created_by` still names the person who pasted the rows. If T1 reads the
   ticket as `files.uploaded_by`, it is a one-line change in `_LIST_SPREADSHEETS`.
2. **Files the ticket did not name.** `App.tsx` had to change to replace `<ComingSoon />` on
   `/spreadsheets`, which is the ticket's own instruction. `types.ts` gained `SpreadsheetRow`,
   following PL-035's precedent (its report named it as the one unnamed file) and the repo rule that
   every API shape lives in `types.ts`. No migration, no new dependency.
