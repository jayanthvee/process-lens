# PL-024 — Teach, spreadsheet upload, column matching, Try one row and Run, from the web app

Branch `pl-024` (cut from `origin/pl-024-027-tickets`). Ticket: `internal/agent/tickets/PL-024.md`.
Status: **built, gated, reviewed; T1's browser run is the remaining acceptance step.**

## What this ticket makes possible

Before: a task could only be taught from the popup, and running one needed an input batch inserted by
hand through SQL. Now a person can go from "I have a spreadsheet" to "the rows are in the app"
without leaving the web app, and without a single model call anywhere.

## The API

- **`packages/ledger/batches.py`** (new, 191 lines). Every `input_batches` / `input_records`
  statement. `insert_batch` writes the batch and all its rows in one call; `get_batch`,
  `list_batch_rows`, `set_batch_mapping`, `set_row_verdict`, `set_row_clean` are the rest. Types are
  frozen dataclasses (`BatchRow`, `BatchRowInfo`, `StoredRow`), re-exported from `packages.ledger`.
  Functions open no transaction: the caller owns the boundary, as every other ledger function does.
- **`db/migrations/0005_batch_mapping.sql`** (new). One statement:
  `ALTER TABLE input_batches ADD COLUMN column_mapping jsonb;`. This is the only migration.
- **`services/api/batches.py`** (new, ~500 lines), mounted in `main.py`.
  - `POST /api/v1/batches` — multipart `workflow_id` + `file`; `.csv` (`utf-8-sig`, `csv.DictReader`)
    and `.xlsx` (`openpyxl`, `read_only`, first sheet); at most 2,000 rows and 5 MB; a blank header
    becomes `Column N`; `record_key` is built exactly the way `tests/e2e/conftest.py` built it
    (lower-cased `email`, else `row-NNNN`). Returns `batch_id`, `row_count`, `columns`.
  - `GET /api/v1/batches/{id}/check?recipe_version_id=` — matches the spreadsheet's columns to the
    recipe's `meta.input_schema.fields`, then decides each row and **writes that verdict onto the
    row**. Returns `mapping`, `rows_ok`, `rows_need_a_look`, `first_ready`.
  - `PUT /api/v1/batches/{id}/mapping` — the mapping a person confirmed, stored on the batch. The
    recipe is never touched.
- **The matching is deterministic** (`packages/...` no model is called anywhere): normalise
  (lowercase, non-alphanumerics to `_`, digits kept), then exact name, then a value match against the
  taught sample row, then synonym groups and token overlap, then no match. Ties go to the first
  column in file order.
- **`services/runner/creation.py`** — when the batch carries a mapping, each ready row's values are
  rebuilt as the recipe sees them (`{recipe_column: raw[spreadsheet_column]}`), the keys are rendered
  from those values, and they are written to `input_records.clean` inside the same transaction that
  inserts the run and its records. `raw` is never touched. A batch with no mapping behaves exactly as
  before. `create_run` also gained `limit`, so `mode="preview", limit=1` runs exactly the first ready
  row.
- **`services/api/runs.py`** — `limit: int | None` (`ge=1`) on the create-run body, passed through.

## The web app

- **`/tasks/:id/run`** (`TaskRun.tsx`, new) — three steps on one page, revealed in order, with **at
  most one primary button on screen at any moment** (asserted at each step, and while the preview
  runs):
  1. **Add your spreadsheet** — drag and drop or browse, both on one handler; shows "20 rows, 8
     columns".
  2. **Check it** — one row per task column: its label, a `<select>` of the spreadsheet's columns
     (plus "Not in my file"), a status chip (Matched / Check this / Not found) and the alternatives.
     Below: "18 rows ready · 2 need a look" and the reasons. **Continue** is enabled only when every
     required column is matched; it saves the mapping, asks the check again, and only then moves on.
  3. **Try one row** — the first ready row as "About to add: …". **Try it** starts the preview and
     the screen follows it live (2 s poll, switched off the moment the run is not open). Then **Run
     the other 19**, which starts the batch and opens that run's page.
- **`/teach`** (`Teach.tsx`, new) — the three plain steps, `GET /api/v1/tasks` polled every 2 s, and
  the first task not in the opening answer shown as "Got it: \<name\>" linking to it.
- `TaskDetail` gained its one primary action ("Run this task"); `Shell` gained the run flow's page
  title; `App` routes both pages. `lib/api.ts` gained `apiPostFile` (never sets `Content-Type`, so
  the browser's multipart boundary survives) and `apiPut`. No new colours, fonts or components: the
  existing tokens and primitives only.

## One deliberate change to a security control — read this

`services/api/middleware.py` refused every state-changing request whose body was not
`application/json`. The upload is multipart, so the front door would have answered 403 before the
route ran. The exception is **one path wide**: `POST /api/v1/batches` also accepts
`multipart/form-data`; every other path keeps the JSON-only rule, and the origin, loopback and host
checks are untouched. This is defensible because `multipart/form-data` is a CORS-safelisted type, so
the content-type check was never the barrier for a form — the **origin** check is, and it still
refuses every `Origin` that is not this API's own. The module docstring says this, and
`tests/api/test_frontdoor.py` now proves the exception is one path wide in both directions.

## Where the recorded sample values come from

The ticket's value match needs the values typed while teaching, as it types them. Nothing in this
repo persists a recording's sample row: the extension keeps it in its own storage
(`processlens:executor-row`) and the compile route receives it in the request body without storing
it. So the check takes it as an **optional `sample_row` JSON object** (`{"email": "…"}` keyed by the
recipe's column). With it, the value rule fires; without it, matching is name/synonym/token only.
That is the whole of the mechanism — no LLM, and no guessing.

## Independent review: one real defect, found twice and fixed

A read-only reviewer attacked the branch on the eight axes it was given and returned **REFUTED**. I
had independently hit the same thing with a probe minutes earlier, which is why it is in this report
as a fixed defect rather than a footnote.

**HIGH — the check ignored the mapping a person saved.** `check_batch` built the mapping purely from
the auto-matcher, while the verdicts it writes are what gate the run (`create_run` takes only
`status = 'ready'` rows). So a person re-mapping a column the matcher could not find changed nothing:
the rows stayed `needs_review` and were silently left out of the run. My probe reproduced it exactly —
first check chosen `None`, `rows_ok` 0; after `PUT` of the mapping a run was still built with **0
rows**. The page advertised the opposite in a comment, and my own re-check test had encoded the false
premise (its stub invented a second answer the real API could never produce).

Fixed in `services/api/batches.py`: the saved mapping now wins over the guess (`_with_saved`), so the
verdicts, `first_ready` and the counts are all computed from the columns the person confirmed, while
a first check with no mapping behaves exactly as before. A saved name the file does not have is
ignored rather than trusted (the API refuses to save one; this is the second line of defence). The
probe now shows `rows_ok` 2 after the mapping is saved and a run built with **2 rows**, and two new
API tests pin it (`test_the_check_uses_the_mapping_a_person_saved`,
`test_a_saved_mapping_that_names_no_column_is_ignored`). The web test was rewritten to assert
something the real API can produce — that Continue asks the check a second time — which is the
habitable half of that idea.

**MEDIUM — after Continue the mapping table stayed editable but unsavable.** A change made in step 3
would not be saved, would not be checked, and the run would use the older mapping: the screen showed
one thing and the run used another. Fixed: the selects read rather than edit once the flow has moved
on, and a quiet **Change the columns** button (offered only before a run exists, since afterwards the
rows are already built) takes the person back to step 2, where Continue is again the one primary
button. Both behaviours are pinned by the web test.

**LOW — the chip described the guess, not the person's choice.** A column a person picked themselves
was still labelled with the matcher's own confidence ("Check this" on a column they had just
deliberately chosen). Fixed: a column the person picked reads **Matched**; the guess's confidence is
used only while the two agree.

Everything else the reviewer attacked held: the e2e contract change, the front-door exception's
width, `raw`/transaction/idempotency behaviour, `limit`, tenant scoping, the one-primary-button rule
and the engine-word rule.

## Residual risks, stated plainly

- **The web flow never sends `sample_row`.** Nothing on the web holds the recorded sample row (the
  extension does), so from the browser the value match cannot fire and matching falls back to
  name/synonym/token. The API supports it and a pytest covers it; wiring it through would mean the
  extension handing its sample row to the page, which this ticket does not ask for.
- **The check is not a preview of the run's own work.** It applies the recipe's precheck rules and
  the in-file key repeat; it does not drive a browser. A row that is ready can still need a person at
  run time, which is what the run page and Needs help are for.
- **`/teach` decides "new" from the page's first answer.** A task that appears before the page is
  opened reads as pre-existing — the plan's own wording, and the only thing the poll can know.
- **A large `GET /api/v1/batches/{id}/check` writes every row's verdict** on each call, and the page
  calls it once per Continue. For the 2,000-row ceiling that is 2,000 small updates in one
  transaction; fine here, worth knowing if the ceiling moves.
