## The independent review, and what it found

A read-only reviewer was sent at the branch with one instruction: try to refute it. It reported
that it could not run `pytest` or `ruff` (its shell would not admit the programs), so everything
below is its static reading, and I re-verified each finding myself before acting on it.

**The finding that mattered, and it was real: the freeze could be bypassed through the approval
resume.** `POST /api/v1/approvals` called `resume_run` with no gate. An approved decision therefore
restarted a run in a frozen tenant — a third resume path that the ticket's list of two does not
name, contradicting both "Nothing new will start" and "Unfreeze does not resume runs. Each run is
resumed by a person". I reproduced it against the real app before changing anything:
`services/api/admin.py`'s `runs_gate` was not in that route, `packages/ledger/runs.py::resume_run`
moves `paused → queued`, and a worker would then claim the run and do its pre-boundary work before
pausing it again.

Fixed, and the fix is the strict reading: a decision that resumes a run *is* a resume, so the route
now answers to the same gate with the same 409 sentence, before anything is written, so the request
stays open for the person to decide again once runs are allowed. Pinned by
`..._test_an_approval_cannot_restart_a_frozen_run` (409, run still `paused`, no `approvals` row, the
request still unresolved) and, so the gate is not over-tightened,
`..._test_an_approval_may_restart_a_run_when_nothing_is_frozen` (201, `resumed: true`).

**Two smaller real defects from the same review, both fixed.**
- A configured `PROCESSLENS_ADMIN_TOKEN` carrying a non-ASCII character made
  `secrets.compare_digest` raise `TypeError`, turning every admin request into a 500 instead of the
  documented refusal (it still failed closed, so it was not an open door). A non-ASCII configured
  token is now the 503 it is, with the variable named. Pinned by
  `..._test_an_admin_token_that_is_not_ascii_closes_the_surface`.
- A floor written to `tenants.min_extension_version` past the API — and the admin role *does* hold
  that column, which is the point of the role — made the run gate and the workspace read raise
  `InvalidVersion`: a 500 on `POST /runs`, `/resume` and the banner's own read. I reproduced that
  too, then split the comparator's question in two: `is_below` keeps its strict behaviour, and the
  gate and the page read use `floor_is_met`, which answers "not met" for a floor nobody can read.
  That refuses the run and names the value, which is what an admin can act on, and it fails in the
  safe direction. Pinned by `..._test_a_floor_written_past_the_api_is_refused_rather_than_crashing`
  and three cases in `test_versions.py`.

**What the review could not refute** (its own words, and I agree after checking): the commit window
is not torn; the token guard fails closed; the manifest's grants are exactly the ticket's list; the
front door is not widened beyond the extension's own three paths; the comparator is correct.

**One finding I am recording rather than fixing.** Requirement 4 says a deactivated user cannot
approve anything, and the route checks `decided_by` — a body-supplied id, so a deactivated person
could approve by naming someone else's. This is pre-existing and structural: there is no
authentication in this build at all, which is why the ticket defers sign-in to the Railway ticket.
Start and resume are *not* spoofable, because they read `PROCESSLENS_OPERATOR_ID` from the
environment. I left it as it is — fixing it means inventing the identity layer the ticket defers —
and flagged it for T1 in "What T1 should look at hardest".

## Decisions this ticket made that the ticket's text left open

- **The approval resume is gated (409) rather than a recorded-but-not-resumed decision.** Both
  readings keep the freeze honest; refusing was chosen because it is the ticket's own sentence for a
  resume and it leaves nothing half-done, and the ticket's acceptance list already says "starting
  and resuming a run return 409 while frozen".
- **The admin token's header.** The ticket says a shared `PROCESSLENS_ADMIN_TOKEN` header. The
  canonical spelling is `X-ProcessLens-Admin-Token`; the environment variable's own name
  (`processlens_admin_token`) is accepted as a second spelling, so a caller that reads the ticket
  literally still gets in. Both are asserted.
- **`GET /api/v1/workspace/state` is new, and requirements 5 and 6 do not name it.** Requirement 5
  says the page shows banners and disables its Run buttons; the page cannot do either without
  reading the two switches, and requirement 6 says the admin endpoints are for the panel. So the
  page's read is a separate, token-free, read-only route that shows nothing about anyone else, and
  the guard stays where D-024 puts it — the API's gate on the write routes. `runsBlocked(null)`
  returns `false` on purpose: an API that cannot answer must not disable the page silently.
- **The runner's check is the boundary check, and only that.** A record that a precheck rule exits
  never reaches a step boundary and so is never checked. That path makes no executor call and cannot
  reach a commit — it walks `claimed → prechecked → skipped|parked` from the database's own rules —
  so it is the accepted limit of the ticket's words "pauses it at the next boundary", not a hole. A
  worker claiming a queued run also does its pre-boundary work (`skip_already_committed`, the
  stranded-record reconcile) before pausing, which is existing loop behaviour and not a commit.
- **`unfreeze_runs` takes an `actor_user_id` it does not use.** Lifting a freeze clears the author
  with the timestamp; the parameter exists so a caller can pass it to the audit row it writes in the
  same transaction, and the docstring says so.

## What T1 should look at hardest

1. **The deactivated-person check on approvals is spoofable** (see above). Requirement 4 is
   implemented and tested for the honest caller; an adversarial caller can name an active id. This
   is the identity layer the ticket defers, so the question for T1 is whether that deferral is
   acceptable or whether `POST /approvals` should take its `decided_by` from
   `PROCESSLENS_OPERATOR_ID` the way start and resume do. That would be a one-line change and a
   consistency win, but it would break the existing approval flow that sends the deciding reviewer's
   id, which is why it was not made unilaterally.
2. **The freeze's blast radius is the boundary, not the gate.** A frozen tenant's *queued* run is
   still claimable and does its pre-boundary ledger work before pausing. No destination interaction
   and no commit — the check precedes `begin_commit` — but T1 may want the claim itself to consult
   the flag if "nothing happens" is meant literally.
3. **`GRANT SELECT ON ALL TABLES` is a point-in-time grant.** A later admin-module migration that
   forgets its own `SELECT` grant on a table it adds would leave the panel unable to read it and
   nothing in CI would notice; the DB test spot-checks six tables by hand. The rule is written down
   in `ADMIN-MODULES.md`, but nothing enforces it yet.
4. **The web flake above**, if T1 sees it during the e2e run.
5. **`POST /api/v1/executor/version` is a new extension-origin path on the front door.** It takes
   `X-ProcessLens-Client: extension` and it is one of exactly three paths that accept a
   `chrome-extension://` origin. Two tests assert a foreign origin and a wrong extension id are
   refused, but this is the surface T1 should attack.
