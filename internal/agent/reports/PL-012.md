## Summary

Migration `0002_ledger_hardening.sql` makes the database enforce the ledger rules that `0001_init.sql`
left to code review. It closes all ten confirmed gaps (G1–G10): the commit-attempted re-queue path, the
insert/delete guards, the attempts cap, `parked → skipped`, `TRUNCATE` protection, the transition audit,
one active run per destination, a lease, the idempotency key, and the approvals table. `0001_init.sql`
is untouched. Each gap has a named test that is unmet on 0001 alone and met with 0002, shown by running
the same checks against both schemas.

   the fixtures build rows the way production must, which is stronger, not weaker.

## The migration, by ticket section

- **a. Commit-attempted flag (G1).** `run_records.commit_attempted` (default false), set by the guard when a row enters `submitting`; plus `destination_checked_by` and `destination_checked_at`.
- **b. Replaced `guard_record_transition()` (G1, G3, G4).** All 28 transitions kept, plus `failed → reconciling`, `parked → reconciling`, `parked → skipped`. A commit-attempted record cannot go `failed|parked → pending` unless the same `UPDATE` sets `destination_checked_by`. Any `attempts` change other than the trigger's `+1` on `pending → claimed` is rejected, and `max_attempts` is fixed at insert. The trigger now fires on `UPDATE OF state, attempts, max_attempts`, so a direct write to `attempts` is caught.
- **c. Insert and delete guards (G2).** A row is inserted only as `pending`, `attempts = 0`, `commit_attempted = false`, with a non-null `idempotency_key`; `DELETE` is rejected; `runs` require a `destination_key`.
- **d. Transition audit (G6).** `run_record_transitions` (append-only) gets one row per actual state change, `actor` from `claimed_by` or `current_setting('processlens.actor', true)`, including bulk updates.
- **e. Idempotency key (G9).** `run_records.idempotency_key` (nullable for existing rows, required on insert) and an index on `(tenant_id, idempotency_key)`.
- **f. One active run + lease (G7, G8).** `runs.destination_key` and `runs.lease_epoch`; a partial unique index on `(tenant_id, destination_key) WHERE status IN ('running','paused')`.
- **g. Approvals (G10).** The append-only `approvals` table with the `approval_kind`/`approval_decision` enums.
- **h. TRUNCATE protection (G5).** a `BEFORE TRUNCATE` statement trigger on `recipe_versions`, `committed_keys`, `step_events`, `ai_calls`, `run_record_transitions`, `approvals`, and `run_records`.

The three confirmed decisions, and how they are enforced:

1. **A key already in `committed_keys` ends `skipped`, never `verified`.** The updated skip pattern in `sql-patterns.md` joins on `r.idempotency_key = k.idempotency_key`; `test_g9_the_skip_pattern_ends_a_committed_record_skipped_not_verified` shows it, and `test_g9_a_pending_record_cannot_be_marked_verified` (also part of the matrix) shows `pending → verified` is still rejected.
2. **Empty or in-file duplicate keys never become ledger rows — the insert guard only.** A row without an `idempotency_key` is rejected (`test_g9_a_row_without_an_idempotency_key_is_rejected`). No input-review code was written.
3. **A commit-attempted record leaves `failed`/`parked` through `reconciling`, or straight to `pending` only when the same `UPDATE` sets `destination_checked_by`.** Both allowed paths and the rejected path are tested (`test_g1_a_commit_attempted_failed_record_can_go_to_reconciling`, `..._can_be_requeued_after_a_destination_check`, `..._cannot_return_to_pending`).

## Deviations from the ticket, and why

- **Two existing files changed beyond the ticket's list** (`test_migration_runner.py`, `seed.py`) — see "Read this first". Both are forced by the migration and neither weakens an assertion.
- **`make` is unavailable**, so `python -m db.migrate` (the exact command the `migrate` target runs) was used.
- **The transition guard fires on `UPDATE OF state, attempts, max_attempts`** rather than `state` alone. The ticket requires attempts/max_attempts to be unwritable; a trigger on `state` alone would not fire when only those columns change, so the trigger had to widen to enforce it.
- **The gap tests use `TRUNCATE ... CASCADE`.** A plain `TRUNCATE` of a table referenced by a foreign key is refused by Postgres before any trigger fires; `CASCADE` lets the statement reach the statement-level trigger under test. A plain `TRUNCATE` is still refused (by the foreign-key check), so the table is protected either way.

## New dependencies, and why

None.

## Open questions for the owner or T1

1. **`failed → pending` / `parked → pending` with `destination_checked_by` are still allowed from a plain application write.** The guard trusts that whoever set `destination_checked_by` is a person. A CHECK that the column is set only by a role, or a required `approvals` row of kind `requeue`, would close that. Out of this ticket's scope.
2. **`lease_epoch` is incremented only by the takeover pattern**, which is documentation in this ticket. The runner (PL-013) must implement it, or the lease does nothing.
3. **The `destination_key` backfill.** Existing development rows keep `destination_key = NULL`; they do not collide (NULLs are distinct in the index), but a run created before 0002 has no destination and cannot be deduplicated. A backfill from the workflow is possible if wanted.
4. **`run_record_transitions` has no retention policy.** It grows with every transition; personal-data retention for append-only tables is explicitly out of scope.
5. **`attempts` is still writable by the trigger only on `pending → claimed`; recovery never resets it.** Matches the spec; noted so T1 can confirm it is intended.
