### B1 — a failed condition check reached the runner as a real "no" (R1 defeated)

`checkCommandCondition` returned `false` for a missing tab, a throwing evaluate, and a malformed
condition; `command-session.ts` sent that as `condition passed:false`, which `browser_executor.py`
read as an answered "no" — a failed duplicate search then took the `else` branch and created the
lead again.

- `service-worker.ts`: `checkCommandCondition` now returns `{ok:true, passed}` only for a completed
  poll, and `{ok:false, reason}` for every other outcome (no tab, attach or evaluate failure,
  an unrenderable condition, a withdrawn command).
- `command-session.ts` (`onCommand`, the `check` branch): an `ok:false` answer is sent as
  `result status=refused`, never as a `condition`.
- Tests: `command-state.test.ts::a check that could not be evaluated is refused, never answered
  false` (asserts no `condition` frame and a `refused` result); the runner side is already pinned by
  `test_a_condition_with_no_answer_is_not_an_answer` and `test_a_refused_check_is_reported_as_refused_not_as_false`.

### B2 — the bound tab was not restored after a worker restart (R5)

`commandBoundTabId` was set only by `bindActiveTab`, so after an MV3 restart every step failed
"no tab is bound".

- `command-session.ts::restore()` now adopts `stored.boundTabId` through the new
  `SessionDeps.restoreBoundTab`, which confirms the tab still exists; when it does not, the session
  announces `event tab_closed` on the next `open`. Restore never binds the active tab.
- `service-worker.ts` supplies `restoreBoundTab` (`chrome.tabs.get` then set `commandBoundTabId`),
  and `onOpen` sends the queued `tab_closed` event.
- Test: `command-state.test.ts::a restore adopts the stored bound tab and reports it when the tab is
  gone` (asserts the stored id is adopted — not the active one — and that a missing tab emits
  `tab_closed`).

### B3 — a command kept running after the socket dropped

`onClose` cleared the in-flight command, but `runStep` had no abort, so an abandoned dispatch could
still click after the runner had written it off as `lost`, and a new command could run concurrently.

- Each command gets an `AbortController`; `onClose` aborts the current one and marks the command id
  `unwinding`.
- `beforeInput` is threaded from the session through `step-runner` into `dispatch.ts`, and runs
  immediately before **every** trusted input CDP call (`Input.insertText`, the Backspace pair, the
  three mouse events of a click, the select's value write, and `Page.navigate`). It throws when the
  command was withdrawn or has expired.
- A new command is refused while `unwinding` is set; the aborted command's own `finally` clears it,
  so the block lasts exactly as long as the unwind.
- Events are sent only inside `current()`.
- Tests: `command-state.test.ts::a socket close mid-dispatch aborts the command before its next
  input` (the second input never happens) and `::a new command is refused while an aborted one is
  still unwinding`.

### B4 — the hub sent `peer_ready` with no extension attached (S5 defeated)

- `hub.py`: `peer_ready` is now sent to the runner only when the extension is attached (the
  extension's own `peer_ready` is likewise sent to it only when a runner is attached).
- `test_hub.py::test_the_hub_never_queues_a_command_for_an_absent_peer` asserted the wrong
  behaviour (T1 authorised correcting it: it was written in this ticket) and now asserts no
  `peer_ready` is sent to a runner with no extension.

### B5 — attach race in the hub

- `hub.py`: in both `executor_socket` and `runner_socket` the token match / expiry check and the
  slot reservation now happen inside `_sessions_lock`, and the slot is reserved **before**
  `await websocket.accept()` yields. A refusal is decided under the lock and issued after it.
- Test: `test_hub.py::test_two_concurrent_attaches_with_one_token_leave_exactly_one` — two threads
  attach with the same token; exactly one receives the `session` frame and one is refused with 4401
  or 4403, and the session is left claimed.

### B6 — the navigate load-event race (the last e2e failure)

Confirmed as diagnosed. `dispatchNavigate` subscribed to `Page.frameNavigated` /
`Page.loadEventFired` only after `Page.navigate` replied, and `chromeDebuggerTransport` has no event
buffer, so a fast page's load event was dropped and the wait burned its whole timeout; a late load
event from the previous document could also settle it, since the main frame id is unchanged.

- `dispatch.ts`: `startLoadWatcher` subscribes and buffers **before** the send, and settles only on

  `loadEventFired` after it. A reply with no `loaderId` is a same-document navigation and resolves
  without waiting.
- Tests (vitest): `a load event that arrives before the navigate reply still settles the wait`;
  `a stale load event from the previous document does not settle the wait`; `a same-document
  navigation resolves without waiting for a load`; plus the existing `a navigate waits for the load
  event` and `a command-mode navigate waits for the timeout on the wire`, updated to carry a
  `loaderId`.

## Update after the T1 timeout fix: the deadlines agree, and one defect is left

T1 found the cause of the failures in the section below: it was never latency, it was a **timeout
mismatch**. `browser_executor._result_budget` waits `step.timeout_ms or 0` plus 5s, so a step that
names no `timeout_ms` (every fixture navigate and fill) was written off after 5s, while the
*extension* was free to spend a default of its own (8s for a navigate's load wait) and R4 then
paused the run. The old section's "measure where the five seconds go" was the wrong next step.

**The rule the fix implements, for every command** (T1's words, verbatim in
`internal/agent/reports/PL-014-plan-review.md`'s follow-up): the runner always puts an explicit
`timeout_ms` on the wire — the step's own value, or the run loop's `fallback_timeout_ms` when the
step has none — and the extension uses that value and never its own default for command-mode steps;
the runner waits for the reply for `timeout_ms` + 5s slack, and the wire `expires_at` is that same
deadline; for a commit dispatch the ack deadline and `expires_at` are the step's resolve timeout +
5s, and the extension still re-checks `expires_at` before any input, so R4 holds.

Where it lands:

- `services/runner/run_loop.py` (`_command`): `timeout_ms` is now written onto the wire for *every*
  command — the step's own value, else `fallback_timeout_ms` (10 000ms by default).
- `services/runner/browser_executor.py`: `prepare`, `dispatch` and `perform` all mint the wire
  `expires_at` from `_result_budget` (the same number they then wait for); a commit dispatch's ack
  deadline is that same instant, replacing the bare 5s ack budget.
- `apps/extension/src/executor/step-runner.ts`: `stepTimeoutMs()` gives a step's own waits the
  timeout the runner stated; in command mode a step that arrives without one is **refused** rather
  than given an extension default. `dispatchNavigate` is now called with it.
- `apps/extension/src/background/service-worker.ts`: the command session tags its step deps
  `commandMode: true`.

### The one remaining defect: a navigate can miss its own load event

The failures in both runs (and the third in the full suite, which parks before it can reach the
commit window) are all one thing: `dispatchNavigate` reports "the page did not finish loading ...
within 10000ms" for a static local page that loads in milliseconds. It is nondeterministic per
navigate — `bo` verified in the batch run and parked on the same fixture page in the suite, and `di`
is the mirror image — which rules out the page and points at the wait itself.

Mechanism, from the code and not from speculation: `apps/extension/src/executor/dispatch.ts`
(`dispatchNavigate` → `waitForLoad`) sends `Page.navigate`, awaits its reply, and only *then*
subscribes to `Page.frameNavigated` / `Page.loadEventFired`. `apps/extension/src/executor/cdp.ts`
is a thin adapter with **no event buffer** — `chromeDebuggerTransport.on()` adds a
`chrome.debugger.onEvent` listener, and an event that arrives when no listener is registered is
dropped. For a fast local document the load event can be delivered between the navigate reply and
the subscribe, and the wait then burns its whole timeout. It is also self-masking: on a slow page
(human-scale, or a loaded machine) the event arrives after the subscribe and the step passes.

I did **not** fix this: the brief for this pass is the timeout rule, and it says "no other changes".
The fix is one of (a) subscribe to the load events *before* sending `Page.navigate`, or (b) buffer
events in `chromeDebuggerTransport` so a late subscriber can still see them; (a) is smaller but has
to decide the frame filter before `frameId` is known, (b) is the more general repair and would also
protect `waitForCondition`'s event-driven paths. Either deserves its own ticket and its own e2e run
rather than being smuggled into this one.

### The defect T1 corrected (kept for the record)

Before T1's diagnosis this section read "the extension sometimes takes longer than 5s, so measure
where the five seconds go". That was wrong in an instructive way: the five seconds were never spent
being slow — they were the runner's `0 + 5s` budget, and the extension's legitimate 8s wait was
never given the chance to finish. The R4 behaviour it described (stop, flag a detach, pause
`executor_disconnected`, leave the record `pending`) is unchanged and still correct.

### The six defects this pass fixed

1. **A guard's event was never sent (R6).** Only `policy_blocked` emitted an `event`; a challenge, a
   login wall and an off-origin page produced a bare `result refused`. The runner therefore parked
   the record instead of releasing it and pausing the run. `ExecutorError` now carries an optional
   `event`, the guards fill it in, and the session sends the event **before** the refusal.
   Proven by `command-state.test.ts::a guard failure sends its run-level event before the refusal it
   causes`; and end to end, the challenge and login cases now pass.
2. **The destructive guard judged the ladder, not the control.** It read the name from the step's
   `targets`, so a recipe pointing at `#danger` was never refused — the button's own accessible name
   was never consulted. `resolveTargetInPage` now reports the matched element's accessible name, the
   guard uses it, and the check moved after resolution in both command mode and the attended
   executor. Proven by
   `executor-hardening.test.ts::refuses a click by the resolved accessible name, not the ladder's
   declaration` plus two companions.
3. **`box.state` never followed the write-ahead.** The record loop's box stayed `filling` after
   `begin_commit` had written `submitting`, so an event drained in the commit window asked the ledger
   for an illegal `filling -> pending` and the run paused `internal_error`. Proven by
   `test_a_disconnect_mid_save_parks_the_record_without_a_duplicate` reaching its assertion.
4. **A condition check did not drain events (R6).** The assertion is an executor call, so an event
   that arrived while it ran had to beat its result; it did not, so a disconnect during the assertion
   parked the record and paused the run `canary_failed` instead of `executor_disconnected`. Drains
   added after the assertion, the branch condition and the gate condition.
5. **The hub's `close` never told the runner.** `POST .../close` detached the extension's socket
   without sending `peer_gone`, so the runner kept waiting for a reply that could not come. The
   announcement is now a shared, idempotent `_announce_gone`, so the endpoint and the retire that
   follows it send exactly one `peer_gone`.
6. **The debugger was attached and detached per command.** Six-plus CDP round trips per command, plus
   an attach each time, which is what pushed a command past the ack budget. The debugger is now
   attached once for the session's life and dropped when the session goes idle or disconnected; a
   command also no longer resolves its target twice (the element the guards approved is the element
   acted on).

### The one remaining defect as it looked before T1's diagnosis (superseded)

Every remaining failure has the same cause, and it is a budget mismatch rather than a wrong state:

```

  the extension did not answer within the command budget)]
```

The extension sometimes takes longer than `DISPATCH_BUDGET_SECONDS` (5 s) to answer a command on a

why the batch got *worse* before it got better: it used to hide the latency behind `parked` records
with a misleading reason.

Not fixed, and the honest next step: measure where the five seconds go. The candidates, in order,

service worker's wake cost. Raising the budget instead is not available: `DISPATCH_BUDGET_SECONDS`
feeds the heartbeat-headroom rule, and `test_the_default_timeout_has_headroom_for_the_largest_legal_recipe`
pins 3x120s + 5s against the 365 s default, so a larger budget would break an existing test.

### The bugs the end-to-end run found (and fixed)

The e2e suite earned its keep before it went green: it caught five defects in shipped code that the unit suites
and the scripted fake could not see. Each is fixed and committed in `4d5ca05`.

1. **The wire expiry used a monotonic clock.** `BrowserExecutor` stamped `expires_at` from
   `time.monotonic()`, while the extension compares it to `Date.now()`. Every command arrived looking decades
   expired, and every record parked with *"the command expired before it was received"*. Wall clock now.
2. **`_command` never carried the step's `url`.** A rendered `navigate` step reached the extension with no
   destination at all (*"the navigate step has no usable URL"*). It is rendered now, like every other field.
3. **A value source arrived as a bare literal.** `_render_value_source` returns the resolved value, which the
   extension refused (*"cannot resolve a value source of kind undefined"*). It now travels as
   `{kind: "constant", value: ...}` — which is also the honest boundary: the runner resolves values, the
   extension does not.
4. **`prepare` performed the action.** The extension's command handler resolved *and* performed for every
   command, so a commit's `prepare` would click Save and its `dispatch` would click Save again. A `prepare` now
   stops after resolving and hit-testing, sending no input (the plan's R2), and `navigate` is performed without
   resolving a ladder it does not have.
5. **`value_equals` compared against nothing.** `_render_condition` rendered every predicate except
   `value_equals`, so a condition's expected value was empty and a branch comparing a field against the record's
   own value matched the empty field instead. Both sides fixed: the runner renders the value source to a
   literal, and the extension reads it from the condition.

Items 1, 2 and 3 are worth T1's attention precisely because they were invisible to every green test: the fake
executor never inspects a step, and the extension unit tests inject a `runStep` stub. Only a real browser
against a real hub could fail them.

## The existing-test changes I had to make (flagged, per the brief)

  tracking the reply budget, and it grew a companion (`test_a_step_without_a_timeout_reaches_the_extension_with_the_fallback`)
  that pins the fallback case. If T1 would rather keep prepare's roomier TTL, the one line to change back is the
  `ttl=budget` in `BrowserExecutor.prepare`.
