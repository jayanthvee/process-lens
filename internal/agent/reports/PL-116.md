## 1. A busy button is waited on inside the existing ready wait

**Before.** `resolveStepTarget` (`apps/extension/src/executor/step-runner.ts`) re-climbed the ladder
only when `measureTarget` said `no longer in the document`. The ladder's busy refusal
(`the target is busy (disabled | busy | not taking clicks)`, PL-113 S3) came back through
`measureTarget` and the prepare returned it on its first look. On the owner's Goodlabs sign-in the
Continue button shows a spinner for a moment after the email is typed; the record parked in about a
second. The failing test's own run:

```
ExecutorError: the click target could not be resolved:
  the target is not clickable: the target is busy (not taking clicks)
```

**After** (`apps/extension/src/executor/step-runner.ts`, `resolveStepTarget` only):

- a `measureTarget` refusal containing `the target is busy` is treated as a wait reason beside the
  re-render case: nothing is pressed, the ladder is climbed again after `READY_WAIT_POLL_MS`, and
  the loop is bounded by the existing `prepareDeadline` (`readyWaitMs(step)` -- the step's own
  timeout share). No new timeout and no new constant;
- if the ladder can no longer see the target during that wait (the page disabled it, or it went
  away), the last busy sentence is kept. When the deadline passes the step fails with the same busy
  message as before, so the runner's busy check still recognises it;
- `runStep`'s click path, `ladder.ts`, `services/runner` and the schema are untouched. The prepare
  sends no input while waiting.

**Tests.** `apps/extension/tests/pl116-busy-click.test.ts` (2 tests), driving the real resolver and
guards through `dispatchCommandStep` with `fakeCdp` and `installLayout`:

- *waits while the button takes no clicks, then prepares and clicks it once* -- the button is busy
  (`pointer-events: none`) until the second measure and then enabled. The command returns `done`,
  exactly one `Input.dispatchMouseEvent` press is sent, and the explicit measure ran more than
  once. **Before the fix this rejected with the busy sentence immediately.** The busy state is
  released by the measure count, not by a timer, so the test cannot race a slow machine.
- *fails with the busy message after the ready wait, and sends no click* -- the button stays busy;
  a 400 ms step (250 ms ready wait) rejects with `/the target is busy/`, no press is sent, and the
  target was measured more than once. **Before the fix it failed on the retry count: one measure,
  because the prepare never waited.**

`pointer-events` is the state the test uses because the ladder's own resolver already waits on
`disabled` and `aria-busy`; `pointer-events: none` is the busy form that reaches the separate measure
and is therefore the gap this ticket closes. The first test also covers the reported spinner shape:
the button is busy, then enabled while the same prepare is waiting.

### A first version stranded a username sign-in

The first version (commit `6242032`) hid the whole `.panel-key` block for any sign-in. For an
identifiable value that is right, and it is what the ticket asks for. But a sign-in whose typed
value is none of an email, an id or a person's name (a plain username such as `jsmith`) gets no
default key, so `keyColumn` is `""`. With the block gone there was no way to choose one while
`Save as task` stays disabled on `values.length > 0 && keyColumn === ""` -- a dead end, and a
change to something other than the three elements the ticket names. The added test failed against
`6242032` for exactly that reason (no combobox, `Save as task` disabled):

```
Unable to find an accessible element with the role "combobox" and name
  "Which value is different for every row?"
```

`885877e` hides the block only when the key is already decided (`keyColumn !== ""`), and leaves the
note out in both sign-in branches. A sign-in with an identifiable key looks exactly as the ticket
asks; a sign-in without one can still be saved.
