Status: done · Agent: T2 DeepSeek · Commit: a027553 (branch `pl-010`)

## Summary

The extension now has an attended executor at `apps/extension/src/executor/`. It
attaches `chrome.debugger` to the active tab, resolves each target by climbing the
5-rung ladder inside the page, and replays a compiled recipe with real CDP input:
keystrokes through `Input.dispatchKeyEvent`, a click through `Input.dispatchMouseEvent`
at the element's box center, a select through a value update, and a navigation
through `Page.navigate`. Every step that carries an `assert_after` is verified by
polling its condition up to `timeout_ms`, and the run is fail-closed: an assertion
that never holds stops the run. Start, pause, resume, and abort are exposed over
the extension's messaging channel, and the popup drives them. The executor makes
no model calls and holds no workflow state of its own.

Proved live: the built extension replayed a compiled recipe against a real
Chromium tab through `chrome.debugger`, and the page ended with the typed email,
the chosen option, and the confirmation the assertion required.

## Deviations from the ticket, and why

- **The resolver is a self-contained function injected as source, not a bundled file.** It must run in the target page, not the extension; keeping it as one function (`resolveTargetInPage`) that the executor serializes with `.toString()` means the page needs no bundled script and no globals, and the unit tests can call the same function directly against a document.
- **The control messages touch `shared/messages.ts`, the service worker, and the popup.** Scope item 5 says "via extension messaging"; a message channel needs a sender, a handler, and an owner of run state. The run itself lives in the service worker, so a content script keeps holding no state.
- **The executor performs exactly `navigate`, `fill`, `select`, and `click`.** Any other action is skipped and reported in the run summary rather than performed or guessed. The commit-capable action `upload_file`, and `wait_for`/`assert`/`end_record`, are the runner's or a later ticket's concern.
- **Visibility is judged from the `hidden` attribute and computed `display`/`visibility`, not layout rects.** `getClientRects()` is empty in jsdom, so a rect-based test would be untestable; the chosen test is the one that also behaves sensibly in a browser for the common cases.
- **A native `<select>` is set directly; a custom combobox is opened and its option clicked.** The ticket names "locate the `<select>` option and dispatch a value update"; a non-native combobox has no value to set, so the executor clicks it open and clicks the matching option by the same ladder.
- **Frame support resolves the frame's execution context and runs that step's page calls in it; a click inside a nested frame is best-effort.** CDP mouse coordinates are viewport coordinates, while the resolver measures a box inside its own frame, so a nested-frame click is confirmed by the step's assertion rather than assumed. Documented at the top of `frames.ts`.
- **The popup's Run button reads the recipe and input row from `chrome.storage.session`.** A recipe picker is product UI that does not exist yet; the message API (`executor:start` with a recipe and row) is the real entry point, and the popup surfaces start/pause/resume/abort over it.

## Open questions for the owner or T1

1. **`upload_file` is commit-capable but not performed here.** Should the attended executor grow it (a `DOM.setFileInputFiles` dispatch), or does a file upload belong to a later ticket?
2. **The destructive-control guard is not enforced.** A `click` step carries `allow_destructive_control` and `on_failure`; the executor currently performs the click it is given. Should the executor refuse a destructive control, or is that the runner's approval gate?
3. **Nested-frame clicks** use viewport coordinates and are verified by assertion only. Is a frame-aware coordinate translation worth a follow-up, or is a top-frame-only click the accepted limit?
4. **Where a run's recipe and input row come from.** Today an operator loads them into `chrome.storage.session`; a picker (and a connection to the API) is later product work.
5. **Run state is not yet written to the ledger.** The extension reports a run summary over messaging; the ledger state machine stays the runner's job, which keeps the extension out of workflow state.
