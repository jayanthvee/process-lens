## The blocker: the harness's extension binding never becomes ready

Every e2e attempt failed identically at `tests/e2e/conftest.py:1479` — `bind_extension_to`
clicks the popup's Connect and waits 30 s for `session-state` to reach `ready`; it never does:

1. **Invoice golden, run 1** (worktree venv: playwright 1.64.0, chromium-1248): `ERROR at setup
   … TimeoutError: Page.wait_for_function … Timeout 30000ms exceeded`, 176 s.
2. **Invoice golden, run 2** (T1's interpreter from the main checkout: playwright 1.63.0,
   chromium-1243 — the exact environment that passes the quotation golden): the same
   `bind_extension_to` timeout, 106 s. **Two identical failures of the same command — stop rule
   applied.**
3. **Quotation golden, run once at the end** (the ticket's own cross-check): the **same** fixture
   timeout, 106 s. This golden passes for T1 on this very branch, so the failure is the
   environment, not the new files.

What the probes established (`scratch under .cache/pl063/`): the extension **does** load in the
persistent Chromium (the popup opens, its service worker starts on demand, `session-state`
reaches `pairing`), and Odoo itself was reset and healthy before each run (reset ≈ 130 s each
time). The broken half is the pairing handshake between the popup/service worker and the
session hub — the same failure this worktree produced for PL-048's golden runs (see
`internal/agent/reports/PL-048.md`), before this branch's `pl-048b` fixes landed. It is not new
to these tests, and it is not mine to fix here (no product or harness changes in this ticket's
file list).

**Because no run got past fixture setup, there are no replay observations to report yet** —
not the invoice rows' park/pass state, not whether the price rows park at "open the record the
search found" (the recorded click's rungs name the demonstration's product; a replay row's
search returns a different product, so that step is the most likely product finding), not the
second-run dedupe shape, not whether the popup proposed the duplicate branch, and not whether
the compiled `idempotency_key` carries `{{row.sku}}:{{row.new_price}}` (the compiler's default
is the record key alone, so the last assertion is the expected finding). All of these are set
up to land in the trace files on T1's first successful run.

## For T1

1. Run the three goldens from the main checkout (the environment where the binding handshake
   works). The tests are written to self-report through their trace files.
2. Expected findings, in the order a replay meets them (to confirm, not conjecture):
   - **Price golden — "open the record the search found".** The recorded click on the searched
     row carries the demonstration's product in its rung names; a replay row's search returns a
     different product, so that click cannot resolve. Smallest product change: let the compiler
     parameterize a click rung's name from the record-key column (the way option rungs already
     are), or give the runner an "open the one result of this step's own search" step kind.
   - **Price golden — idempotency key.** The compiler sets `idempotency_key = record_key`
     (compiler.py:334); an update workflow needs the new value in it
     (`{{row.sku}}:{{row.new_price}}` per RECIPE_SPEC), otherwise a later, different price
     change to the same product is refused as an already-committed key.
   - **Price golden — duplicate branch.** The popup auto-proposes the skip-if-the-search-finds-
     it branch when the recording holds a search; for an update that would skip every row. The
     person can untick it (the test does, and traces it); the popup could propose it off for
     update-shaped flows.
3. The binding-handshake failure in this worktree is the same one PL-048 reported; worth one
   look in the main checkout's working environment to find what this worktree lacks.
