## 1. `services/ai`

**Before.** `services/ai` held one `.gitkeep`. Nothing in the product could call a model, and no
code held a provider key.

**After.** Four modules, one public entry point, no provider SDK imported anywhere:

- `service.py` — `AiService.find_target` and `AiService.clean_recording`. Each runs the same
  pipeline in `AI_BOUNDARIES.md` order: validate the input against the call type's schema; apply the
  data policy and redact; call the model with no tools; validate the output against the output
  schema; run the call type's code check; write the `ai_calls` row; return a typed result.
  `find_target`'s gate is: the token exists, it is unique, the element is visible and enabled, the
  role fits the action (fill → textbox/searchbox/combobox, select → combobox/listbox, click → not a
  field, check → checkbox/radio/switch, press → a field), and it is not destructive unless the step
  allows it. `clean_recording`'s gate allows only dropping and naming: every recorded step exactly
  once, no added step, no kept step without an intent, no intent over 300 characters.
- `client.py` — the `ModelClient` protocol (one method: `complete(model, system, user)`), the
  DeepSeek implementation over the OpenAI-compatible chat API with
  `response_format={"type":"json_object"}`, `thinking: disabled`, `temperature: 0`, no tools, and no
  SDK import (`urllib` only). Pricing per 1M tokens lives here so the ledger's cost is computed, not
  guessed.
- `redact.py` — removes every typed value (`value`, `typed_value`, `input_value`) from snapshot
  elements and recorded steps, drops keys that could be a secret, and masks emails and phone numbers
  in page text.
- `schemas.py` — the two input schemas, the two output schemas (both closed objects), and the two
  system prompts, which say page text is data and never instructions.

The provider sits behind `ModelClient`, so another provider is one class and no caller changes.
With no key, `AiService.from_env` builds a service with `client=None`, `find_target` answers
`unavailable`, and nothing raises. A tenant whose `data_policy` does not allow the provider gets
`unavailable` without a call. A schema or gate failure retries once on
`DEEPSEEK_ESCALATION_MODEL` when it is set, and each attempt is its own `ai_calls` row with
`escalated_from`.

`.env.example` now carries `DEEPSEEK_MODEL=deepseek-flash` and
`DEEPSEEK_ESCALATION_MODEL=deepseek-v4-pro`.

**Tests.** `tests/ai/test_ai_service.py` (14) and `tests/ai/conftest.py`. Covers: a found token; a
typed value absent from both the prompt and the stored request; a schema failure logged as
`validation = 'fail'` that escalates once with `escalated_from` set; a token not in the snapshot; a
destructive button; a text box for a click; `not_here`; no key → `unavailable` with no `ai_calls`
row; a closed tenant policy → `unavailable` with no call; `clean_recording` keep/drop/naming; an
added step refused; a recorded value stripped; and an invalid input raising before the model is
reached.

## 2. Page snapshot (extension)

**Before.** The extension had no command that returned page structure. The recorder's
`content/snapshot.ts` reads field state for diffing and is not addressable from the runner.

**After.** `apps/extension/src/executor/page-snapshot.ts` exports `pageSnapshotInPage`, written as
one self-contained function so `snapshotExpression()` can serialize it into the tab with
`Runtime.evaluate`, exactly like the ladder resolver. Each element carries a short token (`e1`,
`e2`, …) also written to the element as `data-pl-snap`, plus role, accessible name, label,
placeholder, clipped visible text (excluding every input, textarea, select and contenteditable
subtree), the nearest preceding heading, visible and enabled, tag, and its own ladder. Password,
hidden and file inputs are skipped before any read. A page off `allowed_origins` returns nothing at
all. Iframes are never entered. The cap is 400 elements, nearest the viewport first, with an
internal scan bound of 2000 candidates so a very large page cannot stall the tab.

`command-protocol.ts` gained the `snapshot` command; `command-session.ts` answers it from an injected
`readSnapshot`; `service-worker.ts` implements that over the same debugger `ensureDebugger` already
holds; `browser_executor.py` sends it with the command's own lease, expiry and origins and parses the
answer.

The `snap` rung resolves only the element carrying `data-pl-snap="<token>"`. It sorts before every
recipe rung, it never falls back to a role or name, and an unknown token is a refusal.

**Tests.** `apps/extension/tests/pl122-snapshot.test.ts` (6) and `pl122-snap-rung.test.ts` (3). The
snapshot never contains `hunter2` (a password), `typed-secret-799` (a search box's value),
`hidden-secret` (a hidden input) or `typed note` (a textarea's text, including through its parent
card); every token is on its element; an off-origin page yields nothing; 450 elements cap at 400 with
`truncated`; a frame's content is absent; the function works after `toString()` serialization; and
the `snap` rung resolves one tagged element, resolves a token the snapshot just wrote, and fails on
an unknown token. `tests/runner/test_browser_executor.py` gained 2 wire tests: the command is a
`snapshot` carrying `allowed_origins` and no step, and a refusal raises `SnapshotUnavailable` rather
than looking like an empty page.

## 3. Run-time finding (runner)

**Before.** A step whose ladder resolved to zero elements (or more than one) parked the row after the
extension's ready wait. That is the owner's price task: `branch-1` looks for a table cell, the list
shows cards, and all three rows parked in 6 s.

**After.** `services/runner/finding.py` holds `TargetFinder` (memory reads and writes, and the one
call to `AiService.find_target`) and `find_failed_reason`. In `run_loop.py`:

- A non-commit step whose result is a *missing* target — never a busy, covered or off-page one —
  first retries with the remembered ladder for any of the recipe's origins; if that fails, it takes a
  snapshot and asks `find_target` with the step's intent, action and recorded targets as hints; on a
  token it sends the step again with `{"by": "snap", "value": "<token>"}` first and the recorded
  ladder behind it.
- A commit step does the same at `prepare`, before any input and before the write-ahead, so a find
  can never make a locator failure look like a commit attempt.
- The step's `intent` is used when present; otherwise its `name`, then its id. Templates in the
  intent are rendered with the row.
- Success stores the element's own ladder (role+name, label, css — sanitised, five rungs at most) in
  `target_memory`.
- `not_here` or a failed gate parks with exactly `ProcessLens couldn't find '<intent>' on this page.`
  A step event with `outcome = 'failed'` is written under the step.
- The cap is 6 model calls per record, checked before the call, so the 7th never happens. Reaching it
  parks the row with the same sentence.
- `step_events.locator_rung` accepts only 1–5, so a `snap` rung is logged as no rung rather than as a
  number the recipe format never defined; the executor's own `by` still says how it found it.
- With no key the finder is unavailable, no snapshot is taken, and the row parks exactly as before.

**Tests.** `tests/runner/test_pl122_find_target.py` (11). On the owner's fixture: the row carries on
when the product is a card (both the branch question and the click are found, and the click's retry
starts with `{"by": "snap", "value": "e7"}`, after which the row parks only at the recording's own
last step); a second run uses the memory and makes no model call; a branch asks its intent when the
card is present; `not_here` keeps today's answer; a token not in the snapshot, a destructive button
and a text box for a click each park with the sentence; the 7th call is never made (6 calls, 6 snap
retries, then parked with `open product 7`); no key parks as today with no snapshot and no
`ai_calls` row; a commit's `assert_after` never asks a model; and a snapshot with no readable origin
(multi-origin recipe) is unavailable with no `ai_calls` row and no `target_memory` write, rather than
an exception out of the loop.

## 4. `target_memory`

**Before.** No table remembered an element. A step that missed was recomputed from the recipe alone.

**After.** `db/migrations/0014_target_memory.sql`: `target_memory` keyed by
`(tenant_id, workflow_id, step_id, origin)`, holding `ladder jsonb`, `hit_count`,
`last_used_at`, `created_at`. One row per step per site, updated in place. It is read before
`find_target` on the next run. A recipe is never written.

**Tests.** `tests/db/test_target_memory_migration.py` (2): an upsert returns the same row and counts

enumerates every migration file).

## 5. Conditions use it too

**Before.** An `element_present` / `element_absent` condition whose targets found nothing took
today's answer, so the owner's `branch-1` always believed the search found nothing.

**After.** A branch is eligible only when its condition is exactly one of those two kinds and the
branch it would take ends the record for a person (`end_record` with `outcome` `parked` or
`skipped`). Then: memory is re-asked as `element_present` first; if that fails, the condition's
intent is asked as `find_target` with action `present`; a hit answers the condition as though the
element had been found, and the ladder is remembered. `not_here` keeps today's answer — the branch
still fires, so the row still parks with the owner's own sentence. A commit's `assert_after` never
reaches this path, and no condition can produce `verified`: `_person_condition_kind` returns `None`
for anything else.

**Test.** Same file: the branch asks when the card is present, and `not_here` keeps
`No search called ‘Oak Standing Desk’ was found.`

## Cost and model input size

Measured by serialising the exact redacted `find_target` payload and estimating tokens at 4
characters per token — an estimate, not a bill. DeepSeek's peak rates are used, so these are upper
bounds (off-peak is half).

- **The fixture's page as the runner test sees it** (one card, three hints): 826 characters,
  ~207 tokens in, ~10 out → **$0.000074** per call on `deepseek-flash`.
- **A representative Odoo kanban product list** (18 elements: search, menu item, three cards, tabs,
  All Apps, Close menu, back button, pager, heading, New): 5,556 characters, ~1,389 tokens in →
  **$0.000429** per call.
- **A full 400-element snapshot**: 118,786 characters, ~29,697 tokens → **$0.008921** per call.

A row that needs two finds costs about a tenth of a cent; the 6-call cap bounds one record at about
5 cents on a full snapshot. The provider reports real usage in `usage.prompt_tokens` /
`completion_tokens`, and that is what `ai_calls.tokens_in`, `tokens_out` and `cost_usd` store once a
real key is present.

## Not verified

- **No real model call was made.** There is no `DEEPSEEK_API_KEY` in this workspace, so neither the
  DeepSeek client nor the prompt was exercised against the provider. The trial's answer quality,
  latency and real token counts are the owner's run to establish.
- **No browser was driven.** The extension's page function is tested in jsdom and through a fake
  socket; the snapshot has not been taken from a real Odoo tab, so its element choice on that page is
  unconfirmed.
- **PL-123 is what writes `intent` at teaching.** PL-122 consumes it and falls back to the step's
  name. Until PL-123 lands, the owner's existing recordings have no intents, which the fallback
  covers but does not replace.
- The whole suite passes with `DATABASE_URL` from `.env`; the tests create and drop their own
  databases, so a Postgres on `localhost:5432` is required.
- **One flaky extension run.** During the final gate sweep, one run of the full extension suite
  reported `2 failed | 816 passed`. Four subsequent full runs (and the `check` chain in between)
  passed 818/818, and the failing log was not captured, so the two tests are unidentified. Treat it
  as load-sensitive flakiness in an existing timing test, not as a PL-122 failure — but it is
  unproven, and worth watching if the gate fails in CI.
