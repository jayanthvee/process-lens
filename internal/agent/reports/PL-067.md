# PL-067: Runs go at a person's pace, stay under a daily cap per site, and stop at a warning page

Owner: T2 (GLM Flash) · Reviewer: T1 · Branch `pl-067`

## Status: **done — all gates green**

Pacing, the per-site daily cap, and the warning-page markers are in, each behind tests written
first. No fingerprint, user-agent, webdriver or mouse-path changes: pacing is a rate limit, not
a disguise, and a warning page stops the run instead of being worked around.

## 1. Pacing (`services/runner/run_loop.py`)

- **Settings on the run row.** `runs` had no settings JSON, so migration `0010_run_pacing.sql`
  adds `min_seconds_between_rows` and `min_seconds_between_steps` — nullable smallints with one
  CHECK of `0..3600` (NULL = unset = 0 = today's behaviour). The ledger guard is untouched.
- **The waits.** `_pace` waits at least the gap, plus a jitter of 0–25% of it, entirely through
  the injected `Clock` (`clock.pause`), in slices of at most one second; each slice re-reads
  `runs.status` and `cancel_requested_at` from the database, so **a pause or cancel during a
  wait is noticed within about a second**. The row gap is measured from the previous claim and
  only runs when a row is left to claim (`has_pending_records`, appended to
  `packages/ledger/reads.py`); the step gap is measured from the previous executor command, in
  `_run_steps`. A stop during a step wait releases the record the same way the step boundary's
  own pause does (`filling → pending`, attempt refunded).
- **Reads.** `run_pacing_settings(conn, run_id)` (read once per run), `has_pending_records`.

## 2. The daily cap per site (`packages/ledger/reads.py`, the runner, the API, the run page)

- **The setting.** `tenants` had no settings column, so `0010` adds
  `settings jsonb NOT NULL DEFAULT '{}'`; the cap lives at `settings->'site_daily_caps'` as
  `{origin: number}` (`tenant_site_caps`).
- **The check.** Before claiming any row, the runner counts this tenant's rows that entered
  `submitting` today (UTC) on runs whose pinned recipe's `meta.allowed_origins` includes the
  origin (`site_rows_submitted_today`, reading the append-only transition audit). At the cap the
  run pauses with `pause_reason = 'site_daily_cap'` **before** claiming: every record stays
  `pending`, nothing reaches the commit window, and the ledger's invariants are untouched. A run
  with no row left to claim completes instead of pausing.
- **The run page.** The API's `/api/v1/runs/{id}` carries `site_cap: {origin, limit, used}`
  while that pause stands (`run_site_cap`, appended to reads). `words.ts` gains
  `siteCapWords` ("Paused: today's limit for linkedin.com (25 rows) is reached. It can continue
  tomorrow.") and `siteCapReached`; `RunDetail.tsx` shows the sentence in the pause line and
  **keeps Resume on the same screen, disabled while the count stands**, with the sentence beside
  it.

## 3. Warning pages (`apps/extension/src/executor/guards.ts`)

`challengeOrLoginInPage` gains one list inside the page-side function (it is serialized into the
page, so the list must live in its scope): visible text "unusual activity", "we've restricted",
"too many requests", "verify you're human", "temporarily blocked", "security check", and the
title "Security Verification" — matched case-insensitively, and **only on page-level surfaces**:
the document title, a visible `h1`–`h6`, or a visible dialog's text. Never the page's body copy
and never an input's value, so a LinkedIn job description that merely says "security check" does
not stop anything. Every hit raises the existing `challenge` event; nothing is clicked or solved,
and the reason names the page: *"The site showed a warning page ('unusual activity'). Check it
yourself, then Resume."*

  run completes); the cap pauses with `site_daily_cap` before claiming (all records pending, zero
