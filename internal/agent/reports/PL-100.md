# Report PL-100

Status: done (T2) · Branch `pl-100` · Reviewer: T1

## Summary

Every zip now says which build it is. A package is written as
`processlens-<version>-<date>-<commit>.zip`, its built manifest carries the same stamp as
`version_name` (which Chrome shows on `chrome://extensions`), and the popup prints it at its foot.
`npm run bump` moves the patch version in both `manifest.json` and `package.json` so a release has
something to bump.

Nothing about the source `manifest.json` changes on a build: the stamp is written only into
`dist/manifest.json`, and the version stays `0.1.0` on this branch, as the ticket asked.

## Files changed

- `apps/extension/scripts/release-lib.mjs`:
  - `packageExtension({ ..., stamp })`. `stamp` is `{ date: "YYYYMMDD", commit: "<short sha>" }`.
    When it is not given, the date is today's local date and the commit is
    `git rev-parse --short HEAD` run with `cwd` set to the extension root; any git failure (no
    git, not a repository, a detached toolchain answering nothing) yields `nogit`.
  - The zip is `processlens-<version>-<date>-<commit>.zip`.
  - After the build, `dist/manifest.json` is rewritten with
    `"version_name": "<version> (<date> <commit>)"` before validation, so `validate-package.mjs`
    validates exactly what is zipped. The build's own `options.dist` is honoured throughout.
  - `bumpVersion({ root })`: reads `manifest.json` and `package.json`, refuses anything that is not
    `N.N.N` (naming the version in the error), prepares both rewrites, and only then writes both.
    The rewrite is surgical — it replaces the one `"version"` value and leaves the file's layout
    alone — so a bump's diff is the version digits, not a reformat.
  - `readJson` strips a byte-order mark on read, so a `package.json` saved with one still parses.
- `apps/extension/scripts/release-lib.d.mts`: `ReleaseStamp`, `PackageOptions.stamp`,
  `BumpOptions`, `bumpVersion`. The declarations are what `tsc --noEmit` checks the tests against.
- `apps/extension/scripts/bump.mjs` (new): prints the new version, exits 1 with one line on a
  version it cannot read.
- `apps/extension/package.json`: `"bump": "node scripts/bump.mjs"`.
- `apps/extension/scripts/package.mjs`: the header comment names the new zip name. The command's
  output is unchanged — it still prints the zip path.
- `apps/extension/src/popup/build-label.ts` (new): `buildLabel(manifest)` and

  `renderBuildLabel(document, chrome.runtime.getManifest())`.

## Review

Two independent reviewers were dispatched; the first failed before reading anything — its route
was Anthropic-pinned and the account is out of credit (`400: Your credit balance is too low`), so
it contributed no findings. The second (DeepSeek `reviewer-deepseek-flash`) returned **FAIL** with
one MAJOR and four minor findings. Each was checked rather than taken at face value:

- **MAJOR, "every modified file is a whole-file CRLF rewrite" — false.** Its `numstat` numbers
  (e.g. 455/365 for `release-lib.mjs`) reproduce only under `git -c core.autocrlf=false diff`.
  This checkout has `core.autocrlf=true` and *every* tracked text file is CRLF in the work tree,
  including ones this branch did not touch (`README.md`, `scripts/build.mjs`). Git normalises on
  `add`, so the staged diff is 222 insertions / 7 deletions, and `git diff --check` is silent. No
  change was made for this.
- **MINOR, stale install doc — real, fixed.** `INSTALL-EXTENSION.md` still promised
  `processlens-<version>.zip` and hand-editing the manifest per release.
- **MINOR, `bumpVersion` leaves a byte-order mark behind — real, and the fix is constrained.**
  Stripping the BOM is *required*: `release-version.test.ts:45` parses the bumped file with a bare
  `JSON.parse`, so a preserved mark makes the ticket's own spec fail (I tried it and saw that
  failure). The bump therefore writes plain JSON, and the commit it produces carries a one-line
  change to line 1 of `package.json`. The JSON round-trip was also replaced with a surgical text
  replacement, because `JSON.stringify` reflowed `manifest.json`'s inline arrays (16/5 lines) for a
  one-number change.
- **MINOR, `package-lock.json` keeps `0.1.0` — noted, deliberately not changed.** See below.
- **NIT, the popup test did not cover the popup's own manifest source — real, fixed.**
  `popup-build.test.ts` now also asserts `popup.ts` wires
  `renderBuildLabel(document, chrome.runtime.getManifest())`, so a hardcoded version cannot pass.

The reviewer also could not run `npm run check` (its shell refused npm); the parent ran it, twice,
before and after these fixes, and it passes.

## Notes for T1

- **One file outside `apps/extension/` changed**: `internal/docs/INSTALL-EXTENSION.md`. The
  ticket's out-of-scope list covers the Python side, the hub and Render, not docs, and leaving this
  one alone would have told the owner at release time to hand-edit `manifest.json` and hand out a
  zip named in a way this ticket removes. It is prose only; drop it if you would rather it were
  its own ticket.
- **`apps/extension/package-lock.json` still says `0.1.0` after a bump.** The ticket names exactly
  two files, so `bumpVersion` writes exactly those two; bumping the lockfile as well would change
  what the spec's `bumpVersion` test asserts about the world. The next `npm install` will bring the
  lockfile's two `version` fields along. If you want them in step, it is a one-line change in
  `bumpVersion` and a second assertion in the spec — say the word.
- **The `nogit` fallback has no test.** The spec's default-stamp test only runs where git works.
  The branch is exercised by inspection (`spawnSync` returns `status: null` with `error.code
  === "ENOENT"` when the binary is missing, which falls through to the fallback) and cannot be
  asserted by the frozen spec tests without faking `git`.
- The stamp is taken once, at package time, and used for both the zip name and `version_name`, so
  the two can never disagree.
- `git rev-parse --short HEAD` names the commit that is checked out, not the commit the working
  tree would produce: `npm run package` with uncommitted changes stamps the last commit. The
  install doc tells the owner to commit the bump before packaging for that reason.
