# PL-016 — From a recording to a running recipe

Branch: `pl-016` (first commit: the ticket file). Status: **implementation complete, all gates
green, 20/20 requirement changes proved by revert, one adversarial review pass applied.**

The ticket's two halves are both closed: the recorder and the runner are connected (a recording
can be compiled over HTTP and stored where **Run** reads it), and the seven recorder bugs the
owner found by hand — plus navigation recording and the second page load — are fixed with a test
each. No e2e or Playwright work was done; the whole-chain proof is PL-016b, and the messy fixture
is in place as its target.

## What changed

**Requirement 1 — the compile route** (`services/api/compile.py`, `services/api/main.py`,
`services/api/middleware.py`, `packages/compiler/`).
`POST /api/v1/recipes/compile` takes `{recording, name, when_to_use, sample_row,
record_key_column, allowed_origins, commit_step_ids}`, calls
`compile_recording(recording, CompileOptions(...))` and returns `{recipe, warnings}`. It stores
nothing and imports no database. A `CompileError` is a 422 whose `detail` is
`{message, problems:[...]}` — every problem, with the missing `assert_after` named in the text. The
front door now exempts exactly two paths from the own-origin rule, and both only for the pinned
`chrome-extension://{PROCESSLENS_EXTENSION_ID}`: the session route (as before) and
`/api/v1/recipes/compile`. `/api/v1/runs/{id}/cancel` still refuses the extension origin — there is
a test for exactly that.

`parse_events` also learned the recorder's `navigate` kind: where the page moved on its own is a
recorded fact, not an action, so it becomes no step and earns no warning. An unknown kind still
warns.

**Requirement 2 — "Make recipe" in the popup** (`apps/extension/src/popup/make-recipe.ts`,
`popup.ts`, `popup.html`, `popup.css`). After Stop the form asks for the workflow name, the record
key (from the recorded values) and the commit step (the **last** click pre-selected). It posts the
recording to the route, shows the warnings, and on success stores the recipe under
`processlens:executor-recipe` and the sample row under `processlens:executor-row` — the two keys
`Run` already reads. A 422 shows the problems and stores nothing. The form also takes in
`record:appended`, so an observation that lands a moment *after* Stop is still compiled (this was a
review finding; see below).

**Requirements 3–10 — the recorder**
(`apps/extension/src/content/recorder.ts`, `apps/extension/src/background/recorder-session.ts`,
`apps/extension/src/shared/fingerprint.ts`, `shared/events.ts`, `shared/messages.ts`,
`shared/recipe-types.ts`, `service-worker.ts`, `manifest.json`).

- **(3) Observations survive a full-page save.** The page that sends a click and unloads says so
  (`pagehide` → `record:leaving`); the worker keeps that step as the target of the navigation; the
  page that lands is handed the target, watches for `role=status` / `role=alert` / live-region /
  toast text for three seconds from load, and reports it; the worker attaches it to the click. The
  target is handed out **once**, only to the top frame of the recorded tab, and it is persisted, so
  a worker restart between the click and the destination does not lose it.
- **(4) A `<select>` is one event.** A select's `input` is no longer buffered, and its `change`
  clears any buffer, so the `focusout` that follows cannot invent a second `fill`. A
  `role="combobox"` field is also one event: typing it is a `fill`, choosing from it is a `select`,
  and a `change` that merely repeats an already-recorded value is not a second step.
- **(5) Step ids are the session's.** The worker mints ids from one counter per action for the whole
  recording and rewrites the provisional id the content script sent, so a page load cannot restart
  the count. `restore` reads the counters back out of the stored ids, so a worker restart keeps
  counting up.
- **(6) Navigation is recorded.** `chrome.webNavigation.onCommitted` (new `webNavigation`
  permission) records a `navigate` event with the URL for a typed URL, a bookmark, a reload, and
  back/forward (the `forward_back` qualifier), and not for a link or form submit, a subframe, a
  redirect/script, a second tab, or while recording is off.
- **(7) No invalid role names.** `label` is no longer mapped to a role at all, and a role outside
  the schema's `^[a-z][a-z0-9-]*$` falls back to the tag. A click on a `<label>` is recorded against
  the control it labels.
- **(8) An icon button is recorded by its own name.** The resolver takes the innermost *named*
  button-like element first, so the ✕ inside a recipient chip is recorded as `button "Remove …"`,
  never as the chip, option or form around it. The ✕'s own `title` now outranks its glyph text when
  the accessible name is computed, which is why the name is "Remove alice@example.test" and not "×"
  (the executor's resolver computes names the same way, so the recorded rung still matches).
- **(9) Generated ids are not selectors.** `isStableToken` drops any id containing `:`
  (Gmail's `:1a`, React's `:r1:`), and already dropped long hex runs and numbered rows
  (`a3f9c2b41d`, `row-0042`). `#lead-email` and `#lead-save` are still kept. A step always keeps its
  other rungs, and the positional path means no step is ever left without one.
- **(10) Rich-text fields are captured.** Typing into a `contenteditable` is one `fill` with the
  element's text, on `input`/`focusout` like a text field, and the typed text never enters a target
  rung. It is never recorded inside a credential context: a password field, an
  `autocomplete="off"` container, or a form/dialog that holds a password field.

**Requirement 11 — the messy fixture** (`fixtures/sites/messy-crm/`). A stdlib-only, in-memory site
in the lead-crm pattern, with its own `selftest.py` (77 checks) and README: ids minted fresh on
every load in three shapes (`:1a`, `:r1:`, a hex blob), a recipient field with autocomplete and
removable chips whose ✕ carry `aria-label="Remove <name>"` in the *served* markup, a
contenteditable notes box, a full-page `POST /save` → 303 → `/saved.html` rendering
`<div role="status">Saved</div>`, a second page and a way back, and `@example.test` values only.
The recorder's own tests also drive the fixture's real served HTML
(`apps/extension/tests/recorder-messy-fixture.test.ts`).

Two honest notes on this list. First, requirement 8's test fails on the *name* half of the change

## What is still not recorded

The ticket asks for this list, and it is the honest complement of the fixes above.

**Keyboard-only edits (out of scope by the ticket — no `press` action in the schema):**

- **Enter in a field** to submit a form with no clickable submit control: the `submit` event is
  captured but carries no step, so the compiler drops it with "dropped a form submit with no
  identifiable control" and the commit step is missing. Enter on a form that *has* a submit
  control is fine (the control is recorded).
- **Tab / Shift-Tab** between fields: focus movement is not an action.
- **Escape** closing a dialog, menu or picker.
- **Arrow keys / Home / End** in a listbox or a combobox list: choosing an option by keyboard sets
  the value and fires `change`, so the value is captured — but *how* it was chosen is not, and the
  open-the-list keystroke is not recorded at all.
- **Space** on a checkbox or radio: the resulting `change` is captured as a click step; the
  keystroke itself is not distinguished from a mouse toggle.
- **Keyboard shortcuts** (`Ctrl+S`, `Cmd+Enter`, `Ctrl+K`): invisible to the recorder.
- **Typing while a `contenteditable` is inside a credential context**: deliberately not recorded.

**Other interactions the recorder never sees:**

- **File uploads.** `type="file"` inputs are skipped entirely (`onInput`/`onChange` return early),
  so an attachment is not recorded even though the schema has an `upload_file` action. A step of
  that kind can only be written by hand today.
- **Drag and drop**, including dropping a file onto a page.
- **Hover-revealed controls.** A menu that opens on hover is not recorded; only the click inside it
  afterwards is, so replaying the recipe can fail to find the target.
- **Right-click / context menus**, and anything done in browser chrome: back/forward *buttons* are
  recorded (as `navigate`), but zoom, print, downloads, new tabs and tab switching are not.
- **Shadow DOM.** Events from inside a shadow root are retargeted to the host, so a click on a
  custom element's inner button is recorded against the host element.
- **Canvas / WebGL surfaces** (Google Sheets cells, Maps): there is no element to describe.
- **Text selection**, copy, and paste-as-rich-text: a paste fires `input` and is captured as a
  `fill` for a plain field, but not for a `contenteditable` in a credential context, and formatting
  is not preserved.
- **Script-driven route changes** (`history.pushState` with no click): observed only as a
  `url_matches` observation for the preceding action; they do not become `navigate` steps.
- **Multi-tab recordings.** Events from any tab are appended to one recording, and the tab the
  recording follows for navigations is whichever tab last sent an event. A demonstration spread
  across two tabs mixes them.
- **A confirmation that appears more than three seconds after a full-page load**, or one that is
  not text (an icon, a colour change): the arrival window closes and the commit keeps only the
  navigation-derived assertion.
- **A click whose target exists only after an `alert`/`confirm` dialog** is handled by the
  browser's own modal, not by the page: the dialog is never recorded or dismissed.

## Review pass (one, as the ticket requires)

A read-only adversarial reviewer was given the branch and the eleven requirements, and told to
refute each. It filed two MAJOR findings and several minor ones. Both majors were reproduced by
hand before being fixed, and the fixes have their own tests:

- **MAJOR — arrival evidence could be attached to the wrong page or frame.** `all_frames: true`
  means every frame runs the content script, and the worker handed the pending target to any
  asker, first-come-first-served; a chat widget, an ad frame or a later unrelated load within the
  window could supply a click's `assert_after`. Fixed: the target is handed out **once**, and only
  to the top frame of the recorded tab (`senderIsTheRecordedPage`); the tab check is now strict
  (`recordedTabId !== null`), `record:start` forgets any outstanding target, and the target is
  persisted so a worker restart does not lose it. Tests:
  `recorder-session.test.ts` ("hands the target to one page only", "owes nothing to the previous
  demonstration once a new one starts", "survives a worker restart").
- **MAJOR — one entry into a `role="combobox"` text field recorded two steps** (a `fill` and a
  `select`). That field is exactly the messy fixture's recipient input, the shape PL-016b will
  drive. Fixed: a combobox the person typed into is recorded as one `fill` of what it holds; a
  value chosen without typing is one `select`; and a `change` that repeats an already-recorded
  value is not a second step. Tests: four cases in `recorder-capture.test.ts` under
  "a role=combobox field".

The reviewer's minor findings were fixed where cheap and recorded where not:

- **Fixed:** a stale popup event list (the popup now merges `record:appended`, so an observation
  arriving just after Stop is still compiled).
- **Refuted by reading, kept:** the `forward_back` qualifier admitting a click-into-a-backed page
  adds a `navigate` event, but `parse_events` drops `navigate` silently and no step is affected;
  likewise the `role="label"` mapping, which is now absent by construction.
- **Not implemented, and reported as such:** requirement 9's "a step left with no rung at all is
  recorded with a warning". No such step can exist — `stableSelector` always falls back to a
  positional path — so no warning channel was added; if T1 wants the warning as a belt for a
  future selector change, it is a small addition to `makeEvent`.
- **Not tested:** the service worker's `sender.frameId`/`sender.tab` gate (no worker harness in
  this repo), and `isCredentialContext`'s decision to stop at the nearest form/dialog boundary.

## Still not recorded into the repository

- **No e2e or Playwright proof.** By the ticket's design; PL-016b owns it.
- **No Chrome run.** Every extension test is jsdom plus the fixtures' real HTTP servers; the
  recorder has never been driven by a real Chrome against `messy-crm`.
- **No schema change.** None was needed; `packages/recipe/schema/` is untouched.
- **No `press` action**, so the keyboard gaps above stay gaps.
- **The scratch artefacts** (the revert-proof driver, its JSON log, the hand-check driver and its
  two JSON outputs) live under `.cache/` and are **not committed**; the numbers they produced are
  quoted above. If T1 wants the driver committed as a tool, say so and it can move to `tools/`.
- **`.codewhale/agents/*.toml`**: the five `pl-*` profiles could not be loaded at the start of this
  ticket — their instruction strings contained `C:\Users\...`, and `\U` is an invalid escape in a
  TOML basic string, so every spawn failed with "Saved project agent profile `pl-implement` is
  invalid or unreadable ... its route was not replaced with a default". They were repaired locally
  (backslashes doubled; the decoded text is byte-for-byte the same) and all five then loaded with
  `profile_load_issue_count: 0`. `.codewhale/` is in `.gitignore` (line 6), so the repair cannot be
  committed without changing that rule — **T1 should decide**, because without it the ticket's own
  spawn rule cannot be followed.
