## Requirement 2 — claim records in row order

`packages/ledger/records.py` `_CLAIM_RECORD` now joins `input_records` and orders by the input row:

```sql
WITH next AS (
  SELECT rr.id FROM run_records rr
  JOIN input_records ir ON ir.id = rr.input_record_id
  WHERE rr.run_id = %(run)s AND rr.state = 'pending' AND rr.attempts < rr.max_attempts
  ORDER BY ir.row_index, rr.id
  FOR UPDATE OF rr SKIP LOCKED
  LIMIT 1
)
UPDATE run_records r
SET state = 'claimed', claimed_by = %(worker)s, claimed_at = now()
FROM next
WHERE r.id = next.id
RETURNING r.*
```

`FOR UPDATE OF rr` keeps the lock on `run_records` alone (as before); the lease check in
`claim_record` and the `input_record_id NOT NULL` foreign key are untouched. The matching pattern in
`internal/docs/sql-patterns.md` (§ Claim the next record in a run) is updated.

## Requirement 3 — the messy chip-removal replay gap

### Diagnosis (one visible run, `PROCESSLENS_E2E_HEADED=1`)

**What the page showed at click-3.** At every step boundary of the replay the driven compose page
showed exactly one chip, the pre-rendered `alice@example.test`, with its ✕ named
`Remove alice@example.test`. The row's two chips — the one the row adds, and the one it then
removes — were **never present**: the Add clicks added nothing, so `click-3`'s role rung
`Remove {{row.add_recipient_2}}` matched nothing and the step parked
("no rung of the target ladder resolved to exactly one element"). The fixture's own save during the
demonstration stored `{alice@example.test: 1}` with notes `""` — i.e. the demonstration's own Add
clicks had added no chip either, and its notes never reached the form.

**Root cause.** The fixture's autocomplete listbox, `.suggestions`, was **in normal document flow**.
Opening it (the debounced `/recipients.json` render after typing) reflowed the page and pushed the
Add button down: measured in the fixture, the button's box centre moved from y≈228 to y≈273. The
executor measures a click target's box once (`measureTarget`), then dispatches the mouse
press/release at that measured point; a listbox that opens between the measure and the mouse events
moves the button out from under the click, which lands on the listbox and adds nothing. Reproduced
deterministically with raw `page.mouse.click` at the pre-open centre — no chip added, the fixture's
own `addChip` never ran. A second, independent defect: the demonstration leaves the compose page
(the "Second page" leg) and returns with Back, and a plain fixture reload dropped the composer, so
the demonstration's own save persisted only the pre-rendered chip and empty notes.

**This is the fixture behaving unlike a real site**, so the fixture is fixed (per the ticket: "if
the fixture behaves unlike a real site, fix the fixture and say why").

### Fix (fixtures/sites/messy-crm/public/)

- The suggestion listbox is now an **overlay**: the input, the Add button and the listbox sit in a
  `position: relative` `.combo`, and `.suggestions` is `position: absolute; top: 100%`. Opening it
  moves nothing on the form, and the Add button is beside the input, out of the listbox's path —
  exactly how a real autocomplete behaves.
- The composer keeps a **draft**: `app.js` persists the chips and the notes to `sessionStorage` as
  they change and restores them on load, and clears the draft on submit. A real CRM keeps a
  half-filled composer across the Back round trip; a browser replays the flow by re-navigating.
- `index.html` and `recipients.html` gained the `.combo` wrapper (the markup, ids, labels,
  `aria-*`, `data-testid`s and the ✕-in-chip nesting are otherwise unchanged; the fixture selftest
  still passes all 77 checks).

### Test

The `xfail` marker is removed from `tests/e2e/test_record_compile_run_messy.py` in the same change,
and the fixture is reset right after the recording so the run's three saves are the only ones the
state assertions see. The test passes as written in PL-016b requirement 2 (`1 passed`).

## Requirement 4 — duplicate check, from a recorded search

**Compiler** (`packages/compiler/compiler.py`). `CompileOptions` gains `duplicate_check: bool = True`
and `park_fields`; the compile route (`services/api/compile.py`) carries both.

- `detect_record_key_search` finds a `fill` whose recorded constant equals the record key column's
  sample value, **immediately followed by the click that runs it** (a control that
  `_looks_like_a_search` recognises — a `searchbox` role, or a name/value/text/within mentioning
  "search"), with the create's own commit still to come. No search means no branch.
- The detected search click is **demoted** from commit (the search button submits its own form, so
  the recorder collapses it into a commit; it reads the destination, it does not change it) and the
  branch is rendered straight after it:
  `{action: branch, when: {text_visible: "{{row.<key> | lower}}"}, then: [{end_record, skipped,
  reason: "duplicate"}]}`.

**Make recipe form** (`apps/extension/src/popup/make-recipe.ts`, `popup.html`, `popup.css`). A
**"Skip a record if the search finds it"** checkbox (`#make-duplicate`) is pre-ticked when
`searchDetected(events, key)`, and re-evaluated when the key changes. Unticked, `duplicate_check` is
false and the compiler makes no branch. With no search, the box is disabled with the hint
`Record a search for the key first to turn on the duplicate check`. The compiler never invents a
search — and, importantly, neither does the form: `searchDetected` mirrors the compiler's
"looks like a search" check, so a wizard's `fill → Next` is not mistaken for one.

**Safety.** R1 from PL-014 stands and is untouched: an unanswered check parks the record and takes
neither branch.

**Tests.** Compiler `packages/compiler/tests/test_pl017_rules.py`: the branch and the demoted search
click are produced from a search recording, none without one, none when `duplicate_check=False`, and
none for a wizard `fill → Next`. vitest `popup-make-recipe.test.ts`: pre-ticked and
`duplicate_check: true` when a search is detected; unticking sends `false`; disabled + the exact hint
+ `false` with no search.

**Revert-proof.** Reverting `compiler.py` to HEAD fails the three feature-asserting compiler tests
(`TypeError: CompileOptions.__init__() got an unexpected keyword argument 'park_fields'`); reverting
the extension files fails 10 `popup-make-recipe` cases. Both restored, green.

## Requirement 5 — required fields

**Recorder** (`recorder.ts`, `recipe-types.ts`, `events.ts`). The recorder notes whether each filled
or selected control is `required` (`el.required === true`) or `aria-required="true"`, and attaches
`required: true` to the **event envelope** — never to the step (the recipe schema forbids an unknown
step property, and `apps/extension/tests/schema-conformance.test.ts` enforces exactly that).

**Make recipe form.** Each input field gets a **"Park the record if this is empty"** checkbox
(`#make-park-fields`, one `data-column` checkbox per column), pre-ticked for required fields and for
the record key; the key's row follows the key select. Ticked fields become `input_schema` rules
(`{when: {missing: <column>}, then: park, reason: "missing <column>"}`), so the record parks before
any fill.

**Tests.** Compiler `test_pl017_rules.py`: the rule is produced for the ticked columns (and none when
none are ticked). vitest: pre-ticked for a required field and the record key, unticked for an
optional one, the body carries exactly the ticked columns, and the key's row follows a key change;
`recorder-capture.test.ts` asserts `required: true` on the envelope (native `required` and
`aria-required`) and no `required` on the step.

**Revert-proof.** Same reverts as requirement 4 (the compiler tests and the popup tests fail; one
`recorder-capture` case fails without the recorder change).

   `searchDetected`, with a new compiler test (`test_a_wizard_fill_then_next_is_not_a_search`) and a
   form test.
5. *The branch condition ignores scope and key case.* Conservative by construction: an unmatched
   lowercased key **never skips**, so a miss is safe (no duplicate check is a safe failure). No
   results region was recorded in either golden recording, so unscoped is per the requirement.
   `text_visible` case-sensitivity is runner/extension behaviour a browser run would settle; not
   changed.
6. *Park rules are prepended to caller rules.* Noted; precedence intended (park before any input).
   No mixed-rule test exists in this ticket's scope.
7. *Hardcoded branch-internal `end-record-1` id.* Noted; a second branch could collide. Left as-is
