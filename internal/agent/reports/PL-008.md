## Summary
The compiler now exists in `packages/compiler/`: it takes the recorder's event stream and produces a recipe that
validates against `packages/recipe/schema/recipe.schema.json`. It drops focus/blur/scroll noise, folds fragmented
keystrokes into one `fill` per field, folds a click and the submit it caused into a single commit step, binds the
recorded literals to input columns (both as step values and inside target rungs that carry the record's value), and
gives each commit step an assertion — from the caller, else from what the recording observed, else from a navigation
it observed, and otherwise it refuses rather than guessing. The compiler validates its own output against the schema
before returning. One hundred and three compiler tests cover every stage and the refusals; the full suite is 293
passing, and a recording captured from the real extension in a browser compiles into a schema-valid recipe.

## Deviations from the ticket, and why
- **A caller-supplied assertion was added (`commit_assertions`).** The ticket asks the compiler to infer
  `assert_after` from observed DOM changes. The **recorder does not yet capture observations** (PL-007 records the
  interaction, not what the page showed after it), so inference alone cannot produce a compilable recipe from a real
  recording. A human builder must be able to decide the assertion anyway — the design has them mark a step as a
  commit in the editor — so the caller's assertion is the highest-priority source, and inference is used when it is
  absent. The fail-closed property is unchanged: with no assertion from anywhere, the compile fails.
- **A rung that echoes the value being typed is not templated.** The extension's `text_fuzzy` rung for a text field
  carries the typed value. Templating it would produce a rung that cannot match before the value is set, so it is
  left as recorded. This is a deliberate reading of "parameterization": bind the record's values, not the input's own
  echo. Recorded in `parameterize.py` and covered by tests.
- **`jsonschema` moved to runtime dependencies** (outside the ticket's Scope): the compiler validates its own output
  at compile time, so the dependency is no longer test-only.
- **Tests, the event builders (`testing.py`), and the error type were added**; the ticket asks for unit tests, and
  the builders keep the input shape in one place rather than copied across seven test files.
- **A contract test against PL-007's output shape lives in the suite.** The captured browser recording itself is not
  committed (it is a run artifact, and the port would be noise); `test_pl007_recording.py` reproduces its structure
  with synthetic values.
- **The compiler is a Python package under `packages/compiler/`,** the first of the two paths the ticket offers. The
  alternative (`services/runner/compiler.py`) would have put pure code in a service that owns the ledger.
- **Local, gitignored, not part of the deliverable:** `.data/pl007_capture.mjs` (the browser capture harness),
  `.data/pl007_events.json` (the captured stream), and `.data/compile_real_recording.py`.

## New dependencies, and why
- No new dependency. `jsonschema` was already present for the schema tests; it moves from the development extras to
  the runtime dependencies because the compiler validates at run time. The compiler itself is pure standard library.

## Open questions for the owner or T1
1. **The recorder does not capture post-action observations.** This is the one place the recorder and the compiler do
   not meet: assertion inference needs the page's state after the action (a confirmation appeared, a dialog closed, a
   value changed, the URL moved). Without it, every real recording needs a caller-supplied assertion. Should the
   recorder learn to capture observations — a small addition to PL-007's content script — as its own ticket?
2. **Where the input schema comes from.** The compiler accepts `input_fields`, or derives string fields from the
   sample row. The design has the user upload a CSV and review the parsed input; who owns the CSV-to-`input_schema`
   step — this compiler, or the input-review service?
3. **Assertion inference breadth.** Only the six condition predicates in the schema are read from an observation.
   Should the recorder emit a richer observation (an element's role and name, a dialog's title) so the compiler can
   produce a more precise assertion than a page-text match?
4. **The fuzzy rung's quality.** The extension emits a `text_fuzzy` rung that, for a text field, is the typed value.
   The compiler leaves it in place. Should the recorder stop emitting a value-based fuzzy rung for input fields, and
   should the compiler drop rungs it can prove are unusable?
5. **Compiling several recordings.** One demonstration produces one recipe. Use case 1 needs a branch ("the search
   found a match → skip") and precheck rules, which are builder decisions a single recording cannot imply. Should the
   compiler grow an "apply an editor document" step, or does the editor assemble the recipe around the compiled core?
