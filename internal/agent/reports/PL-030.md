## Requirement 1 — `POST /api/v1/tasks` (`services/api/tasks.py`, new)

- Body `{name, recipe}`; the tenant and the person are the configured operator via
  `require_operator_user` (`services/api/operator.py`), used exactly as `workspace.py` uses it —
  inside the request's connection, so an unset `PROCESSLENS_OPERATOR_ID` is a 503 and an id that
  names nobody is a 403. The operator is resolved **before** the recipe is judged, so the 503 is
  the answer whatever the body carries.
- In one transaction: insert the `workflows` row (`destination_key` = the host of the recipe's
  first `meta.allowed_origins` entry, `allowed_origins` from the recipe, `created_by` the operator)
  and store the recipe as version 1. Storage is **reused, not copied**: `store_recipe_version` was
  lifted out of `recipes.ingest_recipe` and both routes call it, so the problems list and the
  immutable version row cannot drift between them. (The refactor first dropped `ingest_recipe`'s
  `change_reason` parameter — the full-gate rerun caught it as a real failure in
  `test_ingest_twice_creates_two_immutable_versions`, and it is fixed; that failure is exactly why
  the gate runs after every slice.)
- Returns `{workflow_id, recipe_version_id}`, status 201. An invalid recipe is a 422 with the same
  problems list `/recipes` gives — asserted by posting the same document to both routes in one
  test. A duplicate task name in the tenant is a 409 with a plain sentence, not a 500 (the
  workflow table's `UNIQUE (tenant_id, name)` is the authority).
- The front door's JSON-only and origin rules are unchanged; `/api/v1/tasks` joined the three
  routes that accept exactly `chrome-extension://{PROCESSLENS_EXTENSION_ID}` (the popup has no
  other origin to present), and a test proves a foreign extension id still gets 403.

## Requirement 2 — the popup saves the task (`apps/extension/src/popup/make-recipe.ts`)

After a successful compile the form POSTs `{name, recipe}` to `/api/v1/tasks` on the same
ProcessLens address (the hub field's value, re-resolved per submit as before). On success
`#make-result` says `<name> is ready. Open it in ProcessLens.` with a link to
`<address>/tasks/<workflow_id>`; the sentence is built from DOM nodes, never HTML, so a task name
is never markup. On failure it says `Could not save the task: <plain reason>`, the reason taken
from the route's own error body and filtered through the same `plainSentences` guard that watches
`#make-warnings`.

**The frozen e2e contract stays** (checked against PL-025's table): every frozen id is untouched
(no markup changed at all — the link lives inside `#make-result`), the words `is ready` and
`Could not` decide success and refusal exactly as `compile_via_popup` reads them, the in-flight
note is still neither, and the two session storage keys are written on compile success exactly as
before — `Try one row` keeps working whatever the save answers. `popup-words.test.ts` (the
frozen-id test) passes unchanged except for one example sentence updated to the new wording.

## Requirement 3 — one command (`scripts/demo.py`, `make demo`)

`python scripts/demo.py --extension-id <id>` (or `make demo ARGS=--extension-id <id>`):

- applies migrations (`db.migrate`);
- makes sure one operator user (owner role) exists in one tenant; its id and a generated runner
  secret live in `.data/demo.env` (already gitignored) and are reused on later starts — but only
  while the stored id still names a `users` row, so a wiped database cannot leave the API
  configured with a person who does not exist (that would be a 403 on every save);
- builds `apps/web` (when `dist/index.html` is missing) and `apps/extension` (when
  `dist/manifest.json` is missing), installing `node_modules` first when needed;
- starts the API on `127.0.0.1:8000` with `PROCESSLENS_EXTENSION_ID` (when given;
  explicitly removed when not), `PROCESSLENS_OPERATOR_ID` and `PROCESSLENS_RUNNER_SECRET` —
  copied from `tests/e2e/conftest.py`'s `api_server`: same uvicorn command, same env shape, log
  to `.data/api.log`, wait for `/health`;
- prints the four steps in plain words and names `fixtures/demo/odoo-inquiries.csv` (8 rows; the
  two already-seeded leads and the no-email row are spelled out);
- **the supervisor** wakes every 2 s, reads `GET /api/v1/executor/session` and the runs a worker
  could take, and starts at most one `python -m services.runner` — the harness's own
  `start_worker` arguments (`--worker-id demo-worker-N --executor browser --session <id> --hub-url
  ws://127.0.0.1:8000 --runner-secret <secret> --poll-seconds 0.5 --max-seconds 90`), `DATABASE_URL`
  and `PYTHONPATH` set the same way, per-worker log under `.data/worker-logs/`. Ctrl+C terminates
  the worker and the API cleanly.

Two supporting reads made the supervisor possible without breaking the rules:

- `GET /api/v1/executor/session` now answers `{"attached": bool, "session_id": str | null}`. The
  session id is the one thing the runner needs and nothing outside the extension could read; the
  four exact-shape assertions in `tests/api/test_hub_session_state.py` were updated with it. The
  sidebar consumes `attached` only, and the hub's socket protocol is untouched (out of scope,
  respected).
- `packages.ledger.reads.list_open_runs` (with `OpenRunRow`) returns every queued/running run with
  whether a live worker holds it, by the same lease rule `find_stale_run` applies. The demo
  writes no ledger SQL of its own (the separation rule; the scan covers `services/` and
  `packages/`, and `scripts/` keeps the same discipline by calling the ledger).

The decision itself is the pure function `worker_decision(runs, session, worker_alive) -> start | wait`:
wait while our worker lives (only one at a time) or while no extension session is attached (a
worker with no browser refuses to claim); start on a queued run or a running run whose lease
lapsed; wait otherwise. Unit-tested with no processes and no database.

## Things worth recording

- **`destination_key` is the bare host; the dashboard's `app` keeps the port.** The ticket says
  the host of the first origin — `urlsplit(...).hostname` — so `http://127.0.0.1:8123` stores
  `127.0.0.1`. The dashboard's existing `app` derivation (`_LIST_TASKS`) strips only the scheme,
  so it shows `127.0.0.1:8123`; both are asserted, separately, in the API test.
- **Save-failure wording overlaps the harness's refusal word on purpose.** A save that fails shows
  `Could not save the task: …`, which `compile_via_popup` reads as a refusal — correct, because
  in that state the task does not exist in the database. The session keys still hold the compiled
  recipe, so nothing is lost locally.
- **The supervisor deliberately ignores `paused` runs.** A paused run waits for a person
  (approval, resume); starting workers at it would fight the product. A running run with a lapsed
  lease is the one takeover case the ticket names, and the ledger read marks it with the same
  rule a takeover uses.
- **The default lease (365 s) is slow to declare a crashed worker dead.** That is the ledger's
  existing constant; the demo inherits it rather than inventing a second timeout. On the happy
  path it never matters — the supervisor's own worker exiting after its 90 s window is noticed
  immediately via the process handle, not the lease.

## What T1 should look at hardest

1. **The e2e harness has no operator configured.** `tests/e2e/conftest.py`'s `api_server` sets
   `DATABASE_URL`, `PROCESSLENS_EXTENSION_ID` and `PROCESSLENS_RUNNER_SECRET` but not
   `PROCESSLENS_OPERATOR_ID` — so the popup's new save call will get a 503 there and
   `#make-result` will say `Could not save the task: …`, which `compile_via_popup` reads as a
   refusal and every golden test asserts against. The fix is one or two lines in the harness
   (seed the operator the fixture's own `operator_id()` already creates, then pin the env var
   before uvicorn starts). I left `tests/e2e/` untouched — the ticket names it as a reference, I
   cannot run e2e to verify a change, and T1 runs the e2e anyway — but the first e2e run on this
   branch **will** hit this. Flagging it plainly rather than shipping an unverified harness edit.
2. **The demo end to end is untested by me, by design.** `scripts/demo.py` runs processes, not
   unit tests: the pure decision is tested, the ledger read is tested against Postgres, and the
   API/worker invocations are copied line-for-line from the harness — but nobody has yet pressed
   Ctrl+C on it or watched it start a worker. That is exactly what T1's real-demo run is for.
3. **`GET /api/v1/executor/session` now carries the session id.** Additive, and the four
   exact-shape assertions were updated, but it is the one contract change outside the ticket's
   three named surfaces — worth a second look in review.
4. **A duplicate task name is a 409** (my call; the ticket is silent). The popup renders it as
   `Could not save the task: a task named '…' already exists`, which reads well, but if T1
   prefers a different status for the same-name case, it is one `except` clause in
   `services/api/tasks.py`.
