## The route chosen for item 1, and why

**The runner's route:** a `wait_for` step is checked in slices of 3 s or less until the step's own
deadline, and every busy slice gets the extension's existing wall probe.

Why not the extension's route: the extension's wait poll (`waitForCondition`) is a tight loop that
evaluates only the recipe's condition, and the code-page look lives one layer up in
`checkCommandCondition`, which visits the page once, after the poll has finished. Teaching the poll
itself to probe would have meant a second page evaluation on every poll of every check in the
product — duplicate searches, read-backs, freshness probes — to fix one step type. Slicing fixes
only waits, and it needs no wire change: `checkCommandCondition` already probes the page
(`probeWallForCheck` → `checkCodePage`) on every busy poll it makes, so a 3 s poll notices a code
page with the machinery that is already there. It also means a run picks the fix up without a new
extension build, which matters because the owner's Chrome is on the shipped one.

The step's total wait is still its own `timeout_ms`: `_wait_for_condition` sets one deadline from
`condition_timeout(...)`, exactly the number the single check used to compute, and the slices divide
it. No new constant for a person to set — `WAIT_SLICE_SECONDS = 3.0` and
`WAIT_CODE_GRACE_SECONDS = 30.0` are runner-side policy, beside `PACING_SLICE_SECONDS`.

## 1. The sign-in wait notices a code page within 5 seconds

**Before.** `sign-in-finished` was one `_check` of 90 s. The extension looked for a code page only
after that check failed, so on the owner's run the code prompt was first noticed at about 06:08:42
— and the email from 06:07:12 was then 90 s older than the code look's own 10 s window.

**After** (`services/runner/run_loop.py`). `_wait_for_condition` loops: each pass asks the executor
for a poll of `min(3 s, time left on the step's deadline)`, and after each pass the run loop drains
events exactly where it did before. A pass that is answered "not yet" is paced out to its own end
(the executor usually spends the whole budget polling; when it answers early the wait still does not
spin faster than the slice). A pass nobody answered is not a "no" — the wait goes on rather than
calling the sign-in finished, and if no pass is ever answered the last verdict is what the step
parks on, as before.

**Test.** `tests/runner/test_pl121_sign_in_wait.py::test_the_code_page_is_noticed_on_a_short_slice_not_after_the_whole_wait`.
The scripted page puts its code prompt up 3 s after Continue and its poll spends its own budget, as
a real one does. The test asserts `page["timeouts"][0] <= 3000` (the run asked for a slice, not the
whole 90 s), that the run asked for the code at `page["asked_at"][0] <= 5.0` s, and that the row
ends `verified`. Seen failing first with `AssertionError: [90000, 90000]` / `assert 90000 <= 3000`:
two whole 90 s waits, the second because the first one's code page had released and re-claimed the
record.

## 2. A code typed during a wait doesn't restart the row

**Before.** `_apply_event` sent every `code_required` whose record was working down the PL-102 path:
release to `pending` (refunding the attempt), then claim again from step 1. For a sign-in that means
reopening `/login` while already signed in and looking for an email box that is no longer there, so
the row parks on the next run.

**After** (`services/runner/run_loop.py`). While a wait is running, `RunLoop._wait_deadline` is set,
and a `code_required` that arrives then and is successfully answered from email keeps the record
`filling`: the same wait goes on, steps 1–3 are not re-sent, and nothing is released or claimed. If
less than 30 s of the wait is left when the code is typed, the deadline is pushed out to 30 s from
that moment (never shortened — `max`), so a dashboard that loads slowly still has time to appear.
When the code is not typed (`entered`/`cleared` not both true), the branch is untouched: the record is
released and the run pauses `code_required` with the extension's own reason, exactly as today. A
`code_required` during any other step is also untouched, because `_wait_deadline` is only set for the
duration of a wait step (restored in a `finally`).

**Test.** `tests/runner/test_pl121_sign_in_wait.py`:

  page moves on, the next check sees `/home/dashboard`; the row is `filling -> verified`, the reason
  is `done`, `committed_keys` has no row, and `navigate-1`, `fill-1`, `click-1` were each sent
  exactly once. Seen failing first with
  `['navigate-1', 'fill-1', 'click-1', 'navigate-1', 'fill-1', 'click-1']` (the restart).
- `::test_a_code_page_near_the_end_of_the_wait_gets_thirty_seconds_more` — the prompt appears at
  85 s and the dashboard takes 20 s; the code is typed at 87 s and the row is still `verified`, with
  the wait asking for more than its own 90 s in total and still exactly one `fill-1`. Seen failing
  first (`assert 2 == 1` on `fill-1`).
- `::test_without_a_code_the_run_pauses_for_the_person_as_before` — the code look answers `none`,
  the run pauses `code_required` with `pause_detail == "none"` and the row is `pending`.
- `::test_a_sign_in_stuck_after_the_code_parks_with_pl117s_sentence` — the code is typed and the page

Two of those six passed before the fix, by design: they are the two "unchanged" cases (no code →
pause; code page outside a wait → release and claim). They are there to catch a fix that changes
behaviour it was not asked to change, so they should pass on both trees.

## 3. The panel's "no code" sentence is PL-119's

**Before.** `apps/web/src/panel/PanelTasks.tsx`'s `codeProblem` built its own sentence for
`pause_detail == "none"`: `No code arrived at <address>. Check that this inbox is signed in to Gmail
in this Chrome, then press Try again.` — which blames the inbox for something Gmail's unread-only
feed cannot show.

**After.** That branch returns `codeFromEmailWords("none")`, the run page's own words:
`No new code email arrived. If you already opened it in Gmail, ProcessLens can't see it — type the
code here.` The now-unused `where`/`email` lookup is gone with it; `"ambiguous"` and every other
detail still go through `codeFromEmailWords`, as before.

**Test.** `apps/web/tests/pl121NoCodeSentence.test.tsx` renders `PanelTasks` over a paused
`code_required` / `none` sign-in task and asserts PL-119's sentence is on screen and

with the text: No new code email arrived. …`, with the old sentence in the printed DOM.
`apps/web/tests/pl112SignIn.test.tsx`'s `says no code arrived at the picked address` asserted the old
wording, so that one expectation was moved to PL-119's sentence and the test renamed; it is the only
existing test whose expectation a sentence change necessarily moves.

  case passes on the real site, from the side panel. This ticket forbids browsers and e2e, so the
  proof here is the fixture replayed through the real run loop against a scripted page: slices of

- **The extension was not changed, so nothing proves the shipped extension's probe fires on a 3 s
  poll in a live Chrome.** The behaviour it relies on (`checkCommandCondition` probing the page on
  every clean `passed: false`) is existing code with its own tests, and the change makes the run ask
  for more polls, not different ones. A code page that only exists mid-poll and is gone by the poll's
  end would still be missed until the next slice.
- **The 30 s grace is not a setting.** A site whose dashboard takes longer than 30 s to appear after
  the code is typed still parks. That matches the ticket ("If less than 30 s of the wait is left …
  it gets 30 s more"); nothing exposes it to a person.
- **`_wait_deadline` assumes one wait at a time.** It is an instance attribute saved and restored
  around each wait, so a wait nested inside a branch's `then` is still correct, but two overlapping
  waits in one loop would not be — the runner is single-threaded per run and no recipe can nest one,
  so nothing needs it today.
