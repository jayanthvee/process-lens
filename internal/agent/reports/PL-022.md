# PL-022 — Real test apps (Odoo 18 and Twenty CRM) running locally

Status: **complete** — branch `pl-022`, pushed for T1. No e2e was run in this ticket.

## What this ticket added

Odoo 18 Community and Twenty CRM now run locally in Docker with seed data and a reset
script, so recording and replay are tested against real software instead of pages we wrote.
Everything lives under `infra/test-apps/` plus one test file. Nothing in `apps/`,
`packages/`, `db/` or `services/` was touched, and the repository root `docker-compose.yml`
was not edited or committed.

| Path | What it is |
| --- | --- |
| `infra/test-apps/docker-compose.yml` | The stack: Odoo + Postgres, Twenty + its server, worker, Postgres and Redis, pinned tags, named volumes, loopback-only ports, mail off |
| `infra/test-apps/.env.example` | Committed test logins and settings (the real `.env` is gitignored) |
| `infra/test-apps/seed_data.py` | The one source of truth for every seeded record |
| `infra/test-apps/testapps_env.py` | Settings loader (`.env`, else `.env.example`) |
| `infra/test-apps/seed_odoo.py` | Seeds Odoo through XML-RPC |
| `infra/test-apps/seed_twenty.py` | Seeds Twenty through its own API |
| `infra/test-apps/reset.py` | `odoo` \| `twenty` \| `all` |
| `infra/test-apps/README.md` | Start, seed, reset, URLs, logins, RAM |
| `infra/test-apps/samples/*.csv` | Use-case inputs (see below) |
| `tests/infra/test_test_apps_samples.py` | CSV shape test, no app or network needed |
| `internal/docs/DECISIONS.md` | D-021 (hosting) and D-022 (test targets) appended |

Pinned images: `odoo:18.0-20260926`, `twentycrm/twenty:v2.47.0`, `postgres:16`,
`redis:7.4-alpine`. Only `127.0.0.1:8069` and `127.0.0.1:3000` are published.

## Things worth recording

- **Two real defects were found and fixed before this report, both by running the code
  rather than reading it.** First, Odoo 18 dropped the `--smtp-server` CLI flag (it is
  `--smtp` now), which made the container crash-loop. Second, and more interesting:
  `stock.quant.action_apply_inventory` returns `None`, and Odoo marshals its XML-RPC
  replies with `allow_none=False`, so calling it fails with "cannot marshal None" *after*
  applying the count server-side — the products step died every time. `_set_on_hand` now
  writes `inventory_quantity_auto_apply`, whose inverse applies the inventory and returns a
  plain `True`. `stock_mismatches: []` is the proof it works: every seeded quantity reads
  back exactly.
- **`reset.py all` is deliberately not fail-fast.** The two apps are independent, so a
  broken Odoo run must not hide that Twenty was never reseeded. Every seeder is attempted,
  both outcomes are reported, and the exit code is non-zero if any failed. Verified by
  simulating an Odoo failure: the Twenty seeder still ran, the failure was named on stderr,
  and the exit code was 1.
- **Twenty's API surface is not what the docs alone suggest.** The core/auth/workspace API
  is `POST /metadata` (`signUp` lives only there, not on `/graphql`); the data API is
  `/graphql` and `/rest`. A workspace is reachable via `signUp` → workspace-agnostic token →
  `signUpInNewWorkspace` → `getAuthTokensFromLoginToken` → `activateWorkspace`, and a token
  minted before activation is refused afterwards, so the seeder signs in again after
  activation. Twenty's own sample people and companies arrive with a new workspace, so the
  reset clears them too and the workspace ends up holding exactly the seeded records.
- **Bulk destroy needs a filter.** `DELETE /rest/people` refuses without one ("Filters are
  mandatory for bulk destroy operations"), so the reset uses a match-all filter
  (`createdAt[lt]:2100-01-01...`) to clear records.
- **Mail is off in both apps.** Odoo has no `ir.mail_server` record (the seeder checks and
  reports `mail_servers: 0`) and its SMTP fallback points at the reserved, non-resolving
  name `smtp.invalid`. Twenty runs with `EMAIL_DRIVER=logger`, a null mailer that logs
  instead of sending.
- **RAM.** About 1.7 GB for the six containers at rest (Twenty's worker ~780 MB, its server
  ~710 MB, the two Postgres instances ~150 MB together, Redis ~19 MB, Odoo ~80 MB idle). It
  fits a 16 GB laptop with room; the README states this.

## Sample CSVs

`samples/usecase-1-leads.csv` (20 rows: 3 duplicate a seeded lead's email, 2 have no
email), `samples/usecase-4-products.csv` (10 rows: 9 known codes, 1 unknown),
`samples/usecase-6-enrollment.csv` (8 contacts with semicolon tag lists, some already
seeded), `samples/twenty-leads.csv` (10 rows: 3 duplicate a seeded person).

`tests/infra/test_test_apps_samples.py` binds them to `seed_data.py` so they cannot drift:
row counts, the three duplicate emails matching real seeded leads by name as well as email,
the two empty emails, the one unknown product code, tag membership, and a synthetic-address
sweep. It needs no running app.

The test catches a renamed duplicate row or a deleted row. It does **not** catch a changed
`phone` or `company` on a duplicate row, and it accepts any `new_price` that is merely
different from the seeded `list_price` — both noted so T1 knows the edges.
