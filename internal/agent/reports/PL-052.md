# PL-052 report (T2): an extension a coworker can install

**Status:** done. Branch `pl-052` (worktree `.worktrees\deepseek2`), pushed, one commit plus this
report. Extension build and docs only: no runner, API or extension logic changed. No private key
was written into the repository and none is committed.

## 1. A fixed id

`scripts/release-lib.mjs` (with `release-lib.d.mts` for types) holds the pieces; the `.mjs` scripts
beside it are thin command lines.

- **`extensionIdFromPublicKey(derBase64)`** -- the first 32 hex digits of the key's SHA-256, with
  `0-9a-f` mapped to `a-p`. That is Chrome's own derivation, so the id printed is the id Chrome
  gives the extension.
- **`npm run make-key`** (`scripts/make-key.mjs`) generates an RSA 2048 key pair, writes the
  private half to `private/extension-key.pem` (mode 0600) and the public half to
  `apps/extension/extension-key.pub`, and prints the base64 SPKI key and the id. It refuses:
  a path git does not ignore (asked of `git check-ignore`, not of a copy of git's rules), and an
  existing private **or public** key -- a second key pair is a second id, and every copy already
  handed out would be refused.
- **`npm run extension-id`** prints the id the committed public key gives.
- **The build** reads `apps/extension/extension-key.pub` and puts it in `dist/manifest.json` as
  `key`. With no key file the manifest is copied byte-for-byte, so the e2e harness's build is
  exactly what Chrome loaded before.
- **`.gitignore`**: `*.pem` and `apps/extension/release/`.

The owner runs `make-key` once and commits `extension-key.pub`; I did **not** commit one. The tests
use a public key generated once for them (its private half was discarded when it was printed), and
`make-key` is exercised against `.cache/` paths only.

## 2. The hosted address as the default

`PROCESSLENS_HUB_URL` is read at build time and baked into the popup bundle as
`__PROCESSLENS_HUB_URL__`, so `DEFAULT_HUB_URL` in `src/popup/popup.ts` is that address when the
build was given one and `http://127.0.0.1:8000` otherwise. The popup's address field still lets a
person change it. Validation is strict: an `http(s)` origin, no userinfo, no path, no query, no
fragment. Anything else stops the build with one line:

> PROCESSLENS_HUB_URL must be an origin like https://processlens.up.railway.app, with no path.

## 3. A package to hand out

`npm run package` builds, runs the repository's own `scripts/validate-package.mjs` against that
build (it now honours `PROCESSLENS_DIST`, so it validates what is about to be zipped), and writes
`apps/extension/release/processlens-<version>.zip`. The zip holds `dist`'s contents at its root, so
unzipping gives a folder "Load unpacked" accepts. It is written by a small store-only zip writer in
`release-lib.mjs` -- no new dependency -- and the tests read the archive back through its central
directory.

`internal/docs/INSTALL-EXTENSION.md` is the one-pager: unzip, `chrome://extensions`, Developer mode,
Load unpacked, pin, open (the address is already filled in), Connect; then how to update. The
owner's section covers `make-key` once, `PROCESSLENS_EXTENSION_ID` on Railway, `npm run package` per
release, and bumping `version` in the manifest.

## Tests

`apps/extension/tests/extension-release.test.ts`, 15 tests, all red before the work (the module did
not exist), all green now. It runs in the node environment (a `@vitest-environment node` docblock)
because esbuild cannot load inside jsdom.

- the id of a fixed, known public key, and that it is 32 characters in `a-p`;
- the manifest carries `key` with a key file, and without one is **byte-identical** to
  `apps/extension/manifest.json`;
- a build given `https://processlens.up.railway.app` bakes it into `popup/popup.js`; a build given
  nothing bakes in `http://127.0.0.1:8000`;
- `hubUrlFromEnv`: origins accepted (with a port), unset and blank fall back, a path, a query, a
  missing host and a non-http scheme are refused with exactly one plain line;
- `package` writes `processlens-<version>.zip` whose entries include `manifest.json` at the root,
  `popup/popup.html` and `background/service-worker.js`, none under `dist/`, and no `.pem`;
- `make-key` writes a private key and a matching public key (the id derives from it), and refuses
  a path git would commit, and refuses to overwrite an existing key pair.

Every build in the tests writes under `.cache/` and is removed afterwards; the tests never touch
`dist/` and never read a private key.

## Notes for T1

- **An existing key pair was found in the worktree after a test run** -- wasted, generated by the
  `make-key` test, which was writing its public half to the default `apps/extension/` path. The
  test now passes explicit paths under `.cache/`, the file is deleted, and `make-key` refuses to
  overwrite an existing public key so this cannot bite the owner. Nothing from it was committed.
- **The e2e harness's build changes once the owner commits `extension-key.pub`**: a plain
  `npm run build` will then add `key` to the manifest and Chrome will give the extension the fixed
  id. That is the point of the ticket, but if the harness asserts the folder-derived id anywhere,
  it will notice. (Nothing in `scripts/e2e-smoke.mjs` names an id; it reads the id Chrome reports.)
- **`validate-package.mjs` gained `PROCESSLENS_DIST`** so packaging can validate the build it is
  about to zip. A plain `npm run validate` still checks `dist/`.
- **The zip is stored, not deflated** (about 1 MB): no dependency, and Chrome does not care.
- **No browser install was done by me.** The zip was unzipped and inspected, not loaded in Chrome;
  T1's install is the real check.
