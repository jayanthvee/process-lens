## 1. A sign-in task saves nothing

**Before.** `compile_recording` took the person's commit choice for any recording. The teaching
screen sends the last click as the commit, so on the owner's Goodlabs sign-in Continue was compiled
`commit: true` with an `assert_after` of `url_matches "/home/"` — the page the *code* step reached,
not the page Continue opens. It could never pass in 8 s, so the run parked before step 4, where the
code is typed. Running it as a commit also gave the email an idempotency key, so one finished
sign-in would make every later sign-in with that email "already done".

**After** (`packages/compiler/compiler.py`, at the top of `compile_recording`):

```python
if options.sign_in:
    options = replace(options, commit_step_ids=[], commit_assertions={})
```

A sign-in is now compiled exactly as PL-112's "Nothing gets saved": no step has `commit`, no step
carries an `assert_after`, and `sign-in-finished` (90 s) is the only proof that the sign-in
finished. The teaching screen no longer sends a click either
(`apps/web/src/panel/PanelTeach.tsx`), so an older panel and a newer compiler agree; and the panel
now says **"A sign-in saves nothing."** where it used to say "The Continue click saves your work.
Change". A sign-in whose landing could not be seen still compiles read-only and still carries
today's warning (`this task is a sign-in, but the recording couldn't see the page after the code…`).

**Tests.** `packages/compiler/tests/test_pl117_sign_in_compile.py` (3):

- *a sign-in has no commit step and no landing check* — the owner's three steps plus
  `sign_in_after_path`, with `commit_step_ids=["click-2"]` still sent by the panel. **Before the
  fix the Continue click was `commit: True` with the `/home/` pattern as its check.**
- *a sign-in ends with the one check that its sign-in finished* — `sign-in-finished`, `wait_for`,
  90 s.
- *the same recording is still a commit when it is not a sign-in* — the rule is scoped; an ordinary
  compile keeps its commit and its observation check.

`apps/web/tests/pl117SignInTeach.test.tsx` (1): the save screen says "A sign-in saves nothing", has
no "… click saves your work" line and no Change button, and the compile request carries
`commit_step_ids: []` with `sign_in: true`.

## 5. Let go of the tab while a run waits

**Before.** The command session kept the debugger attached between commands; nothing ever detached
it except a disconnect. Chrome's `ProcessLens Recorder started debugging this browser` bar stayed on
every window while a run sat parked (or finished) waiting for the person.

**After** (`apps/extension/src/background/command-session.ts`,
`apps/extension/src/background/service-worker.ts`):

- A command that actually used the debugger arms a one-shot quiet-spell timer
  (`DEBUGGER_IDLE_RELEASE_MS = 2_000`). When it fires with no command in flight and the session
  `ready`, the session calls `deps.releaseDebugger()` — once. That covers every pause the ticket
  lists (parked row, approval, canary, code window, daily cap) and the end of a run, because in all
  of them the runner stops sending commands.
- Every command starts with `cancelIdleRelease()`, waits out a release that is still in flight, and
  calls `deps.wakeDebugger()` before its step — so Resume / Try again / Go ahead hold the debugger
  again before the next step. `ensureDebugger` also waits for an in-flight release, so the two can
  never cross.
- Letting go is not a Cancel: `releaseDebugger()` still removes the detach watcher **before**
  detaching (the ordering the ticket names), the session never reports `detached` for its own
  release, and nothing aborts.
- The abandon guard (PL-027) survives the detach: a detach drops its CDP listeners, so
  `releaseDebugger` remembers that the guard was armed, clears the module flag, and `wakeDebugger`
  re-arms it before the next step. Pausing therefore does not weaken a resumed run's protection.

**Tests.** `apps/extension/tests/pl117-debugger-release.test.ts` (4), driving the real
`CommandSession` through its injected dependencies:

- *releases it exactly once after the quiet spell, and never reports a detach* — events go
  `wake, step` then one `release`; a second firing releases nothing more; no `event` frame is sent.
  **Before the fix the session had no release at all (`['step']`).**
- *holds the debugger again before the next step when the run resumes* — `wake, step, release, wake,
  step`, both results `ok`, no event. This is the "Resume attaches before the next step, and letting
  go did not abort the run" proof.
- *keeps the debugger when the next command arrives inside the quiet spell* — the first timer is
  cancelled, nothing is released.
- *removes the detach watcher before its own detach, so it is never taken for a Cancel* — reads
  `service-worker.ts` and asserts `stopCommandDetachWatch()` comes before `detachDebugger(` inside
  `releaseDebugger`.
