| D-017 | Resolutions for the recipe format (PL-004): keep the schema tests permanently in `packages/recipe/tests/`; restrict `commit` steps to `fill`, `select`, `click`, `upload_file` (never `navigate`, which changes no data); no bounded autonomous agent step in v1; `extract` and `classify` are pre-batch staging operations only, so a clean batch run makes no model call; an AI value used in a commit step always sets `requires_approval: true`; `end_record` may end a record `verified`, `skipped`, or `parked`, and `failed` is runner-managed only | ProcessLens is a deterministic compiler, not an autonomous agent: the batch loop stays deterministic and every AI value stays reviewable by a person | Accepted (owner) | 2026-10-08 |
| D-018 | Supersedes the D-014 delivery model: there is now a single repository (`process-lens`) with `internal/` co-located inside it rather than a separate private repository. `internal/` still holds the constitution, design, decisions, board, tickets, and reports, and product rules are unchanged (synthetic data only, no secrets, no internal content in public product files). The repository is public, so the contents of `internal/` are visible; treat anything written there as public | One clone, one CI, and no cross-repository drift to maintain | Accepted (owner) | 2026-10-08 |
| D-019 | Recipes are built in layers. The compiler's built-in rules come first. AI suggestions (PL-018) fill what the rules miss, and each suggestion carries its reason. Where the rules and the AI are unsure or disagree, the person is asked. The person confirms every rule. Every new or changed recipe is verified by preview and canary before a batch (PL-019). Locator repair is proposed from parked records and approved by a person (PL-020). AI never runs inside a batch (D-017 stands) | Rules are free and deterministic, AI generalizes across sites, and questions capture nuance only the person knows. Verification makes a wrong suggestion safe, and human approval keeps every run auditable | Accepted (owner) | 2026-10-13 |
| D-020 | Supersedes the layer numbering in D-019, and records the recording-first order: the recorder comes first, before AI. The recorder captures what changed rather than the events it hears (state-diff recording, PL-018), so the layers now read: AI suggestions and summary (PL-019), verification (PL-020), self-healing (PL-021). D-019's rules stand unchanged: built-in compiler rules first, each AI suggestion carries its reason, the person is asked where the rules and the AI disagree, the person confirms every rule, preview and canary verify every new or changed recipe, locator repair is proposed from parked records and approved by a person, and AI never runs inside a batch (D-017 stands) | A recorder that trusts specific DOM events misses editors, autofill, keyboard selection, paste, IME and password managers; state-diff capture makes the recording the source of truth every later layer builds on, and the AI layers move behind it | Accepted (owner) | 2026-10-14 |
| D-021 | Hosting: Railway runs the API, the workers, Postgres and the web app | The choice was Vercel or Railway. Vercel cannot hold the hub's WebSocket connection and cannot run long-lived workers, and those are the two constraints this system actually has; Railway runs both, with a managed Postgres beside them in the same project | Accepted (owner) | 2026-10-15 |
| D-022 | Test targets: real open-source apps run locally in Docker (Odoo 18 Community and Twenty CRM, PL-022) replace the hand-built mock sites as the main targets for recording and replay. The mocks stay for unit-level fixture tests | Pages we wrote ourselves contain only the bugs we already thought of. Real software brings autocompletes, inline editing, command menus and duplicate checks that nobody here wrote, so replay is tested against software we do not control. The mocks stay because unit and fixture tests need a target that cannot drift under them | Accepted (owner) | 2026-10-15 |
| D-023 | The admin panel lives in its own repository (owner's mandate), sharing the ProcessLens database through a separate, least-privilege Postgres role. Schema and migrations stay owned by this repo; the admin repo never runs migrations. Supersedes D-018 for the admin panel only | Owner's mandate. The admin panel is a separate deliverable with its own access surface, while the schema and its migrations stay in exactly one place and the admin repository reaches the database only through a role that can do what the panel needs and nothing more | Accepted (owner) | 2026-10-15 |
| D-024 | Internal tool first, SaaS-ready: one company uses ProcessLens now, but nothing assumes a single company. Every table keeps its `tenant_id` and every query filters by it; sign-in sits behind one interface (company SSO now, sign-up later); usage (rows done, AI spend) is metered from day one; the landing page stays in the backlog for the SaaS phase. The admin panel (D-023) changes run state only through the ProcessLens API, never by writing ledger tables | Owner's call: ship an internal tool this week without closing the door on selling it. These choices cost almost nothing now and are expensive to retrofit; routing admin actions through the API keeps the ledger's invariants in one place | Accepted (owner) | 2026-10-15 |
| D-025 | The admin panel is built from modules. Each module is an API folder and a web folder with a manifest that names the `admin_modules` row it needs and the columns it writes; a registry mounts only the modules whose row the database has, and the shell knows no module by name. A module that needs schema is a pair of tickets: a PL migration in this repository (its tables, its `admin_modules` row and its column grants to `processlens_admin`) and an ADM ticket for the module | Owner's call: admin features that need a migration must slot in without touching the others. Migrations stay in one repository (D-023), the admin panel keeps working against an older schema, and each module's write access is granted column by column | Accepted (owner) | 2026-10-15 |
| D-026 | Supersedes the "no model call in a batch" part of D-017, D-019 and D-020. A run may call a model through `services/ai` to find an element: `find_target` gets the step's `intent` and a redacted snapshot of the page, and answers with one element id or "not here". Code gates check the answer (it exists and is unique, its role fits the action, it is on an allowed origin, it isn't destructive unless the step allows it). A hit is remembered per task, step and site in `target_memory`; recipes stay immutable. At teaching, `clean_recording` may only drop and name steps, and the person confirms the list. A model never decides an outcome: `verified` comes only from a check (read-back, landing page, confirmation), and a model's "not here" can only park a row. There is a cap of model calls per row. Everything else in D-017 stands | The owner's production targets are outside websites and internal tools with no API, which can't be tested in advance. Three weeks of hand-written rules didn't make three real tasks work, because every unforeseen page behaviour needed a new rule. A model finds elements where rules don't reach, and checks keep the outcome deterministic and auditable. See `AI_RUNTIME.md` | Accepted (owner), trial: PL-122, PL-123 | 2026-10-28 |
